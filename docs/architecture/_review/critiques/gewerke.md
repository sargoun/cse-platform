# Adversarial review — gewerke

## BLOCKING (16)

### B1. §1.5 Standard-Mandantenpolicy has no role dimension, and every role-specific policy is OR'd ON TOP of it. `USING (mandant_id = aktiver_mandant() OR (ist_gruppenansicht() AND hat_mandant_zugriff(mandant_id)))` grants SELECT on all 33 tables to every principal whose session has that mandant active — including `mitarbeiter` and `kunde`.

**Why it breaks:** A `kunde` user with an active mandant reads every other customer's `leistungsnachweis`, every `projekt.auftragssumme_netto_cent`, every `lv_position.einheitspreis_cent`, and the entire `wachbuch_eintrag` table. A `mitarbeiter` reads all customer commercials and all colleagues' Wachbuch entries. This breaks EMP-13 ('Employees never see group financials, other employees' data, or customer commercials'), AUT-01 (Kunde = own projects/orders/invoices only), AUT-05 ('RLS policies mirror application authorization') and the D-09 §6 principle that role scope is enforced in RLS, not only in the app. It also makes the four hand-written role branches (leistungsnachweis, dienstanweisung, wachbuch_eintrag, schluessel_quittung, qualitaetspruefung, projekt, reklamation) pure no-ops — they only widen an already-total grant, which is proof the widening was not noticed.

**Required fix:** Split the tenant branch by role: `USING ((mandant_id = aktiver_mandant() AND ist_rolle(ARRAY['super_admin','admin','leitung'])) OR <role-specific branch>)`, or add a second policy of type `AS RESTRICTIVE` per table that denies `kunde`/`mitarbeiter` everything the specific branch does not name. Then re-derive every role branch as the ONLY grant for that role and state, per table, which of the five AUT-01 roles may read it.

### B2. The document never states which Postgres role the Next.js server connects as. All delete protection on master data (`revier`, `turnus`, `posten`, `projekt`, `leistungsverzeichnis`, `lv_position`, `gewerk`, `dienstanweisung`, `schluessel`, `wetter_station`) rests solely on 'there is no DELETE policy' (§1.4) — no `prevent_delete()` trigger is installed on any of them.

**Why it breaks:** Supabase's `service_role` and the table owner have BYPASSRLS. If Drizzle connects with the service key or as the owner — the default in almost every Supabase/Drizzle setup — §1.5 is inert in its entirety and a `DELETE FROM lv_position` succeeds silently. That is precisely the failure CLAUDE.md invariant 3 forbids ('RLS is the second line of defence, never the only one') and it breaks invariant 8 and LEG-01 (GoBD: no deletion) for the contract documents that a Werkvertrag dispute turns on. A missing DELETE policy also does not raise — it deletes 0 rows and returns success, so a bug in a service that deletes the wrong rows is indistinguishable from a no-op.

**Required fix:** State the role contract explicitly: the request path connects as a non-superuser, non-BYPASSRLS role with `SET LOCAL app.aktiver_mandant` per request; `service_role` is forbidden outside migrations and the DWD import job. Independently, install `prevent_delete()` on every table in the domain (master data included) so protection does not depend on which role won.

### B3. `has_required_qualifikation()` and `enforce_posten_qualifikation()` in §8 are declared `LANGUAGE sql STABLE` / `LANGUAGE plpgsql` with no `SECURITY DEFINER`, yet they read `nachweis` — a table that by D-09 lives at the person head and spans entities — and `anstellung`, which is strictly tenant-scoped.

**Why it breaks:** Trigger functions run as the invoker and are subject to RLS (aggravated by the draft's own `FORCE ROW LEVEL SECURITY`). A security planner assigning a person who also cleans sees only the `nachweis` rows their own RLS permits. If `nachweis` is person-scoped or mandant-scoped in the Personal domain, the §34a certificate is invisible to the checking session and the function returns false for a fully qualified guard (fails closed, blocks lawful assignments) — or, if a permissive policy exists, it silently reads a filtered subset and passes an unqualified one. Either way SEC-04/LEG-04 is not enforced, and D-09's whole point — the certificate belongs to the human, not the job — is defeated at exactly the join that crosses entities.

**Required fix:** Declare both functions `SECURITY DEFINER` with `SET search_path = pg_catalog, public`, owned by a role that can read `nachweis` and `anstellung` group-wide, and grant EXECUTE narrowly. Add a test: guard employed in `security` and `reinigung`, planner session in `reinigung`, §34a certificate valid — the check must see it.

### B4. `enforce_posten_qualifikation()` raises on any `einsatz` row where `anstellung_id` is NULL or `ende` is NULL, and the companion `CHECK (posten_id IS NULL OR (qualifikation_geprueft_am IS NOT NULL AND qualifikation_snapshot IS NOT NULL))` demands a documented check even when nobody is assigned.

**Why it breaks:** `SELECT a.person_id INTO v_person WHERE a.id = NULL` yields NULL; the inner `NOT EXISTS` then matches nothing, so `has_required_qualifikation` returns false and the INSERT throws. Unstaffed shifts therefore cannot exist. That kills the TIM-03 generator (eight weeks of Posten shifts are generated before anyone is assigned), TIM-04 (parallel columns of open shifts), SEC-08 short-notice event staffing, and the SPEC §14 watchdog 'Tomorrow's shift unstaffed', which by definition needs an unstaffed row to find. It also directly contradicts the draft's own §5 justification for not constraining `min_besetzung` ('ein unterbesetzter Plan muss speicherbar sein'). The same NULL path bites `v_bis := (NEW.ende AT TIME ZONE 'Europe/Berlin')::date`: with a NULL `ende`, `n.gueltig_bis >= NULL` is NULL, no nachweis matches, and every such assignment is rejected.

**Required fix:** Guard the trigger with `IF NEW.anstellung_id IS NULL THEN RETURN NEW; END IF;` and make the CHECK conditional on assignment: `CHECK (posten_id IS NULL OR anstellung_id IS NULL OR (qualifikation_geprueft_am IS NOT NULL AND qualifikation_snapshot IS NOT NULL))`. Handle NULL `ende` explicitly (`coalesce(NEW.ende, NEW.beginn)`) rather than letting three-valued logic decide a compliance question.

### B5. The SEC-04 gate fires only `IF NEW.posten_id IS NULL THEN RETURN NEW`, i.e. it is keyed on the existence of a `posten` master row.

**Why it breaks:** SEC-08 event security is short-notice staffing where no Schichtposten is created; a planner books guards against an `objekt` (or a bare `einsatz`) and the §34a/Sachkunde block is bypassed completely, as is the Bewacherregister check. §34a Abs. 1a GewO attaches to the deployment of a person in a Bewachungstätigkeit, not to the existence of a planning artefact in this database. This is an unlawful assignment that the platform will not stop, and LEG-04 says the enforcement is at assignment.

**Required fix:** Key the gate on the work being Bewachungstätigkeit, not on `posten_id`: derive the requirement set from `posten_qualifikation` when a Posten exists, and otherwise from a mandant-/objekt-level requirement set (e.g. `objekt_qualifikation` or a mandant-level baseline requirement row). Add `// TODO(client): welche Qualifikationsanforderung gilt für Veranstaltungseinsätze ohne festen Posten (SEC-08)?` rather than leaving the path open.

### B6. The §1.3 tenancy design requires composite FKs `(parent_id, mandant_id) REFERENCES parent(id, mandant_id)` against tables owned by other domains — `objekt`, `raum`, `kunde`, `auftrag`, `leistungskatalog`, `anstellung`, `einsatz`, `zeiteintrag`, `firma` — but the §1.6 cross-domain contract requires only `anstellung UNIQUE (id, person_id)`. It never requires `UNIQUE (id, mandant_id)` on any consumed table.

**Why it breaks:** Postgres refuses a foreign key unless the referenced column list is backed by a unique constraint. Every composite FK in §4–§7 pointing at a foreign-domain table fails at migration time. The whole 'a cross-tenant child row is unrepresentable' defence — the draft's stated reason for preferring composite FKs over RLS alone — does not build.

**Required fix:** Add a row to the §1.6 contract table for every consumed table stating `UNIQUE (id, mandant_id)` as a required constraint, and add `zeiteintrag UNIQUE (id, mandant_id)`, `einsatz UNIQUE (id, mandant_id)` explicitly. Also add the columns the §8 trigger reads but the contract omits: `einsatz.anstellung_id`, `einsatz.beginn`, `einsatz.ende`. State the required vocabulary of `nachweis.status` — §8 hard-codes the literal `'gueltig'` against a column whose value set the contract does not fix; a Personal domain that names it `aktiv` turns the gate into a universal block.

### B7. `CREATE INDEX turnus_generator_idx ON turnus (...) WHERE archiviert_am IS NULL AND (gueltig_bis IS NULL OR gueltig_bis >= current_date);`

**Why it breaks:** `current_date` is STABLE, not IMMUTABLE. PostgreSQL rejects the statement with 'functions in index predicate must be marked IMMUTABLE'. The migration fails outright, and the index the TIM-03 nightly generator depends on does not exist. (A predicate on 'today' is also semantically wrong — the index would have to be rebuilt every midnight to stay correct.)

**Required fix:** `CREATE INDEX turnus_generator_idx ON turnus (mandant_id, letzte_generierung_bis) WHERE archiviert_am IS NULL;` and put the `gueltig_bis >= current_date` filter in the generator's WHERE clause where it belongs.

### B8. `wachbuch_eintrag` carries `breitengrad`/`laengengrad` on every entry, including `art = 'rundgang'`.

**Why it breaks:** A guard writing ten to twenty Rundgang entries across a night shift produces a timestamped movement profile of an identifiable employee. LEG-10 is explicit and is not a TODO: 'Geolocation at check-in — single point at start and end, no continuous tracking'. The draft's mitigation (a `app.geo_erfassung_erlaubt` GUC plus a Betriebsrat TODO) addresses consent, not the prohibited pattern: even with a works agreement, a per-patrol coordinate trail is continuous tracking and is a §87 Abs. 1 Nr. 6 BetrVG performance-monitoring system built into an evidentiary table that can never be deleted (§1.4 prevent_delete). DSGVO Art. 5(1)(c) data minimisation is the second problem.

**Required fix:** Remove the geo columns from `wachbuch_eintrag` (and from `da_kenntnisnahme`, which needs no location at all). If proximity proof at a patrol point is genuinely required by the customer contract, model it as a boolean/NFC-tag match against a pre-registered `kontrollpunkt` — 'was at checkpoint 4' — never as raw coordinates, and record `// TODO(client): fordert ein Auftraggebervertrag einen Standortnachweis je Rundgang?`

### B9. The Wachbuch hash chain is scoped per `(mandant, objekt, jahr)` with `vorheriger_hash` NULL at the start of each chain, `canonical_payload` is never defined, and there is no uniqueness on `vorheriger_hash`.

**Why it breaks:** Three separate holes in the only anti-tamper control on the security domain's evidentiary book. (a) On 1 January the chain restarts unanchored, so an entire prior year can be regenerated and re-hashed without any surviving link contradicting it — the control the design borrows from FIN-06 evaporates at the exact boundary an auditor tests. (b) A hash over an unspecified payload cannot be verified by anyone, including the nightly job; the field list is part of the control, not an implementation detail. (c) Without `UNIQUE (mandant_id, objekt_id, jahr, vorheriger_hash)` two rows can claim the same predecessor and fork the chain, which is exactly how an inserted page hides.

**Required fix:** Chain per `(mandant_id, objekt_id)` without a year reset (keep `jahr` for the human-readable `laufnummer` only), seeding `vorheriger_hash` from the last entry of the previous year. Enumerate the canonical payload fields in the schema doc (objekt_id, anstellung_id, art, erfasst_am, betreff, text, schluessel_id, einsatz_id, laufnummer, jahr — and explicitly exclude the storno columns, since those are written after hashing). Add the unique on `vorheriger_hash`. Also pin BEFORE-trigger firing order: Postgres fires BEFORE triggers alphabetically, so `assign_wachbuch_laufnummer` currently runs before `stamp_server_time` and would derive `jahr` from an unstamped `erfasst_am`.

### B10. `aufmass_signatur`: 'Trigger setzt bei Vorliegen beider Rollen bzw. bei erhebungsart = "einseitig" und Rolle auftragnehmer den Kopf auf gegengezeichnet'.

**Why it breaks:** The contractor's own signature promotes the Aufmaß to a status literally named 'countersigned'. The record then asserts that the Auftraggeber joined the measurement when he did not, and `aufmass_abrechenbar_idx` (`WHERE status = 'gegengezeichnet'`) feeds those blätter straight into invoicing. BAU-03 requires countersignature; §14 Abs. 2 VOB/B allows a one-sided Aufmaß only under its own notice conditions and it carries a different evidentiary weight in a Werklohnprozess. Falsifying that distinction inside a frozen, hash-snapshotted record is worse than not recording it.

**Required fix:** Add `einseitig_festgestellt` to `aufmass_status` and set that on a one-sided sign-off; keep `gegengezeichnet` for the AG signature only. Make `aufmass_abrechenbar_idx` cover both states so billing still works, and let the billing service decide which is invoiceable. Add `// TODO(client): unter welchen Voraussetzungen wird ein einseitiges Aufmaß abgerechnet (§14 Abs. 2 VOB/B: Ankündigung, Frist)?`

### B11. `CREATE UNIQUE INDEX lv_nachtrag_uk ON leistungsverzeichnis (nachtrag_id) WHERE nachtrag_id IS NOT NULL` ('genau ein LV je Nachtrag') contradicts the `fassung` column and its unique key `(projekt_id, art, coalesce(nachtrag_id,'…'), fassung)`.

**Why it breaks:** A Nachtrag is renegotiated: submitted, priced down, resubmitted (`nachtrag_status` itself models `kalkuliert → eingereicht → beauftragt|abgelehnt`). The unique on `nachtrag_id` makes a second Fassung of the Nachtrags-LV impossible, so the only way to revise a Nachtrag price is to overwrite the existing LV positions in place — destroying the record of what was originally submitted, which is the document a §2 Abs. 6 VOB/B dispute turns on. BAU-04 exists to preserve exactly this history. (Separately, `coalesce(nachtrag_id,'…')` is written with a literal ellipsis, not a sentinel UUID — it will not compile.)

**Required fix:** Drop `lv_nachtrag_uk`. Keep versioning through `UNIQUE (projekt_id, art, coalesce(nachtrag_id, '00000000-0000-0000-0000-000000000000'::uuid), fassung)` and add a partial unique for the current fassung if one is needed: `UNIQUE (nachtrag_id) WHERE nachtrag_id IS NOT NULL AND archiviert_am IS NULL`.

### B12. `schluessel.status` is declared derived: 'abgeleitet aus dem Quittungs-Ledger, per Trigger gepflegt' by `refresh_schluessel_status()`. But `quittung_richtung` has only `ausgabe` and `ruecknahme`.

**Why it breaks:** `verloren`, `gesperrt` and `vernichtet` are unreachable through the derivation, and any manual UPDATE that sets them is overwritten by the next quittung's AFTER trigger. `CHECK (status <> 'verloren' OR verlust_gemeldet_am IS NOT NULL)` guards a state the design cannot enter. SEC-07 key management is precisely about knowing that a key is lost — that is the event that triggers a Schließanlagen-Austausch and a liability claim.

**Required fix:** Make the ledger the sole source of truth for all state changes: extend `quittung_richtung` with `verlustmeldung`, `sperrung`, `vernichtung` (each still an append-only signed row), and derive `status` from the last ledger row of any kind. Alternatively split `status` into a derived `besitz_status` and an independent `lebenszyklus_status` that the trigger never touches — but do not leave a trigger-owned column with four values the trigger cannot produce.

### B13. `behinderung` has `angezeigt_am`, `versandart`, `empfaenger` and `versand_dokument_id`, and `freeze_after_send()` — but no approver, no approval timestamp and no immutable snapshot of what was approved.

**Why it breaks:** A Behinderungsanzeige is an outbound legal declaration to the Auftraggeber with a claim-preserving effect. Invariant 7 ('nothing leaves the system without human approval') and APR-07 ('immutable snapshot of exactly what was approved, plus approver and timestamp') both apply, and the draft cites APR-07 on this very table while providing neither field. Freezing the text after the fact records what was sent, not who authorised sending it — in a dispute over whether the Anzeige was properly issued, that is the missing half.

**Required fix:** Add `freigegeben_von uuid REFERENCES benutzer(id)`, `freigegeben_am timestamptz` (server-stamped), `freigabe_snapshot jsonb NOT NULL`, `freigabe_snapshot_hash text CHECK (~ '^[0-9a-f]{64}$')`, with `CHECK (angezeigt_am IS NULL OR freigegeben_von IS NOT NULL)`. Apply the same triple to any other row this domain lets leave the system.

### B14. Composite FKs enforce same-tenant but never same-parent. `aufmass_zeile.lv_position_id` may point at an `lv_position` from a different project's LV; `aufmass_foto.aufmass_zeile_id` at a zeile of a different aufmass; `leistungsnachweis_position.zeiteintrag_id` at a zeiteintrag of a different objekt/auftrag; `bautagebuch.behinderung_id` at another project's Behinderung; `schluessel_quittung.wachbuch_eintrag_id` at another object's entry. Additionally `aufmass_zeile.einheit` is free text with no relation to `lv_position.einheit`.

**Why it breaks:** These are the join paths FIN-07 traceability and FIN-08 Aufmaß-based billing run on. A zeile measured in `m` booked against a position priced in `m²` — or against the right OZ in the wrong project — produces a wrong invoice amount that is structurally invisible: the FK is valid, RLS is satisfied, and the nightly re-computation job only re-evaluates the Rechenansatz, not the target. Both mis-bookings survive the hash snapshot and end up in a festgeschriebene Rechnung that cannot be corrected except by Storno.

**Required fix:** Carry the grandparent key down and use it in the FK: give `aufmass_zeile` a `projekt_id` with `FOREIGN KEY (lv_position_id, projekt_id) REFERENCES lv_position(id, projekt_id)` (requiring `lv_position` to carry and expose `projekt_id`), give `aufmass_foto` an `aufmass_id`-scoped FK `(aufmass_zeile_id, aufmass_id) REFERENCES aufmass_zeile(id, aufmass_id)`, and apply the same shape to the other four. Add a trigger asserting `aufmass_zeile.einheit = lv_position.einheit` when `lv_position_id IS NOT NULL`, or drop the column and inherit the unit from the position.

### B15. §7 specifies `stamp_server_time()` on `reklamation.eingang_am`, but `reklamation` has no `geraete_zeit` and no `zeitabweichung_sek` columns, while §1.7 defines the trigger body as unconditionally referencing `NEW.geraete_zeit`.

**Why it breaks:** The trigger raises `record "new" has no field "geraete_zeit"` (42703) on every insert, so no Reklamation can be created at all — or, if a second silently-different trigger variant is meant, invariant 5's contract ('device time is stored separately with zeitabweichung_sek') is quietly dropped for a customer-reported record whose arrival time drives the SLA clock (NOT-01, CRM-03).

**Required fix:** Either add `geraete_zeit timestamptz` / `zeitabweichung_sek integer` to `reklamation` (and to any other table given the trigger), or split into two functions — `stamp_server_time()` for tables with device columns and `stamp_server_time_only()` for the rest — and say per table which one applies. The same audit is needed for `qualitaetspruefung.geprueft_am` (it does have the columns — fine) and for `leistungsnachweis.vorgelegt_am`, `aufmass.gesperrt_am`, `bautagebuch.abgeschlossen_am`, which are currently service-set and unguarded.

### B16. Two role branches are dead policies because their subqueries read tables the same principal cannot read: `qualitaetspruefung`'s customer branch does `EXISTS (SELECT 1 FROM objekt o WHERE o.id = objekt_id AND o.kunde_id = aktueller_kunde())`, and `dienstanweisung`'s employee branch does `EXISTS (SELECT 1 FROM einsatz e WHERE e.anstellung_id = ANY(aktuelle_anstellung_ids()) ...)`.

**Why it breaks:** A subquery inside a policy is itself subject to the referenced table's RLS. If `objekt` is not readable by role `kunde` (it should not be — AUT-01 scopes customers to their own records, and the draft never defines an `objekt` customer policy), the EXISTS returns no rows and the branch never grants. Same for `einsatz` under a `mitarbeiter` session. Today this is masked by the over-broad tenant branch (finding 1); the moment that is fixed, EMP-09 (Dienstanweisung on the phone) and the customer's view of a joint Begehung both stop working, and the failure looks like an empty list rather than an error.

**Required fix:** Express these through `SECURITY DEFINER` helpers that encapsulate the lookup — `hat_objekt_kundenzugriff(uuid)`, `ist_eingesetzt_auf_objekt(uuid)` — the same pattern already used for `aktiver_mandant()` and `aktuelle_anstellung_ids()`. Never reference a base table directly from a policy predicate.

## MISSING (14)
- SEC-03 / `bewacher_eintrag` is absent from the entire document — not in §1.6's cross-domain contract, not in the §8 gate. §34a GewO requires the guard to be entered in the Bewacherregister and the employer to verify it; a person can hold a valid Sachkunde certificate and still be barred (Zuverlässigkeitsüberprüfung negative, registration revoked). `has_required_qualifikation()` checks `nachweis` only, so the platform will happily schedule a guard whose registration was withdrawn. LEG-04 says enforcement is at assignment. The gate must also read `bewacher_eintrag` (person_id, bewacher_id, status, gueltig_bis) and the contract must specify its status vocabulary.
- CLN-03 ('Berlin public holidays excluded automatically') has an enum and a `feiertagsregel` column but no holiday source. There is no `feiertag` table, no contract row for one, and no statement of where the Berlin Feiertagskalender comes from. The turnus generator cannot honour `feiertagsregel = 'ausfall'` against data that does not exist, and hard-coding a holiday list in TypeScript makes an operational calendar invisible to the DB and to seed data.
- TIM-02 ('recurring series with single-occurrence overrides') is satisfied for `turnus` (via `turnus_ausnahme`) but not for `posten`: `posten.abdeckung_rrule` has no exception table, so a Posten shift cannot be cancelled or moved for one night. SPEC §22 names a single entity `planungsserie` for recurring series; the draft invents two independent RRULE carriers on `turnus` and `posten` and reconciles neither with it. Either add `posten_ausnahme` with the same shape as `turnus_ausnahme`, or state explicitly why `planungsserie` is replaced by two per-trade carriers and how the shared generator reads both.
- APR-03 ('every extracted value carries its source — page, table — and a confidence flag; uncertain fields highlighted') has no representation. `leistungsverzeichnis` carries `quelle_dokument_id` but `lv_position` — the table AGT-02's `extrahiere_lv` writes into — has no `quelle_seite`, no `quelle_bereich`, no `konfidenz`, no `geprueft_von`. Without them the approval screen cannot highlight uncertain fields and the reviewer is approving unmarked machine output, which is what APR-08 is designed to detect.
- FIN-07 names four traceability sources — Zeiteintrag, Aufmaß, contract, material — but `leistungsnachweis_quelle` offers only `zeiteintrag`, `aufmass_zeile`, `leistungskatalog`, `manuell`. Material consumption has no source value and no FK, so a Leistungsnachweis line for consumed material is forced into `manuell` and loses its trace. Either add `material` plus the FK, or state which table owns material and why it never reaches a Leistungsnachweis.
- §12 VOB/B Abnahme is modelled as two columns (`abnahme_am`, `abnahme_art`) with no Abnahmeprotokoll, no Mängel-/Restleistungsliste, and — critically — no `vorbehalt_vertragsstrafe`. Under §11 Abs. 4 VOB/B a Vertragsstrafe claim is forfeited unless reserved at Abnahme. The platform records the date on which the claim was lost without recording whether it was preserved. Add an `abnahme` table (protokoll, Vorbehalte, Mängel with Fristen, signatures via the same snapshot pattern) or state that Abnahme lives in another domain.
- LEG-09 (deletion concept), DOC-07 (retention per category) and LEG-02 (§17 MiLoG: two years) have no schema representation anywhere in the domain. No table carries `aufbewahrung_bis`, `loeschsperre` or a retention class. The draft's answer to O-27 is 'until the client answers: no deletion' — safe as a default, but there is no field a Löschkonzept could ever drive, so answering O-27 later becomes a migration across 33 tables rather than a configuration change. Add a retention class column (or a single `aufbewahrung` join table) now, even if every row starts at 'unbefristet'.
- PRO-05 ('references pulled from real jobs where `freigegeben_vom_kunden = true`') is implemented only on `projekt`. Reinigung and Security work hangs off `auftrag`/`objekt`, not `projekt` — the draft says so itself in its assumptions — so under this schema three of the four business areas can never produce a website reference, and `projekt_referenz_idx` serves only Bau. Put the release flag and its `freigabe_dokument_id` where PRO-05 actually needs them (`auftrag`), or state that the `referenz` table in SPEC §22 owns this and remove the duplicate flag from `projekt`.
- SEC-06 ('read acknowledgement per employee') has no requirement set. `da_kenntnis_offen_idx` is justified as 'Anti-Join gegen die eingesetzten Anstellungen' — i.e. the population that must acknowledge is derived from `einsatz`. A newly hired guard assigned to an object but not yet scheduled therefore never appears as outstanding, and the acknowledgement gap is invisible until after the shift. Model the obligation explicitly (`da_pflicht(dienstanweisung_id, anstellung_id)` or derivation from objekt assignment), and state whether a new *version* re-opens the obligation for everyone who acknowledged the previous one.
- The §1.6 contract is incomplete for tables the design depends on: `qualifikation` (its tenancy semantics are asserted in §5 — 'nicht mandantengebunden' — for a table this domain does not own, and §22 groups it with the tenant-scoped person block; if it turns out tenant-scoped, `posten_qualifikation` has a cross-tenant hole), `steuersatz` (referenced by `lv_position.steuersatz_id`, listed only in the assumptions), `ausschreibung` (referenced by `leistungsverzeichnis.ausschreibung_id`), `objekt.kunde_id` (required by the `qualitaetspruefung` customer policy but not in the contract), and `aktueller_kunde()` (used in four policies, declared only as an assumption). Add a contract row for each.
- The `nummernkreis` contract specifies only `naechste_nummer bigint`, but this domain needs two differently-keyed counters from it: one per `(mandant_id)` for `leistungsnachweis.nummer` and one per `(mandant_id, objekt_id, jahr)` for `wachbuch_eintrag.laufnummer`. A counter table designed for a handful of invoice circles will hold one row per object per year. Specify the key/scope shape in the contract (e.g. `nummernkreis(mandant_id, kreis_typ, kontext_id, jahr)`) before Finance builds it for invoices only.
- Index gaps on query paths the SPEC demands: (a) `leistungsnachweis` has no index supporting the customer-portal list its own RLS branch defines — add `(mandant_id, kunde_id, leistungszeitraum_bis DESC) WHERE status IN ('vorgelegt','signiert') AND storniert_am IS NULL` (AUT-01 Kunde scope); (b) `wachbuch_eintrag` has no index on `(mandant_id, anstellung_id, erfasst_am DESC)`, yet its RLS predicate filters by `anstellung_id` on the largest table in the domain, so the employee portal's own-entries view is a sequential scan under a per-row policy; (c) `reklamation.wiederholung_von_id` has no index although 'Wiederholungsfall' traversal is the stated purpose of the column.
- TIM-09 ('offline capture queued locally, submitted flagged as late, claimed time recorded') is honoured only on `wachbuch_eintrag` via `nachgetragen boolean`. `leistungsnachweis_signatur`, `schluessel_quittung`, `da_kenntnisnahme`, `aufmass_foto` and `qualitaetspruefung` all capture in the field, all store `geraete_zeit`, and none carries the late-submission flag — so a signature collected offline at 14:00 and uploaded at 22:00 is indistinguishable from one collected at 22:00 except by reading `zeitabweichung_sek`, which conflates clock drift with queue delay.
- SEC-A9 requires the audit actor to be 'human / agent / system', but §1.2's Auditblock has only `erstellt_von uuid REFERENCES benutzer(id)` with the convention 'NULL = system/job'. Employees authenticate through `mitarbeiter_zugang` at the person level (EMP-01: phone + SMS, no password), so exactly the people who write Wachbuch entries, Kenntnisnahmen and Schlüsselquittungen have no `benutzer` row and land in the same NULL bucket as cron jobs. An AI agent writing a row is also indistinguishable. Add an actor type discriminator plus the person/agent reference to the Auditblock.

## INVENTED RULES — must become TODO(client) (6)
- `projekt.vertragsgrundlage vertragsgrundlage NOT NULL DEFAULT 'vob_b'` — the draft's own O-20 asks whether BGB-Bauverträge occur at all, then defaults every project to VOB/B. VOB/B and BGB differ on Nachtragsanspruch (§2 VOB/B vs §650b/c BGB), Behinderung (§6 VOB/B), Abnahme (§12) and Gewährleistungsfrist (4 vs 5 years) — the four things this schema models. Defaulting the legal regime while the question is open is precisely the 'silently pick a plausible value for a legal rule' failure. Make the column NOT NULL with no default and force an explicit choice at project creation, with `// TODO(client): kommen BGB-Bauverträge vor? (O-20)` on the column.
- Wachbuch employee visibility: 'eigene Einträge plus Einträge desselben Objekts aus den letzten 24 Stunden (Übergabe)'. The 24-hour window is a hard-coded access rule with data-protection consequences (a guard reads a named colleague's incident reports) that no SPEC line states. The author flags it in the assumptions as 'mit dem Betriebsrat abzustimmen' but it appears in the schema as a literal `interval '24 hours'` inside an RLS policy with no `// TODO(client)` and is absent from the open-question list. Make the window a configurable value and add `// TODO(client): welche Wachbuch-Einträge darf die Folgeschicht zur Übergabe sehen, und für welchen Zeitraum?`
- SEC-04 validity window: `has_required_qualifikation` requires `n.gueltig_ab <= p_von AND (n.gueltig_bis IS NULL OR n.gueltig_bis >= p_bis)`, i.e. the certificate must be valid through the shift *end*. SPEC SEC-04 says 'expired at the shift date'. The author declares the divergence in the assumptions, but it is a compliance rule that decides whether a lawful assignment is refused (a certificate expiring at midnight blocks the whole night shift) and it appears nowhere as a `// TODO(client)` or an open question. Surface it as one.
- `aufmass_signatur` treating a one-sided Aufmaß as `gegengezeichnet` once the Auftragnehmer signs invents the condition under which a §14 Abs. 2 VOB/B einseitiges Aufmaß becomes binding — the statute attaches notice and participation requirements the schema does not model. See the corresponding blocking entry.
- `bautagebuch_mannstunden CHECK (stunden >= 0 AND stunden <= 24)` puts an arbitrary numeric limit on a field that feeds Behinderungsschaden calculations; it is neither an ArbZG limit (which is per person, aggregated across entities per D-09/TIM-14, and is 8h/10h — not 24h) nor a stated rule. Harmless in practice but it reads as a validated business rule and is not one.
- `leistungsnachweis.nummer` assigned at the `entwurf → vorgelegt` transition. FIN-03's mechanism is reused but the *moment* of assignment is invented — a Nachweis that is rejected and re-created burns a number, and a customer receiving Nr. 41 after Nr. 39 will ask why. Declared in the assumptions; should be an explicit `// TODO(client): sollen Leistungsnachweise fortlaufend und lückenlos nummeriert sein?`

## MINOR (18)
- `schluessel` `UNIQUE (objekt_id, schluessel_nummer)` is not partial on `archiviert_am IS NULL`, unlike the `revier` bezeichnung index. When a Schließanlage is replaced after a `verloren` key, the new keys legitimately carry the same engraved numbers and cannot be entered. Same pattern on `revier.kurzzeichen` and `posten.kurzzeichen` — archived rows permanently reserve a short code that operations will want to reuse.
- `turnus_ausnahme` `UNIQUE (turnus_id, datum, art)` wrongly collapses legitimate duplicates: two `zusatz` cleanings on the same day (morning + evening special) are normal in Unterhaltsreinigung and cannot both be recorded.
- Enum type names are schema-global in Postgres and several are unprefixed generics that other domains will need: `prioritaet` (CRM-02 lead priority), `versandart`, `empfaenger_art`, `abnahme_art`, `vertragsgrundlage`, `foto_zweck`. The first domain to create them wins and the second gets a migration conflict or an enum with foreign values. Prefix them per domain (`reklamation_prioritaet`, `behinderung_versandart`, …).
- `wetter_quelle` is reused for three different concepts: `bautagebuch.wetter_quelle` (how the weather got attached), `wetter_station.quelle` (who operates the station) and `wetter_beobachtung.quelle`. A station with `quelle = 'keine'` is meaningless. Split into `bautagebuch_wetter_quelle` and `messwert_quelle`.
- `da_kenntnisnahme`'s RLS ANDs `mandant_id = aktiver_mandant()`, yet `da_kenntnis_person_idx (person_id, bestaetigt_am DESC)` is justified as 'Mitarbeiterportal über alle Anstellungen (EMP-14)' — a query the policy forbids. Its two sibling tables (`wachbuch_eintrag`, `schluessel_quittung`) OR the anstellung branch *outside* the mandant predicate and so behave differently. Three tables with the same 'my rows across my employments' requirement get three policy shapes; pick one and apply it consistently. The `da_kenntnisnahme` policy also drops the `ist_gruppenansicht()` branch entirely, silently removing that table from TEN-05.
- `revier_raum` is the target of a composite FK from `qualitaetspruefung_position.revier_raum_id` but its column list does not declare `UNIQUE (id, mandant_id)` (unlike `revier`, `turnus`, `lv_position`, `aufmass_zeile`, which do). §1.3 states the rule generally, but the per-table listings make the omission read as deliberate; the FK will not compile.
- `aufmass_foto.aufgenommen_am` is documented as 'Serverempfangszeit' but named 'taken at'. With TIM-09 offline queues the two differ by hours. Rename to `empfangen_am` and keep the actual capture claim in `geraete_zeit`, or the BAU-03 photo evidence will be read as taken at upload time.
- `revier.sollzeit_minuten integer` and `revier_raum.sollzeit_minuten numeric(8,2)` are the same concept in two types; the OPS-07 costing engine will round twice between them. Likewise `qualitaetspruefung.punkte numeric(8,2)` sums `qualitaetspruefung_position.punkte smallint`, and `skala_max` duplicates `max_punkte`.
- `turnus`'s RRULE regex `^FREQ=(DAILY|WEEKLY|MONTHLY|YEARLY)(;[A-Z]+=[^;]+)*$` rejects RFC 5545-valid rules where FREQ is not the first part (part order is free in the grammar). Since the doc already says full validation lives in a tested TypeScript parser, the CHECK adds a false-negative risk for no gain — keep only the `DTSTART`/`TZID`/`RRULE:` exclusion checks.
- `wetter_beobachtung`'s BRIN index on `zeitpunkt` assumes physical/temporal correlation, which a per-station backfill of historical data destroys; the actual query (`bautagebuch` resolves one station and one day) is already served by `UNIQUE (station_id, zeitpunkt)`. Drop the BRIN or make it `(station_id, zeitpunkt)`.
- `qpp_mangel_idx (mandant_id, ergebnis, frist_am) WHERE ergebnis = 'nio'` carries a column in the key that is constant in the predicate; `da_kenntnis_offen_idx (mandant_id, dienstanweisung_version_id)` duplicates the leading column of the unique index above it. Both are dead weight on write paths.
- `reihenfolge` uniques (`leistungsnachweis_position`, `aufmass_zeile`) are not DEFERRABLE, so reordering lines in the UI requires a temporary-value dance or a full renumber in one statement. Mark them `DEFERRABLE INITIALLY IMMEDIATE`.
- `prevent_delete()` raising `ERRCODE 23514` (check_violation) mislabels a delete refusal as a constraint violation; error-mapping code and users will read it as bad data. Use a distinct SQLSTATE in the 'P0' class with a clear message.
- `wachbuch_eintrag.text` and `behinderung.text` use a type keyword as a column name — legal but a persistent quoting and ORM-mapping footgun. `inhalt` / `anzeigetext` cost nothing.
- `posten.art` and `schluessel.art` are single-value placeholder ENUMs, which will each require a migration when the client answers O-14/O-15 — while `gewerk` is deliberately a table 'weil die Liste keine Migration erfordern darf'. Same argument, opposite choice; make the two placeholder vocabularies catalogue tables too, or accept the migration for `gewerk`.
- `posten_qualifikation.geltung = 'mindestens_einer'` combined with `zwingend = true` is enforced nowhere at write time — §8 explicitly excludes it from the row trigger and describes only a deferred check and a Dienstplan conflict display, which is not written. If a §34a requirement is ever entered with that Geltung, SEC-04's hard block silently does not apply. Add a `CHECK (NOT zwingend OR geltung = 'jeder')` until the deferred check exists, or specify it fully.
- RLS policies containing `EXISTS` over `einsatz` (dienstanweisung, wachbuch_eintrag) are evaluated per row on the two largest tables in the domain. Even once they are rewritten as SECURITY DEFINER helpers (see blocking), mark them `STABLE` and ensure the helper returns a pre-computed id array once per statement rather than a per-row subquery.
- The §10 seed list and test list are good but omit the two cases this domain's own design makes riskiest: an unstaffed generated Posten shift (must be insertable) and a person employed in both `reinigung` and `security` whose §34a certificate must be visible to the security planner's session. Both belong in `pnpm db:seed` and in the pre-UI test set alongside the Aufmaß parser and the DST nights.
