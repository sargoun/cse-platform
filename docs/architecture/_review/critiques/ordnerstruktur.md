# Adversarial review — ordnerstruktur

## BLOCKING (17)

### B1. RLS is designed as "the second line of defence" but the draft never names the Postgres role the application connects as, and never requires ALTER TABLE ... FORCE ROW LEVEL SECURITY. Drizzle over a Supabase connection string connects as the table owner by default, and a table owner bypasses RLS entirely unless FORCE is set.

**Why it breaks:** Invariant 3, TEN-03, AUT-05, SEC-A2. Every policy in src/server/db/rls/*.sql would be dead code in production while tests/isolation/db/rls.test.ts could still be authored to pass (it exercises the same owner role). A cross-tenant leak between three legal entities is exactly the failure SEC-A3 calls engagement-ending, and it would be invisible in review because the SQL files exist and look correct.

**Required fix:** State in this document: (a) the app connects as a dedicated non-owner role (e.g. app_runtime) with GRANT on tables and no BYPASSRLS; (b) every tenant table gets ENABLE ROW LEVEL SECURITY *and* FORCE ROW LEVEL SECURITY; (c) db/rls/_helpers.sql carries a migration-time assertion listing any table where relrowsecurity or relforcerowsecurity is false; (d) tests/invariants/mandant-id-and-rls.test.ts asserts relforcerowsecurity, not just relrowsecurity, and runs as the app role, not the owner.

### B2. The read path has no legal door to the database. §13 forbids `src/app/**/page.tsx` and `layout.tsx` from importing `@/server/db/**`, which includes `db/tenant.ts` — so no page can call `withTenant`. Simultaneously §4 says `components/features/` "may be async Server Components, may call services", while §13 forbids `src/components/**` from importing `@/server/**` at all. Services accept a TenantDb and never open their own transaction.

**Why it breaks:** Invariant 3 and L1/L2 contradict each other: as specified, nothing in the rendering tree can legally obtain a TenantDb, so every Server Component read is either impossible or will be implemented by someone quietly widening the ESLint zone — which is how the withTenant door stops being the only door. This is a hard contradiction inside the document, not a gap.

**Required fix:** Introduce an explicit read facade, e.g. `src/server/queries/<domain>.ts`, whose functions take a SessionContext (not a TenantDb), call withTenant internally, and return finished DTOs. Allow `src/app/**` and `src/components/features/**` to import `@/server/queries/**` only, keep `@/server/db/**` and `@/server/services/**` forbidden there, and delete the "features may call services" sentence in §4.

### B3. `withTenant` sets exactly one `app.mandant_id`, but four first-class read scopes in this very document need more than one: the worker portal reading shifts and hours across all of a person's employments (EMP-14, EMP-03, EMP-15), the customer portal reading across all four entities (CRM-06), the mandant switcher's live per-area counters (TEN-10), and `services/kern/anstellung.ts listAnstellungenForPerson`. Only the *write* helpers (`withAnstellung`, `withKundenVorgang`) are defined; no read handle and no RLS policy shape exists for any of these.

**Why it breaks:** Invariant 3 plus SPEC requirements EMP-14, EMP-15, CRM-06, TEN-10. Under a policy of `mandant_id = current_mandant()` these queries return zero rows; a developer will fix it at 2am by looping withTenant per mandant (N transactions, and the loop authorises itself) or by reaching for db/client.ts. Required queries are impossible as designed.

**Required fix:** Define `withPerson(personId, fn)` and `withKunde(kundeId, fn)` alongside the write helpers: each resolves the permitted mandant set server-side from `anstellung` / `auftrag` respectively, sets `app.mandant_ids`, opens a READ ONLY transaction, and returns a `ScopedReadDb`. Add the matching `current_mandant_ids()` helper to `db/rls/_helpers.sql` and state that every tenant table's SELECT policy is `mandant_id = current_mandant() OR mandant_id = ANY(current_mandant_ids())`. Name the switcher counter query explicitly — it runs under the user's `benutzer_mandant` set, not under the active mandant.

### B4. `person`, `nachweis`, `qualifikation`, `bewacher_eintrag` and `mitarbeiter_zugang` are listed in `kern.ts` next to tenant tables with no documented exemption, while `tests/invariants/mandant-id-and-rls.test.ts` is specified as asserting that *every* tenant table has `mandant_id` AND RLS, and `tests/isolation/matrix.ts` generates its cases from the schema barrel with no exception list.

**Why it breaks:** Invariant 9 and D-09. These five tables must NOT carry `mandant_id` — a §34a certificate belongs to the human. The generated test will fail on them, and the cheapest way to make a red required check green is to add `mandant_id` to `nachweis`. That produces exactly the failure D-09 spells out: one valid and one expired copy of the same certificate, and a scheduler that passes its own check while assigning an unqualified guard (SEC-04, LEG-04). Also note `personal/nachweise/page.tsx` is placed under `[mandant]`, so a mandant-scoped page is reading a non-tenant table with no stated policy.

**Required fix:** Add to this document an explicit, reviewed table classification with three buckets — tenant-scoped (carries mandant_id + RLS), person-scoped (no mandant_id; RLS `EXISTS (SELECT 1 FROM anstellung a WHERE a.person_id = <t>.person_id AND a.mandant_id = current_mandant())`), and global (`mandant`, `rolle`, `berechtigung`). Make the classification a checked-in list that both the invariant test and the isolation matrix read, so adding a table forces a classification decision in review.

### B5. D-09 clause 6 ("a manager in cleaning must not see security wage rates") is enforced only by a comment. `gruppe/personen/page.tsx` says "identity only, no wage data" with no mechanism, and `withGruppe` sets `app.mandant_ids` to the user's entire readable set, which for a multi-entity Leitung includes another entity's `anstellung` rows carrying `stundensatz_intern_cent`.

**Why it breaks:** Invariant 9, D-09.6, EMP-13, TEN-05. A row-level policy that grants the whole `anstellung` row grants the wage column with it. The document also never says who may enter the group view or how `ctx.readableMandantIds` is derived, so the protection has neither a subject nor an object.

**Required fix:** State that (a) group-view entry requires an explicit `gruppe_lesen` permission and `readableMandantIds` is derived server-side from `benutzer_mandant`, never from the request; (b) cross-entity person reads go through a dedicated view `person_gruppe_v` (id, vorname, nachname, mandant labels) declared `WITH (security_invoker = true)`, and the underlying `anstellung` columns `stundensatz_intern_cent`, `wochenstunden`, `arbeitszeitmodell` are REVOKEd from the app role on that path; (c) tests/isolation gains a case asserting a reinigung Leitung cannot read a security `stundensatz_intern_cent` by any route, including the group view.

### B6. The cross-entity ArbZG check (TIM-14, D-09.1/2) is described as having "its own RLS policy allowing a planner to see the existence of a conflicting shift in another entity". A row-level policy is a row grant; it cannot return "only start/end and entity label". And under `withTenant` only one `app.mandant_id` is set, so no policy keyed on it can match another entity's rows at all.

**Why it breaks:** This is the single most important consequence of D-09 and it is under-specified in both directions. Either the query returns nothing — a 6h cleaning + 5h security day is not detected, which is an unlawful assignment under ArbZG/LEG-03 — or the policy grants the whole `einsatz` row of another GmbH, leaking objekt, posten and customer detail across legal entities (EMP-13, D-09.6).

**Required fix:** Specify a single `SECURITY DEFINER` SQL function `arbzg_konflikte(p_person_id uuid, p_von timestamptz, p_bis timestamptz)` owned by a privileged role, whose RETURNS TABLE is fixed to (mandant_id, mandant_name, beginn_zeitpunkt, ende_zeitpunkt) and nothing else, with EXECUTE granted to the app role only. `services/zeit/arbzg.ts` calls that function; it never SELECTs `einsatz` cross-tenant. Record the fixed return shape here so O-17 can only widen it by amending this document.

### B7. `middleware.ts` is placed at the repository root while the application lives in `src/app/`. Next.js only picks up middleware at `src/middleware.ts` when a `src/` directory is used.

**Why it breaks:** The middleware is assigned four jobs in §12: Supabase session refresh, security headers, locale negotiation for worker routes, and the rate-limit hook for `(auth)` and `api/formular`. All four silently do nothing. AUT-07 (rate limiting and lockout on auth endpoints) and SEC-A7 (CSP, HSTS, X-Frame-Options) become unimplemented while the file exists and looks correct — the exact silent, late-discovered failure mode CLAUDE.md's invariant preamble describes.

**Required fix:** Move it to `src/middleware.ts` in the tree, and add a smoke test in `tests/e2e` asserting that a response to `/login` carries the CSP and HSTS headers and that the eleventh request in a minute is rate-limited.

### B8. The invoice number and the hash-chain head are treated as two independent mechanisms. §3.3 has `nummernkreis.assignNumber (SELECT … FOR UPDATE)` and `hash-chain.ts hashChain · verifyChain` as separate modules, and §14 says only "the counter row is keyed so a per-document-type split is a data change". Nothing states that the previous hash is read under the same row lock.

**Why it breaks:** Invariant 4, FIN-03, FIN-06, LEG-01/GoBD. Two concurrent finalizations serialise correctly on the counter row for the *number* but can both read the same `letzter_hash` before either commits, producing two invoices claiming the same predecessor. The chain forks; `hash-chain-verify.ts` then reports a break nightly on a chain that was never tampered with, and the real tamper signal is lost in the noise. Finalisation is exactly the operation where this must be right the first time — it is one-way.

**Required fix:** State that the counter row itself carries `letzter_hash`, and that `finalizeRechnung` performs number assignment, payload hashing and the counter update inside one transaction under a single `SELECT … FOR UPDATE` on that row. Add `src/server/services/finanz/rechnung.concurrency.test.ts` to the mandatory list: ten parallel finalizations produce ten consecutive numbers and one unbroken chain.

### B9. The policy gate is entirely data-driven: `policy.ts` "Reads `agent_richtlinie`. Nothing leaves without it" and `autonomy.ts` holds "the SPEC §17 autonomy matrix as data, not scattered conditionals", with `agenten/richtlinien/page.tsx` marked "editable, no code" (AGT-03).

**Why it breaks:** Invariant 7 and ROADMAP Phase 8 acceptance: "A €25,000 offer cannot be sent automatically under any configuration." If the matrix is data and the data is UI-editable, a configuration exists in which it can. SPEC §17 states three rules as absolute — any offer at any value is proposal-only, offers over €20,000 are never automatic, discounts and concessions never — and they cannot live in an editable row.

**Required fix:** Split the gate: `agent/policy-invariants.ts` holds the non-overridable rules as code constants that `policy.ts` evaluates *after* `agent_richtlinie`, and no richtlinie row can relax them. Document that AGT-03's UI can only tighten. Add `src/server/agent/policy.test.ts` to the may-never-be-skipped set with the €25,000 case asserted against an `agent_richtlinie` row that explicitly permits automatic sending.

### B10. The ESLint zone forbids `src/server/agent/tools/**` from importing `@/server/db/**`, but `src/server/agent/rag/**` (chunk, embed, retrieve) is unrestricted, and nothing in the document states that `wissens_chunk` carries `mandant_id`, that retrieval runs under `withTenant`, or that `jobs/index/wissensindex.ts` indexes per mandant.

**Why it breaks:** Invariant 3 and SEC-A3. AGT-06 indexes contracts, objects, offers and correspondence — the most commercially sensitive text in three separate GmbHs — into one pgvector table. A similarity search is a query with no tenant predicate unless one is added; the CEO Assistant of the cleaning entity would answer from a REALTIME contract, and nothing in the isolation matrix covers a vector search because it derives its cases from table rows, not from embeddings.

**Required fix:** Extend the ESLint zone to `src/server/agent/{tools,rag}/**`; require `wissens_chunk` to carry `mandant_id` and its RLS policy to be listed in `db/rls/radar-ki-inhalt.sql`; state that `retrieve.ts` takes a TenantDb and that the ANN index is `(mandant_id, embedding)` so the filter is not applied after the top-k cut. Add a case to tests/isolation asserting a retrieval as a user of A returns no chunk of B.

### B11. `auth/switch-mandant.ts` is described as "the ONLY writer of the active mandant" and as writing the session, writing `audit_log` and redirecting — with no authorization step against `benutzer_mandant`.

**Why it breaks:** Invariant 3 and TEN-06. The document correctly establishes that `params.mandant` is powerless, then leaves the one function that *does* set the tenant without a check. A Server Action is a public HTTP endpoint; `switchMandant('bau')` invoked by a reinigung-only user would set a session the whole RLS layer then trusts. This defeats the entire tenancy model through its single intended door.

**Required fix:** Specify the order explicitly: resolve target slug → assert a `benutzer_mandant` row exists for (benutzerId, targetMandantId) → write session → write audit_log (TEN-09) with old and new mandant → redirect. Add the negative case to tests/isolation/http: a user of A calling switchMandant for B gets 404 and no session change.

### B12. `[mandant]` is a dynamic segment at the *root* of the URL space, sharing that space with `(public)` (`/news`, `/kontakt`, `/leistungen`, `/karriere`, `/projekte`, `/unternehmen`, `/ueber-uns`, `/bereiche`, `/rechtliches`, `/angebot-anfragen`), `(mitarbeiter)` (`/meine`), `(kunde)` (`/portal`) and `(checkin)` (`/einsatz`).

**Why it breaks:** TEN-08 says a fifth business area requires a DB row and no code change. A mandant seeded with the slug `news`, `portal`, `meine` or `einsatz` is shadowed by a static route and its entire portal becomes unreachable — a data change silently breaking the application, with no test that would catch it. The collision also makes URLs like `/reinigung/reinigung/reviere` and `/security/bau/projekte` well-formed.

**Required fix:** Move the staff application under a fixed prefix — `(portal)/app/[mandant]/…` yielding `/app/reinigung/dienstplan/woche` — or, if the bare slug is wanted, add a reserved-slug list validated in `services/kern/mandant.ts createMandant` and asserted by a test that enumerates every static first segment in `src/app`. Also gate the trade folders: `[mandant]/security/**`, `/reinigung/**` and `/bau/**` must `notFound()` unless the active mandant's `gewerk` matches, otherwise every entity exposes every trade module's routes.

### B13. The RLS section names only the reading side (`current_setting('app.mandant_id', true)::uuid`) and never mentions `WITH CHECK`. §3.2's narrative is entirely about SELECT visibility.

**Why it breaks:** Invariant 3. A `USING`-only policy filters reads and leaves INSERT and the post-image of UPDATE unconstrained: a service with a bug, or a Zod-validated body carrying a mandant_id, can write a row into another entity. The isolation suite as described tests "user of A selecting B's row gets zero rows" — a write-side leak would pass every listed test.

**Required fix:** State that every tenant-table policy declares both `USING (mandant_id = current_mandant())` and `WITH CHECK (mandant_id = current_mandant())`, that `mandant_id` is never accepted from an input schema (it is set by `_shared.mandantId()` defaults or by the service from `ctx`), and add `tests/isolation/db/write-check.test.ts` asserting an INSERT with a foreign mandant_id raises.

### B14. No rule for views or materialized views anywhere in the document, while REP-01..07, DSH-01, ACC-07, ACC-08 and `services/gruppe/aggregat.ts` are precisely the aggregation workloads that get built on them.

**Why it breaks:** Invariant 3, SEC-A2. A Postgres view executes with the *view owner's* permissions unless created `WITH (security_invoker = true)` (PG15+), and a materialized view ignores RLS entirely — its contents are computed once by its owner and readable by anyone with SELECT. One BWA matview (ACC-08) or one revenue rollup (REP-01) built the obvious way exposes three entities' figures to every role. `tests/isolation/matrix.ts` enumerates tables from the schema barrel and would not see a view at all.

**Required fix:** Add to §7/§13: every view is created `WITH (security_invoker = true)`; materialized views are forbidden for tenant data — where one is needed for performance it must carry `mandant_id` and be wrapped in a security_invoker view with an RLS-equivalent predicate. Extend the invariant suite to enumerate `pg_class.relkind IN ('v','m')` as well as tables.

### B15. `_shared.ts` hard-codes `.notNull()` into `geldCent()`, and §13 bans `numeric`, `decimal`, `real`, `doublePrecision` and `float` across all of `src/server/db/schema/**` with no carve-out and no prescribed alternative for non-money quantities.

**Why it breaks:** Two distinct defects. (a) Legitimately nullable money — `ausschreibung.geschaetzter_wert_cent` (OCDS often omits it, RAD-01), `radar_profil` value bounds (RAD-04), an unknown `stundensatz_intern_cent`, a `mahngebuehr_cent` before a level is reached — cannot use the helper, so those columns will be written as raw `bigint` and escape the one place invariant 1 is expressed as code. (b) OPS-02 room area in m², OPS-03 performance values in m²/h, BAU-01 `lv_position.menge` and BAU-02's computed result (`30,87 m²`, which an auditor must be able to reconcile with the Rechenansatz) all need exact decimals. With every exact and every inexact numeric type banned, the implementer's remaining options are float-by-another-name or an undocumented integer scale — and the ban is by type name, so nothing catches it.

**Required fix:** Change `geldCent` to return a nullable column with an explicit `geldCentNotNull` variant, and scope the lint rule by column role rather than type name: ban `real`/`doublePrecision`/`float` everywhere in `schema/**` unconditionally; ban `numeric` only on columns whose name ends in `_cent`; add a `menge(name, precision, scale)` helper returning `numeric(p,s)` for physical quantities and require it for `flaeche_qm`, `leistungswert_qm_h`, `menge` and `aufmass_ergebnis`. Update `tests/invariants/money-is-bigint.test.ts` to assert the pairing (every `_cent` column is bigint; no column anywhere is float8/float4).

### B16. SEC-A9 requires the audit log to record actor (human / agent / system), action, before, after, timestamp and IP, and `db/triggers/audit-log.sql` is specified to write before/after payloads at the database level. But `withTenant` sets only `app.mandant_id` and `app.benutzer_id`, and `_shared.audit()` gives `created_by uuid` with no reference and no actor-type column.

**Why it breaks:** The trigger physically cannot record the actor type or the IP — they are never transported into the session. Agent-initiated and job-initiated writes have no `benutzer` row at all, so `created_by` is null and indistinguishable between "system job" and "unknown". SEC-A9 is an explicit SPEC requirement and the audit log is one of the no-hard-delete domains, so this is not repairable retroactively.

**Required fix:** Extend `withTenant` / `withGruppe` / `withAnstellung` / `withKundenVorgang` to also `set_config('app.akteur_typ', …)` (`mensch` | `agent` | `system`), `app.akteur_id` and `app.ip`, all sourced server-side; have `jobs/_runner.ts` and `agent/orchestrator.ts` set `system` / `agent` respectively. Add `akteur_typ` to the `audit_log` columns and have the trigger read all four settings.

### B17. Three independent write paths exist for one punch: `(checkin)/einsatz/[token]/_actions.ts`, `api/checkin/[token]/route.ts`, and `supabase/functions/checkin-punch/index.ts` (a Deno Edge Function described as "same service call as api/checkin/[token] — no duplicated logic").

**Why it breaks:** Invariant 5, TIM-08. A Deno Edge Function cannot import `src/server/services` from the Next.js application, so "no duplicated logic" is not achievable — it will be a second implementation. Worse, it is a different machine with a different clock, so "the server clock is the source of truth" now has two servers, and `zeitabweichung_sek` becomes meaningless because the reference instant depends on which endpoint the phone reached. There is also no tenant handle defined for any of them: the check-in flow has no session, so `withTenant` (which throws without `ctx.mandantId`) cannot be used.

**Required fix:** Delete `supabase/functions/checkin-punch` from the tree, or specify it as a pure proxy that forwards to `api/checkin/[token]` and never stamps a time. Keep exactly one punch entry point. Define `withCheckinToken(token, fn)` in `db/tenant.ts`: it validates the single-use token, resolves einsatz → anstellung → mandant server-side, opens the tenant transaction, and stamps the instant from the injected Clock inside that transaction.
