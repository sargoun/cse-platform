# Adversarial review — finanzen

## BLOCKING (21)

### B1. `app.hat_recht(p text)` takes no mandant argument. Every STP policy in the domain calls it as a global predicate, so a right granted to a user in one Mandant is carried into every other Mandant they can reach.

**Why it breaks:** D-09 clause 6 and SPEC §22 state explicitly: "a cleaning manager must not see security wage rates." A user who is `leitung` in `reinigung` (holding `finanzen.lesen`) and has any benutzer_mandant row for `security` passes `mandant_id = app.aktiver_mandant() AND app.hat_recht('finanzen.lesen')` the moment they switch tenant, and reads security `ausgabe` rows carrying `anstellung_id` and security `buchungssatz` personnel-cost lines. Also violates AUT-03 ("permissions configurable per role per mandant") and AUT-05 (RLS mirrors application authorization).

**Required fix:** Change the helper to `app.hat_recht(p text, m uuid default app.aktiver_mandant())` resolving through `benutzer_mandant → rolle → berechtigung` for that specific mandant, and rewrite STP as `mandant_id = app.aktiver_mandant() AND app.hat_recht('finanzen.lesen', mandant_id)`. The group branch must call `app.hat_recht('gruppe.finanzen.lesen', mandant_id)` per row, not once globally.

### B2. The group-mode branch of STP (`app.gruppen_modus() AND mandant_id IN (SELECT app.sichtbare_mandanten()) AND app.hat_recht('gruppe.finanzen.lesen')`) grants row-level SELECT on **every** table in the domain, including `ausgabe` (which carries `anstellung_id`), `buchungssatz`, `zahlung` and `eingangsrechnung`.

**Why it breaks:** TEN-05 says the group view *aggregates*; D-09 clause 6 says `anstellung` and everything below it stay strictly tenant-scoped. Granting base-table row access across Mandanten in group mode reproduces exactly the leak D-09 forbids — a reimbursement row for a named security employment becomes readable from the Reinigung session. EMP-13 likewise.

**Required fix:** Group mode must not read base tables. Expose group figures through aggregate-only views (`security_barrier`, no `anstellung_id`, no `person`-identifying column, grouped to at least mandant × period × account) and remove the `gruppen_modus()` branch from the STP of `ausgabe`, `buchungssatz`, `zahlung`, `eingangsrechnung`, `eingangsrechnung_extraktion` and `beleg`. Keep it, if at all, only on `rechnung`/`rechnung_steuer` totals.

### B3. `aufbewahrung_bis date GENERATED ALWAYS AS (make_date(extract(year from erstellt_am at time zone 'Europe/Berlin')::int + 10, 12, 31)) STORED` will not create. `timestamptz AT TIME ZONE text` is `timezone(text, timestamptz)`, which Postgres marks **STABLE**, not IMMUTABLE, and STORED generated columns require an immutable expression. Postgres raises `ERROR: generation expression is not immutable`. Separately, on `rechnung_snapshot` the expression references `erstellt_am`, a column that table does not have (it has `erzeugt_am`).

**Why it breaks:** Every archive-bearing table in the domain (`rechnung_snapshot`, `beleg`, `buchungssatz`, `datev_export`) fails DDL. The GoBD retention field (ACC-06, LEG-01, DOC-07) does not exist at all, and the first migration of Phase 6/7 does not apply.

**Required fix:** Make `aufbewahrung_bis date NOT NULL` a plain column populated by a `BEFORE INSERT` trigger calling an immutable helper, or derive it from a plain `date` column (`belegdatum`, `buchungsdatum`, `rechnungsdatum`) so the expression is immutable. Do not hard-code the `+ 10` — see the retention entry under invented_rules.

### B4. `rechnung.zahlbetrag_cent = brutto_cent − abzug_brutto_cent − bauabzugsteuer_cent`, enforced by CHECK, and this is the value handed to the XRechnung generator as the amount due.

**Why it breaks:** EN 16931 rule **BR-CO-16** requires `BT-115 (Amount due for payment) = BT-112 (Grand total) − BT-113 (Paid amount) + BT-114 (Rounding)`. Bauabzugsteuer is not an EN 16931 concept and has no slot in BT-113. An invoice with §48 EStG withholding therefore produces a BT-115 that fails BR-CO-16 and is rejected by the KoSIT validator — which FIN-11 requires to pass in CI, and without which the group cannot invoice GIZ, DRV Bund or the Berlin districts at all.

**Required fix:** Split the two concepts: keep `zahlbetrag_cent` as the EN 16931 BT-115 value (`brutto − abzug_brutto`), and add a separate `einbehalt_bauabzugsteuer_cent` plus a derived `ueberweisungsbetrag_cent` used only on the PDF and in the open item. Emit the withholding as a BT-22 note ("Steuerabzug nach §48 EStG …") in the XML, never inside the payable-amount arithmetic.

### B5. `rechnungsposition.einheit text` holds display labels (`h`, `m²`, `Stk`, `Monat`, `pauschal`). There is no UN/ECE Recommendation 20 unit code column anywhere, and none in the canonical snapshot payload.

**Why it breaks:** EN 16931 BT-130 (Invoiced quantity unit of measure code) is mandatory and must be a UN/ECE Rec 20 / Rec 21 code (`HUR`, `MTK`, `H87`, `MON`, `LS`). A free-text German label cannot be mapped deterministically at render time — `Stk` is `H87` or `C62` depending on convention, `pauschal` is `LS` — so the XRechnung is either invalid (FIN-11 KoSIT fails) or the mapping is guessed at render time, meaning two renders of the same finalised invoice can differ.

**Required fix:** Add `einheit_code text NOT NULL` constrained to a seeded `masseinheit` reference table (code, UN/ECE Rec 20 value, German label), keep `einheit` as the display label only, and include `einheit_code` in the `cse.rechnung.v1` payload.

### B6. The canonical payload `cse.rechnung.v1` omits data that is printed on the issued document and required by EN 16931: the paying bank account (BG-16 / BT-84 IBAN, BT-81 payment means code), `kopftext`/`fusstext`, `steuerhinweis`, `sprache`, the per-line unit code, the invoice type code (BT-3, UNTDID 1001), and seller/buyer electronic addresses (BT-34 / BT-49). `rechnung` has no `bankkonto_id` at all.

**Why it breaks:** §11 of the draft justifies the whole design with "the PDF is a rendering of the snapshot". It is not: the snapshot cannot reproduce the invoice, because the IBAN printed on it lives in a mutable `bankkonto` row and the free texts live in `rechnung` columns that are outside the hashed bytes. Change the entity's bank account in 2028 and every re-render of a 2026 invoice shows the wrong IBAN while the hash still verifies. That defeats FIN-06 and the GoBD Unveränderbarkeit claim (LEG-01, ACC-06), and BT-34/BT-49 are mandatory in XRechnung so FIN-11 fails without them.

**Required fix:** Add `bankkonto_id` (composite FK, frozen at finalisation), `zahlungsbedingung_text`, `rechnungsart_code` (UNTDID 1001: 380 standard, 381 storno, 386 abschlag, 384 korrigiert), `verkaeufer_eadresse`/`kaeufer_eadresse` with their scheme ids, and include all of them plus `kopftext`, `fusstext`, `steuerhinweis`, `sprache` and per-line `einheit_code` in the payload. Bump `schema_version` before any invoice is finalised.

### B7. Invoice number uniqueness is `UNIQUE (nummernkreis_id, nummer)`, not per Mandant.

**Why it breaks:** §14 Abs. 4 Nr. 4 UStG requires a "fortlaufende Nummer …, die zur Identifizierung der Rechnung vom Rechnungsaussteller **einmalig** vergeben wird" — unique per issuer, not per counter row. One Mandant legitimately owns several circles (`periode` 2026 and 2027 when `zuruecksetzung='jaehrlich'`, plus any future second circle). With a mask that does not embed the year, two circles of the same GmbH produce the identical number `RE-00042` twice and the database accepts it. LEG-05 is then unenforced at the only layer that can enforce it.

**Required fix:** Replace with `UNIQUE (mandant_id, nummer)` (keep `UNIQUE (nummernkreis_id, nummer_laufend)` for the gap proof), and add a CHECK/trigger that `format_maske` contains `{jahr}` whenever `zuruecksetzung = 'jaehrlich'`.

### B8. When `zuruecksetzung = 'jaehrlich'`, a new calendar year means a new `nummernkreis` row, and because the hash chain is scoped `(nummernkreis_id, kette_position)` with a 64-zero genesis, **each year starts a fresh chain**.

**Why it breaks:** An entire fiscal year of invoices can be removed and the following year's chain still verifies cleanly — the nightly job (SPEC §14 watchdog "Invoice hash chain broken → nightly → alert immediately") reports nothing. FIN-06 promises a hash chain "across finalized invoices"; a per-year restart makes the most valuable tampering case invisible.

**Required fix:** Scope the chain per Mandant, not per `nummernkreis`: key `rechnung_hash` on `(mandant_id, kette_position)` with a mandant-wide monotonic position, or keep the per-circle chain but seed a new circle's genesis with the last `hash` of the Mandant's previous circle and store `vorgaenger_nummernkreis_id` so the walk crosses the year boundary.

### B9. `abzug_brutto_cent bigint NOT NULL CHECK (>= 0)`, `bauabzugsteuer_cent bigint NOT NULL CHECK (>= 0)`, and `abschlagsrechnung_bezug.abzug_netto_cent CHECK (> 0)` / `abzug_steuer_cent CHECK (>= 0)`.

**Why it breaks:** Invariant 4 permits correction only by reversing entry, and the draft's own `storno_verweis` trigger demands "the Storno's signed amounts must be the exact negation of the original's per tax group". A Storno of a Schlussrechnung must carry a **negative** `abzug_brutto_cent`, and a Storno of a Bau invoice must carry a negative `bauabzugsteuer_cent` — both are rejected by these CHECKs. The single most common construction correction (Storno of a Schlussrechnung) cannot be recorded.

**Required fix:** Drop the `>= 0` / `> 0` CHECKs on `abzug_brutto_cent`, `bauabzugsteuer_cent`, `bauabzugsteuer_grundlage_cent` and both `abschlagsrechnung_bezug` amounts. Replace with a sign-coherence CHECK keyed on `rechnungsart`: `sign(abzug_brutto_cent) = sign(brutto_cent)` (allowing 0), so a Storno mirrors the original and a normal invoice cannot go negative by accident.

### B10. `CHECK (status <> 'festgeschrieben' OR (… leistung_von IS NOT NULL AND leistung_bis IS NOT NULL …))` applies to every `rechnungsart`, including `abschlag`. There is no `vereinnahmung_am` column and no `anzahlung`/`vorauszahlung` rechnungsart.

**Why it breaks:** §14 Abs. 4 Nr. 6 UStG requires either the Zeitpunkt der Leistung **or** the Zeitpunkt der Vereinnahmung des Entgelts. A Vorauszahlungs-/Anzahlungsrechnung is issued before any service is rendered and has no Leistungszeitraum; the CHECK makes it impossible to finalise one, and there is nowhere to put the payment date the statute accepts instead. FIN-08 requires Abschlagsrechnungen; the schema forbids the prepayment case of them.

**Required fix:** Relax the CHECK to `(leistung_von IS NOT NULL AND leistung_bis IS NOT NULL) OR (rechnungsart IN ('abschlag','anzahlung') AND vereinnahmung_geplant_am IS NOT NULL)`, add the `vereinnahmung_geplant_am date` column and the `anzahlung` enum value, add validator rule "Anzahlungsrechnung must state that the service has not yet been rendered", and include the field in the payload.

### B11. `ux_quelle_aufmass (aufmass_id) WHERE quelle_typ='aufmass' AND wirksam` — a global partial unique on the Aufmaß.

**Why it breaks:** Under VOB/B §16 an Aufmaß is routinely billed once in an Abschlagsrechnung and again (net of the deduction) in the Schlussrechnung, and partial quantities of one Aufmaß are billed across successive Abschläge. The unique index makes the second reference a constraint violation, so FIN-08 (Abschlag → Schluss for the Bau entity) cannot be executed on measured work — which is the only kind Bau produces (BAU-02). The `menge_anteil` column exists precisely for partial takes and is then unusable.

**Required fix:** Drop the unique index on `aufmass_id`. Replace the double-billing guard with a tested service function plus a deferred constraint trigger asserting `Σ menge_anteil over wirksam rows ≤ aufmass.menge` per `aufmass_id`, and keep `ix_quelle_aufmass (aufmass_id) WHERE wirksam` as a plain index. Apply the same treatment before answering the open question on splitting a `zeiteintrag`.

### B12. Validator rule 13 offers exactly two outcomes for §48 EStG: a valid Freistellungsbescheinigung, or a 15 % withholding. The §48 Abs. 2 EStG Bagatellgrenze is absent, and nothing in the schema accumulates the Gegenleistung per calendar year per (Leistungsempfänger, Leistender).

**Why it breaks:** §48 Abs. 1 S. 1 EStG only requires withholding when the consideration to that Leistender in the current calendar year is expected to exceed the statutory Freigrenze (a higher one applies where the recipient only performs tax-exempt lettings). Withholding on a €900 subcontractor invoice is unlawful over-withholding, and the group is liable to the subcontractor for the amount it kept. Silently choosing "always withhold" is the exact class of legal rule CLAUDE.md forbids picking.

**Required fix:** Add `bauabzugsteuer_freigrenze` as a versioned, per-year reference table with `// TODO(client): confirm the §48 Abs. 2 EStG thresholds and which of the two applies per entity with the tax advisor`, plus a materialised running total `bauleistung_jahressumme (mandant_id, lieferant_id, jahr, gegenleistung_cent)` maintained on `eingangsrechnung` approval. Until the threshold row is `bestaetigt`, the validator must **block** (fehler), not withhold.

### B13. `datev_export_zeile` has `umsatz_text text NOT NULL`, `soll_haben_kz char(1) NOT NULL CHECK (IN ('S','H'))`, and `datev_export` has `summe_soll_cent`/`summe_haben_cent` `NOT NULL` with `CHECK (summe_soll_cent = summe_haben_cent)` — while `export_typ` includes `z3_gdpdu`, `lohn_zeitdaten` and `extf_debitoren_kreditoren`.

**Why it breaks:** Three of the four declared export types are not booking stacks. A Z3/GDPdU export (ACC-09, §147 Abs. 6 AO) contains arbitrary table extracts; a payroll time export (ACC-12) contains hours per employment; a debtor/creditor master export (ACC-07/ACC-11) contains addresses and account numbers. None has an Umsatz or a Soll/Haben indicator, so their lines cannot be inserted and the file-level balance CHECK is a fiction satisfied only with 0 = 0. ACC-09, ACC-11 and ACC-12 are unbuildable on this model.

**Required fix:** Split the line table: keep `datev_buchungsstapel_zeile` with the booking-shaped NOT NULLs, and add `export_zeile` with `felder jsonb NOT NULL` plus a nullable typed projection for non-booking exports. Make `summe_soll_cent`/`summe_haben_cent` nullable and move the balance CHECK to `WHERE typ = 'extf_buchungsstapel'`.

### B14. `eingangsrechnung.interne_belegnummer` is drawn from a gapless `nummernkreis` at status `freigegeben`, while the status trigger permits `→ abgelehnt` "from any pre-booked state", which includes `freigegeben`.

**Why it breaks:** A supplier invoice approved and then rejected has consumed a number from a gapless circle and abandoned it — exactly the gap the draft spends a whole section proving is impossible for outgoing invoices. GoBD/LEG-01 gapless numbering applies to the internal Beleg circle too, and the Phase 6 acceptance criterion ("zero gaps") is contradicted inside the same document.

**Required fix:** Assign `interne_belegnummer` at `gebucht`, not at `freigegeben` (booking is the irreversible step), or forbid `freigegeben → abgelehnt` and require a booked-then-reversed path. Add the transition table to the trigger explicitly rather than the prose "from any pre-booked state".

### B15. Deletion protection is `BEFORE DELETE` row triggers + `REVOKE DELETE` + no DELETE policy. `TRUNCATE` is covered by none of the three: it fires no row-level triggers, is not gated by RLS, and is not covered by `REVOKE DELETE`.

**Why it breaks:** ACC-06 requires "deletion impossible" and LEG-01 GoBD Unveränderbarkeit. Any role able to `TRUNCATE rechnung_hash` or `beleg` wipes the archive with no trigger fired and no audit row written — and the nightly verification job then finds an empty chain rather than a broken one.

**Required fix:** Add a statement-level `BEFORE TRUNCATE` trigger raising on every table in the domain, `REVOKE TRUNCATE ON ALL TABLES IN SCHEMA … FROM app_rw`, and ensure `app_rw` is not the table owner (owner bypasses `REVOKE`; `FORCE RLS` does not cover TRUNCATE).

### B16. `rechnung_snapshot` and `rechnung_hash` revoke UPDATE and DELETE but leave INSERT reachable by `app_rw` under the STP insert policy. The claim "insert is only reachable from `fin.finalisiere_rechnung()`" is not enforced anywhere.

**Why it breaks:** Anyone holding `finanzen.schreiben` can insert a snapshot and a chain link directly, forging a chain entry or pre-claiming a `kette_position`. The hash chain's evidential value (FIN-06, LEG-01) rests entirely on the write path being closed.

**Required fix:** `REVOKE INSERT ON rechnung_snapshot, rechnung_hash FROM app_rw`, drop their INSERT policies, and make `fin.finalisiere_rechnung()` `SECURITY DEFINER` owned by a role that holds the INSERT right, with `SET search_path` pinned. Grant EXECUTE on the function to `app_rw` only.

### B17. `buchungssatz.konto` is nullable "when `konto_mapping` is unconfirmed", but nothing prevents such a row from being set `festgeschrieben = true`, and the export-selection index `ix_bs_export (mandant_id, buchungsdatum) WHERE datev_export_id IS NULL AND festgeschrieben` does not exclude `konto IS NULL`.

**Why it breaks:** An unmapped booking can be frozen and swept into an EXTF file with an empty Konto field. The delivered file is silently unusable and the Phase 7 acceptance criterion — "the tax advisor accepts a real EXTF file without rework" — fails at the tax advisor, months later, which is the exact late-discovered failure mode CLAUDE.md names.

**Required fix:** Add `CHECK (NOT festgeschrieben OR (konto IS NOT NULL AND gegenkonto IS NOT NULL))`, and change the export index predicate to `WHERE datev_export_id IS NULL AND festgeschrieben AND konto IS NOT NULL`. Keep `ix_bs_offen (mandant_id) WHERE konto IS NULL` as the worklist.

### B18. `abschlagsrechnung_bezug` and `storno_verweis` carry only STP — no customer policy — while `rechnung`, `rechnungsposition`, `rechnung_steuer` and `offener_posten` all have one.

**Why it breaks:** A required query becomes impossible under RLS: the customer portal renders a Schlussrechnung from the database and gets zero deduction rows, so the customer is shown an invoice whose positions and totals do not reconcile with `zahlbetrag_cent` — and a customer whose invoice was cancelled sees the cancelled invoice with no indication it was stornoed. DSH-04 ("every figure links to the records behind it") and the SPEC §3 Kunde scope ("own … invoices") are unmet.

**Required fix:** Add the same customer SELECT policy (joined through `rechnung`) to `abschlagsrechnung_bezug` and `storno_verweis`, restricted to `status = 'festgeschrieben'` on both referenced invoices.

### B19. `nummernkreis` `BEFORE UPDATE` trigger enforces `NEW.letzter_wert = OLD.letzter_wert + 1` on every update.

**Why it breaks:** Setting `bestaetigt = true` after the client answers the numbering question, editing `format_maske`, or deactivating a circle (`aktiv = false`) are all updates in which `letzter_wert` is unchanged — the trigger rejects them. The mask can never be confirmed, so finalisation (which refuses while `bestaetigt = false`) is permanently blocked in production.

**Required fix:** Rewrite as: `IF NEW.letzter_wert <> OLD.letzter_wert AND NEW.letzter_wert <> OLD.letzter_wert + 1 THEN RAISE`. Add a second clause forbidding any change to `format_maske`, `zuruecksetzung`, `typ` or `periode` once `letzter_wert > 0`, which is the property that actually matters.

### B20. A Storno's open item cannot be netted against the original's. `offener_posten` is `UNIQUE (rechnung_id)`, `zahlung_zuordnung.betrag_cent CHECK (> 0)` and `zahlung.betrag_cent CHECK (> 0)` — every clearing path requires a `zahlung` row, i.e. money that moved.

**Why it breaks:** The normal correction sequence (finalise invoice → customer disputes → Storno → re-issue) leaves two open items, one positive and one negative, that can only be closed by recording a payment that never happened. ACC-07 open-item lists and the aging report are then permanently wrong, and the "Invoice overdue > 14 days" watchdog (SPEC §14) duns an invoice that was cancelled.

**Required fix:** Add an `op_ausgleich` table (`mandant_id`, `op_soll_id`, `op_haben_id`, `betrag_cent`, `grund`, `erstellt_von`) for OP-to-OP clearing, extend `fin.op_fortschreiben()` to consume it, and have the Storno transaction create the clearing row automatically. Do not relax the `> 0` CHECK on `zahlung`.

### B21. `fin.finalisiere_rechnung(p_rechnung_id uuid)` is specified as a database function whose step 2 is "pre-flight validator → zero Fehler, else ABORT", while §5 places the validator in `src/server/services/finanzen/pflichtfelder.ts` ("pure, tested, no HTTP").

**Why it breaks:** A plpgsql function cannot call TypeScript. Either the validator runs in the application *before* the `FOR UPDATE` of steps 1/3 — in which case a concurrent edit between validation and lock acquisition finalises an invoice that failed §14 UStG (LEG-05, FIN-04) — or the rules are duplicated in SQL and the two copies drift. The contract does not say which, so the implementation PR will pick one arbitrarily.

**Required fix:** State the boundary explicitly: the application opens the transaction, `SET LOCAL app.mandant_id`, takes `SELECT … FROM rechnung … FOR UPDATE` **first**, then runs the TypeScript validator inside that transaction, then calls a `SECURITY DEFINER` function for steps 3–11. Store the validator's `regelwerk_version` and report in the snapshot as already designed.

## MISSING (27)
- ACC-08 ("monthly figures (BWA-style) per entity and group") and FIN-17/REP-01 have no structure at all — only a passing mention in an index comment. There is no period table, no `monatsabschluss`/`perioden_sperre` row locking a closed month against further postings, and no BWA aggregation view. GoBD Festschreibung is modelled per `buchungssatz` but not per period, so a month handed to the tax advisor can still receive new bookings afterwards.
- ACC-10 (`Verfahrensdokumentation` generated from live configuration) has no table. GoBD requires a dated, versioned Verfahrensdokumentation and the ability to show which version was in force at any past date. `beleg_quelle` values are described as things the Verfahrensdokumentation "must state", but nothing stores the generated document, its version, its effective period or its approver.
- §13b UStG evidence is a bare `kunde.bauleistender boolean` with no validity window, no document and no revocation. The USt-1-TG-type Bescheinigung has a limited validity and can be revoked; the schema has a full `freistellungsbescheinigung` table for §48b EStG and nothing equivalent for §13b, so `reverse_charge` is set from an undated flag. Add a `ust13b_bescheinigung` table with `gueltig_von/gueltig_bis`, `dokument_id`, `widerrufen_am`, and evaluate it at `leistung_bis` exactly as FIN-10 does.
- §13b Abs. 2 Nr. 8 UStG (Gebäudereinigungsleistungen an einen Unternehmer, der selbst Gebäudereinigungsleistungen erbringt) is unrepresentable. The domain models §13b as construction-only (`kunde.bauleistender`, `lieferant.bauleistung`), yet `reinigung` is one of the four Mandanten and subcontracting cleaning to another cleaning contractor is routine. Needs a per-Leistungsart flag (`bauleistender` / `gebaeudereiniger`) on both customer and supplier, both evidenced and dated.
- §48a EStG is absent: there is no record of the Anmeldung and Abführung of withheld Bauabzugsteuer to the Finanzamt (due by the 10th of the following month), no Abrechnung issued to the Leistender, and no open item for the liability. The platform withholds the money and then loses track of the obligation to pay it on.
- Cash is unmodelled although `zahlungsmittel` has `bar`, `karte` and `verrechnung` and `beleg_typ` has `kassenbeleg`. `konto_schluessel_typ = 'geldkonto'` resolves only through `bankkonto_id` (an IBAN-bearing FK), so a cash or card payment can never resolve a Geldkonto. There is no `kasse` table and no running cash balance, which GoBD requires for Kassensturzfähigkeit.
- §20 UStG Ist-/Soll-Versteuerung is listed as an open question but has no placeholder anywhere — no column on `mandant`/`datev_konfiguration`, no interface, no TODO in the schema. It changes the booking date and the DATEV BU-Schlüssel on every outgoing invoice, so ACC-01/ACC-02 cannot be built without it. Add `datev_konfiguration.versteuerungsart` nullable with `// TODO(client)` and gate `bestaetigt` on it.
- SEC-A9 requires a full audit log with actor, action, **before**, **after**, timestamp and IP. The domain has `erstellt_von`/`geaendert_von` (last writer only) and references `audit_log` solely as the nightly job's output target. There is no before/after audit trigger on the mutable rows — `eingangsrechnung` while `in_pruefung`, `nummernkreis`, `konto_mapping`, `mahnstufe`, `datev_konfiguration`, `steuersatz_gruppe` — so the change history GoBD asks about does not exist.
- APR-07 ("immutable snapshot of exactly what was approved, plus approver and timestamp") is implemented only for outgoing invoices. The incoming-invoice approval has no frozen record: `eingangsrechnung_extraktion` stays mutable in `status`, `uebernommen_felder`, `korrekturen` and `geprueft_*`, so what the human accepted can be rewritten afterwards. Needs an append-only `freigabe_snapshot` (proposal + accepted values + typed result + approver + timestamp) written in the approval transaction.
- APR-08 ("measure review duration; flag consistent sub-3-second approvals") is cited on `eingangsrechnung_extraktion.korrekturen` but no duration can be computed: there is `geprueft_am` and nothing recording when the reviewer was shown the item. Add `angezeigt_am timestamptz` (server clock) and a derived `pruefdauer_ms`.
- `ausgabe` carries one `steuersatz_gruppe_id` and a single `netto/steuer/brutto` triple, so a mixed-rate receipt — the most common petty-cash case (fuel at 19 % plus food at 7 % on one Beleg) — cannot be entered. The draft raises this question for `eingangsrechnung` and not for `ausgabe`, where it is more frequent. Needs an `ausgabe_steuer` child table keyed per tax-rate group.
- Skonto has no VAT treatment. `zahlung_zuordnung_art` has `skonto` and `konto_schluessel_typ` has `skonto_aufwand`/`skonto_ertrag`, but a Skonto deduction reduces the Entgelt and requires a §17 UStG correction split across the invoice's tax-rate groups. The allocation row has no `steuersatz_gruppe_id` and no correction `buchungssatz` path, so an invoice mixing 19 % and §13b lines cannot have its Skonto booked correctly.
- There is no way to record an overpayment or a customer credit balance. `zahlung_zuordnung` rejects an allocation exceeding the open item unless `art='differenz'`, so a customer paying €500 too much either creates a fake `differenz` (writing off real money) or cannot be recorded at all. ACC-07 debtor lists will be wrong.
- `buchungssatz` has no grouping key tying the rows of one economic event together. An invoice with two tax-rate groups produces three or more rows and nothing asserts they balance; the only balance check is at file level on `datev_export`. Add `buchung_id uuid NOT NULL` (a per-event group) and a deferred constraint trigger asserting `Σ soll = Σ haben` per `buchung_id`.
- `buchungssatz` has no `(mandant_id, buchungsdatum)` index. `ix_bs_export` is partial on `datev_export_id IS NULL AND festgeschrieben` and `ix_bs_konto` leads with `konto`, so the two required period scans — the Z3/GDPdU export for a fiscal year (ACC-09) and the year-end package (ACC-11) — have no supporting index and will seq-scan the largest table in the domain.
- `rechnung` has no frozen `bankkonto_id`, no `zahlungsbedingung_text`, and EN 16931 BG-16 payment means (BT-81 payment means type code, BT-84 payment account identifier) are entirely absent. XRechnung requires payment means; without them FIN-11 cannot produce a valid document.
- EN 16931 document-level allowances and charges (BG-20 / BG-21, BT-92 / BT-99) have no representation. `rechnung` has only line-level `rabatt_basispunkte`, so a negotiated global discount or a freight/Anfahrt surcharge must be smuggled in as a negative line, which then also has to carry a tax-rate group and a `handelsübliche Bezeichnung` under §14 Abs. 4 Nr. 5.
- The Kleinbetrag threshold is asserted in prose ("currently €250 gross, §33 UStDV") and evaluated "against the threshold then in force", but there is no versioned table storing it — unlike `basiszinssatz`, which does exactly this correctly for §288 BGB. `ist_kleinbetrag` therefore freezes a decision made against a constant compiled into code.
- `basiszinssatz` has no defined behaviour when no row covers the `mahndatum` (a new half-year rate not yet entered) and no watchdog for a missing rate, so `mahnung_position.zins_basispunkte` silently resolves against a stale half-year. The dunning service must refuse rather than fall back, and a watchdog belongs alongside the SPEC §14 list.
- LEG-09/DSGVO is unaddressed. The domain holds personal data (`camt_umsatz.gegenpartei_name/iban` of natural-person customers, `ausgabe.anstellung_id` reimbursements, extraction payloads, `beleg` scans) with no deletion path of any kind and `aufbewahrung_bis` computed but never acted upon. The GoBD-retention-versus-Art.-17-erasure tension resolves to restriction of processing (Art. 18) and anonymisation after the retention period — neither exists. Needs a `sperrung`/`einschraenkung` marker, an anonymisation job keyed on `aufbewahrung_bis`, and an Art. 15/20 export path.
- `mandant.ist_rechtstraeger boolean` is required from the Stammdaten domain (O-01) but nothing uses it. Nothing stops `operations` — which may be a department, not a GmbH — from owning a `nummernkreis` and issuing invoices. TEN-02 says only separate legal entities get an invoice circle. Add a trigger on `nummernkreis` and `rechnung` refusing a Mandant with `ist_rechtstraeger = false`.
- The GiST indexes `ix_fsb_inhaber_gueltig (mandant_id, lieferant_id, gueltigkeit)` and `ix_fsb_eigen_gueltig` place `uuid` columns in a GiST index, which requires the `btree_gist` extension. It is not listed anywhere; the migration fails without `CREATE EXTENSION btree_gist`.
- The `ausgabe` employee policy ("an employee sees their own reimbursements through a separate policy on `anstellung_id`") is asserted but never written, and no helper exists to resolve it — the RLS helper list defines `aktiver_mandant`, `gruppen_modus`, `sichtbare_mandanten`, `hat_recht` and `kunden_id` but no `app.anstellung_ids()`. `app.benutzer_id()` is likewise used inside `sichtbare_mandanten()` without being declared.
- The customer portal cannot show CRM-06 cross-area history: `app.kunden_id()` returns a single uuid and the customer policy is `AND mandant_id = app.aktiver_mandant()`, but `kunde` is tenant-scoped, so one real company is several `kunde` rows across Mandanten. A customer of both `reinigung` and `security` sees one entity's invoices at a time and can never see the group view of their own documents.
- Self-billing (Gutschrift under §14 Abs. 2 UStG, mandatory designation "Gutschrift" under §14 Abs. 4 Nr. 10) has no representation, although a Generalunternehmer settling a subcontractor by Gutschrift is standard practice in construction and directly affects the Bau entity. `rechnungsart` deliberately excludes it and `eingangsrechnung` has no flag marking that we are the Leistender on a document numbered by the customer.
- CAMT deduplication relies on `camt_import.datei_sha256` (byte-identical files only) and a nullable `camt_umsatz.bank_referenz`. Banks routinely redeliver overlapping or corrected statement files with different bytes; those import cleanly and create duplicate `camt_umsatz` rows, from which duplicate `zahlung` rows can be accepted. Needs a transaction-level dedup key such as `UNIQUE (bankkonto_id, buchungsdatum, betrag_cent, richtung, coalesce(bank_referenz, end_to_end_id, md5(verwendungszweck)))`.
- `erstellt_von uuid NOT NULL REFERENCES benutzer(id)` is imposed as a convention on every table, but `offener_posten` and `buchungssatz` rows are written by the finalisation function, `camt_import` by a cron job, `rechnung_hash` by the chain writer and extraction proposals by an agent. SEC-A9 requires the actor to be recordable as human / agent / system. Either make `erstellt_von` nullable with a mandatory `akteur_typ` enum plus `agent_aufgabe_id`, or seed system principals — but the current contract forces a fake human on every automated row.

## INVENTED RULES — must become TODO(client) (10)
- `rechnung.zahlungsziel_tage integer NOT NULL DEFAULT 14`. The TODO is present, but a NOT NULL DEFAULT is not a placeholder — it is the production value. It silently sets `faellig_am` on every invoice, which then drives the dunning run, the "overdue > 14 days" watchdog and §288 BGB interest. Make it nullable with no default, resolve it from `kunde.zahlungsziel_tage`, and have the pre-flight validator raise a Fehler when neither is set (the same `bestaetigt` gating pattern the draft applies elsewhere).
- `mahnung_position.verzugstage` is computed from `faellig_am`, i.e. Verzug is assumed to begin at Fälligkeit. §286 BGB requires a Mahnung, or §286 Abs. 3 (30 days after Fälligkeit *and* receipt of the invoice, and for consumers only if they were warned of that consequence). Charging interest from `faellig_am` over-claims, and the design cannot even represent Zugang. Needs `zugang_am` plus a per-Mandant `verzugsbeginn_regel` and `// TODO(client)`.
- `mahnung_position.zins_cent = rundeCent(offener_betrag × zins_bp / 10000 × verzugstage / 365)` picks act/365 as the day-count convention. That is a commercial/legal choice (act/act versus act/360 versus act/365, plus §187/188 BGB day counting and leap years) that the SPEC does not state and that changes the amount claimed. Mark the convention as `// TODO(client)` and store the applied convention on the row so the claim stays reproducible.
- §48 EStG withholding is applied whenever `bauabzugsteuer_pflichtig` and no certificate exists, with no Bagatellgrenze. Choosing "always withhold" is itself picking a legal rule, and it is the wrong one (§48 Abs. 2 EStG). See the corresponding blocking entry.
- `rechnung.leistung_bis` is designated "the **service date** for FIN-10 and §13b" without a TODO. For a service spanning a period that crosses a Freistellungsbescheinigung's expiry, this silently decides that the whole invoice is withheld (or not), which is a legal determination the SPEC does not make. Mark it `// TODO(client): which date governs §48b validity for period-spanning services — Leistungsende, Zahlungszeitpunkt, or a per-period split?`
- `eingangsrechnung` `CHECK (freigegeben_von <> erstellt_von)` hard-codes a four-eyes rule into the database. No SPEC or DECISIONS entry requires it. In a group whose back office may be two people, this can block approval of every supplier invoice with no override. Make it a configurable `mandant`-level policy with `// TODO(client): is four-eyes approval on incoming invoices required, and from what amount?`
- The ten-year retention is baked into a `GENERATED ALWAYS AS … STORED` column on `rechnung_snapshot`, `beleg`, `buchungssatz` and `datev_export`. The author lists confirming it as an open question, yet a generated column can only be changed by a migration that rewrites every archive table. It is also very likely wrong: the Viertes Bürokratieentlastungsgesetz shortened the retention for Buchungsbelege from ten to eight years (§147 Abs. 3 AO, §14b Abs. 1 UStG) with effect from 1 January 2025, while Bücher, Inventare and Jahresabschlüsse remain at ten. Store the period as a per-`beleg_typ` configuration row with `// TODO(client): confirm 8 vs 10 years per document class with the tax advisor` and compute `aufbewahrung_bis` from it in a trigger.
- `nummernkreis.zuruecksetzung nummernkreis_zuruecksetzung NOT NULL DEFAULT 'nie'`. The enum carries the correct TODO, but the DEFAULT makes 'nie' the operative numbering policy for every circle created before the client answers. Since `bestaetigt` already gates finalisation, drop the DEFAULT and make the column nullable until confirmed.
- `ausgabe.beleg_id` is required only "from status `freigegeben`", and `beleg_id` is nullable on `buchungssatz`. "Keine Buchung ohne Beleg" is a GoBD principle the draft asserts in prose for `eingangsrechnung` (`beleg_id NOT NULL`) but declines to enforce for expenses and bookings, without stating that as a decision. Either enforce it (`CHECK (NOT festgeschrieben OR beleg_id IS NOT NULL)`) or record the exception with a TODO.
- `mahnstufe.stufe CHECK (stufe BETWEEN 1 AND 9)` and `steuersatz_gruppe.satz_basispunkte CHECK (BETWEEN 0 AND 10000)` are arbitrary bounds presented as if derived. Harmless in practice, but the nine-level cap is a business rule with no source, and the domain's own convention is that unsourced business values carry a TODO.

## MINOR (21)
- `eingangsrechnung.eingang_am date NOT NULL DEFAULT current_date` — `current_date` resolves in the session time zone. With the connection on UTC (the normal Supabase default), an invoice registered at 00:30 Europe/Berlin in summer is stamped the previous day. Invariant 2 requires Europe/Berlin for display and for calendar-date derivation. Use `(now() AT TIME ZONE 'Europe/Berlin')::date` as the default here and anywhere else `current_date` appears.
- The `rechnungsausgardsbuch` view defines `luecke = nummer_laufend <> lag(nummer_laufend) OVER (…) + 1`. On the first row of every partition `lag()` is NULL, so `luecke` is NULL, not false — and the stated assertion "`luecke` must be false on every row, always" then fails or silently passes depending on how the nightly job tests it. Use `coalesce(nummer_laufend <> lag(nummer_laufend) OVER (…) + 1, nummer_laufend <> 1)`.
- §0.1 says "every table except the four global reference tables named in §1", but §1 is the enum section and names no tables, and only three non-tenant tables exist (`steuersatz_gruppe`, `basiszinssatz`, `abrechnungsart`). An implementer cannot tell which tables are exempt from `mandant_id`.
- §3 `rechnungsposition_quelle` says "three sibling partial uniques for `aufmass_id`, `auftrag_leistung_id`, `ausgabe_id`" and then, in the same sentence, excludes `auftrag_leistung_id`. Two, not three — and given the blocking finding on `aufmass_id`, one.
- `fin.rechnung_unveraenderlich()` fires only when `OLD.status = 'festgeschrieben'`. A `verworfen` draft header therefore stays fully mutable, although its positions are frozen by `fin.kind_unveraenderlich()`. A discarded draft with a reason is a GoBD record; freeze the header too (allowlist: nothing).
- Ordering hazard: `rechnung_steuer` carries `fin.kind_unveraenderlich()` (raises when the parent is not `entwurf`), but the finalisation pseudocode sets `status = 'festgeschrieben'` at step 6 before the snapshot at step 7. If `berechneSteuer()` is ever called as part of finalisation rather than during draft editing, the insert raises. State that `rechnung_steuer` and `rechnungsposition` are complete before step 1.
- The deferred `fin.rechnung_summen_stimmig()` re-sums `rechnungsposition` and `rechnung_steuer` but not `abschlagsrechnung_bezug`. Nothing ties `rechnung.abzug_brutto_cent` to `Σ (abzug_netto_cent + abzug_steuer_cent)`, so the deduction rows and the header total can disagree and `zahlbetrag_cent` is then wrong while every CHECK passes. Add the third sum to the deferred trigger.
- `rechnung.nummernkreis_id` is NOT NULL at draft creation, but the finalisation transaction selects the circle by `typ` and `periode = :jahr` (step 3), ignoring the column. A draft created 2026-12-30 and finalised 2027-01-02 under `zuruecksetzung='jaehrlich'` references one circle and consumes another. Either make the column nullable until finalisation or have step 3 lock `rechnung.nummernkreis_id` and validate its `periode`.
- `buchungstext` has a `CHECK (length(…) <= 60)` for the DATEV field limit, but `belegfeld1`/`belegfeld2` (36 and 12 characters in EXTF) and `kostenstelle`/`kostentraeger` have none. The truncation surfaces only when the tax advisor rejects the file.
- The STP template hard-codes `app.hat_recht('finanzen.lesen')`, while individual tables say "STP with right `buchhaltung.lesen`" / `buchhaltung.eingang.lesen` / `buchhaltung.export` / `buchhaltung.konfigurieren` / `finanzen.versenden`. It is not stated whether those replace or add to `finanzen.lesen`. As a contract for implementation PRs this must be explicit per table.
- `ux_er_dublette (mandant_id, lieferant_id, rechnungsnummer_lieferant)` has no partial predicate excluding `abgelehnt`. A supplier invoice rejected in error can never be re-captured, and a supplier who legitimately restarts numbering each year ("001") collides with themselves. Make it `WHERE status <> 'abgelehnt'`, add `rechnungsdatum`'s year, or demote it to a non-unique index plus a service-layer warning.
- `ux_beleg_hash (mandant_id, datei_sha256)` UNIQUE blocks filing the same PDF under two `beleg` rows — e.g. a collective supplier invoice that is the Beleg for two bookings, or a contract PDF that is also an invoice annex. A non-unique index plus a duplicate warning at upload preserves the detection without the dead end.
- `mahnung` has no `nummernkreis_id`, unlike `rechnung`, although `nummernkreis_typ` includes `mahnung` and `ux_mahnung_nummer` is `(mandant_id, nummer)`. The service cannot tell which circle/`periode` to lock. Add the composite FK for symmetry.
- `datev_konfiguration.wj_beginn date` stores a specific calendar date for a value that recurs annually. Use `wj_beginn_monat smallint CHECK (1..12)` plus `wj_beginn_tag smallint`, or the fiscal year would have to be edited every January — and the frozen copy on `datev_export` would then be meaningless.
- `konto_mapping` has separate `erloes_leistung` and `steuer_gruppe` rows, but the DATEV BU-Schlüssel depends on the account **and** the tax rate together. No precedence rule is stated for resolving "revenue account plus BU key for 19 % cleaning revenue", so two mapping rows can contradict each other silently.
- `mahn_folgeaktion` values `lieferstopp`, `inkasso` and `mahnbescheid` are stored on `mahnstufe` and applied without any per-action approval record of their own — only the letter itself is approved. Against a natural-person debtor an automatically triggered Inkasso handover has legal effect and touches DSGVO Art. 22 / LEG-12. Give the escalation its own `freigegeben_von`/`freigegeben_am`.
- `rechnung_versand.empfaenger text` is free text with no FK to `ansprechpartner`. The recorded recipient cannot be reconciled against CRM-08 `rechtsgrundlage` or against the customer's contact record, and a typo'd address is indistinguishable from a deliberate one in the audit trail.
- `quelle_typ` has no `leistungsnachweis` value. FIN-07 names four sources verbatim, so the draft is SPEC-faithful, but CLN-04 makes the customer-signed Leistungsnachweis (with its item snapshot) the cleaning trade's actual proof of performance, and it cannot be attached as the evidence behind a cleaning invoice line. Worth raising with the client rather than deciding silently.
- `rechnung` has no `objekt_id`. Cleaning and security invoice per building (OPS-01, OPS-02), and the customer portal, the Leistungsort on the document and per-object margin reporting (REP-05) all need it; only `auftrag_id`/`projekt_id` exist.
- `rechnungsposition` stores a live `steuersatz_gruppe_id` with no frozen `satz_basispunkte`/`kategorie` copy, unlike `rechnung_steuer` which freezes both. Reconstructing a per-line VAT figure for a Storno mirror or a customer query after a rate change reads the current rate. The snapshot covers the legal record; the operational query path does not.
- `basiszinssatz` and `steuersatz_gruppe` are described as populated "from migrations/seed" and "entered by an admin" with RLS granting no write policy at all. No path exists for an admin to enter the new half-year base rate, so §288 interest goes stale by design. Name the write path (a migration, or a policy scoped to `super_admin`).
