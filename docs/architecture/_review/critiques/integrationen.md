# Adversarial review — integrationen

## BLOCKING (14)

### B1. Invariant 3 is never actually applied to a single table this section introduces. `integration`, `integration_aufruf`, `datev_profil`, `konto_mapping`, `social_channel`, `mandant_mail_absender`, `agent_budget`, `kontoauszug`, `zahlungsvorschlag` and `vergabeplattform` are all specified without a word about RLS, and `mandant_id` is listed as the last column of `integration` with no nullability rule.

**Why it breaks:** `datev_profil` holds Beraternummer/Mandantennummer, `social_channel` holds decryptable OAuth tokens, `integration_aufruf` holds per-mandant AI spend and korrelation ids that link to Vorgänge. Without RLS these are readable by any authenticated user of any of the four entities — the exact cross-entity leak SEC-A3 calls the highest-priority test in the codebase. A nullable `mandant_id` for 'global' integrations (openai, dwd) makes it worse: in Postgres NULL != NULL, so a UNIQUE (mandant_id, integration_id) silently permits an unlimited number of duplicate global rows and no RLS predicate `mandant_id = current_mandant()` can ever match them, so the global row becomes invisible to every tenant.

**Required fix:** Enumerate per table: mandant_id NOT NULL + RLS ENABLE + policy for tenant tables (`integration_aufruf`, `datev_profil`, `konto_mapping`, `social_channel`, `mandant_mail_absender`, `agent_budget`, `kontoauszug`, `zahlungsvorschlag`, `vergabeplattform` — platform registration is per legal entity); split global integration state into a separate non-tenant table `integration_global` rather than a nullable column, or use `UNIQUE (integration_id) WHERE mandant_id IS NULL` plus `UNIQUE (mandant_id, integration_id)`. State explicitly which of these tables are system tables (`job_lauf`, `modell_register`, `feiertag`, `restore_protokoll`) and that they carry no tenant data.

### B2. The `Freigabe` token carries no `mandant_id`, and no `freigabe` table is ever defined even though `integration_aufruf.freigabe_id` is a foreign key to it and the runtime re-check reads 'the row'.

**Why it breaks:** Two failures. (a) Tenancy: a Freigabe minted while mandant `bau` is active satisfies the branded-type check for a send executed under mandant `security`; nothing in the type or the runtime re-check binds the approval to a tenant, so approval of a REALTIME offer can release an SSE Security email. That breaks invariants 3, 7 and 10 at once. (b) APR-07 requires an immutable snapshot of exactly what was approved plus approver and timestamp; a `snapshot_hash` alone proves a payload matches but does not preserve the payload, so a dispute about what a human released cannot be answered.

**Required fix:** Add `mandant_id` to the `Freigabe` interface and make the adapter assert it equals the session's active mandant. Define the table: `freigabe(id uuid pk, mandant_id not null, vorgang_typ, vorgang_id, snapshot jsonb not null, snapshot_hash not null, erteilt_von, erteilt_am timestamptz, gueltig_bis timestamptz, verbraucht_am timestamptz, verbraucht_durch, richtlinie_id)` — RLS on, no hard delete (invariant 8, it is an audit record), unique partial index on (vorgang_typ, vorgang_id) WHERE verbraucht_am IS NULL. Add it to SPEC §22's data model, which does not list it either.

### B3. The cross-entity ArbZG check required by TIM-14, LEG-03 and D-09 clauses 1 and 2 is impossible under the access rules this section lays down. The document states 'Service-role access is confined to `src/server/jobs/**`' and that everything else runs under the user's JWT so RLS applies — but conflict detection fires in a request path (a planner saving an `einsatz` in the Dienstplan), and it must read `einsatz`/`zeiteintrag` rows belonging to other mandanten to sum 6h cleaning + 5h security = 11h and to test the 11h rest period spanning two entities.

**Why it breaks:** Under RLS scoped to the active mandant, the cleaning planner's query returns only cleaning shifts. The ArbZG check therefore passes on an assignment that is an actual breach — a silent, expensive, late-discovered failure of exactly the kind the invariants exist to prevent, and the specific scenario ROADMAP Phase 5 names as an acceptance criterion.

**Required fix:** Specify a narrowly-scoped `SECURITY DEFINER` function, callable from a request under the caller's identity, e.g. `person_arbeitszeitfenster(person_id, von_utc, bis_utc)` returning only `{mandant_id, beginn_utc, ende_utc, art}` intervals — never `stundensatz_intern`, never `anstellung` rows, never object or customer data — so D-09 clause 6 ('a cleaning manager must not see security wage rates') holds while clause 1 and 2 are satisfiable. Every call audited with actor and person_id. This function is the single place the tenant boundary is crossed for reads and belongs in this section because it is what makes the boundary provable.

### B4. EMP-01 login and the EMP-14/EMP-15 cross-employment portal view have no defined access path. `mitarbeiter_zugang` hangs off `person_id` (correct per D-09), but the phone-number lookup at login happens before any session exists and therefore before any active mandant exists, and the portal must then read shifts and hours across employments in several mandanten from one login.

**Why it breaks:** The document forbids service-role access outside `src/server/jobs/**` and CLAUDE.md invariant 10 forbids any path executing without exactly one active mandant. As written there is no legal route for the login lookup or for the combined hours view, so either EMP-01/EMP-14 cannot be built or someone will reach for the service-role key in a route handler and silently defeat the tenant boundary for the highest-volume user population on the platform.

**Required fix:** Define a pre-authentication, tenant-free read context as named `SECURITY DEFINER` RPCs with their own rate limit, lockout and audit: `zugang_by_telefon(hash)` returning only `{person_id, gesperrt_bis}` (no name, no employments — no user enumeration, per AUT-07), and `person_einsaetze(person_id, von, bis)` returning mandant-labelled shift rows without any rate or customer commercial field (EMP-13). State that these are the only two functions permitted to cross the boundary in a request path and that both are covered by the SEC-A3 suite.

### B5. Inbound applications have no tenant. `MailboxPort.holeNeue({seit, max})` carries no mandant dimension, yet 'One message → one `bewerbung`' and `bewerbung` is a tenant-owned table under SPEC §22.

**Why it breaks:** Invariant 10: the ingest job would have to insert a tenant row without exactly one active mandant, and there is no stated rule for deriving it. A speculative application ('Ich suche Arbeit') references no `stelle`, so nothing in the message determines whether it belongs to CSE Dienstleistungen, SSE Security or REALTIME. Either the job guesses (an invented business rule) or the insert has no legal mandant_id.

**Required fix:** Either one monitored mailbox per entity (then `holeNeue({mandantId})` and the register lists four rows, four DPAs), or a non-tenant staging table `bewerbung_eingang(id, message_id unique, empfaenger_adresse, eingegangen_am timestamptz, roh_ref, zugeordnet_mandant_id null, zugeordnet_von, zugeordnet_am)` from which a human assigns the entity before a tenant `bewerbung` row is created. Add `// TODO(client)` under O-16: which address belongs to which Gesellschaft, and who triages an application addressed to none of them. The REC-07 purge job must cover the staging table too.

### B6. A full KoSIT run is made a hard precondition of invoice finalization ('Any failure blocks finalization', 'unavailable at runtime → finalization is blocked') while the same document establishes there is nowhere to run it: §9 states 'Vercel functions are Node, so there is no JVM'. The KoSIT validator is a Java tool, so the JVM problem applies to it identically. §9 also defers ZUGFeRD composition to 'a queued job', but no queue or worker substrate exists — the locked stack is Supabase cron + Edge Functions, and this section itself bans business logic from Edge Functions.

**Why it breaks:** As specified, the group cannot issue an invoice at all whenever an unspecified external process is unreachable, and the mitigation for the Vercel function limit ('a queued job') names infrastructure that does not exist in the stack. SPEC FIN-11 requires KoSIT validation *in CI*; elevating it to a runtime gate on FIN-02/FIN-03 invents an availability dependency for a legally required act and hands a third component the power to stop invoicing.

**Required fix:** Make the finalization gate the deterministic §14 UStG / EN 16931 field validator that is our own tested code (FIN-04, FIN-05, Leitweg-ID) plus XSD/Schematron validation available in Node; keep KoSIT as the CI gate SPEC actually demands and as an asynchronous post-finalization check whose failure raises an incident (the document already handles that case correctly via Storno). Separately, name the worker substrate for KoSIT/veraPDF/ZUGFeRD/backup dump/DATEV export as an explicit ADR (a container job runner outside Vercel) — or state that these run only in CI and in a scheduled job endpoint, and that no request path depends on them.

### B7. The `ausschreibung` idempotency design contradicts itself: 'Idempotency via `quell_id` unique per `quell_system`' and 'a changed payload creates a new version row rather than overwriting' cannot both be true of one table.

**Why it breaks:** With `UNIQUE (quell_system, quell_id)` the second version insert fails and the amended notice is lost — precisely the case the paragraph says must be visible, and an amended submission deadline is the single most expensive thing to miss in this domain (RAD-06, RAD-03).

**Required fix:** Head row `ausschreibung` with `UNIQUE (quell_system, quell_id)` holding the current normalised state, plus `ausschreibung_version(ausschreibung_id, quell_version, payload_roh, payload_hash, abgerufen_am timestamptz, normalisierung_fehlgeschlagen bool)` with `UNIQUE (ausschreibung_id, payload_hash)` so a re-fetch of an unchanged payload is a no-op and a changed payload is a new version. Index `(quell_system, abgerufen_am DESC)` for the ingest cursor and `(frist_datum)` for the RAD-06 countdown.

### B8. VIES is designed as the §13b UStG gate: 'whether a valid check is *required* before applying §13b is a business rule the client must state (O-26)', and register row 20 books the VIES check under FIN-09.

**Why it breaks:** Wrong legal instrument. FIN-09 is domestic construction-to-construction reverse charge under §13b Abs. 2 Nr. 4 in conjunction with Abs. 5 UStG; the evidence that the recipient is a Bauleistender is the customer's Freistellungsbescheinigung USt 1 TG, not a VIES confirmation of a USt-IdNr. VIES is relevant to intra-Community supplies, which is a different case entirely. Building the §13b decision on a VIES result means either applying reverse charge without the required evidence or blocking a correct §13b invoice because a German customer has no USt-IdNr. on file — a wrong-VAT invoice for three construction entities.

**Required fix:** Model `nachweis_bauleistender` (USt 1 TG) on the customer with `gueltig_von`/`gueltig_bis` as DATE, evaluated at the service date by a tested function — structurally identical to the §48b Freistellungsbescheinigung handling in §21 and correctly separate from it. Keep `VatIdPort`/VIES for intra-Community cases only and relabel register row 20. Restate O-26 as: does a §13b invoice require a USt 1 TG on file at the service date, and what happens when it expires mid-contract.

### B9. XRechnung has no delivery route. §8 builds and validates the XML and §15.2 is the only send path in the whole section — ordinary transactional email, itself blocked on O-15.

**Why it breaks:** The Leitweg-ID exists because German public buyers receive invoices through ZRE / OZG-RE / a Land portal or Peppol, not through an arbitrary sender's SMTP. SPEC says without XRechnung the group cannot invoice GIZ, DRV Bund and Berlin districts *at all* — producing a valid file with no route to the buyer leaves FIN-11 unmet while looking complete.

**Required fix:** Add an `EInvoiceDeliveryPort` (`sende({mandantId, rechnungId, leitweg_id, xml, freigabe})`, `status(vorgangId)`) with adapters for the buyer-specified route, status `nicht_verbunden`, plus a register row and a DPA row. New open question: through which channel does each public buyer receive its XRechnung — OZG-RE/ZRE upload, a Peppol Access Point, or the buyer's e-invoice mailbox — and who holds those accounts?

### B10. AI cost is stored as `kosten_mikro_eur (bigint)` and the budget cap is the environment variable `AI_BUDGET_MIKRO_EUR_MONAT`.

**Why it breaks:** Two problems. (a) Invariant 1 says money is integer cents; micro-EUR is a silent deviation of a locked invariant, recorded only in the author's assumption list, with no named conversion function, no stated rounding direction and no DECISIONS.md entry — so the budget report and the DATEV-side cost figure will disagree by rounding and nobody will know which is right. (b) A global env var contradicts AGT-05 (per-mandant budget), contradicts this section's own §23 rule that per-mandant business configuration lives in DB rows, and contradicts TEN-08 — a fifth business area would need a deployment change to get a budget.

**Required fix:** Keep micro-EUR only as an explicitly non-money consumption unit (`verbrauch_mikro_eur`), add `mikroEuroZuCent(n: bigint): bigint` as a tested pure function with the rounding direction stated (round *up* when comparing against a cap so the cap can never be exceeded, round half-up at reporting), record the deviation in DECISIONS.md under D-08, and move the cap into `agent_budget(mandant_id, jahr, monat, budget_cent bigint, verbraucht_mikro_eur bigint)` with RLS — which is where the FOR UPDATE lock already lives.

### B11. Invariant 7 has holes in two port signatures: `AlertPort.alarmiere({ schluessel, schwere, text, freigabe? })` makes the approval token optional, and `JobBoardPort` lists `aktualisiere` and `zurueckziehen` with no `Freigabe` at all (unlike `SocialChannelPort.zurueckziehen`, which correctly requires one).

**Why it breaks:** The document's own guarantee is 'a send adapter that does not receive a `Freigabe` does not compile'. An optional field compiles without it, so the prose rule 'email only through the gate' is enforced by convention, not by the type — the failure mode the branded token was introduced to eliminate. Updating a live job advert is an externally visible publication under a company brand and is unapproved as written.

**Required fix:** Split alerting into `alarmiereIntern({schluessel, schwere, text})` (in-app, no gate) and `alarmiereExtern({..., freigabe: Freigabe})`; make `freigabe` required on `JobBoardPort.aktualisiere` and `zurueckziehen`. Add a CI gate asserting that no exported adapter method whose name is in the send set has an optional `freigabe`.

### B12. A scheduled job that never starts is undetectable. `pg_cron` → `pg_net` is asynchronous fire-and-forget, `job_lauf` is written by the receiving endpoint, and §19 then derives failed-job alerting from `job_lauf`.

**Why it breaks:** If the POST never lands (bad JOB_TOKEN after a rotation, cold-start timeout, a deploy that removed the route), no `job_lauf` row is written, so there is no failed run to alert on and the absence is silent. That silently disables `hashkette_pruefen` — the nightly invoice hash-chain verification which is the strongest single GoBD/LEG-01 control and an explicit SPEC §14 watchdog — as well as `bewerbungen_purge` (REC-07/LEG-11, a DSGVO deletion duty).

**Required fix:** Add `job_plan(job, cron, erwartet_alle_min, aktiv)` and a heartbeat watchdog comparing `now()` against `max(job_lauf.beendet_am WHERE ergebnis='erfolg')` per job, alerting on overdue; surface a `jobs_ueberfaellig` count on `/api/health` so the external uptime probe catches it even when the platform's own alerting is the thing that broke. Reject a job POST whose token fails a constant-time comparison and record the rejection.

### B13. `IntegrationError.meldung_de` is a pre-rendered German string explicitly described as 'rendered in the UI'.

**Why it breaks:** EMP-12 and SPEC §10 require worker-facing screens in de/en/ar/tr, and the errors that reach workers are exactly these: SMS login not connected (EMP-01), check-in link failure (TIM-07), upload rejected (DOC-06). A German-only error on the one screen designed to be used one-handed with gloves on by a workforce the spec explicitly says may not read German is an accessibility and comprehension failure, and it is baked into the kernel type where every adapter will copy it.

**Required fix:** Replace with `meldung_schluessel: string` plus `parameter?: Record<string, string|number>`, resolved against the de/en/ar/tr catalogues in the UI layer. Keep a German fallback for admin-only surfaces if desired, but never as the only representation.

### B14. The backup design is internally impossible: artifacts are 'encrypted with a public key the platform can write with but not read back; the private key is escrowed offline with the client, never in an environment variable' — and a monthly restore into a scratch project is required (SEC-A10) with five acceptance checks including end-to-end hash-chain verification.

**Why it breaks:** The drill cannot decrypt without the private key. Either the key is genuinely offline and the monthly restore never runs (an untested backup, which the document itself calls not a backup), or the key is available to the drill and the 'never readable' property is false. SEC-A10 is a SPEC requirement and Phase 10 acceptance.

**Required fix:** State the actual custody model: the drill is a human-attended procedure in which the key custodian supplies the key into an ephemeral scratch environment and signs off in `restore_protokoll`, or a second escrowed key pair exists whose private half is held by a named operator for drills only. Record who holds which half and add `schluessel_verwendet_von` to `restore_protokoll`. This belongs in O-18.

## INVENTED RULES — must become TODO(client) (6)
- Backup retention '30 daily · 12 monthly · 7 yearly' is stated as fact. Retention of financial and employment data is a legal decision (GoBD 10 years for the archive, §17 MiLoG two years for hour records, DSGVO minimisation for applicant data), and the section's own claim that the REC-07 purge is 'satisfied in backups by rotation' depends entirely on this invented number. No DPA required' — the conclusion (no DPA) is right but the stated reason is a legal claim that is wrong: professional contact data is personal data under Art. 4(1) DSGVO. - §7 of the body calls the EXTF conventions 'Fixed format rules' while the author's own assumption list says they must be confirmed against the client's real sample. Keep one wording — the assumption list is the honest one — so nobody implements the header as settled.

- `/api/health` is described as returning the status of every integration with no stated authentication. An unauthenticated endpoint enumerating providers, last error codes and migration version is free reconnaissance. Split it: unauthenticated liveness (build id, region, db reachable, jobs overdue count) and authenticated detail for the admin status page.
- §4 allows a browser-side Supabase client 'only if needed' while §4 also rejects Realtime because it 'would push tenant rows to the browser with RLS as the only boundary'. The same objection applies to any browser-side client read. State that the anon key is used for auth flows only and that no tenant table is read from the browser.
- `restore_protokoll.dauer_min` is a derived value stored beside `gestartet_am`/`beendet_am`; per invariant 2 a duration is the difference of two UTC instants. Drop the column or make it explicitly a cached report field.
- The Freigabe `snapshot_hash` is defined as covering 'text, media ids and target channels' for a social post. For `MailerPort.sende` it must also cover the recipient list and the sha256 of every attachment — an approval that does not bind the recipients permits an approved invoice PDF to be released to a different address.
- §23 asserts 'each secret has a documented owner and rotation interval' but no owner or interval is given for any of the ~40 variables. Either add the two columns to the table or drop the claim.
- The `systemnachricht` pre-approval carve-out (O-28) is correctly flagged, but the fail-closed default is not stated. Until O-28 is answered the shipped default must be `freigabe_erforderlich` for every category, with the pre-approved `agent_richtlinie` shipped disabled — otherwise an unanswered question ships as a live exception to invariant 7.
- `HolidayPort` is marked `Verbindbar` while no upstream is named ('a maintained public dataset or an actively maintained offline library'). A status of connectable is a claim about a specific source; name the candidate and its licence in the ADR, since CLN-03 correctness for a whole scheduling year depends on it.
- No accessibility gate appears in the CI list although BFSG/WCAG 2.1 AA (PUB-09, LEG-07) is a legal requirement and Phase 2 acceptance demands an audit. If a11y gating is owned by another section, say so explicitly so it is not lost between sections.
- The DSGVO-erasure vs GoBD-retention conflict is not addressed: `archiv_gobd.loesche` returns POLICY_BLOCKED, which is correct, but a data-subject erasure request touching archived invoice data must be answered with a stated legal basis (Art. 17(3)(b) DSGVO in conjunction with §147 AO). That belongs in the LEG-09 deletion concept this section feeds.
