# Adversarial review — radar-ki-inhalt

## BLOCKING (30)

### B1. Seven composite foreign keys reference a parent that never declares the matching UNIQUE (mandant_id, id). The draft declares `UNIQUE (mandant_id, id)` only on radar_profil, ausschreibung_vorgang, seite, stelle and kandidat — but writes composite FKs against vergabemappe (from vergabemappe_position), freigabe_anfrage (from freigabe_feld AND freigabe_entscheidung), agent_aufgabe (from agent_schritt), social_post (from social_post_ziel), kalender_eintrag (from kalender_teilnehmer), bewerbung (from kandidat_bewertung) and nachricht (from nachricht_empfaenger).

**Why it breaks:** Postgres requires the referenced column list of a FK to be covered by a unique or primary key constraint. `ALTER TABLE agent_schritt ADD FOREIGN KEY (mandant_id, agent_aufgabe_id) REFERENCES agent_aufgabe(mandant_id, id)` fails with 'there is no unique constraint matching given keys for referenced table'. The very first Drizzle migration of this domain does not apply. And because the composite FK is the draft's stated mechanism for tenant consistency ("das ist der stärkere Weg"), falling back to a single-column FK silently removes the mandant guarantee on seven parent/child pairs.

**Required fix:** Add `UNIQUE (mandant_id, id)` to vergabemappe, freigabe_anfrage, agent_aufgabe, social_post, kalender_eintrag, bewerbung and nachricht, exactly as already done for radar_profil. State it as a standard bundle (call it S6) so no future child table repeats the omission.

### B2. `freigabe_feld.wissens_chunk_id uuid` is declared as a reference to wissens_chunk, whose primary key is deliberately `(mandant_id, id)` because the table is LIST-partitioned. There is no unique constraint on `id` alone.

**Why it breaks:** A single-column FK to wissens_chunk cannot be created — same 'no unique constraint matching given keys' error. Silently dropping the FK loses the APR-03 evidence link between an extracted field and the RAG chunk it came from, which is the one thing that makes 'jedes Feld nennt seine Quelle' verifiable rather than aspirational.

**Required fix:** Make it a composite reference: `(mandant_id, wissens_chunk_id) REFERENCES wissens_chunk(mandant_id, id)`. That is also correct on the merits — an approval field must never cite a chunk from another mandant.

### B3. `ausschreibung` carries `INDEX (frist_angebot) WHERE frist_angebot > now()`.

**Why it breaks:** Index predicates must be IMMUTABLE. `now()` is STABLE, so CREATE INDEX fails with 'functions in index predicate must be marked IMMUTABLE'. The migration aborts, and the index that RAD-06 (deadline countdown, red under five days) and the `ausschreibung_frist` watchdog depend on does not exist. Even conceptually the predicate is wrong: a partial index whose predicate depends on the current time would need rebuilding continuously.

**Required fix:** Use an unconditional `INDEX (frist_angebot)` (or `INDEX (frist_angebot) WHERE frist_angebot IS NOT NULL`) and put the `> now()` filter in the query. Apply the same rule to every future partial index.

### B4. `app.agent_budget_reservieren` sets `status='gestoppt', gestoppt_am=now()` and then immediately calls `raise exception 'AGENT_BUDGET_ERSCHOEPFT'` in the same transaction.

**Why it breaks:** RAISE EXCEPTION aborts the transaction and rolls the UPDATE back. The budget row never reaches `gestoppt`, `gestoppt_am` stays NULL, and the trigger the draft relies on to emit the stop notification never fires (its write is rolled back too). AGT-05 demands 'hard stop with notification, never silent degradation' — this produces a hard stop with *no* record and *no* notification, and the next call re-runs the identical check and raises again, forever, with nothing visible in the UI.

**Required fix:** Split the two effects: the reservation function returns a status value (e.g. `('ok'|'gestoppt')`) instead of raising, and the caller in `src/server/services/` performs the state write plus the notification in a committed transaction before refusing the run. If an exception is preferred at the boundary, write the stop state via a separate connection/`dblink`-style autonomous step, or have the watchdog job `agent_budget_pruefung` reconcile it. Add a test: exhaust a budget, then assert `status='gestoppt'` and a `benachrichtigung` row both exist after the failed call.

### B5. The same function resolves the budget with `where mandant_id = p_mandant and (agent_id = p_agent or geltungsbereich='mandant') ... order by geltungsbereich desc for update`, then uses `select ... into b`, which keeps only the first row.

**Why it breaks:** Two defects at once. (a) Enum ordering follows declaration order, so `budget_geltungsbereich` = ('mandant','agent') sorted DESC puts 'agent' first: whenever a per-agent budget row exists, the mandant-wide cap is fetched but never evaluated. A mandant cap of 200 € with four agent caps of 500 € each permits 2.000 € of spend. (b) Because the mandant row is never the row that is checked and updated, two agents running concurrently each lock only their own row — the shared cap is never serialised, so even if (a) were fixed the check would race. AGT-05's cap becomes advisory.

**Required fix:** Lock and evaluate both rows in a deterministic order (mandant row first, then agent row) with explicit `FOR UPDATE` on each, and refuse if *either* would be exceeded. The lock order must be fixed (mandant before agent) to avoid deadlocks between concurrent agents in the same tenant.

### B6. `agent_budget.reserviert_mikrocent` is a bare counter with no per-reservation ledger and no release path. The only decrement is in `trg_budget_fortschreiben`, which fires when an `agent_kosten` booking is written.

**Why it breaks:** Every agent run that crashes, times out, is killed by `max_schritte`, or is aborted by the policy gate after reserving leaves its reservation on the counter permanently. There is no reservation id, no expiry, no way to identify which reservations are stale. Within weeks `reserviert_mikrocent` grows until the hard stop fires on phantom spend — AGT-05 stops the agents on money that was never spent, and no query can distinguish real from leaked reservations.

**Required fix:** Introduce `agent_reservierung (id, mandant_id, agent_budget_id, agent_aufgabe_id, betrag_mikrocent, angelegt_am, freigegeben_am, verfallen_am)`; the counter becomes a derived sum or is adjusted only against a named reservation row. Add a sweeper (extend `watchdog_job` with `agent_reservierung_verfall`) that releases reservations older than the task timeout.

### B7. `bewertung` is P-ANHANG (no UPDATE, no DELETE) and carries `UNIQUE (ausschreibung_id, radar_profil_id, regel_version)`, while `regel_version` versions the *code* rule set, not the profile.

**Why it breaks:** RAD-04 makes `radar_profil` user-editable (keywords, NUTS prefixes, value bounds, CPV rows). A user edits a profile; the nightly scoring run recomputes the same notice against the same profile and the same code version and tries to insert. The unique index rejects it, `ON CONFLICT DO UPDATE` is forbidden by the append-only trigger, and the job dies on the first previously-scored notice — i.e. the moment anyone tunes a profile, the radar stops scoring. The table even carries `eingaben_hash` precisely to distinguish these cases, but it is not in the key.

**Required fix:** Key on the inputs, not on the code version: `UNIQUE (ausschreibung_id, radar_profil_id, regel_version, eingaben_hash)`, and treat a duplicate insert as an idempotent no-op (`ON CONFLICT DO NOTHING`). Alternatively add a monotonically incremented `radar_profil.version` bumped by a trigger on every profile or profile-CPV change and include it in the key. Either way add the regression test: edit a profile, re-run scoring, assert a new row and no error.

### B8. `radar_ingest_lauf.status watchdog_status NOT NULL DEFAULT 'erfolg'` and `watchdog_lauf.status watchdog_status NOT NULL DEFAULT 'erfolg'`. The row is inserted at start and updated once at the end.

**Why it breaks:** A run that is killed, OOMs, times out, or loses its container never performs the closing UPDATE — and leaves behind a row that says the run **succeeded**. Both tables exist for exactly one purpose: the draft's own words, "ohne Laufprotokoll ist eine still gescheiterte Quelle nicht von 'heute keine Ausschreibungen' zu unterscheiden". The default inverts that: a crashed source is indistinguishable from a good one, the `INDEX (job, gestartet_am DESC)` 'when did it last succeed' query answers 'just now', and the meta-job that checks watchdog cadence stays quiet. This silently disables RAD-01/RAD-02 monitoring and the whole SPEC §14 watchdog-of-watchdogs.

**Required fix:** Default to `'laeuft'` (add the value to `watchdog_status`) or to `'fehler'`; only the closing UPDATE may set `'erfolg'`. Add a CHECK that `status='erfolg'` requires `beendet_am IS NOT NULL`, and have the meta-job treat rows with `beendet_am IS NULL` older than the expected duration as failures.

### B9. P-MANDANT has no role dimension at all. Every table in the domain grants SELECT to any authenticated user who has *any* row in `benutzer_mandant` for that tenant.

**Why it breaks:** AUT-01 defines five roles and AUT-05 requires 'RLS policies mirror application authorization'; EMP-13 states employees never see other employees' data or customer commercials; the `kunde` role is scoped to its own records. Under the draft's policy a `kunde` login attached to the reinigung mandant can SELECT the full `kandidat` and `bewerbung` tables (names, e-mail, telephone, parsed CVs), every `freigabe_anfrage.vorschau_payload` (offer prices, monthly invoice drafts), every `agent_schritt.eingabe/ausgabe` (contract text passed to the model), every `nachricht` and the entire `ausschreibung`/`vergabeplattform` reference set via P-KATALOG. A `mitarbeiter` gets the same. This is a DSGVO breach on applicant data and a direct AUT-05/EMP-13 violation, and SEC-A3's isolation suite will not catch it because it only tests cross-tenant access.

**Required fix:** Define `app.hat_recht(modul text, aktion text) returns boolean` (SECURITY DEFINER, pinned search_path) over the `rolle`/`berechtigung` tables from Domäne 1, and add it as an AS RESTRICTIVE policy to every table here. At minimum: kandidat/bewerbung/kandidat_bewertung restricted to recruiting rights; freigabe_* and agent_* to `leitung` upwards; nachricht/nachricht_empfaenger to participants; wissens_chunk role-gated (see the vertraulichkeit finding). Extend the SEC-A3 suite with a role matrix, not only a tenant matrix.

### B10. Four tables are specified as "P-MANDANT **und** <extra predicate>" — benachrichtigung (`empfaenger_benutzer_id = auth.uid()`), benachrichtigung_praeferenz (`benutzer_id = auth.uid()`), nachricht_empfaenger (`empfaenger_id = auth.uid()` for mitarbeiter), kalender_eintrag (the `sichtbarkeit <> 'privat' or besitzer = auth.uid()` clause).

**Why it breaks:** Multiple PERMISSIVE policies on the same command are combined with OR, not AND. Implemented literally — P-MANDANT's `<t>_sel` plus a second policy carrying the extra predicate — the extra predicate *widens* access instead of restricting it: every user in the tenant reads everyone's notifications, everyone's preferences, everyone's private calendar entries and everyone's message read-status. This is the single most common RLS mistake in Postgres and the draft repeats it four times while presenting it as a tightening.

**Required fix:** Express every narrowing predicate as `CREATE POLICY ... AS RESTRICTIVE`, or fold it into the single `<t>_sel` policy's USING clause. Make it explicit in §0.2 that P-MANDANT is the only permissive policy and all additions are restrictive, then test it: a second user in the same mandant must get zero rows from another user's notifications.

### B11. `nachricht_empfaenger` policy compares `empfaenger_id = auth.uid()` while `empfaenger_typ` may be `person`, `kandidat` or `ansprechpartner`. There is no function mapping the authenticated principal to a `person` row anywhere in §0.2.

**Why it breaks:** `auth.uid()` is a Supabase auth user id; `person.id` is not. Per D-09 and EMP-01/EMP-14 the human logs in once via `mitarbeiter_zugang`, which hangs off `person_id`. So a message addressed to `empfaenger_typ='person'` is invisible to the person it was sent to — EMP-11 ('Messages and documents relevant to them') simply does not work — while the intended narrowing does nothing for the other types. The same missing mapping affects any future 'my shifts / my certificates' query, which is the whole employee portal.

**Required fix:** Define `app.aktuelle_person() returns uuid` (SECURITY DEFINER, pinned search_path) resolving auth.uid() → benutzer → person (or mitarbeiter_zugang → person), and write the policy per type: `(empfaenger_typ='benutzer' and empfaenger_id = auth.uid()) or (empfaenger_typ='person' and empfaenger_id = app.aktuelle_person())`. Declare the function as a dependency of this domain on Domäne 1 so it is not forgotten.

### B12. APR-05 delayed release is modelled as `freigabe_anfrage.verzoegerte_freigabe_bis` plus a job, with `freigabe_entscheidung_art='automatisch_nach_frist'` and the CHECK `art='automatisch_nach_frist' OR entschieden_von IS NOT NULL`. Nothing restricts which `vorgang_typ` or which `risiko` may carry a delayed-release deadline.

**Why it breaks:** SPEC APR-05 says delayed release is for **low-risk actions**; the autonomy matrix says 'Any external send: approval required', 'Booking to accounting: approval required', 'Publishing a post: approval required', 'Any offer, at any value: proposal — never automatic'. As designed, a request with `vorgang_typ='externer_versand'` or `'angebot_erstellen'` and a `verzoegerte_freigabe_bis` set (by an editable `agent_richtlinie` row) is auto-approved by the `freigabe_frist` job with no human in the loop, and the CHECK explicitly blesses the resulting `entschieden_von IS NULL` row. That is a direct breach of Invariant 7 and of the ROADMAP Phase 8 acceptance criterion.

**Required fix:** Add `CHECK (verzoegerte_freigabe_bis IS NULL OR (risiko = 'niedrig' AND vorgang_typ NOT IN ('externer_versand','angebot_erstellen','nachlass_gewaehren','buchung_uebernehmen','beitrag_veroeffentlichen','mahnung_vorschlagen')))`, mirror the same exclusion list as a hard constant in `src/server/agent/policy.ts`, and forbid the `freigabe_frist` job from acting on any request failing it.

### B13. P-OEFFENTLICH grants `anon` SELECT on the base tables `stelle`, `referenz`, `social_post` and `seite`, not on a public projection.

**Why it breaks:** Row-level policies do not filter columns. Anonymous internet visitors therefore read `stelle.bedarf_quelle` — the draft defines it as 'aus welchen unbesetzten Schichten/Pipeline der Bedarf abgeleitet wurde', i.e. a machine-readable list of which objects are currently understaffed, published for a *security services* company; plus `verantwortlich_benutzer_id`, `ki_entwurf`, `freigabe_anfrage_id`, `objekt_id`. From `referenz` they read `auftrag_id`, `objekt_id`, `kundenname_anzeige` and `kunde_anonymisiert`; from `social_post` they read `freigegeben_von` (a named approver's uuid) and `auftrag_id`; from `seite` they read `freigabe_anfrage_id` and `erstellt_von`. This is an operational-security failure for SEC-01 objects and a DSGVO data-minimisation failure, and it contradicts SEC-A5's spirit.

**Required fix:** Never expose a base table to `anon`. Create SECURITY INVOKER views (`v_oeffentlich_stelle`, `v_oeffentlich_referenz`, `v_oeffentlich_post`, `v_oeffentlich_seite`) selecting only the columns the public site renders, grant SELECT on the views to `anon` and nothing on the base tables, and keep the `status='veroeffentlicht' AND geloescht_am IS NULL` predicate inside the view. `bedarf_quelle` must never leave the portal.

### B14. The REC-07/LEG-11 purge is specified only for columns of `kandidat`. Personal data of the same applicant survives in at least five other places: `bewerbung.anschreiben` (the full cover letter), `bewerbung.absage_grund`, `bewerbung.utm`, `kandidat_bewertung.kriterien`/`begruendung`/`merkmale_quelle` (which quote CV content and are declared **P-ANHANG, append-only**), `kalender_eintrag.titel`/`beschreibung` and `kalender_teilnehmer` rows for the interview, `nachricht`/`nachricht_empfaenger` for the invitation and rejection mails, and `agent_schritt.eingabe/ausgabe` from the CV-parsing run. The completeness CHECK on `kandidat` also omits `lebenslauf_dokument_id`.

**Why it breaks:** REC-07 and LEG-11 require applicant data to be purged; DSGVO Art. 17 erasure is not satisfied by clearing one table. `kandidat_bewertung` is worse than incomplete — it is declared append-only with no UPDATE and no DELETE, so its copy of the applicant's CV-derived features is structurally *unpurgeable*, and the draft's own AGG argument (§22 AGG, Beweislastumkehr) makes retaining it the exact liability it was trying to avoid. Meanwhile the `anonymisiert_am` CHECK certifies completeness that has not occurred.

**Required fix:** Define the purge as a set of writes across kandidat, bewerbung, kandidat_bewertung, kalender_eintrag/kalender_teilnehmer, nachricht/nachricht_empfaenger and agent_schritt, driven by one `loeschfrist_am` and one job. Give kandidat_bewertung the same named exception agent_schritt already has (a `nutzlast_geloescht_am` column, with the redaction UPDATE whitelisted in the append-only trigger) instead of pure append-only. Extend the completeness CHECK to `lebenslauf_dokument_id IS NULL` and add a test that asserts zero personal data remains in every one of those tables after the job runs. Reconcile the storage deletion with DOC-07's no-delete rule by giving `dokument.kategorie='bewerbung'` an explicit retention exemption.

### B15. `wissens_chunk.vertraulichkeit vertraulichkeit NOT NULL DEFAULT 'normal'` is the only protection against personnel files, wage rates and CVs entering the RAG index — and nothing reads it. No policy, no index predicate, no constraint on `suche_bestand` references it. The HNSW index is `WHERE ist_aktiv` only.

**Why it breaks:** The default is fail-open: every chunk written by an indexer that forgets to classify is searchable. The draft's own open question proposes that everything personal be `vertraulich`, but the schema makes 'normal' the outcome of doing nothing. Combined with the missing role dimension in RLS, a `mitarbeiter` or `kunde` in reinigung can retrieve verbatim contract text with customer pricing, and `anstellung.stundensatz_intern` if it was ever indexed — the exact outcome D-09 clause 6 and EMP-13 forbid. It also reopens the AGG exposure the draft closed elsewhere: `kandidat.parsed` refuses AGG features, but the raw CV PDF behind `lebenslauf_dokument_id` can be chunked and indexed under the default.

**Required fix:** Default to `'vertraulich'`; make `'normal'` an explicit classification decision. Build the HNSW index `WHERE ist_aktiv AND vertraulichkeit = 'normal'`, add a RESTRICTIVE policy gating `vertraulich` chunks behind an explicit right, and add a hard exclusion list of source categories (Personalakte, Lohn, Krankmeldung, Bewerbung) enforced at insert. Keep the SEC-A3-style test the draft proposes and add a second one: a reinigung `mitarbeiter` asking for wage rates gets nothing.

### B16. `wissens_chunk` is `PARTITION BY LIST (mandant_id)` with one partition and one HNSW index per mandant, and no automatic partition creation or DEFAULT partition is specified.

**Why it breaks:** TEN-08 is explicit: 'A fifth area requires a DB row, no code change', and the ROADMAP Phase 1 acceptance repeats it. With LIST partitioning, inserting a new `mandant` row and then writing a chunk raises 'no partition of relation "wissens_chunk" found for row'. Adding a mandant now requires DDL plus an index build — a code change. If a DEFAULT partition is added instead, chunks for the new tenant land in a shared partition with a shared index, which quietly reintroduces exactly the global-index leak the partitioning existed to prevent.

**Required fix:** Attach an AFTER INSERT trigger on `mandant` calling a SECURITY DEFINER function `app.mandant_partition_anlegen(mandant_id)` that creates the partition and its HNSW index, so the promise 'a DB row is enough' still holds. Do not add a DEFAULT partition; if one is added for safety, alert on any row landing in it. Cover it with the TEN-08 test: insert a fifth mandant, index a document, search it, and assert isolation.

### B17. `aufgabe` deduplicates watchdog-created tasks with `UNIQUE (watchdog_lauf_id, bezug_typ, bezug_id) WHERE watchdog_lauf_id IS NOT NULL`.

**Why it breaks:** `watchdog_lauf_id` is new on every run. The stated intent — 'ein Watchdog erzeugt zu demselben Sachverhalt nicht zweimal dieselbe Aufgabe' — is not achieved by a key that changes daily. The SPEC §14 jobs are recurring by definition: 'Nachtrag announced, not submitted after 14 days — daily', 'Invoice overdue > 14 days — daily', 'Tender deadline < 5 days — daily'. Each produces a fresh duplicate task every night until the underlying condition clears. Thirty duplicate tasks per finding is precisely the 'forty approval requests a day and the human stops reading' failure SPEC §17 warns about, transplanted into the task list.

**Required fix:** Key on the *job* and the subject, restricted to still-open tasks: `UNIQUE (mandant_id, quelle_job, bezug_typ, bezug_id) WHERE status IN ('offen','in_arbeit')` — which requires adding a `quelle_job watchdog_job` column alongside `watchdog_lauf_id` (the run stays as provenance). Have the job insert with `ON CONFLICT DO NOTHING` so a repeat run touches nothing rather than erroring. The same reasoning applies to the `benachrichtigung` debounce index.

### B18. `ausschreibung_dokument` is shared reference data (P-REFERENZ, readable by every authenticated user of any mandant) but carries `dokument_id` into the tenant-scoped `dokument` table, `agent_aufgabe_id` into a tenant-scoped agent run, and `extraktion_ergebnis jsonb`, all under `CHECK (abruf_status='abgerufen' ⇒ dokument_id IS NOT NULL)`.

**Why it breaks:** The first mandant to fetch a Vergabeunterlage writes a `dokument` row owned by *its* mandant. A second mandant reading the same shared notice sees `abruf_status='abgerufen'` and a `dokument_id` it cannot resolve under RLS — the UI promises a document that 404s. The obvious 'fix' a developer reaches for is signing the URL with `service_role`, which is a cross-tenant document leak and a SEC-A5 violation. Independently, `extraktion_ergebnis` and `agent_aufgabe_id` publish one tenant's paid agent output, and the fact that it processed this notice, to its three sister companies — the group's own competitive-separation model between separate legal entities.

**Required fix:** Split the row: keep the public facts (bezeichnung, quell_url, mime_typ, groesse_bytes, datei_hash, seiten_anzahl) on the shared `ausschreibung_dokument`, and move `dokument_id`, `abruf_status`, `agent_aufgabe_id`, `extraktion_status` and `extraktion_ergebnis` to a new tenant table `ausschreibung_dokument_abruf (mandant_id, ausschreibung_dokument_id, ...)` under P-MANDANT with `UNIQUE (mandant_id, ausschreibung_dokument_id)`. Alternatively store the fetched file in a group-level reference bucket with its own access rules — but not in the tenant `dokument` table.

### B19. `agent_richtlinie` resolves conflicting rules by `prioritaet` ('kleinere Zahl gewinnt'), with `prioritaet` part of the unique key so several rules may coexist for one (mandant, agent, vorgang_typ). `trg_richtlinie_nicht_abschwaechen` only prevents *editing* a system rule.

**Why it breaks:** Nothing stops a UI user from INSERTing a **new** non-system rule with `prioritaet = 1`, `vorgang_typ='angebot_erstellen'`, `autonomie='automatisch'`, `betrag_grenze_cent = NULL`. It outranks the seeded system rule at prioritaet 100 without ever touching it, and the DB-side guard the draft advertises as its 'zweite Verteidigungslinie' evaporates. ROADMAP Phase 8 acceptance is 'A €25,000 offer cannot be sent automatically **under any configuration**' — this configuration is reachable through the AGT-03 UI, which SPEC requires to be editable without code.

**Required fix:** Resolution must be 'strictest wins', not 'lowest number wins': evaluate all matching rules and take the minimum autonomy on the ordering `nie < freigabe_erforderlich < vorschlag < automatisch_mit_hinweis < automatisch` and the minimum `betrag_grenze_cent`. Enforce it in a single SQL function used by both the policy gate and the UI preview, and add a trigger rejecting any INSERT/UPDATE whose effective autonomy for a `vorgang_typ` would exceed the system rule's. Keep the code-level floor in policy.ts as designed, and test it by attempting the priority-1 insert.

### B20. `app.gruppenansicht()` is `select coalesce(current_setting('app.gruppenansicht', true), 'false')::boolean`.

**Why it breaks:** `current_setting(name, true)` returns NULL only when the GUC was never set in the session. `withTenant()` resetting it — the normal way to clear a transaction-local setting is `set_config('app.gruppenansicht', '', true)` — leaves an empty string, which `coalesce` passes through untouched and `''::boolean` rejects with 'invalid input syntax for type boolean: ""'. Because the function sits in the SELECT policy of every mandant table, one stray reset makes every query in the platform fail, not just the group view. The draft already applies `nullif` correctly in `app.aktiver_mandant()` and simply forgot it here.

**Required fix:** `select coalesce(nullif(current_setting('app.gruppenansicht', true), ''), 'false')::boolean`. Add a unit test that sets the GUC to '' and asserts a normal tenant query still returns rows.

### B21. `app.hat_mandant` and `app.ist_super_admin` are declared `security definer` with no `set search_path`.

**Why it breaks:** A SECURITY DEFINER function without a pinned search_path executes with the definer's privileges against whatever schema the caller puts first. Any role able to create objects in a schema on the caller's search_path can shadow `benutzer_mandant` or `benutzer_rolle_zuordnung` with its own table and make `app.hat_mandant()` return true for every mandant — a complete bypass of the tenant isolation that SEC-A2/SEC-A3 call the highest-priority property in the codebase. This is the standard Postgres privilege-escalation pattern and it sits in the security kernel of the whole platform.

**Required fix:** `... security definer set search_path = public, pg_temp` on both functions (and on every SECURITY DEFINER function added later, including the iCal-token resolver and the partition creator). `REVOKE EXECUTE ... FROM public` and grant only to `authenticated`. Add a lint/CI check that fails on any SECURITY DEFINER function without a pinned search_path.

### B22. `benachrichtigung_typ` is declared as 'NOT-01, genau diese neun', yet the prose requires notifications the enum cannot express: the AGT-05 budget stop ('agent_budget_erschoepft' is named in the agent_budget section), the radar-ingest failure (`radar_ingest` watchdog), and the APR-08 rubber-stamping finding.

**Why it breaks:** The trigger described under `agent_budget` cannot insert its row — the enum value does not exist — so AGT-05's mandatory 'hard stop **with notification**' has no representation, and the same holds for the two watchdog jobs the draft itself added to `watchdog_job`. A watchdog that finds something but cannot notify anyone is the failure mode SPEC §14 exists to prevent.

**Required fix:** Extend the enum with `agent_budget_erschoepft`, `radar_ingest_fehler`, `freigabe_rubberstamp` and `watchdog_ausgeblieben`, and state plainly that these go beyond NOT-01's nine because the domain's own jobs require them. Add a test asserting every `watchdog_job` value has at least one reachable `benachrichtigung_typ`.

### B23. `kandidat` has `UNIQUE (mandant_id, lower(email)) WHERE email IS NOT NULL AND anonymisiert_am IS NULL` and `bewerbung` has `UNIQUE (kandidat_id, stelle_id) WHERE stelle_id IS NOT NULL`.

**Why it breaks:** Both collapse legitimate duplicates. (a) Shared household or shared-device e-mail addresses are common in exactly this workforce; two different people applying for cleaning jobs from one address means the second intake INSERT fails. REC-03 requires intake from a monitored mailbox and a web form — a hard constraint there does not deduplicate, it *drops the application* (or worse, silently attaches one person's CV to another person's record, an AGG/DSGVO problem). (b) An applicant rejected in March and re-applying to the same position reposted in November cannot be recorded at all; REC-01 derives postings from recurring staffing gaps, so repostings of the same `stelle` are the normal case.

**Required fix:** Replace both with non-unique indexes (`INDEX (mandant_id, lower(email))`, `INDEX (kandidat_id, stelle_id)`) and handle duplicates as a *suggested merge* in the service, surfaced in the UI. If a uniqueness guarantee is wanted for re-applications, key `bewerbung` on `(kandidat_id, stelle_id, eingang_am::date)` or add an explicit `bewerbungsrunde` column — but never let intake fail closed on a heuristic.

### B24. `vergabemappe.abgabe_frist` is a copy of `ausschreibung.frist_angebot` ('gespiegelt, damit die Mappe ohne Join sortierbar ist') and the deadline watchdog index `INDEX (mandant_id, abgabe_frist) WHERE status <> 'eingereicht'` reads the copy. No trigger keeps it in sync, and `ausschreibung` is updated in place on every Berichtigung.

**Why it breaks:** Contracting authorities routinely shorten or move deadlines by Änderungsbekanntmachung — the draft models `ist_berichtigung` precisely because this happens. When they do, the mirrored value goes stale and the RAD-06 'Frist < 5 Tage' watchdog counts down to the wrong date. The bid is prepared against a deadline that has already passed. In procurement law that is exclusion without review — the draft's own D-07 rationale. The `ausschreibung_vorgang.frist_angebot_snapshot` drift detector is a good idea but is a *different* column and is explicitly documented as a snapshot, not the operative deadline.

**Required fix:** Either drop the mirror and have the watchdog join `ausschreibung` (the index then lives on `ausschreibung.frist_angebot`, which it should anyway), or add an AFTER UPDATE trigger on `ausschreibung` that propagates `frist_angebot` to every open `vergabemappe` and raises a `frist_naht`/`planaenderung` notification whenever the new value differs from `ausschreibung_vorgang.frist_angebot_snapshot`. Test: shorten a deadline by re-ingest, assert the watchdog fires on the new date.

### B25. `kalender_eintrag` stores `rrule text` (RFC 5545) alongside `beginn timestamptz` with no time-zone column.

**Why it breaks:** Invariant 2: instants are UTC, display is Europe/Berlin, and durations are differences of UTC instants — but a *recurrence* is not an instant. A weekly 09:00 Berlin meeting expanded from a UTC DTSTART lands at 10:00 Berlin after the March transition and back at 09:00 in October. The same class of bug the CLAUDE.md DST tests exist to catch, in the calendar rather than the Dienstplan. CAL-01 covers deadlines and follow-ups where an hour matters.

**Required fix:** Add `zeitzone text NOT NULL DEFAULT 'Europe/Berlin'` to `kalender_eintrag` and expand every RRULE in that zone before converting occurrences to UTC. Reuse whatever `planungsserie` does in Domäne 3 so there is one expansion implementation, and cover it with the same spring-forward/fall-back tests.

### B26. `kalender_eintrag` carries `UNIQUE (quelle_typ, quelle_id) WHERE quelle_typ <> 'manuell'`, with `kalender_quelle_typ` including `bewerbung`.

**Why it breaks:** One projected calendar entry per source row. For `einsatz` that is right; for `bewerbung` it is wrong — REC-06 schedules interviews, plural (telephone screen, first round, second round, trial shift). The second interview for the same application violates the unique index and cannot be created, and the workaround (creating it as `quelle_typ='manuell'`) severs the link the CAL-02 person filter and the LEG-11 purge both need.

**Required fix:** Either add a discriminator to the key — `UNIQUE (quelle_typ, quelle_id, typ, beginn)` — or model interviews as their own rows referencing `bewerbung` (see the missing interview table) and project *those*. Keep the strict one-to-one only for `einsatz`, `rechnung` and `ausschreibung` projections.

### B27. Single-column FKs are used against tenant-scoped parents in many places despite the draft's own rule that composite FKs are used 'überall, wo Eltern und Kind im selben Mandanten liegen': `ausschreibung_vorgang.radar_profil_id`, `ausschreibung_vorgang.bewertung_id`, `kandidat_bewertung.stelle_id`, `stelle_veroeffentlichung.jobboard_kanal_id`, `social_post_ziel.social_channel_id`, `social_post.referenz_id`, `kanal_statistik.social_channel_id`, `agent_kosten.agent_aufgabe_id`, `freigabe_anfrage.agent_aufgabe_id`, `agent_schritt.freigabe_anfrage_id`, `bewerbung.freigabe_anfrage_id`, `seite.freigabe_anfrage_id`.

**Why it breaks:** Two consequences. (a) Integrity: a tenant can attach another tenant's radar profile, channel or approval request to its own row; the read then returns nothing under RLS and the record is permanently broken, or the join is performed by a job running with elevated rights and leaks. (b) Security: PostgreSQL performs referential-integrity checks **bypassing row-level security**. A single-column FK to a tenant table is therefore an existence oracle — writing a guessed uuid succeeds if the row exists in *any* tenant and raises a FK violation if it does not. AUT-06 exists specifically to deny that signal ('404, not 403, because 403 confirms existence').

**Required fix:** Use the composite form everywhere both sides are tenant-scoped, exactly as done for vergabemappe_position and freigabe_feld — which also requires the missing `UNIQUE (mandant_id, id)` constraints from the first finding. Where a composite FK is genuinely impossible (polymorphic `bezug_id`), the §6.2 argument applies and no FK is the right answer; but a plain FK to a tenant table is the worst of the three options.

### B28. External publication paths have no approval constraint. `stelle_veroeffentlichung` (publishing a job ad to an external board, REC-09) has no `freigegeben_von`/`freigegeben_am`, and `seite` may reach `status='veroeffentlicht'` with `erstellt_durch_agent_id` set and `freigabe_anfrage_id` NULL — while the neighbouring `social_post` and `stelle` both carry exactly such CHECKs.

**Why it breaks:** Invariant 7: 'Email, offers, applications, posts — all pass server/agent/policy.ts'. The autonomy matrix lists 'Any external send: approval required'. A job advertisement carrying the company name onto a third-party board, and a page published to the public website, are both content leaving the system. The draft applies the rule rigorously three times and then omits it twice, which is worse than omitting it everywhere — a reviewer reading the pattern will assume it holds.

**Required fix:** Add `freigegeben_von uuid NOT NULL`-on-publish to `stelle_veroeffentlichung` with `CHECK (status NOT IN ('gesendet','veroeffentlicht') OR freigegeben_von IS NOT NULL)`, and add to `seite` the same CHECK `stelle` already has: `CHECK (erstellt_durch_agent_id IS NULL OR status = 'entwurf' OR freigabe_anfrage_id IS NOT NULL)`.

### B29. `ausschreibung.waehrung char(3)` is nullable while `wert_geschaetzt_cent` may be set, and `radar_profil.wert_min_cent`/`wert_max_cent` are compared against it with `radar_profil.waehrung DEFAULT 'EUR'` and no conversion rule anywhere.

**Why it breaks:** RAD-02 ingests TED, which carries non-EUR values. A notice at 500.000 PLN is compared against an EUR band and scores as if it were 500.000 €, or a value with a NULL currency is compared at all. The result is a wrong `bewertung`, which is the input to RAD-08 notifications and to the decision to spend days preparing a bid. Currency conversion is a financial rule the SPEC does not state, so picking a rate source silently would itself be a violation of the working rules.

**Required fix:** Add `CHECK (wert_geschaetzt_cent IS NULL OR waehrung IS NOT NULL)`. The scoring function must treat a value whose currency differs from the profile currency as *unscored on the value criterion* and say so in `begruendung` and `aufschluesselung`, never as zero and never converted. Emit `// TODO(client): Sollen Fremdwährungsbeträge umgerechnet werden, und mit welcher Kursquelle (EZB-Referenzkurs)?` and record it under Open.

### B30. CAL-03's iCal feed is fetched by an external calendar client with no session, yet `kalender_feed_token`'s only policy is `using (benutzer_id = auth.uid() or app.ist_super_admin())`, and the draft elsewhere forbids `service_role` in application paths and rejects SECURITY DEFINER lookups.

**Why it breaks:** The feed request arrives as `anon` with a token in the URL. `auth.uid()` is NULL, so the `token_hash` lookup returns zero rows and the feed always 404s. The only ways out are the two the draft rules out, so CAL-03 as specified is unimplementable against its own rules — the contradiction will be discovered in Phase 9 by whoever has to ship it.

**Required fix:** Define one narrowly-scoped `app.feed_token_aufloesen(p_token_hash text) returns table(benutzer_id uuid, mandant_id uuid)` as SECURITY DEFINER `set search_path = public, pg_temp`, granted to `anon`, that resolves only non-revoked, unexpired tokens, records `letzte_nutzung_am`, and returns nothing else. Document it as a deliberate, audited exception alongside the partition-creation function. Add `fehlversuche` counting and rate limiting per SEC-A7, since the token is a bearer secret with no second factor.

- `agent_budget.warnschwelle_prozent integer NOT NULL DEFAULT 80`. AGT-05 specifies a monthly cap and a hard stop; it says nothing about a warning threshold. 80 % is a plausible-sounding financial rule picked silently. Needs `// TODO(client): Ab welchem Anteil des Monatsbudgets soll gewarnt werden?` and an entry under Open — the same treatment `budget_cent` correctly received two rows above it.
- `agent.max_schritte integer NOT NULL DEFAULT 25`. Not in the SPEC. It silently caps what any agent can accomplish per task and will be blamed for mysterious truncated results; mark it as a configuration placeholder rather than a schema default with an air of authority.

RAD-04 says only 'positive and negative keywords' and 'value bounds'. Mark all three as TODO(client) and default negative keywords to a deduction until answered.
- `radar_profil_cpv.gewichtung integer NOT NULL DEFAULT 100` with `CHECK (BETWEEN 0 AND 1000)`. The draft marks `radar_profil.gewichtung jsonb` as TODO(client) and then hands every CPV row a concrete weight of 100 on a 0–1000 scale by default. Same rule, two treatments.

Hard-coding it in a CHECK means the client's actual weighting scheme (which may be uncapped, or 0–1, or per-criterion) forces a migration. Make the range a property of `regel_version`, not of the column.
- An implicit 1:1 EUR assumption in tender value matching: `radar_profil.waehrung DEFAULT 'EUR'` and `wert_min_cent`/`wert_max_cent` are compared against `ausschreibung.wert_geschaetzt_cent` with no currency guard and no conversion rule. This is a business rule about how autonomy limits combine — the SPEC §17 matrix gives limits, not a conflict-resolution algorithm — and the one the draft chose is defeatable (see the blocking finding). Present it as a proposal with a TODO(client), not as a settled column list.
- `benachrichtigung_praeferenz.mindest_prioritaet DEFAULT 'niedrig'` combined with the unwritten rule that quiet hours never suppress `dringend`: a reasonable default, but it decides that every user receives every notification by default, which is the 'forty requests a day and the human stops reading' failure mode SPEC §17 explicitly warns about.
