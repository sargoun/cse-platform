# Adversarial review — auth-berechtigungen

## BLOCKING (20)

### B1. §3.2 layer 5 puts a RESTRICTIVE policy `nur_aal2` on `benutzer_mandant`: `using (app.aal() = 'aal2')`. Restrictive policies AND with everything else, and §8.4 `app.sichtbare_mandanten()` reads `public.benutzer_mandant` on every statement.

**Why it breaks:** AUT-02 requires 2FA only for `super_admin` and `admin`. Every `leitung`, `mitarbeiter` and `kunde` runs at `aal1`. For them `benutzer_mandant` returns zero rows, `sichtbare_mandanten()` returns `{}`, and every Class-T select policy (`mandant_id = any(app.sichtbare_mandanten())`) is false. The entire platform returns zero rows for every non-admin — the check-in worker, the Leitung, the customer portal. This is the design's own §8.5 contradicting its own §3.2.

**Required fix:** Remove `benutzer_mandant` from the `nur_aal2` list. The aal2 gate belongs on the *write* path of the permission-administration tables (`rolle_berechtigung`, `benutzer_mandant_modul`, and the INSERT/UPDATE side of `benutzer_mandant`), never on SELECT of a table that membership resolution depends on. State the policy as `as restrictive for insert/update/delete` only, and add an explicit permissive select policy for `benutzer_mandant`.

### B2. `alter table … force row level security` is declared on every application table (§8.2) while `app.sichtbare_mandanten()` is `security definer` reading `public.benutzer_mandant` (§8.4). The owner of that function is never named, and §8.2 says no role has BYPASSRLS.

**Why it breaks:** FORCE RLS makes RLS apply to the table owner too. A SECURITY DEFINER function running as the (forced) owner is therefore subject to `benutzer_mandant`'s own policies — and no permissive policy for `benutzer_mandant` is ever written. The helper returns `{}` for everybody, so every Class-T policy denies every row. The single function on which all of TEN-03/AUT-05 rests cannot execute as specified.

**Required fix:** Name the owner explicitly: a dedicated `cse_rls_owner` role that owns `app.sichtbare_mandanten()` and is either granted BYPASSRLS or exempted from FORCE RLS on `benutzer_mandant` only, with `revoke execute … from public` and `grant execute to cse_app, cse_app_ro, cse_job`. Add a direct-SQL test asserting the helper returns the right array for an aal1 `mitarbeiter`.

### B3. TIM-14 / D-09 clauses 1 and 2 (ArbZG aggregates per person across all employments and entities, including an 11h rest period spanning two entities) is impossible under the RLS the draft specifies. `einsatz` and `zeiteintrag` are Class T; a `leitung_a` scheduling in `reinigung` has `sichtbare_mandanten() = {reinigung}` and cannot see the person's `security` shifts.

**Why it breaks:** The conflict detector queries by `person_id` across entities (D-09 point 1). Under Class T it silently returns zero rows from the other entity, the ArbZG check passes, and a 6h cleaning + 5h security day is scheduled as lawful. This is the exact failure D-09 was written to prevent, and it is silent — no error, just a missing warning. LEG-03 and TIM-05/TIM-06 are unenforceable. The draft names `dienstplan.arbzg_warnung_uebersteuern` but never designs the check the warning comes from.

**Required fix:** Design a `security definer` aggregation function, e.g. `app.arbzg_belastung(person_id, von_utc, bis_utc)` owned by `cse_rls_owner`, that reads `einsatz`/`zeiteintrag` across ALL mandanten of that person but returns only durations, interval boundaries and a conflict code — never `mandant` name, `objekt`, `kunde`, or anything from `anstellung` (no `stundensatz_intern`, no `personalnummer`). Route it through a tested service in `src/server/services/arbzg/`. Add a permission `dienstplan.arbzg_pruefen` and an isolation-suite assertion that the function's return value leaks no other-entity identifiers (D-09 clause 6).

### B4. §1.1 defines the `intern` portal as reachable by "any principal holding at least one `benutzer_mandant` row with a role other than `kunde`", and §2 consequence 3 makes every employee a derived `benutzer_mandant` row with role `mitarbeiter`.

**Why it breaks:** Every employee therefore qualifies for `portal = 'intern'`. §5.2 declares EMP-13 "structural, not a permission" and implements it entirely as restrictive policies keyed on `app.portal() <> 'mitarbeiter'`. In the intern portal those policies do not fire, so the DB-level ceiling evaporates and only the permission bindings stand between a cleaner and `rechnung`, `kalkulation`, `anstellung`. EMP-13 ("employees never see group financials, other employees' data, or customer commercials") is then a single missing `applyScope` call away from breach.

**Required fix:** Derive the portal from the role in the active mandant, not from the existence of a membership: `portal = 'intern'` requires the active membership's role ∈ {super_admin, admin, leitung}; a membership whose role is `mitarbeiter` resolves to `portal = 'mitarbeiter'` and a `kunde` membership to `portal = 'kunde'`. Add isolation assertions: (a) `ma_p2` requesting any `(portal)/[mandant]` internal route gets 404/redirect to `/mein`; (b) a `kunde` principal can never obtain `app.portal() = 'intern'`.

### B5. §8.5 gives mitarbeiter-portal restrictive policies only for `zeiteintrag` and `rechnung`. `anstellung` has none, and `anstellung` carries `stundensatz_intern` and `personalnummer`.

**Why it breaks:** In `portal = 'mitarbeiter'` the employee's `sichtbare_mandanten()` covers every mandant they are employed by, so the Class-T select policy on `anstellung` exposes every colleague's employment row, wage rate included. That breaches EMP-13 and D-09 clause 6 directly. The same hole exists for `person` (Class P has no mitarbeiter ceiling at all), `abwesenheit` (health-adjacent, EMP-10), `stundenkonto` and `urlaubskonto` — all of which hang off `anstellung_id` and are named nowhere in §8.5.

**Required fix:** Write the ceiling for every anstellung-hung table explicitly, not by example: `create policy anstellung_ma on anstellung as restrictive for all using (app.portal() <> 'mitarbeiter' or person_id = app.current_person())`, and the same shape for `stundenkonto`, `urlaubskonto`, `abwesenheit`, `zeit_einwand`, `antrag`, `einsatz`, `da_kenntnisnahme` (via `anstellung_id in (select id from anstellung where person_id = app.current_person())`), plus `person as restrictive … or id = app.current_person()`. Enumerate them in `rls.ts` and fail the build on any anstellung-hung table without one.

### B6. `benutzer_mandant` has PK `(benutzer_id, mandant_id)` and a single `rolle_id`, while §2 consequence 3 has a trigger on `anstellung` maintaining `benutzer_mandant` rows with `quelle = 'anstellung'` and role `mitarbeiter`.

**Why it breaks:** The Leitung of CSE Dienstleistungen is normally also employed by CSE Dienstleistungen. The trigger fires on her `anstellung` and hits the PK: it either overwrites her `leitung` role with `mitarbeiter` (silent privilege loss — she loses her whole area) or throws and blocks the employment insert. `quelle` is a single scalar and cannot record both origins. Symmetrically, §4.2 revokes membership and sessions on "end of the last active `anstellung` for a `mitarbeiter`", which would strip a manually granted `leitung` role when that person's employment ends. §5.1 explicitly says this dual case exists ("they hold one `benutzer` with `person_id` set *and* a `leitung`/`admin` membership") — the schema cannot represent it.

**Required fix:** Either (a) keep the PK and make the trigger strictly additive-if-absent and removal-only-when `quelle = 'anstellung'`, storing the derived flag as a separate boolean column `aus_anstellung boolean not null default false` rather than a `quelle` enum; or (b) change the PK to `(benutzer_id, mandant_id, rolle_id)` and resolve the effective role as the maximum. Whichever is chosen, add a test: person with `leitung` in A plus an `anstellung` in A keeps `leitung` after the trigger runs and after `austritt`.

### B7. §5.3 checks `verwendet_am is not null` at step 4, then opens the transaction and takes `select … for update` at step 5 without re-reading the state it just checked.

**Why it breaks:** Classic TOCTOU. Two concurrent POSTs to the same check-in URL both pass step 4, then serialise on the row lock, and both insert a `zeiteintrag` — the second one after the first has already set `verwendet_am`. TIM-07's "single use" is broken under exactly the condition it will be hit: a worker double-tapping a link on a slow mobile connection. The result is duplicated billable time (FIN-07 traceability, TIM-12 attaches time to the order) and duplicated §17 MiLoG records.

**Required fix:** Make consumption a single conditional write and treat zero rows as the 409: `update checkin_token set verwendet_am = now(), verwendet_ip = $ip where id = $id and verwendet_am is null and now() between gueltig_ab and gueltig_bis returning einsatz_id, mandant_id;` — insert the `zeiteintrag` only if a row came back, in the same transaction. Delete steps 3 and 4 as pre-checks (keep them only to produce the friendlier message after the update returns nothing). Add a concurrency test firing N simultaneous requests at one token and asserting exactly one `zeiteintrag`.

### B8. The check-in endpoint runs on the `cse_checkin` role with no session and therefore no `withTenant` and no GUCs, yet it inserts into `zeiteintrag`, which is a Class T table whose insert policy is `with check (mandant_id = app.current_mandant() and not app.is_readonly())`.

**Why it breaks:** `app.current_mandant()` is NULL (unset GUC) and `app.is_readonly()` defaults to `'on'` by the draft's own fail-closed rule — so the predicate is false/NULL and the insert is refused. No policy is written for `checkin_token`, `einsatz` (select) or `medien` (insert) under `cse_checkin` either. As specified, TIM-07/TIM-08 cannot execute at all. The same gap exists for the whole pre-authentication path: `resolveSession()` must read `sitzung` by `token_hash`, and the rate limiter must write `auth_versuch`, before any principal or mandant is known — yet §8.3 states "the only exported database handle requires `withTenant`" and "a request may never touch the pool outside a transaction".

**Required fix:** Define the pre-session data path explicitly. (1) A `security definer` function `app.checkin_verbrauchen(token_hash, geraet_zeit, ip)` owned by `cse_rls_owner` that performs the conditional update, derives `mandant_id`/`anstellung_id` from the `einsatz`, and inserts the `zeiteintrag` — so the endpoint never needs table grants or GUCs. (2) An equivalent `app.sitzung_aufloesen(token_hash)` and `app.versuch_protokollieren(...)` for the pre-auth path, executed on a distinct `cse_anon` role that holds EXECUTE on those three functions and nothing else. (3) State that these are the only three functions permitted to run outside `withTenant`, and assert that in the route-manifest test.

### B9. Nine tables the draft itself introduces are never assigned an RLS class and receive no policy: `sitzung`, `auth_versuch`, `sperre`, `sicherheits_richtlinie`, `mfa_recovery_code`, `einladung`, `kunde_zugang`, `benutzer_mandant_modul`, `rolle_berechtigung` (and `checkin_token`, which carries `mandant_id`). §8.5 promises a map covering "every SPEC §22 table" — none of these are in SPEC §22.

**Why it breaks:** `sitzung` holds `aktiver_mandant_id`, the single authority for invariant 3, and `token_hash`. With `cse_app` holding SELECT/UPDATE and no policy, one compromised route or one forgotten WHERE clause lets a request read or rewrite another user's active mandant — invariant 3 defeated at its root. `kunde_zugang` and `checkin_token` carry `mandant_id` and would be flagged by the §10.3 meta-test as failures on the first migration, so the draft's own acceptance criterion fails on day one. `mfa_recovery_code` unprotected defeats AUT-02.

**Required fix:** Add a fourth class — Class S (session/security infrastructure) — and enumerate it: `sitzung`, `mfa_recovery_code`, `einladung` visible only where `benutzer_id = app.current_benutzer()`; `auth_versuch`, `sperre`, `sicherheits_richtlinie` readable only under `einstellungen.lesen` and never by `cse_app` at all (move them behind the security-definer functions above); `kunde_zugang`, `checkin_token`, `benutzer_mandant_modul`, `rolle_berechtigung` as Class T. Extend the §10.3 meta-test to assert every table in `public` — not just SPEC §22 tables — appears in `rls.ts`.

### B10. §7.3: "if rolle = super_admin → the whole catalogue, geltungsbereich = 'mandant'", bypassing the binding table entirely. But §14 marks four permissions `—` "never bindable: no UI toggle exists", including `dienstplan.nachweis_block_uebersteuern` ("never bindable for anyone. SEC-04 is a hard block in the service layer"), `zeit.einwand_stellen`, `security.kenntnisnahme_bestaetigen` and `person.eigene_daten_bearbeiten`.

**Why it breaks:** A super_admin resolving to the whole catalogue receives exactly the permissions the matrix declares unreachable. `dienstplan.nachweis_block_uebersteuern` granted to anyone defeats SEC-04 and LEG-04 (§34a GewO): an unqualified or expired-certificate guard can be assigned, which is the unlawful assignment D-05 and SPEC §8 call out by name. `zeit.einwand_stellen` granted to an admin destroys EMP-07's evidentiary point ("the employee never edits a time entry") in a wage dispute. `security.kenntnisnahme_bestaetigen` granted to an admin lets a manager acknowledge a Dienstanweisung on an employee's behalf (SEC-06).

**Required fix:** Make `berechtigung.bindbar_fuer` authoritative over the super_admin bypass: resolve super_admin as `{ b ∈ catalogue | b.bindbar_fuer @> array[rolle] }`, not the whole catalogue. For `dienstplan.nachweis_block_uebersteuern`, delete the permission from the catalogue entirely — a code that no role may hold should not exist as a code; SEC-04 belongs in the service with no override path at all. Add an assertion: a `super_admin` attempting to assign a guard with an expired §34a certificate fails.

### B11. §3.2 layer 5 applies the `nur_aal2` restrictive policy to `nummernkreis`, while §14.5 makes `rechnung.festschreiben` bindable to `leitung` (`○`) — a role for which AUT-02 requires no 2FA.

**Why it breaks:** FIN-03 assigns the invoice number via `SELECT … FOR UPDATE` on the `nummernkreis` counter row at finalisation. Under an aal2-only restrictive policy an aal1 `leitung` reads zero rows from `nummernkreis`, so the counter row cannot be locked and finalisation either fails opaquely or — worse, if the code treats "no row" as "first invoice" — restarts the sequence and produces duplicate numbers across a GoBD-relevant circle (LEG-01). `nummernkreis` also gets no Class-T policy, so it has no working read path for anyone.

**Required fix:** Remove `nummernkreis` from the `nur_aal2` list and classify it as Class T with the standard policies plus a restrictive `app.portal() = 'intern'`. If a step-up is genuinely wanted for finalisation, put it in `requirePermission` as an explicit `{ erfordertAal2: true }` option on `rechnung.festschreiben` — an application decision the client can confirm — not as a blanket DB policy on the counter table.

### B12. §3.1: "`benutzer.auth_user_id` is a unique, non-null FK to `auth.users.id`", while §1 defines `benutzer.art ∈ {mensch, agent, system}` where agent and system principals have "no interactive login".

**Why it breaks:** An agent principal (AGT-01) and the job runner have no `auth.users` row. A non-null FK forces the implementation to fabricate fake `auth.users` rows for every agent and every cron identity — synthetic credentials in the auth store that can, in principle, be issued tokens, and that pollute Supabase's own user counts and password-reset surfaces. It also breaks the seed: the four agents of D-03 cannot be inserted by migration.

**Required fix:** `auth_user_id uuid null unique` with `check ((art = 'mensch') = (auth_user_id is not null))`, and state that `art in ('agent','system')` principals are never issuable a Supabase session — `resolveSession()` refuses them, and they reach `withTenant` only via the job/agent orchestrator.

### B13. §4.2 declares `sitzung.portal text not null`; §3.3 declares the enrolment-only session as `portal = NULL` (and `berechtigung_version` is `bigint not null` while such a session has no mandant and therefore no version).

**Why it breaks:** The 2FA-enrolment session — the mechanism by which AUT-02 is actually enforced for a not-yet-enrolled admin — cannot be written to the table the design defines. The first admin created after enforcement goes live cannot log in to enrol.

**Required fix:** `portal text null` with `check (portal is null or portal in ('intern','mitarbeiter','kunde'))` and `check (aal = 'aal2' or portal is not null or aktiver_mandant_id is null)`; `berechtigung_version bigint null`. Add the enrolment session to the isolation suite as its own fixture.

### B14. `kunde_zugang.benutzer_id` is declared `unique` and `benutzer.kunde_id` is a single scalar mirrored into the `app.kunde_id` GUC — while §15.2 states "A customer of `reinigung` who is also a customer of `bau` has two `kunde` rows in two mandanten" and raises the one-login-or-two question as open.

**Why it breaks:** A unique constraint on `benutzer_id` and a scalar `kunde_id` structurally forecloses the answer the draft says is open: one login over two `kunde` rows becomes impossible without a migration. This is precisely the case of a unique constraint wrongly collapsing legitimate duplicate rows — CRM-06 ("customer history across all four areas") points the same way, and the group buys and sells across four entities.

**Required fix:** Drop the unique on `benutzer_id`; make the key `(benutzer_id, mandant_id)` unique, so one login can hold one `kunde_zugang` per mandant. Replace `benutzer.kunde_id` with resolution at session-build time: `app.kunde_id` is set from the `kunde_zugang` row for the *active* mandant, and is empty when none exists. Keep the customer switcher question open, but do not let the schema answer it.

### B15. `requireKunde(code): Promise<MandantKontext>` and `MandantKontext` is `WritableKontext`.

**Why it breaks:** Every mutating service signature takes `WritableKontext`, so `assertWritable` passes for a customer context and the compile-time guard the draft relies on in §11 layer 1 does nothing for the customer portal. Meanwhile the draft's own open question is whether a customer may write anything at all (accept an offer with legal effect, OPS-09). The type system silently grants what the design says is undecided — the exact pattern CLAUDE.md's "never invent a business rule" forbids, because "accepted offer converts to order in one action" carries legal effect.

**Required fix:** Introduce `KundeKontext extends BasisKontext { kind: 'kunde'; readonly: true; mandantId; kundeId }` and exclude it from `WritableKontext` until the client answers. Where a customer write is later permitted, add an explicit `requireKundeSchreibend(code): Promise<KundeSchreibKontext>` per approved action, so each write is an individually authorised decision rather than a blanket capability.

### B16. §5.1 puts `sprache` and `telefon_e164` on `mitarbeiter_zugang`. D-09 defines the `person` row explicitly as `id, vorname, nachname, geburtsdatum, telefon, sprache`, and invariant 9 says facts about the human hang off `person_id`.

**Why it breaks:** Language and phone number are facts about the human, not about a login. Two consequences: (a) a person who has no `mitarbeiter_zugang` — a candidate, a person entered by HR before onboarding, a person whose login is `gesperrt` per §5.1 because they hold a `leitung` role — has no language, so EMP-12's de/en/ar/tr choice and every notification to them lose their locale; (b) `person.telefon` and `mitarbeiter_zugang.telefon_e164` are two columns for one fact with no stated source of truth, which is how an OTP goes to the old number after HR updates the record. It also contradicts an explicitly CONFIRMED-BY-CLIENT decision, which CLAUDE.md says must not be silently reversed.

**Required fix:** `sprache` and `telefon` stay on `person` (`telefon` normalised to E.164, unique). `mitarbeiter_zugang` keeps only login facts: `person_id pk`, `auth_user_id`, `telefon_bestaetigt_am`, `status`, `letzter_login_am`. The uniqueness that makes SMS login work becomes a unique index on `person.telefon`, not on a second copy.

### B17. §14.5 grants `rechnung.entwurf_loeschen`, while §8.5 states "No DELETE policy is created for finance, time-tracking or audit tables" and §8.2 gives `cse_app` "no DELETE on finance/time/audit tables".

**Why it breaks:** The permission cannot execute — the design grants a capability its own database layer makes impossible. Worse, if the ambiguity is resolved the other way at implementation time, a hard DELETE on `rechnung` breaches invariant 8 and LEG-01/GoBD. ROADMAP Phase 6 acceptance ("Deleting 1000 drafts leaves zero gaps in the sequence") is satisfied by soft deletion, but the draft never says which it is.

**Required fix:** Rename to `rechnung.entwurf_verwerfen` and define it as a status transition `entwurf → verworfen` with `verworfen_am`, `verworfen_von`, `verworfen_grund`, executed through the UPDATE policy. State explicitly that no row is ever removed from `rechnung`, and that a `verworfen` draft still has no number (invariant 4).

### B18. §13 proposes "24 months for login and OTP attempts" retention inside `audit_log`, while §8.5 Class A gives `audit_log` no delete policy, revokes DELETE from `cse_app`, and adds a `before update or delete` trigger raising `AUDIT_UNVERAENDERLICH`.

**Why it breaks:** The design proposes a DSGVO deletion rule (LEG-09) that its own immutability construction makes unexecutable. Either the trigger is later weakened — destroying the GoBD/LEG-01 guarantee for the 10-year permission-change records that share the table — or the retention promise is never kept and the DSGVO deletion concept is false on paper.

**Required fix:** Separate the two lifetimes into two tables: `auth_versuch` (already exists, hashed keys, prunable, DSGVO-scoped) carries login/OTP attempt telemetry and is deleted on schedule; `audit_log` carries only the events with evidentiary value and is never deleted. Where a DSGVO erasure must touch `audit_log`, implement it as partition detach for whole expired months plus field-level pseudonymisation of `ip`/`user_agent`, not row deletion — and record that as an explicit DECISIONS.md entry.

### B19. `Geltungsbereich = 'zugewiesen'` is used throughout §14 for `mitarbeiter` on `objekt.lesen`, `auftrag.lesen`, `security.wachbuch_lesen`, `security.dienstanweisung_lesen`, `bau.lv_lesen`, `bau.bautagebuch_lesen`, `reinigung.leistungsnachweis_lesen`, `dokument.lesen` — none of which hang off `anstellung_id`, and none of which get a mitarbeiter restrictive policy in §8.5.

**Why it breaks:** For every one of those tables the only thing standing between an employee and the whole tenant's data is a service-layer `applyScope` call. §5.2 claims EMP-13 is "structural, not a permission… invisible even to a bug" — for these tables it is neither. A guard on one object can read every Dienstanweisung, every Wachbuch and every LV of the entity. The isolation suite has no assertion covering `Z` scope, so this ships green.

**Required fix:** Define `Z` in the database as well: add `einsatz`-derived restrictive policies, e.g. `create policy objekt_ma on objekt as restrictive for all using (app.portal() <> 'mitarbeiter' or id in (select e.objekt_id from einsatz e join anstellung a on a.id = e.anstellung_id where a.person_id = app.current_person()))`, and the equivalent for `auftrag`, `dienstanweisung`, `wachbuch_eintrag`, `lv_position`, `bautagebuch`, `leistungsnachweis`, `dokument`. Add isolation assertion: `ma_p2` reads exactly the objects of their own Einsätze and 404s on every other object of the same mandant.

### B20. §7.3's fifth-mandant trigger "creates a `benutzer_mandant` row for every `super_admin`" on mandant insert. Nothing creates memberships for a super_admin created *after* the mandanten exist.

**Why it breaks:** AUT-01 says Super Admin means "all four areas, all modules". `app.sichtbare_mandanten()` derives strictly from `benutzer_mandant`, so a newly promoted super_admin has `{}` and sees nothing — including the permission editor they were promoted to use. §3.3 compounds this: a promoted admin has all sessions revoked and must enrol in 2FA, and the design also requires at least two super_admins to exist for 2FA reset. The bootstrap and the recovery path both dead-end.

**Required fix:** Make the derivation symmetric: a trigger on `benutzer_mandant` insert/update where `rolle = super_admin` fans the membership out to all mandanten, and the mandant-insert trigger fans out to all super_admins. Alternatively special-case `super_admin` inside `app.sichtbare_mandanten()` (`select array_agg(id) from mandant` when the principal holds super_admin anywhere) — and test it by promoting a user in the isolation suite.

## MISSING (19)
- `benutzer` — the central table of the whole section — is never defined. Columns referenced across §1, §3, §4, §5, §7, §13 (`auth_user_id`, `art`, `person_id`, `kunde_id`, `zwei_faktor_pflicht`, `zuletzt_genutzter_mandant_id`, `aktiv`, `deaktiviert_am`) have no declared types, nullability or constraints. The document says "Everything named here — table, column, function — is the name the implementation must use"; the contract is unfulfillable for its own primary table.
- `mandant` is never defined either, although the section claims TEN-01, TEN-02, TEN-07 and TEN-08. Needed at minimum: `id`, `schluessel` (reinigung|security|bau|operations), `slug` (unique — §4.4 resolves URLs against it), `firma`, `rechtsform`, `identitaets_hue` (DESIGN §5 area colours), `logo_pfad`, `ist_rechtstraeger boolean` (TEN-02, blocked on O-01), `berechtigung_version bigint not null default 1`, `aktiv`.
- `einladung` is used as the mechanism for both `benutzer.einladen` and `kunde_zugang` activation (§15.1) but never defined: no columns, no `token_hash`, no single-use flag, no `rolle_id`/`mandant_id` binding, no audit event beyond `benutzer.eingeladen`. An invitation that carries a role assignment is a privilege-granting bearer token and needs the same treatment as `checkin_token`.
- `sicherheits_richtlinie`, `mfa_recovery_code` and `benutzer_mandant_modul` are named as tables but have no column list, no types and no PK. `mfa_recovery_code` in particular gates AUT-02 recovery.
- CAL-03's per-user iCal feed token is a third bearer capability (after the check-in token and the signed URL) and is missing entirely from §1's "two things that look like principals and are not" table. It needs: a table with `token_hash`, `benutzer_id`, `erstellt_am`, `widerrufen_am`; rotation and revocation; a rate-limit row in §12; audit events; and an explicit statement that it exposes only `kalender_eintrag` rows the holder could read interactively, with no mandant switching.
- AUT-07's rate-limit table omits three auth endpoints it must cover: invitation acceptance (`POST /auth/einladung/[token]`), password-reset token consumption (as distinct from reset *request*, which is listed), and the iCal feed endpoint. All three are unauthenticated and token-guessable.
- LEG-06 / FIN-09 / FIN-10 have no permission anywhere in the 38-module catalogue. §13b UStG reverse charge and §48 EStG Bauabzugsteuer are per-invoice legal determinations with an override risk: recording or overriding a Freistellungsbescheinigung's validity at the service date (FIN-10) needs its own permission (e.g. `crm.freistellungsbescheinigung_pflegen`, `rechnung.steuerfall_uebersteuern`) and an audit event, or a manager can silently drop a 15% withholding.
- LEG-09's data-subject request process (Art. 15 access, Art. 16 rectification, Art. 17 erasure) has no module, no permission and no audit event. `recruiting.daten_loeschen` covers REC-07/LEG-11 only. Employee and customer data-subject requests are the harder case precisely because of invariant 8 and the GoBD retention that overrides erasure — the tension needs a designed answer, not silence.
- TIM-09 (offline capture queued locally, submitted flagged as late, claimed time recorded) is not designed and is actively contradicted by §5.3: rule 3 rejects anything outside `gueltig_ab..gueltig_bis` with 409, and rule 4 rejects a consumed token. A phone that lost signal at 06:00 on a site cannot submit at 09:00. The design needs a distinct late-submission path that accepts the queued entry, records `beansprucht_zeit` separately from `server_zeit`, and flags it `nachtraeglich = true` for planner review — never silently accepting the claimed time (invariant 5).
- TIM-10 on the check-in path: `medien (insert)` is granted to `cse_checkin` with no mention of EXIF stripping, MIME verification (DOC-06) or the private-bucket path. An unauthenticated endpoint that accepts uploads needs a size cap, a declared content-type allowlist and server-side EXIF removal stated here, because it is the one write path with no session behind it.
- BFSG / WCAG 2.1 AA (LEG-07, PUB-09) is absent from every screen this section introduces: login, OTP entry, 2FA enrolment and verification, the `/auth/bereich` chooser, the tenant-switch interstitial, the 404 page, and lockout messages. Needed: errors announced via `aria-live` (DESIGN §9), `<label>` bound to the OTP and TOTP inputs, focus never removed, and the area chooser operable by keyboard.
- TEN-07 is claimed as covered but not designed. DESIGN §6 rule 4 requires the 3px identity-hue bar across the very top *at all times*, and rule 5 fixes the keyboard contract (⌘K opens, arrows navigate, Enter switches, Esc closes). Since §4.3 makes switching a POST, the keyboard path must be specified as a form submission, not a link — the draft never says how ⌘K reaches the POST, nor what the hue is during a context-less enrolment session.
- APR-05 (delayed release with objection window), APR-06 (undo window) and APR-08 (review-duration measurement / rubber-stamp flagging) have no permissions in §14.6, although APR-01/02/03/04/07 are covered. APR-08 in particular is per-employee performance measurement of a manager and belongs in the same §87 BetrVG TODO as the login metadata.
- AGT-05's monthly budget cap is money and must therefore be `bigint` integer cents (invariant 1), and SPEC §17's €20,000 offer threshold must be stored as `2000000` cents, not a decimal. §14.6 defines `agent.budget_setzen` and cites the threshold without saying so. Whichever section defines `agent_budget`, this contract should state the type here since it grants the permission.
- D-09 clause 5 ("Time never crosses invoice circles: every entry hangs off exactly one employment, which belongs to exactly one mandant") has no enforcement. `zeiteintrag` carries both `mandant_id` (Class T) and `anstellung_id`; nothing asserts they agree. Needed: a composite FK `(anstellung_id, mandant_id) references anstellung (id, mandant_id)` with a matching unique key on `anstellung`, so a mismatch is impossible rather than merely unlikely. Same for `einsatz`, `stundenkonto`, `urlaubskonto`, `abwesenheit`.
- Not one index is specified, on query paths the design itself makes hot: `benutzer_mandant (benutzer_id, mandant_id) where aktiv` — `app.sichtbare_mandanten()` runs as an InitPlan on every statement of every request; `sitzung (benutzer_id) where widerrufen_am is null` — mass revocation on password/2FA/role change and `benutzer.sitzungen_widerrufen`; `sitzung (laeuft_ab_am) where widerrufen_am is null` — the expiry sweeper; `auth_versuch (art, schluessel_hash, zeitpunkt desc)` — a windowed count on every login and OTP request, on the fastest-growing table in the system; `sperre (art, schluessel_hash, gesperrt_bis desc) where aufgehoben_am is null`; `anstellung (person_id, mandant_id)` — the correlated `exists` in the `person_select` policy runs per person row, the mitarbeiter restrictive subquery runs per statement, and the cross-entity ArbZG query needs it; `anstellung (mandant_id, person_id) where austritt is null`; `checkin_token (einsatz_id)` and `(gueltig_bis) where verwendet_am is null` for reissue and cleanup; `kunde_zugang (kunde_id)`; and on each `audit_log` partition `(mandant_id, zeitpunkt desc)` for `audit.lesen`, `(objekt_typ, objekt_id, zeitpunkt desc)` for record history, `(korrelation_id)`, `(benutzer_id, zeitpunkt desc)` for SEC-A9. (The `rolle_berechtigung` PK prefix `(mandant_id, rolle_id)` does correctly serve effective-set resolution — that one is fine.)
- The §10.2 isolation matrix has no assertion for the headline D-09 consequence: `leitung_a` (reinigung) must NOT be able to read `ma_p1`'s `anstellung` in `security` — the wage-rate rule stated twice in DECISIONS.md and SPEC §22. It also lacks the positive counterpart (`leitung_a` CAN read `ma_p1`'s `person` row, proving Class P is not over-restrictive), an assertion that a `kunde` principal cannot obtain `portal = 'intern'`, an assertion that an employee cannot read a colleague's `stundensatz_intern`, and an assertion covering the derived-membership trigger on `anstellung` insert/`austritt`.
- There is no designed path for finding an existing `person` before creating a duplicate. The `person_select` policy hides a human who is employed only in another mandant, so HR in `reinigung` cannot see that the person already exists in `security` — which guarantees duplicates, and duplicates are exactly what defeats the cross-entity ArbZG aggregation (D-09 clause 1). Needed: a `security definer` existence probe keyed on normalised phone or (Nachname, Geburtsdatum) that returns "a person with these details already exists in the group; request a merge" and nothing else — no name, no entity, no employment.
- §16 says n8n "authenticates as a `system` principal against a named, permissioned endpoint, never with a shared secret that bypasses the pipeline" — but no credential mechanism is defined for a `system` principal, and §3.1 says `service_role` is used only by the migration/job runner. Either specify the mechanism (mTLS, a rotating scoped token in `system_zugang` with its own rate limit and audit events) or state that n8n only ever calls public webhook endpoints that create a queued item for human review.

## INVENTED RULES — must become TODO(client) (8)
- §14.5 marks `eingangsrechnung.freigeben_zur_zahlung` and `buchhaltung.buchung_freigeben` as `—` (never bindable) for `leitung`. SPEC §3 states the Leitung scope verbatim as "own business area only: employees, schedules, projects, orders, customers, tasks, **approvals**". Making a whole class of approvals structurally unreachable for the role SPEC gives approvals to is an invented segregation-of-duties rule. It may well be what the client wants — but it must be `// TODO(client): may a Leitung release an incoming invoice for payment and approve a booking within their own area, or is that reserved to Admin?`, not a `—` in a table.
- `rechnung.stornieren` is `—` for `leitung` and `○` for `admin`, i.e. Storno is effectively super_admin-reserved. Invariant 4 says correction is by reversing entry; it says nothing about who may issue one. Unsourced internal-control rule — needs a TODO(client).
- `berechtigung.bearbeiten`, `einstellungen.bearbeiten` and `benutzer.modul_zuweisen` are `—` (never bindable) for `admin`. SPEC §3 gives Super Admin "permission management" but nowhere states that an Admin may never be delegated it, and AUT-03 says permissions are "configurable per role per mandant, editable in the UI". Hard-coding these as unbindable is an invented governance rule; `benutzer.2fa_zuruecksetzen` is separately defensible (it would defeat AUT-02) and can stay, but the other three need a TODO(client).
- "This is why the platform requires at least two `super_admin` accounts to exist; a startup check warns when only one does." An invented operational governance requirement. The related TODO asks *who* the two holders are, which presupposes the answer. Reframe as `// TODO(client): how many super_admin accounts will exist, and what is the break-glass procedure if the sole holder loses both factor and recovery codes?`
- Security parameters chosen without a source and, unlike the session lifetimes and rate limits, not routed through `sicherheits_richtlinie` or a TODO: eight recovery codes; 7-day single-use invitation expiry; 5-minute OTP TTL; 3 verification attempts per issued code; `token_praefix` fixed at 8 characters; 15-minute session-idle semantics for `kunde`. Either put every one of them in `sicherheits_richtlinie` alongside the others, or mark them TODO(client).
- §7.3's fifth-mandant trigger automatically "creates its `nummernkreis` row". TEN-02 says *separate legal entities* get their own invoice number circle, and O-01 (is CSE Operations a GmbH or a department?) is explicitly open and explicitly blocks the invoice circle. Auto-creating a circle for every mandant row silently answers O-01 in the affirmative for every future area. The trigger should read a `mandant.ist_rechtstraeger` flag with `// TODO(client)` on its value for `operations`.
- §15.2 fixes several customer-visibility rules that SPEC does not state: customers see `festgeschrieben` invoices only and never drafts (defensible, but unsourced); Wachbuch and Bautagebuch are `○` (bindable) for customers — a Wachbuch is an incident record naming employees and third parties, and whether it may ever be shown to a customer is a legal question about employee data and §34a documentation, not a UI default; and the customer sees `leistungsnachweis` and `aufmass` "with the item snapshot as signed". Mark the Wachbuch and Bautagebuch rows `—` pending `// TODO(client)` rather than making them a toggle a manager can flip.
- §9's rule that a visible-but-unactionable record inside the active mandant returns 403 while cross-tenant returns 404 is correctly flagged as an assumption in the author's own list — but it is stated in the body as a "Deliberate decision" and must be written into DECISIONS.md as a numbered entry, since AUT-06's literal text ("403 confirms existence") can be read either way and a later reviewer will otherwise treat the 403 path as a bug.

## MINOR (16)
- §3.2 calls `benutzer.zwei_faktor_pflicht` "a generated column… Maintained by trigger" and §15.1 calls `benutzer.kunde_id` "a generated mirror". Postgres GENERATED columns must be immutable expressions over the same row and cannot reference another table. Both are trigger-maintained denormalisations. In a document that says its names are the contract, this will be copied literally into a migration that fails.
- §8.4 `app.is_readonly()` uses `coalesce(current_setting('app.readonly', true), 'on') = 'on'` while every sibling helper uses `nullif(…, '')`. An empty-string GUC therefore yields not-readonly — a fail-open path in the one helper the draft calls out as fail-closed. Use `coalesce(nullif(current_setting('app.readonly', true), ''), 'on') = 'on'`.
- §5.3 step 1 specifies "single indexed lookup; constant-time compare". A constant-time compare after an index probe on the hash is meaningless — the probe itself is not constant time, and the hash is the lookup key. Either drop the claim or state the real mitigation (the 32-byte token gives no timing-exploitable margin; the rate limiter is the control).
- §5.3 records the check-in as `akteur_art = 'system'` with no `benutzer_id`. A check-in is a human act, and the token resolves to `einsatz → anstellung → person`, so the actor is knowable. Recording it as `system` makes a worker's check-in indistinguishable from a cron job in the audit trail and weakens the §17 MiLoG / EMP-07 evidentiary record. Add `akteur_art = 'token'` and populate `person_id` from the einsatz.
- §12's check-in row reads "token invalidated after 5 failures". There are no per-token failures: an unknown hash names no token, so nothing can be invalidated. Separately, 20/h per IP will lock out a building site where ten workers share one connection or one carrier NAT. Rewrite as a per-`einsatz` attempt counter plus a global unknown-hash IP limit, and exempt known-good tokens from the IP dimension.
- `mitarbeiter_zugang.auth_user_id` duplicates `benutzer.auth_user_id`; §5.1's diagram shows both pointing at `auth.users`. Either they are the same value (a drift-prone denormalisation) or the person has two auth identities. Keep exactly one FK — on `benutzer` — and reach it through `benutzer.person_id`.
- `(portal)/mein` and `(portal)/kundenportal` sit outside `[mandant]`, deviating from CLAUDE.md's structure block ("`(portal)/[mandant]/` — tenant-scoped app — always under a mandant"). The deviation is justified — EMP-14 requires a cross-employment portal — but it changes a stated project structure and belongs in DECISIONS.md as an entry, not as an unremarked route group.
- §8.7 openly states RLS does not express per-module permissions, which is a partial deviation from AUT-05's literal wording ("RLS policies mirror application authorization"). The reasoning is sound; record it as a numbered DECISIONS.md entry so a later auditor reading AUT-05 does not treat the divergence as an omission.
- The §4.4 resolution table has no row for: slug is `gruppe`, `gruppen_modus` false, and the user has exactly *one* membership. DESIGN §6 rule 1 says a single-area user gets no switcher at all, so the answer is presumably 404 — but the table is presented as exhaustive and this case is reachable by a pasted link.
- `benutzer.telefon_zuruecksetzen` is `✔` for `admin` and `○` for `leitung`. Rebinding the phone is a complete takeover of an employee's only authentication factor, from which the holder can acknowledge a Dienstanweisung (SEC-06), raise or withdraw a `zeit_einwand` (EMP-07) and check in — destroying the evidentiary value EMP-07 exists to protect. Require a second approver or restrict to `super_admin`, and record old and new number in `vorher`/`nachher`.
- The customer and employee ceilings are opt-out: a table absent from the `rls.ts` map gets no restrictive policy and is therefore fully visible. The meta-test catches unclassified tables, but the *default* should be deny — apply a blanket `as restrictive for all using (app.portal() = 'intern')` to every table, then opt tables in for `mitarbeiter`/`kunde` explicitly. A forgotten opt-in is then a missing feature, not a leak.
- Per-user `benutzer_mandant_modul` changes are user-scoped but the cache key is `(benutzer_id, mandant_id, mandant.berechtigung_version)` with a 60s TTL. Unless a module grant bumps the mandant-wide version (which the text does not say — it says the trigger fires "on any binding change"), a revoked module stays live for up to 60 seconds, contradicting the claim that a change "takes effect on the next request". State that `benutzer_mandant_modul` and `benutzer_mandant` writes bump the version too.
- `benutzer_mandant_modul.modul` is free text with no FK or CHECK against the module list, and `berechtigung.bindbar_fuer text[]` holds role codes with no FK to `rolle.code`. A typo in either silently grants nothing (or, in `bindbar_fuer`, silently widens). Add a `modul` reference table (or a CHECK against the enumerated 38) and a trigger validating `bindbar_fuer` elements against `rolle.code`.
- `person.erst_mandant_id` is a tenant-scoping column that does not match the `mandant_id` name the §10.3 meta-test greps for, so `person` would slip past the RLS meta-test on the column check. Either name it `mandant_id` (and classify `person` as Class P explicitly so the test knows it is intentional) or widen the meta-test to any column ending in `_mandant_id`.
- Column types are unstated for several fields the document does specify by name: `mfa_recovery_code.verwendet_am`, `sperre.gesetzt_von`, `auth_versuch.ergebnis`, `checkin_token.erstellt_von`, `kunde_zugang.*` timestamps. All the time-valued ones must be `timestamptz` per invariant 2; say so, since the document is the contract.
- §5.2 asserts `stundenkonto` "remains per employment (EMP-15); the combined view is a read across the person's employments and computes nothing". Correct per invariant 6 — but the combined view is exactly a cross-mandant read of an anstellung-hung table, so it depends on the same cross-entity read mechanism that §8.5 forbids. It works only because the reader is the person themselves; state that dependency explicitly so it is not implemented as a generic cross-tenant query.
