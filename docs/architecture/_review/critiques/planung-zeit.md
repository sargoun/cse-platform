# Adversarial review — planung-zeit

## BLOCKING (16)

### B1. No RLS policy in the entire domain carries a permission or role predicate. §0.2 defines app.hat_recht(text) and then never uses it: every table's SELECT policy is `USING (mandant_id = ANY (app.current_mandanten())) TO authenticated`. Every authenticated user attached to a mandant — including role `kunde` (AUT-01) and every `mitarbeiter` — can therefore SELECT einsatz, einsatz_zuordnung, zeiteintrag, zeiteintrag_korrektur, zeit_einwand, medien and arbeitszeit_verstoss for every colleague in that tenant. The `OR person_id = app.current_person()` self-read disjuncts are additive to an already tenant-wide read, so they widen nothing and restrict nothing.

**Why it breaks:** Directly violates AUT-05 ('RLS policies mirror application authorization'), SEC-A2, and EMP-13 ('Employees never see ... other employees' data'). A customer login in mandant `reinigung` reads the full §17 MiLoG hour records of every cleaner; a cleaner reads every colleague's ArbZG findings and objections. §0.5's claim that 'the employee self-read policies cannot leak a rate' is true but irrelevant — the leak is everyone else's hours, geo points, no-show flags and ArbZG breaches.

**Required fix:** Every policy predicate becomes `mandant_id = ANY (app.current_mandanten()) AND app.hat_recht('<zeit.einsatz.lesen|zeit.eintrag.lesen|zeit.verstoss.lesen>')`, with the self-read disjunct as the ONLY path for a user without that right: `OR person_id = app.current_person()`. Add a tenant-isolation test per role, not only per mandant (SEC-A3 currently tests A-vs-B, not kunde-vs-employee-data).

### B2. arbeitszeit_verstoss is specified to be written 'once per involved mandant' (§3, §4, and the Phase 5 acceptance test), but its RLS is the standard §0.2 shape with `INSERT ... WITH CHECK (mandant_id = app.current_mandant())`. The live detector runs inside the transaction that assigns the shift in mandant A and therefore cannot insert the mirror finding for mandant B.

**Why it breaks:** The flagship TIM-14 / D-09 consequence 1 requirement is unimplementable as designed: the ROADMAP Phase 5 acceptance test ('6h reinigung + 5h security must trigger a breach in BOTH mandanten') fails, or the service silently bypasses RLS, which reintroduces exactly the leak §4 was built to prevent.

**Required fix:** Write findings through a dedicated SECURITY DEFINER function `app.arbzg_befund_schreiben(...)` owned by the same role that owns arbeitszeit_fenster, which is the only writer of arbeitszeit_verstoss (no INSERT policy for `authenticated` at all), and which asserts that the caller was entitled to the person in the active mandant before writing the mirror row. Reads stay under the tenant + permission predicate.

### B3. arbeitszeit_fenster holds a plan row (quelle='einsatz', from einsatz_zuordnung) AND an actual row (quelle='zeiteintrag') for the same worked shift, and nothing ever deactivates the plan row when the actual arrives — §3 says `aktiv` goes false only when the source is 'cancelled, removed or superseded'. The reader function of §4 deliberately strips quelle_id and, for foreign tenants, all ids.

**Why it breaks:** The ArbZG detector sums plan and actual for the same shift: a single 6h shift becomes 12h. Suppressing that by heuristic overlap is impossible for foreign-tenant windows, because a plan/actual pair from mandant B is indistinguishable from two genuine back-to-back shifts. So the TIM-14/LEG-03 check is systematically wrong in both directions — false breaches inside the tenant, and no reliable cross-entity aggregation, which is the one thing §4 exists to guarantee.

**Required fix:** Give arbeitszeit_fenster a `zuordnung_quelle_id uuid` (the einsatz_zuordnung the row derives from, on both plan and actual rows) and make trg_fenster_ist_projizieren set the matching plan row's `aktiv = false` in the same statement — actual supersedes plan, one window per assignment. Return a stable opaque `fenster_gruppe` (hash of the assignment id) from the reader so the detector can deduplicate foreign windows without learning a source id. Add a test: one person, one shift, both plan and actual present → exactly one window returned.

### B4. §0.2 applies `FORCE ROW LEVEL SECURITY` to every table in the domain except arbeitszeit_fenster, and all policies are granted `TO authenticated`. The unauthenticated paths (checkin_einloesen(), offline_ereignis_annehmen()) run as SECURITY DEFINER under some owner role that is not `authenticated` and for which no policy exists.

**Why it breaks:** Under FORCE RLS the table owner is subject to policies too, and a role with no applicable policy gets zero rows on SELECT and a policy violation on INSERT/UPDATE. The entire TIM-07 check-in path, the TIM-09 offline ingestion path and the checkin_token compare-and-set of §7 cannot execute. This is the kind of failure that only appears when the first worker taps the link.

**Required fix:** Name the owning role explicitly (e.g. `zeit_definer`), and either (a) add policies `TO zeit_definer` on checkin_token, zeiteintrag, offline_queue_eintrag and medien expressing exactly what the definer functions may write, or (b) grant that role BYPASSRLS and drop FORCE on those three tables — and state which, because 'excluded from the PostgREST schema' is not a mechanism for a table in `public` (Supabase exposes the whole exposed schema; the table must live in a non-exposed schema such as `zeit_intern`).

### B5. `CREATE VIEW zeiteintrag_monatsanteil` in §5.2 is declared without `WITH (security_invoker = true)`.

**Why it breaks:** A Postgres view runs with the view owner's permissions by default, so RLS on zeiteintrag is bypassed for anyone granted SELECT on the view. The view exposes mandant_id, anstellung_id, person_id, auftrag_id and minutes for every time entry in all four entities — a full cross-tenant leak of the exact data D-09 §6 and SEC-A3 forbid, through the very ambient-readable-relation mechanism §4 spends five paragraphs arguing against.

**Required fix:** `CREATE VIEW zeiteintrag_monatsanteil WITH (security_invoker = true) AS ...` and add it to the SEC-A3 tenant-isolation suite (a reinigung user selecting from the view must see zero security rows). Same rule for any future view in this domain.

### B6. app.arbeitszeit_fenster_lesen is declared `STABLE SECURITY DEFINER`, while §4 states 'Calls that return a foreign-tenant window are written to audit_log (SEC-A9, LEG-09 accountability)'.

**Why it breaks:** Postgres refuses data-modifying statements inside a non-VOLATILE function ('INSERT is not allowed in a non-volatile function'). Either the function errors at exactly the moment it returns a cross-tenant window — breaking TIM-14 detection — or the audit write is silently dropped and the one accountability control over cross-entity personal-data access does not exist, contrary to SEC-A9 and the LEG-09 processing record.

**Required fix:** Declare the function VOLATILE (it is a leaf, so no plan-inlining benefit is lost) and write the audit row via a small SECURITY DEFINER logging function, capturing caller benutzer, subject person_id, window bounds, and how many foreign-tenant rows were returned. Add a test asserting an audit_log row per cross-tenant call.

### B7. A correction mints a new zeiteintrag version that keeps the original `beginn_utc`, and zeiteintrag_monatsanteil selects rows with `ersetzt_am IS NULL`. There is no column that books a correction into a later period; `gesperrt_am` is only a marker on the superseded row.

**Why it breaks:** EMP-04 is categorical — 'a locked month never changes; corrections flow into the next month — exactly like invoices' — and the ROADMAP Phase 5 acceptance test is 'a locked stundenkonto month cannot change'. As designed, correcting a March entry in May changes March's total retroactively, after the month was locked, after the payroll export (ACC-12) went out, and after any invoice built on those hours (FIN-07) was finalised.

**Required fix:** Add `wirkungs_monat date NOT NULL` (Berlin month the entry counts into) to zeiteintrag, defaulted from beginn_utc but forced by trg_korrektur_kette_pruefen to the first unlocked month when the origin's month is locked; make zeiteintrag_monatsanteil and the stundenkonto aggregate on `wirkungs_monat` for locked periods and on the instants for open ones. Add a test: lock March, correct a March entry, assert March total unchanged and the delta lands in the next open month.

### B8. The assignment hard block (trg_qualifikation_hart_pruefen) validates `nachweis` rows against einsatz.erforderliche_qualifikation_ids only. Nothing checks bewacher_eintrag (SEC-03: Bewacher-ID and registration status), and the check runs once, at assignment time, over an eight-week planning horizon.

**Why it breaks:** LEG-04 names '§34a GewO + Bewacherregister — enforced at assignment', not '§34a certificates only'. A guard whose Bewacherregister registration is absent, suspended or withdrawn passes every check in this schema. And because the check is only evaluated at INSERT/UPDATE of the assignment, a certificate that is valid today and expires in three weeks leaves a materialised shift in week six that no longer satisfies SEC-04 — the frozen `nachweis_pruefung` snapshot actively documents that the check passed against stale facts.

**Required fix:** Extend the trigger and the service check to require an active bewacher_eintrag for the mandant's security posts (behind an interface, with `// TODO(client): which Bewacherregister statuses count as assignable?` if the status vocabulary is not confirmed). Add a nightly re-validation job over all future assignments that writes a conflict row (see the missing `konflikt`/qualification-lapse record) and notifies the planner — the 60/30/7-day certificate watchdog notifies the person, not the roster.

### B9. §8 sets retention as 'shift date + 2 years', extended on billing to 'invoice date + 10 years'. Neither clock start is in SPEC and neither is marked TODO(client) in the schema (O-20 asks only which fields get anonymised).

**Why it breaks:** §147 Abs. 3 AO runs its ten-year period from the END OF THE CALENDAR YEAR in which the document arose, not from the document date. 'Invoice date + 10 years' under-retains by up to eleven months on every record, and the purge job's predicate `now()::date > aufbewahren_bis AND NOT loeschsperre` will act on that wrong date. For a GoBD-relevant record (LEG-01, ACC-06 '10-year retention, deletion impossible') this is a compliance defect, and it is exactly the class of silently-invented legal rule CLAUDE.md forbids.

**Required fix:** Compute the GoBD deadline as `make_date(extract(year from <belegdatum>)::int, 12, 31) + interval '10 years'` behind a tested function in server/services/, and mark the MiLoG clock start `// TODO(client): does the §17 MiLoG two-year period run from the shift date, the date the record was created, or the end of the month?` with an entry in DECISIONS.md Open.

### B10. §7 writes the device-claimed instant into the authoritative `zeiteintrag.beginn_utc` for offline submissions (with zeitquelle='geraet_behauptet', nacherfasst=true, status='zu_pruefen'), even though the table already carries `behauptete_zeit_beginn` for that value. dauer_brutto_minuten / dauer_netto_minuten are then computed from a client-supplied number.

**Why it breaks:** Invariant 5 is absolute: 'Server clock is the source of truth for time entries. Device time is stored separately ... Never trust a client timestamp.' The mitigation rests entirely on `status='zu_pruefen'`/`'freigegeben'` — values the draft itself marks provisional pending O-19. If the client answers O-19 with 'no release step', an unreviewed device-claimed duration flows straight into the §17 MiLoG record, the Stundenkonto (EMP-04) and, via FIN-07, into an invoice line.

**Required fix:** Keep `beginn_utc`/`ende_utc` server-derived at all times (for a pure offline entry, leave them NULL until a human decides). Carry the claim only in behauptete_zeit_*, and require a zeiteintrag_korrektur (art='nacherfassung', a named benutzer, a Begründung) to promote a claim into the authoritative columns. Then the billing and Stundenkonto paths need no dependence on a provisional enum value, and invariant 5 holds regardless of how O-19 is answered.

### B11. zeit_einwand's INSERT policy is described as 'allowing person_id = app.current_person() with mandant_id derived server-side'. An RLS WITH CHECK cannot derive anything, and nothing in the stated predicate binds the referenced zeiteintrag_id / einsatz_id / anstellung_id to the inserting person.

**Why it breaks:** Two failures. (1) A worker can insert an objection — and, through medien.zeit_einwand_id, a photo — against a colleague's time record in their own mandant, which lands in the planner's inbox and can drive a zeiteintrag_korrektur on someone else's MiLoG record (EMP-07, EMP-13). (2) The write requires `mandant_id = app.current_mandant()`, i.e. exactly one active mandant (invariant 10), but EMP-14 gives one login per person showing shifts across employments in a combined view; the design never says how a portal user selects the active mandant for the one write they are allowed. As written, an employee with two employments cannot legitimately file an objection about the other entity's shift.

**Required fix:** WITH CHECK must be `person_id = app.current_person() AND mandant_id = app.current_mandant() AND EXISTS (SELECT 1 FROM anstellung a WHERE a.id = anstellung_id AND a.person_id = app.current_person() AND a.mandant_id = mandant_id) AND (zeiteintrag_id IS NULL OR EXISTS (SELECT 1 FROM zeiteintrag z WHERE z.id = zeiteintrag_id AND z.person_id = app.current_person())) AND (einsatz_id IS NULL OR EXISTS (SELECT 1 FROM einsatz_zuordnung ez WHERE ez.einsatz_id = einsatz_id AND ez.person_id = app.current_person() AND ez.entfernt_am IS NULL))`. Specify that the portal sets the active mandant from the entity label of the shift being objected to (EMP-14 already labels each shift with its entity), and test it from a two-employment account.

### B12. checkin_token.gueltig_ab/gueltig_bis are computed by `trg_token_fenster_ableiten` BEFORE INSERT only. trg_token_widerrufen fires on einsatz cancellation and assignment removal, but nothing reacts to a change of einsatz.beginn_geplant / ende_geplant — and trg_einsatz_unveraenderlich_nach_ist freezes those columns only once a zeiteintrag already exists, so moving a not-yet-worked shift is expressly allowed.

**Why it breaks:** After a planner moves tomorrow's shift by two hours, the outstanding token still carries yesterday's window. TIM-07 ('token valid within shift window ±1h') is violated in both directions: the worker cannot stamp in at the real shift time, so no §17 MiLoG record is created (the 'shift ended, no zeiteintrag' watchdog fires for a shift that was worked), or a token is accepted during a window in which no shift exists.

**Required fix:** Make the derivation an AFTER UPDATE OF (beginn_geplant, ende_geplant) trigger on einsatz that recomputes gueltig_ab/gueltig_bis for all live tokens of that shift (or revokes and re-issues them, which also re-sends the link). Add gueltig_ab/gueltig_bis to the token-immutability whitelist for that path only, and test 'move shift → present old link' → rejected, 'move shift → present re-issued link at the new time' → accepted.

### B13. offline_queue_eintrag.mandant_id is `uuid NOT NULL` and is documented as 'resolved server-side from the token', while the same table defines ablehnung_grund values 'token_ungueltig' and 'bereits_eingeloest' and states that 'a malformed or expired submission is still recorded, and only then rejected'.

**Why it breaks:** When the token is invalid there is no token row, hence no mandant to resolve, hence the row cannot be inserted at all. The submissions that cannot be stored are precisely the disputed ones — a worker claiming they stamped in with a link that had been revoked. TIM-09 requires the claimed time to be recorded, and LEG-02 / a wage dispute needs the rejected claim as evidence.

**Required fix:** Make mandant_id nullable with `CHECK (mandant_id IS NOT NULL OR status = 'abgelehnt')`, keep the UNIQUE idempotency key as `(client_ereignis_id)` globally (or `(geraet_id, client_ereignis_id)`) rather than `(mandant_id, client_ereignis_id)` so unresolved rows still deduplicate, and give the unresolved rows their own RLS: they belong to no tenant and must be readable only through an admin/definer path.

### B14. §4's detector is specified to run 'nightly over a rolling window', but the only data path — app.arbeitszeit_fenster_lesen — begins with `v_mandant uuid := app.current_mandant()`, which raises unless exactly one mandant is active, and then requires `app.current_person() = p_person_id OR app.hat_recht('zeit.planen')`.

**Why it breaks:** A Supabase cron job has neither an active mandant nor a benutzer with a permission, so the nightly cross-entity detector cannot execute at all. The nightly run is the only mechanism by which a change in entity A surfaces in entity B's plan without A knowing B exists — without it, TIM-14 degrades to whatever the live path happens to catch.

**Required fix:** Define a second, job-only entry point (`app.arbzg_fenster_lesen_system(p_person_id, p_von, p_bis)`) executable solely by the job role, with no mandant requirement, no 35-day clamp, and an audit_log row per invocation; document in DECISIONS.md that this role exists, what it can read, and that it is not reachable from any HTTP route. Have the job iterate persons from `anstellung`, not from a tenant session.

### B15. Live ArbZG detection is specified to run 'inside the transaction that creates or moves an assignment', with no serialisation across sessions. The generator takes pg_advisory_xact_lock for its own idempotency, but nothing locks the person.

**Why it breaks:** The exact case TIM-14 exists for — one person, two entities — is the concurrent case: a reinigung planner and a security planner assigning the same person at the same moment. Both transactions read arbeitszeit_fenster before the other's AFTER trigger commits, both find 6h resp. 5h, neither detects the 11h breach, and both commit. The plan then looks clean until the nightly run, and if the nightly run is the one that has no session (see the preceding finding), never.

**Required fix:** Take `pg_advisory_xact_lock(hashtext('arbzg:' || person_id))` at the start of any transaction that inserts or updates einsatz_zuordnung or zeiteintrag for that person, before reading the projection. Add a concurrency test: two parallel transactions in two mandanten for one person must produce exactly one detected breach, not zero.

### B16. zeiteintrag's constraint list contains `CHECK (einsatz_id IS NOT NULL OR auftrag_id IS NOT NULL OR NOT abrechenbar_flag)` — the column `abrechenbar_flag` does not exist on zeiteintrag (only einsatz and planungsserie carry `abrechenbar`).

**Why it breaks:** The migration fails to apply. The parenthetical fallback ('implemented as CHECK (einsatz_id IS NOT NULL OR auftrag_id IS NOT NULL) with a documented exception list') is also a different rule from the one written, and it forecloses O-27 (internal work, training, Bereitschaft) by constraint rather than by an interface.

**Required fix:** Drop the constraint until O-27 is answered; enforce billability in the tested service that builds invoice lines (FIN-07/FIN-18), where an unbillable internal entry is a legitimate row. If a DB-level guard is wanted now, add an explicit `abrechenbar boolean NOT NULL DEFAULT true` to zeiteintrag and write the CHECK against it, with `// TODO(client): are Einsätze planned with no auftrag, and how are those hours costed?`

## MISSING (16)
- TIM-05 names three conflict classes — overlap, missing qualification, ArbZG breaches — but the only finding table is arbeitszeit_verstoss and its `regel` column is the `arbzg_regel` enum, which has no value for a double-booking. There is nowhere to record 'this person is assigned to two overlapping einsätze' (same mandant or across entities), and nowhere to record 'the qualification this assignment relied on has lapsed since'. Needs either a `regel`-neutral `planungs_konflikt` table (art: ueberschneidung · qualifikation_abgelaufen · arbzg) or extra enum values plus the detector rules that write them.
- No re-validation path for SEC-04/LEG-04 over the eight-week horizon: the hard block is a BEFORE INSERT/UPDATE trigger on einsatz_zuordnung, so a certificate expiring between assignment and shift date is never re-examined. The SPEC §14 watchdog ('Certificate expiring in 60/30/7 days') notifies the person; nothing flags the affected future assignments.
- No constraint or detection preventing two simultaneously open zeiteintrag rows for one anstellung. Add `UNIQUE (anstellung_id) WHERE ende_utc IS NULL AND storniert_am IS NULL AND ersetzt_am IS NULL` (within a tenant this is a genuine impossibility, not a legitimate duplicate), and make the cross-entity case a detected conflict since it cannot be constrained. Without it DSH-05 'currently working' double-counts and the check-in path can strand two open records.
- No index supports EMP-02/EMP-14 'my shifts next week across all employments'. einsatz_zuordnung has (person_id, einsatz_id) but carries no time column, and every einsatz index is prefixed with mandant_id, which the cross-entity personal query cannot supply. The query degenerates to fetching all of a person's assignments ever and joining. Either denormalise `beginn_geplant` (or plan_datum) onto einsatz_zuordnung with an index on (person_id, beginn_geplant) WHERE entfernt_am IS NULL, or add a bare (beginn_geplant) index on einsatz.
- zeiteintrag does not inherit revier_id, posten_id or projekt_id — trg_auftrag_erben copies only auftrag_id, auftrag_leistung_id and objekt_id. CLN-01 (Reviere with target minutes) cannot compare target against actual, SEC-01 cannot report hours per Posten, and BAU-07 (Mannstunden per trade in the Bautagebuch) has no source for unplanned time where einsatz_id is NULL.
- No change history for einsatz. zeiteintrag gets a full immutable version chain, but a planner can move or restaff a future shift with only geaendert_am to show for it. NOT-01 requires a 'schedule change' notification (which needs a before/after), and a wage dispute about a shift that was moved twice has no record. The domain asserts audit_log exists but specifies no trigger, no payload and no retention for einsatz/einsatz_zuordnung changes.
- No retention or erasure rule for the personal data outside zeiteintrag: medien has no aufbewahren_bis and no DOC-01 category despite DOC-07 ('retention rules per category'); checkin_token.ip_adresse, offline_queue_eintrag.ip_adresse / user_agent / geraet_id, and zeiteintrag_korrektur.ip_adresse have no deletion horizon at all. LEG-09's deletion concept cannot be written against this schema.
- §17 Abs. 1 MiLoG requires the record to be created by the end of the seventh calendar day following the work. Nothing stores or measures that deadline: nacherfassung_verzoegerung_sek exists but no rule reads it, and O-26 asks the client to name an acceptance threshold without noting that a statutory ceiling constrains the answer. Needs a derived 'aufzeichnungsfrist_verletzt' finding plus `// TODO(client)` on the internal threshold below the statutory maximum.
- Nothing drives which Bundesland's holidays apply. feiertag is keyed (bundesland, datum) and the draft anticipates Brandenburg work, but neither objekt nor planungsserie carries a bundesland and generator step 3 hard-codes `bundesland = 'BE'`. Either add bundesland to the series (defaulting from the objekt) or state that the objekt domain must supply it.
- The §3 ArbZG Ausgleichszeitraum rule ('ausgleichszeitraum_ueberschritten') is declared in the enum but is uncomputable: the only data path, app.arbeitszeit_fenster_lesen, refuses any window longer than 35 days, while the compensation period is six months / 24 weeks (O-16). Either the system entry point of the nightly job carries no clamp, or the rule must be removed from the enum until it has a data path.
- SPEC §22 lists `turnus` (CLN-02) as a distinct entity alongside `planungsserie`; the draft folds one into the other without recording the decision, and §22's `reklamation` and `qualitaetspruefung` — in the same data-model block as planungsserie/einsatz/zeiteintrag/checkin_token/medien — are neither designed here nor delegated to a named domain.
- CAL-01/CAL-02/CAL-03: einsätze must appear in the central calendar and in a per-user read-only iCal feed. There is no read path for a cross-employment personal feed, and an iCal URL is an unauthenticated bearer-token read of exactly the data checkin_token guards so carefully — the same token discipline (hash-only storage, revocation, definer function) has to be specified for it or the domain leaks a person's whole roster to anyone with the URL.
- §9 ArbZG Sonn- und Feiertagsruhe is named in the feiertag table notes as a detector input, but arbzg_regel has no corresponding value and no detection is described. Either implement it or drop the claim (SPEC TIM-06 lists only >8h/10h, <11h rest, missing breaks).
- The 11-hour rest lookback index is `(person_id, ende_utc) WHERE aktiv AND ende_utc IS NOT NULL`, which excludes running entries — a worker still stamped in from yesterday is invisible to the rest check, and the detector's interval arithmetic over a NULL end is never specified (treat as open-ended, clamp to now, or exclude?).
- The roles and grants that make §4 work are never defined: `arbzg_owner` is named once, the definer functions' owner is unnamed, the job role is unnamed, and 'excluded from the PostgREST schema' is not an operation available for a table in `public` under Supabase. Phase 1 cannot implement the session helpers without this being explicit (which schema the tables live in, which roles hold EXECUTE, which have BYPASSRLS).
- SEC-01 requires posts with required qualifications AND minimum staffing, but soll_besetzung is a single integer and erforderliche_qualifikation_ids applies to the shift as a whole. '3 guards, of whom 1 with Sachkunde §34a' is unrepresentable, so the unstaffed-shift watchdog and REC-01's staffing requirement cannot distinguish 'unstaffed' from 'staffed by the wrong qualification mix'.

## INVENTED RULES — must become TODO(client) (8)
- §147 AO retention computed as 'invoice date + 10 years' (§8). The statutory period runs from the end of the calendar year in which the record arose. A concrete legal computation the SPEC does not state, not marked TODO(client), and wrong in a direction that under-retains.
- The §17 MiLoG two-year clock is silently anchored to the shift's Berlin calendar date (`aufbewahren_bis` default). Declared in the assumptions list but not marked `// TODO(client)` in the schema and not in the open-questions list — O-20 asks only what gets anonymised afterwards, not when the clock starts.
- O-06 (Betriebsrat) is treated as gating geolocation alone. zeitabweichung_beginn/ende_sek, geraet_id device fingerprinting, zuordnung_status='nicht_erschienen', the (durchgefuehrt_von, durchgefuehrt_am) 'who corrects a lot' index and the APR-08-style analysis are Verhaltens- und Leistungskontrolle under §87 Abs. 1 Nr. 6 BetrVG and §26 BDSG just as much as a GPS point. Deciding that only geolocation needs the Betriebsrat is an unflagged legal rule; the O-06 question must be widened, or each of these gated by its own configuration flag defaulting off.
- The fall-back ambiguity is resolved to the earlier (CEST) instant, which systematically produces the longer, better-paid duration. The pay treatment is correctly deferred to O-23, but the choice of instant IS the pay rule — it decides 9h vs 8h — so it should carry `// TODO(client)` at the materialiser, not only a note that the consequence is open.
- The TIM-07 ±1h window is applied unchanged to the checkout token (gueltig_bis = ende_geplant + 1h). SPEC says the token is valid within the shift window ±1h; extending that verbatim to checkout invents the operational rule that a worker who stays 90 minutes past the planned end cannot close their own record. Flag it and name the fallback (planner correction with zeitquelle='planer_eingabe').
- `begruendung` length ≥ 10 and zeit_einwand.text length ≥ 5 are invented validation rules that reject legitimate short reasons ('Krank', 'Grip', an Arabic or Turkish equivalent) — and EMP-12 makes multilingual short text likely. Require non-empty and enforce quality in review, not by character count.
- planungsserie.feiertage_ueberspringen defaults to `true` for every trade. CLN-03 is a cleaning rule ('Berlin public holidays excluded automatically'); defaulting holiday-skipping on for security posts and construction series is a business rule the SPEC does not state. Default per trade from configuration, or make the column NOT NULL with no default so the planner must decide.
- zeiteintrag's billing index bakes the provisional status value 'freigegeben' into a partial index that the billing run depends on. If O-19 is answered 'no release step', the FIN-07/FIN-18 billing query silently returns zero hours instead of failing — the placeholder is load-bearing rather than swappable.

## MINOR (20)
- The SELECT policies use `mandant_id = ANY (app.current_mandanten())` unconditionally, so a multi-mandant user reads other entities' rows even while a single mandant is active. app.ist_gruppenansicht() is declared in §0.2 and then never used anywhere. Pin SELECT to the active mandant unless the session is explicitly in group view — otherwise a service-layer bug that forgets a tenant filter leaks across the user's whole readable set, which is precisely what invariant 3's 'second line of defence' is for.
- einsatz carries no anstellung_id; the costed link lives on einsatz_zuordnung. That satisfies the intent of D-09 and is the right shape for SEC-01 multi-staffing, but D-09's FK table explicitly lists `einsatz` under 'attaches to anstellung_id' and SPEC §22 has no einsatz_zuordnung entity. Per the definition of done this deviation belongs in DECISIONS.md, and it is absent from the assumptions list.
- `rrule ~ '^FREQ='` rejects valid RFC 5545 rules: the parts are unordered, so 'INTERVAL=2;FREQ=WEEKLY;BYDAY=MO,WE' is legal and fails the CHECK. Match `(^|;)FREQ=` or validate in the service with the same parser the generator uses.
- zeiteintrag.aufbewahren_bis is given a DEFAULT expression referencing beginn_utc. A column DEFAULT cannot reference another column in Postgres; only trg_aufbewahrung_setzen can do this. Remove the stated default so the DDL is applicable as written.
- quell_schluessel = 'manuell:<einsatz.id>' cannot be produced in the same INSERT as a DEFAULT gen_random_uuid() id. Either mint the uuid in the application or set the key in a BEFORE INSERT trigger.
- offline_queue_eintrag.nutzlast is described as the raw submitted event, 'byte-faithful', but jsonb reorders keys, drops duplicate keys and normalises numbers. If it is evidence, store the raw body as text or bytea plus a sha256, and keep jsonb only as a parsed convenience column.
- §7 states that any redemption failure 'increments versuche' — impossible when no token row matches the hash, which is the common brute-force case. AUT-07 rate limiting therefore needs an IP/route-level limiter that this domain does not describe.
- No CHECK binds erstellt_akteur_art to the actor columns. A row with akteur_art='benutzer' and erstellt_von NULL passes today. Add `CHECK ((erstellt_akteur_art = 'benutzer') = (erstellt_von IS NOT NULL))` on each table, and the analogous constraint on medien (akteur_art defaults to 'person_token' even for planner uploads, with hochgeladen_von_person_id and hochgeladen_von_benutzer_id both nullable and unconstrained).
- The generator's ON CONFLICT DO UPDATE ... WHERE clause silently skips occurrences that fail the guard (past shift, or a zeiteintrag already exists). A series edit that cannot be applied leaves the plan quietly out of sync with the pattern. Return the skipped keys from the job and record them on job_lauf so the planner sees 'series changed, 3 occurrences not updated'.
- arbeitszeit_verstoss.fingerprint includes zeitraum_beginn_utc/ende_utc, so shifting a shift by one minute mints a new finding while the old one stays 'offen' forever. Add a supersede step (set the previous finding 'hinfaellig' when its underlying windows change) or fingerprint on the person + rule + Berlin calendar day.
- zeiteintrag_monatsanteil filters storniert/ersetzt but not status, so 'zu_pruefen' rows (unreviewed offline claims) flow into EMP-04, EMP-06, ACC-12 and REP-04 — contradicting §7's statement that such an entry 'cannot be billed or booked into the Stundenkonto until a planner releases it'.
- There is a CHECK on zeitquelle_beginn ('geraet_behauptet' implies nacherfasst) but no mirror on zeitquelle_ende, so a device-claimed end can be laundered into an unflagged record while the start is clean.
- zeit_einwand.sprache is free text with a default of 'de' and no CHECK against the de/en/ar/tr set EMP-12 names.
- medien's parent CHECK is to be widened by four other domains (SEC-05 Wachbuch, BAU-03 Aufmaß, BAU-07 Bautagebuch, CLN-04 Leistungsnachweis), each ALTERing a table this domain owns. Real FKs are the right call, but say explicitly who owns the migration order and how the num_nonnulls CHECK is kept consistent, or give each parent its own link table.
- Invariant 5 names the column `zeitabweichung_sek`; zeiteintrag splits it into zeitabweichung_beginn_sek / _ende_sek (offline_queue_eintrag keeps the original name). Sensible, but record it in DECISIONS.md — a conformance check or reviewer looking for the invariant's literal column will not find it.
- checkin_token has no INSERT policy for anyone and the issuance path is never specified (ausgestellt_von / ausgestellt_von NULL 'when issued by the nightly dispatch job'), so it is unclear whether a planner issuing a link goes through a definer function too.
- Dispatching a check-in link by SMS or e-mail is an outbound message. Invariant 7 routes external sends through server/agent/policy.ts; the domain never says whether transactional worker notifications are in or out of that gate. State it (and note that §7 UWG does not apply, since this is not advertising) in DECISIONS.md.
- DESIGN.md §'Status pills' declares a fixed vocabulary. The domain introduces roughly a dozen states with no pill mapping — storniert, ersetzt, nicht_erschienen, zurueckgezogen, quittiert, hinfaellig, dupliziert, manuelle_pruefung, laufend, freigegeben, zu_pruefen, abgesagt. CLAUDE.md requires DESIGN.md to be extended first, then used; the domain should list the states the UI will need so DESIGN.md can be amended before Phase 5.
- §3's einsatz notes say trg_besetzung_zaehlen is 'AFTER INSERT/UPDATE/DELETE on einsatz_zuordnung' while listed under einsatz's own triggers, and einsatz_zuordnung has no DELETE path at all (invariant 8, entfernt_am instead) — so the DELETE branch is dead and the UPDATE branch must key on entfernt_am. Reconcile, and specify that the nightly reconciliation reports drift rather than silently repairing it, as arbeitszeit_fenster does.
- The 35-day clamp in the reader function is presented as a technical bound, but it is also the reason the Ausgleichszeitraum rule cannot run and the reason a planner cannot see a rest-period conflict spanning a month boundary at the extremes. Document its interaction with the rules that need longer windows rather than only its anti-extraction purpose.
