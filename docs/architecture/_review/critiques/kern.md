# Adversarial review — kern

## BLOCKING (19)

### B1. `anstellung_sicht` is defined as `select a.*, case when ... then a.stundesatz_intern end as stundesatz_intern_sichtbar from anstellung a` — `a.*` already contains the raw `stundesatz_intern` column. The view hands out the wage rate in the clear and then adds a second, masked copy of it beside it.

**Why it breaks:** D-09 §6 and SPEC §22 ("a cleaning manager must not see security wage rates") plus invariant 3's within-entity half. Any `leitung` without `personal.entgelt_lesen` runs `select * from anstellung_sicht` and reads every internal hourly cost of their own entity. The same defect is in `person_sicht`, which is described as masking `geburtsdatum`/`geburtsort`/`staatsangehoerigkeit` but is built on the same pattern.

**Required fix:** Never use `*` in a masking view. Enumerate the columns explicitly and omit `stundesatz_intern` and `tarifgruppe` from the projection entirely, exposing only the `case`-guarded expression under the real column name: `select a.id, a.person_id, a.mandant_id, a.personalnummer, ..., case when app.hat_berechtigung('personal.entgelt_lesen') or a.person_id = app.aktuelle_person() then a.stundesatz_intern end as stundesatz_intern from anstellung a`.

### B2. The whole column-masking mechanism cannot work as specified. The draft revokes `SELECT` on `anstellung`/`person` from `authenticated` and then reads through views declared `with (security_barrier, security_invoker = true)`. With `security_invoker = true` Postgres checks base-table privileges as the *caller*, who has just had them revoked. Verified on PostgreSQL 16: `set role authenticated; select * from anstellung_sicht;` → `ERROR: permission denied for table anstellung`. The obvious repair — dropping `security_invoker` so the view runs as its owner — is worse: also verified, a definer view owned by a `BYPASSRLS` role (which is what `postgres` is in Supabase, and migrations create objects as `postgres`) returned **all** rows of a FORCE-RLS table with a restrictive tenant policy (2 of 2 rows, policy ignored).

**Why it breaks:** Branch one makes `person` and `anstellung` unreadable to every application user — the personnel module does not load at all. Branch two silently disables the tenant predicate on exactly the two tables D-09 §6 and SEC-A2/SEC-A3 depend on: every user reads every mandant's employments including security wage rates. There is no third branch in the draft.

**Required fix:** Drop the masking views and use column-level privileges, which compose correctly with RLS. Verified working on PG 16: keep `SELECT` revoked on the whole table, then `GRANT SELECT (id, person_id, mandant_id, personalnummer, eintritt, austritt, status, ...) ON anstellung TO authenticated` omitting `stundesatz_intern`/`tarifgruppe`; the row policy still filtered to the caller's mandant and `select stundesatz_intern` returned `permission denied`. Expose the wage rate through a narrow `SECURITY DEFINER` function `app.entgelt_lesen(anstellung_id)` that re-checks `personal.entgelt_lesen` and `mandant_id = app.aktiver_mandant()`. If any view is kept, it must be `security_invoker = true` and the base table must carry column grants, never a definer view under a `BYPASSRLS` owner.

### B3. `create policy person_select on person for select using (app.person_sichtbar(id))` carries no permission predicate at all — unlike every other table, which requires `app.hat_berechtigung('<modul>.lesen')`.

**Why it breaks:** Every authenticated account with a `benutzer_mandant` row for the active mandant — including `mitarbeiter` and, critically, `kunde` (customer-portal logins, AUT-01) — can read the complete staff directory of that entity: name, private address, phone, mobile, email, emergency contact, and (subject to the broken `person_sicht`) date and place of birth and nationality. That is EMP-13 ("employees never see other employees' data"), AUT-01's Mitarbeiter/Kunde scope, and DSGVO data minimisation (LEG-09) in one policy.

**Required fix:** `using (app.person_sichtbar(id) and (app.hat_berechtigung('personal.lesen') or id = app.aktuelle_person() or exists (select 1 from anstellung a join anstellung b on a.person_id = person.id and b.person_id = app.aktuelle_person() and a.vorgesetzter_anstellung_id = b.id)))`. Customer roles must never receive `personal.lesen` in the seed matrix, and the seed `rolle_berechtigung` rows for `kunde` and `mitarbeiter` must be listed explicitly in the document so this is testable.

### B4. The cross-entity ArbZG aggregation (TIM-14, LEG-03, D-09 consequences 1 and 2) is made impossible by the RLS the draft specifies. `anstellung` is `mandant_id = app.aktiver_mandant()` and the document celebrates this: "ein Reinigungsleiter … sieht damit keine einzige Security-Anstellung". A cleaning planner therefore cannot see that the same `person` also has a security employment, and the 6h + 5h = 11h breach — the acceptance criterion in ROADMAP Phase 5 and the worked example in SPEC §19 — cannot be computed. `anstellung_person_idx ON (person_id, mandant_id)` is named "der ArbZG-Aggregationspfad" but no caller can use it.

**Why it breaks:** LEG-03/ArbZG, TIM-05, TIM-06, TIM-14 and D-09 consequences 1 and 2. The check silently returns "no conflict" instead of failing loudly — the exact silent, late-discovered failure mode the invariants exist to prevent.

**Required fix:** Design and name the escape hatch in this document, because it is the only legitimate crack in the tenant wall and it must be auditable. Add a `SECURITY DEFINER` function owned by a privileged role, e.g. `app.arbzg_belastung(p_person uuid, p_von timestamptz, p_bis timestamptz) returns table (tag date, minuten integer, ruhe_luecke_minuten integer)` that returns **only aggregate minutes and rest gaps** — never `mandant_id`, never `objekt`, never `stundesatz_intern`, never the other entity's identity — and only for a person the caller can already see via `app.person_sichtbar`. State in the document that every call is written to `audit_log` with `aktion = 'arbzg.aggregat_gelesen'`, and that the service `server/services/arbzg.ts` is the only caller. Add a test that a reinigung planner gets the breach and gets zero fields identifying the security shift.

### B5. `app.hat_berechtigung()` returns false for every key in the group view, so the group view is empty. The function's only granting branch is an `exists` over `benutzer_mandant` filtered by `bm.mandant_id = app.aktiver_mandant()`, and `app.aktiver_mandant()` is NULL in the group view by the table's own `CHECK ((ansicht = 'mandant') = (aktiver_mandant_id IS NOT NULL))`. The prose claims group keys "werden gegen irgendeine Mandantenzuordnung geprüft", but the function body contains no such branch — and every `T_select` group disjunct is gated on `app.hat_berechtigung('gruppe.lesen')`.

**Why it breaks:** TEN-05 and TEN-10: the group overview renders zero rows on every table, and DSH-01/DSH-02 group aggregation returns nothing. The bug is invisible in single-mandant tests.

**Required fix:** Add an explicit branch to the function: when `app.ist_gruppenansicht()` is true, resolve the permission against **any** active `benutzer_mandant` row of the user (`bm.mandant_id in (select app.sichtbare_mandanten())`) and hard-return false for every key whose `berechtigung.aktion` is not `lesen`/`exportieren`. Add a unit test asserting `app.hat_berechtigung('rechnung.erstellen')` is false and `app.hat_berechtigung('gruppe.lesen')` is true with `app.ansicht = 'gruppe'`.

### B6. `app.ist_super_admin()` is the first disjunct of every RLS policy in the domain, and it checks only `b.status = 'aktiv'` and the role key. It does not check `b.gesperrt_bis`, `b.deaktiviert_am`, or the session's `zwei_faktor_bestaetigt_am`. The 2FA and lockout gates live only inside `app.hat_berechtigung()`, which the super-admin disjunct short-circuits past.

**Why it breaks:** AUT-02 ("2FA mandatory for super_admin and admin") and AUT-07 (lockout) are defeated for the single most privileged role, at the database layer that CLAUDE.md calls the second line of defence. A super-admin session that has passed password authentication but not the second factor, or one that is locked out after brute-force attempts, still reads and writes every row of every mandant.

**Required fix:** Make the super-admin path carry the same gates: `select exists (select 1 from benutzer b join rolle r on r.id = b.globale_rolle_id join benutzer_sitzung s on s.id = nullif(current_setting('app.sitzung_id', true),'')::uuid and s.benutzer_id = b.id where b.id = app.aktueller_benutzer() and b.status='aktiv' and b.deaktiviert_am is null and (b.gesperrt_bis is null or b.gesperrt_bis < now()) and s.beendet_am is null and s.ablauf_am > now() and s.zwei_faktor_bestaetigt_am is not null and r.geltungsbereich='global')`. Also stop hard-coding `r.schluessel = 'super_admin'` — resolve via `geltungsbereich = 'global'` plus a `system.alles` permission, since §6.3 of the draft argues role keys are data.

### B7. The employee identity model contradicts itself. `mitarbeiter_zugang.benutzer_id` is nullable and `zeit_einwand.eingereicht_von_benutzer_id`/`antrag.eingereicht_von_benutzer_id` are documented as "NULL, wenn über den SMS-Zugang ohne Vollkonto eingereicht" — yet every self-access RLS branch in the domain is keyed on `app.aktuelle_person()`, which is `select person_id from benutzer where id = app.aktueller_benutzer()`. For an SMS-only worker there is no `benutzer` row, so `app.aktueller_benutzer()` is NULL, `app.aktuelle_person()` is NULL, and `person_id = app.aktuelle_person()` evaluates to NULL, i.e. false.

**Why it breaks:** EMP-01, EMP-03, EMP-04, EMP-05, EMP-07, EMP-08, EMP-10, EMP-15 all fail for exactly the population they were written for: the SMS-login worker sees no hours, no leave balance, no certificates, no requests, and cannot file an objection. Worse, the `audit_log` actor CHECK is `(akteur_art='mensch' AND akteur_benutzer_id IS NOT NULL AND ...)`, so the `einwand_audit` trigger raises on their submission and rolls the transaction back — EMP-07's objection flow, whose evidentiary value the draft's own §6.4 rests on, cannot be exercised at all.

**Required fix:** Pick one identity model and state it. Either (a) every activated `mitarbeiter_zugang` creates a `benutzer` row — then `mitarbeiter_zugang.benutzer_id` is `NOT NULL` whenever `status = 'aktiv'` (enforced by CHECK), the `eingereicht_von_benutzer_id` columns become `NOT NULL`, and the SMS login is Supabase phone auth so `auth.uid()` exists; or (b) add `app.person_id` as a first-class session GUC set by the server, redefine `app.aktuelle_person()` to prefer it, add `akteur_person_id` to `audit_log`, and widen the actor CHECK to `(akteur_art='mensch' AND (akteur_benutzer_id IS NOT NULL OR akteur_person_id IS NOT NULL))`. Option (a) is the one CLAUDE.md's locked stack implies.

### B8. `anstellung` carries `CHECK (status = 'beendet' OR austritt IS NULL OR austritt >= current_date)`. `CURRENT_DATE` is STABLE, not IMMUTABLE, so the constraint's truth value changes under rows that never change. Verified on PostgreSQL 16: the constraint is accepted at `CREATE TABLE`, but (a) once `austritt` passes and the daily status job has not yet run, **every** `UPDATE` to that row fails — `ERROR: new row for relation "t1" violates check constraint`, so the row is frozen against all edits including the status update the job itself needs; and (b) `pg_dump` emits the constraint inline and `COPY` re-validates it, so restore of a dump containing any past-dated non-`beendet` row aborts: `ERROR: ... violates check constraint ... CONTEXT: COPY t1, line 1`.

**Why it breaks:** The draft explicitly relies on "ein täglicher Job" to maintain `status`, guaranteeing a daily window in which affected rows are unwritable. And it breaks SEC-A10 ("encrypted backups with a **tested** monthly restore") — the restore fails on real data, which is the worst possible time to discover it. Same class of defect anywhere else a CHECK uses `current_date`.

**Required fix:** Delete the constraint. Express the rule where it belongs: a `BEFORE UPDATE` trigger that raises only when the *transition* is illegal, plus the nightly job, plus a monitoring query `select count(*) from anstellung where status <> 'beendet' and austritt < (now() at time zone 'Europe/Berlin')::date`. Ban `current_date`/`now()` from CHECK constraints in the conventions section.

### B9. Unconditional unique constraints combined with the no-hard-delete rule make several ordinary lifecycle events permanently impossible: `benutzer_mandant_key UNIQUE (benutzer_id, mandant_id)` with soft revoke (`entzogen_am`) means a user whose access was revoked can never be granted access to that area again; `mitarbeiter_zugang_mobil_key UNIQUE (mobil_e164)` with `deaktiviert_am` means a company mobile number can never be reassigned to the next holder; `bewacher_eintrag_person_key UNIQUE (person_id)` with `erloschen_am` means a lapsed guard can never be re-registered; `nachweis_aktiv_uk UNIQUE (person_id, qualifikation_id, gueltig_ab)` with `widerrufen_am` means a wrongly entered certificate that has been revoked cannot be re-entered correctly with the same start date; `benutzer_email_key UNIQUE (lower(email))` with `deaktiviert_am` means a returning employee's address is blocked forever.

**Why it breaks:** Invariant 8 (soft delete) and these indexes were designed against each other. In a Berlin cleaning and security group, offboarding and rehiring the same person and recycling company phones are routine, not edge cases. Each collision surfaces as an opaque `duplicate key value violates unique constraint` at the moment someone is trying to get a worker on shift.

**Required fix:** Make each one partial on the liveness column: `UNIQUE (benutzer_id, mandant_id) WHERE entzogen_am IS NULL`, `UNIQUE (mobil_e164) WHERE deaktiviert_am IS NULL`, `UNIQUE (person_id) WHERE erloschen_am IS NULL`, `UNIQUE (person_id, qualifikation_id, gueltig_ab) WHERE widerrufen_am IS NULL`, `UNIQUE (lower(email)) WHERE deaktiviert_am IS NULL`. Where a truly global uniqueness is required (`bewacher_eintrag.bewacher_id`), keep it unconditional and say why.

### B10. `bewacher_eintrag` cannot follow a change of employer, which is the register's central event. `UNIQUE (person_id)` forbids a second row, and the write policy is `app.hat_berechtigung('personal.bewacher_verwalten') AND gemeldet_von_mandant_id = app.aktiver_mandant()` — `gemeldet_von_mandant_id` still names the *previous* employer, so the new employer can neither update the existing row nor insert one.

**Why it breaks:** SEC-03 and LEG-04. The author's own assumption 11 states "Re-notification on employer change updates `letzte_meldung_am`" — the schema as designed makes that update impossible. A guard moving from SSE Security to another group entity is stuck with a register entry nobody may touch, and SEC-04's assignment block reads stale data.

**Required fix:** Split identity from notification: keep one `bewacher_eintrag` per person (the Bewacher-ID follows the human, correctly argued), drop `gemeldet_von_mandant_id` from it, and add a child table `bewacher_meldung (id, bewacher_eintrag_id, person_id, mandant_id, art, gemeldet_am date, dokument_id, ...)` holding one row per notification by one entity. Write policy on the parent: `app.person_sichtbar(person_id) AND app.hat_berechtigung('personal.bewacher_verwalten')`, restricted to the register fields; the employer-specific facts live in the child, which is tenant-scoped normally.

### B11. `EXCLUDE USING gist (anstellung_id WITH =, daterange(von, bis, '[]') WITH &&) WHERE (status IN ('beantragt','genehmigt'))` forbids any two overlapping absences on one employment.

**Why it breaks:** It makes two legally mandatory records impossible. (1) Sickness during approved leave: under §9 BUrlG days of certified incapacity during a holiday are not counted as holiday and must be recorded as sickness — the constraint rejects the Krankheit row because the genehmigter Urlaub overlaps it. (2) The table's own `von_halbtags`/`bis_halbtags` columns exist to express a half day, but a morning Urlaub and an afternoon Fortbildung on the same date collide. The trigger `antrag_erzeugt_abwesenheit` is documented to fail the approval when the exclusion fires, so the approver sees an unexplained error.

**Required fix:** Do not enforce non-overlap structurally. Restrict the exclusion to the case that is genuinely a duplicate — same `abwesenheitsart_id`, whole days: `EXCLUDE USING gist (anstellung_id WITH =, abwesenheitsart_id WITH =, daterange(von,bis,'[]') WITH &&) WHERE (status IN ('beantragt','genehmigt') AND NOT von_halbtags AND NOT bis_halbtags)` — and handle Krankheit-during-Urlaub explicitly in `server/services/abwesenheit.ts`, which must credit the overlapping days back to `urlaubskonto.genommen_tage` and record the credit as an `abwesenheit` correction. Add `// TODO(client): does the group credit sick days during approved leave back to the Urlaubskonto automatically (§9 BUrlG) or on presentation of the AU only?`

### B12. Revocation is not enforced. `benutzer_mandant` carries both `aktiv boolean` and `entzogen_am timestamptz`, but `app.sichtbare_mandanten()` and `app.hat_berechtigung()` both filter on `bm.aktiv` only. Nothing in the schema keeps the two columns consistent.

**Why it breaks:** An administrator who revokes access by setting `entzogen_am`/`entzugsgrund` (the fields the UI will obviously present, since `entzogen_von` and `entzugsgrund` sit beside it) leaves the user with full access to that mandant. This is a silent authorization failure across AUT-03/AUT-04/SEC-A2 and, between three legal entities, the SEC-A3 scenario the SPEC calls the highest-priority test.

**Required fix:** Remove the redundancy — derive `aktiv` or drop it. Concretely: drop the `aktiv` column, add `and bm.entzogen_am is null` to both functions and to every index predicate that currently reads `WHERE aktiv`, and add `CHECK (entzogen_am IS NULL OR gueltig_bis IS NOT NULL)` if a revocation must also close the validity window. Do the same review for the other doubled liveness pairs in the domain (`mandant.aktiv`/`archiviert_am`, `rolle.aktiv`/`archiviert_am`, `benutzer.status`/`deaktiviert_am`, `qualifikation.aktiv`/`archiviert_am`, `abwesenheitsart.aktiv`/`archiviert_am`) — every one of them is two sources of truth for the same fact.

### B13. `audit_log.vorher`/`nachher` hold the whole row as JSONB, and the draft mandates `anstellung_audit` "mit Vorher/Nachher — Änderungen am Stundensatz sind prüfungsrelevant". The redaction list is documented as covering only "Tokenhashes, OTP, Passwortdaten". `audit_log`'s SELECT policy grants rows to anyone with `system.audit_lesen` in the mandant and, additionally, to `akteur_benutzer_id = app.aktueller_benutzer()` regardless of any other permission.

**Why it breaks:** `stundesatz_intern` is readable in cleartext by every holder of `system.audit_lesen` who lacks `personal.entgelt_lesen`, and by any `leitung` who ever edited an `anstellung` — via the self-access disjunct, permanently, for ten years. The column masking that D-09 §6 requires is bypassed by the accountability mechanism. The same applies to `person.geburtsdatum`/`geburtsort`/`staatsangehoerigkeit`, which `person_sicht` is supposed to mask, and to `abwesenheit` rows carrying an Art. 9 absence reason.

**Required fix:** Redact by classification, not by a hand-written secrets list. Add a `sensibel boolean` marker to a per-table column registry (or a `kern.audit_feld_klassifikation` table) and have `app.protokolliere()` replace classified values with a `"***"` sentinel while still recording that the field changed in `geaenderte_felder`, so the audit trail proves *that* the rate changed without disclosing it. Expose the actual old/new value only through a separate `SECURITY DEFINER` reader that re-checks `personal.entgelt_lesen`. Enumerate the classified columns in this document: `anstellung.stundesatz_intern`, `anstellung.tarifgruppe`, `person.geburtsdatum`, `person.geburtsort`, `person.staatsangehoerigkeit`, `abwesenheit.abwesenheitsart_id`, `abwesenheit.au_*`.

### B14. Archiving a mandant makes its retained financial and time data unreachable. `app.sichtbare_mandanten()` filters `m.aktiv and m.archiviert_am is null`; the trigger `sitzung_mandant_pruefen` requires `aktiver_mandant_id` to be in `app.sichtbare_mandanten()`; therefore after `archiviert_am` is set nobody — including a super-admin — can activate that mandant, and every tenant table's mandant branch (`mandant_id = app.aktiver_mandant()`) becomes unreachable for its rows.

**Why it breaks:** LEG-01 and ACC-06 require ten-year retention *and availability* for a tax audit, and ACC-09 requires a Z3 export on demand. Data that legally may not be deleted becomes data nobody can read — the archiving column that exists to satisfy invariant 8 defeats the retention requirement it was added for.

**Required fix:** Separate "not offered in the switcher" from "not readable". Keep `app.sichtbare_mandanten()` filtering archived rows for the switcher, and add `app.lesbare_mandanten()` (archived included) used by the SELECT branch of every tenant policy and by `sitzung_mandant_pruefen`; block only writes for an archived mandant, with `T_insert`/`T_update` additionally requiring `exists (select 1 from mandant m where m.id = mandant_id and m.archiviert_am is null)`.

### B15. The composite-FK rule that §6.2 calls the structural guarantee of tenant isolation is violated twice in the time domain: `stundenkonto_bewegung.korrektur_fuer_stundenkonto_id uuid FK -> stundenkonto.id` and `zeit_einwand.korrektur_bewegung_id uuid FK -> stundenkonto_bewegung.id` are single-column references into tenant tables.

**Why it breaks:** Exactly the failure the draft's own §6.2 describes: a reinigung `stundenkonto_bewegung` can carry a correction pointer into a security `stundenkonto`, and a reinigung `zeit_einwand` can point at a security `stundenkonto_bewegung`, with no database-level obstruction. Both columns feed the correction trail that TIM-11 and §17 MiLoG (LEG-02) rely on, so the cross-entity link would appear in an audit trail as if it were legitimate. `stundenkonto_bewegung` also lacks the `UNIQUE (id, mandant_id)` needed to be a composite-FK target at all.

**Required fix:** Add `UNIQUE (id, mandant_id)` to `stundenkonto_bewegung`, then make both references composite: `FOREIGN KEY (korrektur_fuer_stundenkonto_id, mandant_id) REFERENCES stundenkonto (id, mandant_id)` and `FOREIGN KEY (korrektur_bewegung_id, mandant_id) REFERENCES stundenkonto_bewegung (id, mandant_id)`. Audit the whole document for any remaining single-column FK whose target carries `mandant_id`, and state the rule as "a single-column FK into a table that has `mandant_id` is a review failure".

### B16. TEN-10 cannot be implemented against this schema. DESIGN §6 and TEN-10 require the switcher dropdown to show a live counter per area ("Reinigung · 24 Aufträge", "Bau · 12 Projekte") for the areas the user is *not* currently in, but the standard tenant policy grants SELECT only for `mandant_id = app.aktiver_mandant()` or in group view, and the group view branch is itself broken (see the `hat_berechtigung` finding).

**Why it breaks:** TEN-10 and DESIGN §6 rule 2 ("the switcher is informative, not decorative"). The document names `benutzer_mandant_benutzer_idx` as supporting "Switcher-Rendering" but never addresses where the counters come from, so implementation will either ship a decorative switcher or, worse, reach for a service-role client that bypasses RLS on every page load.

**Required fix:** Add a small, explicitly-scoped read path and put it in this document: `app.mandant_kennzahlen() returns table (mandant_id uuid, kennzahl text, wert integer)`, `SECURITY DEFINER`, restricted to `app.sichtbare_mandanten()`, returning **counts only** — never rows, never money. Back it with a `mandant_kennzahl (mandant_id, schluessel, wert integer, berechnet_am timestamptz)` cache table refreshed by a scheduled job, so the dropdown does not run four cross-tenant aggregates on every render.

### B17. Absence reasons are Art. 9 DSGVO data and are readable by everyone with `zeit.lesen`. `abwesenheit.abwesenheitsart_id` resolves to `krankheit` / `kind_krank`, and `au_bescheinigung_vorliegt` / `au_bis` state that a certificate of incapacity exists and until when. The table uses the plain standard tenant policy for module `zeit`, so every planner, dispatcher and shift-filler in the entity sees who is sick and for how long.

**Why it breaks:** DSGVO Art. 9 and LEG-09 data minimisation. The draft correctly refuses to store a diagnosis and then discloses health data one level up. The Dienstplan conflict check (TIM-05) needs to know that the person is *unavailable*; it does not need the reason.

**Required fix:** Split the read. Grant `zeit.abwesenheit_lesen` (returns `von`, `bis`, half-day flags and a neutral `abwesend` marker) broadly, and gate `abwesenheitsart_id`, `au_bescheinigung_vorliegt`, `au_bis`, `dokument_id` and `bemerkung` behind a separate `personal.abwesenheit_grund_lesen`, enforced with column-level GRANTs on the base table exactly as for `stundesatz_intern`. Note in DECISIONS.md that the Dienstplan renders "abwesend", never "krank".

### B18. `mitarbeiter_zugang` implements a second, home-grown authentication stack — `einladung_token_hash`, `otp_hash`, `otp_gueltig_bis`, `otp_versuche`, `gesperrt_bis` — parallel to Supabase Auth, which CLAUDE.md's stack table locks as *the* auth layer. Separately, `benutzer.zwei_faktor_aktiv` is described as a mirror of `auth.mfa_factors` "per Auth-Hook synchronisiert", and the trigger `benutzer_2fa_pflicht` enforces AUT-02 against that mirror.

**Why it breaks:** Two consequences. (1) Auth state lives in two places with no reconciliation: a user who removes their MFA factor through Supabase Auth leaves `zwei_faktor_aktiv = true` behind, and the trigger that is supposed to implement AUT-02 approves an account with no second factor. (2) A six-digit OTP has 10^6 preimages; "otp_hash" under an unspecified (and, by the pattern set by `benutzer_sitzung.token_hash`, plain SHA-256) hash is reversible in milliseconds if the row is ever read, and the row is readable by anyone with `personal.zugang_verwalten`.

**Required fix:** Use Supabase phone OTP for EMP-01 and delete `otp_hash`, `otp_gueltig_bis`, `otp_versuche` and `gesperrt_bis` from `mitarbeiter_zugang`, leaving it as the person↔login mapping plus the invitation and the two DSGVO acknowledgements. Replace the `zwei_faktor_aktiv` mirror with a `STABLE SECURITY DEFINER` function `app.hat_zweiten_faktor(p_benutzer uuid)` reading `auth.mfa_factors` directly, and have `hat_berechtigung()` and `ist_super_admin()` call it. If a bespoke OTP is genuinely required, state the KDF and the server-side pepper here and record the deviation from the locked stack in DECISIONS.md.

### B19. `audit_log.lfd_nr bigint GENERATED ALWAYS AS IDENTITY` is documented as: "Totale Ordnung des Protokolls; eine Lücke beweist eine Manipulation." Postgres sequences are non-transactional: every rolled-back transaction, every crash, and every `cache` setting above 1 consumes numbers permanently. Gaps are the normal state of this column.

**Why it breaks:** The nightly integrity control described here will alarm constantly on normal operation and, once operators learn to ignore it, will not detect a real deletion either. The audit log then has no tamper evidence at all, while the document claims GoBD-grade immutability (LEG-01, ACC-06, SEC-A9). Note this is the opposite of the invoice number circle (FIN-03), where gaplessness is real precisely because the counter is a row updated with `SELECT … FOR UPDATE` inside the finalisation transaction.

**Required fix:** Keep `lfd_nr` as an ordering key and stop claiming it proves anything. Give `audit_log` the same mechanism the invoices get (invariant 4): `vorheriger_hash text`, `hash text NOT NULL` where `hash = SHA256(canonical_payload || vorheriger_hash)`, computed inside `app.protokolliere()` under a `SELECT … FOR UPDATE` on a per-partition chain-head row, plus a nightly verification job — the same job pattern FIN-06 already requires. Then a removed row is detectable, and the SPEC §14 watchdog "Invoice hash chain broken → alert immediately" can cover the audit chain too.

The column is presented as the TEN-08 mechanism for enabling a fifth area's modules, but `app.hat_berechtigung()` never reads it and only `benutzer_mandant.module` is validated. As shipped it is decorative: a permission for a module the mandant has not enabled still resolves true. - Immutability of `person.erfasst_von_mandant_id`. The `person_update` WITH CHECK is `app.person_sichtbar(id)` only, so a user can re-point the visibility anchor at any mandant they can see, silently granting or revoking another entity's access to that human. Needs a trigger making it write-once.

- A per-user iCal feed token (CAL-03, "iCal feed per user, read-only"). ## INVENTED RULES — must become TODO(client) (10)

Neither the ranking nor the delegation rule appears in AUT-01/AUT-03. Its practical effect is that an `admin` cannot appoint another `admin` and a `leitung` cannot appoint a deputy — only a super-admin can, which is a governance decision the client has not made. It also has a bug: a super-admin has no `benutzer_mandant` row (they hold `globale_rolle_id`), so their own rank in the mandant is undefined and the trigger blocks them from granting anything. Needs `// TODO(client): may an Admin appoint another Admin, and may a Leitung appoint a deputy within their own area?`

O-01 is explicitly open and blocking, yet `false` is not a neutral placeholder — combined with `CHECK (eigener_nummernkreis <= ist_rechtseinheit)` it decides O-01 in the "internal department" direction and forbids the operations invoice circle. Make the column nullable (`NULL = ungeklärt`), change the CHECK to `CHECK (NOT eigener_nummernkreis OR ist_rechtseinheit IS TRUE)`, and let Phase 6 refuse to create a number circle while it is NULL.

The bootstrap problem it solves is real; the fix should be bounded, e.g. `... and not exists (select 1 from anstellung a where a.person_id = p.id)` so the anchor lapses the moment a real employment exists, or a dated `erfassung_gueltig_bis`. - `benutzer.zeitzone text NOT NULL DEFAULT 'Europe/Berlin'` as a per-user override. ## MINOR (18)
- `CHECK (NOT laeuft_ab OR standard_gueltigkeit_monate IS NOT NULL OR true)` on `qualifikation` is a tautology — `X OR true` is always true. It reads like a constraint, enforces nothing, and will mislead the next reader. Delete it.
- The conventions section states all helper functions are `SET search_path = pg_catalog, app, public`, but only `app.person_sichtbar` and `app.hat_berechtigung` carry it in the SQL shown. `app.ist_super_admin()` and `app.sichtbare_mandanten()` and `app.aktuelle_person()` are `SECURITY DEFINER` without it, which is the classic search-path privilege-escalation pattern. Make the code match the prose.
- `current_date` in `app.sichtbare_mandanten()`, `app.hat_berechtigung()` and `person_anonymisierung_sperre` evaluates in the database session's timezone (UTC on Supabase), not Europe/Berlin. Between 00:00 and 02:00 Berlin time an access grant that becomes valid "today" is still invalid, and a `loeschsperre_bis` expires two hours early. Use `(now() at time zone 'Europe/Berlin')::date` consistently, and say so in the conventions section next to invariant 2.
- RLS performance: `app.hat_berechtigung('x')` and `app.person_sichtbar(id)` are `SECURITY DEFINER`, so Postgres cannot inline them and evaluates them once per candidate row. On a Dienstplan month view or a person typeahead this is thousands of function calls per query. Wrap the parameterless ones as `(select app.hat_berechtigung('zeit.lesen'))` so the planner hoists them into an InitPlan evaluated once; `app.person_sichtbar(id)` is row-dependent and should instead be rewritten as an `EXISTS` against a `SECURITY DEFINER` set-returning helper.
- `rolle_berechtigung_aufloesung_idx ON (rolle_id, mandant_id) INCLUDE (berechtigung_id, gewaehrt)` is redundant and worse than the index the unique constraint already creates. The hot-path predicate is `(rolle_id, berechtigung_id, mandant_id)`, which `rolle_berechtigung_key` already covers exactly. Drop the extra index.
- `app.ist_super_admin()` hard-codes `r.schluessel = 'super_admin'`, contradicting §6.3's own argument that role keys are data. Resolve via `rolle.geltungsbereich = 'global'` plus a `system.alles` permission row.
- `berechtigung` grants `SELECT` to all authenticated users on the grounds that "die Matrix ist nicht geheim". Combined with the equally open `rolle` and `rolle_berechtigung` policies, a customer-portal login can enumerate the platform's entire permission model, including which role holds `personal.entgelt_lesen`. Restrict to holders of `system.rolle_verwalten` plus the keys needed to render the caller's own UI.
- `abwesenheit.antrag_id` and `antrag.resultat_abwesenheit_id` are mutual foreign keys expressing the same relationship twice, requiring two statements to establish and offering two ways to disagree. Keep `antrag.resultat_abwesenheit_id` (the direction the trigger writes) and drop the back-reference, or vice versa.
- `abwesenheit.gemeldet_am` is annotated "Serverzeit" but has no `DEFAULT now()` and no constraint, so a client-supplied value can land in it — a soft breach of invariant 5 on the one column in the absence table that records when a sickness was reported.
- Triggers that write to RLS-protected tables are never addressed. `bewegung_summe` updates `stundenkonto`, whose UPDATE policy demands `hat_berechtigung('zeit.aendern')`; `antrag_erzeugt_abwesenheit` inserts into `abwesenheit`, whose INSERT policy demands a `zeit.*` create right; `abwesenheit_urlaubskonto` updates `urlaubskonto`. An approver who holds only the approval permission will get `new row violates row-level security policy`. Either make these triggers `SECURITY DEFINER` (and say which role owns them) or enumerate the exact permission each approval action requires.
- AUT-06 (404, not 403) holds for reads but not for writes: an INSERT that fails `WITH CHECK` raises SQLSTATE 42501, a cross-tenant composite-FK violation raises 23503 naming the constraint, and a `benutzer_mandant` unique violation raises 23505 — each confirming existence. State that the route handler maps 42501/23503/23505 on tenant-scoped tables to 404, and add it to the SEC-A3 suite.
- `benutzer.sprache` and `person.sprache` both exist with no precedence rule. For a worker who has both rows, which one selects the SMS language and which the portal UI (EMP-12)? Pick one and make the other a generated mirror.
- `abwesenheitsart` has no `erstellt_von`/`geaendert_von` although it carries `lohnart_schluessel`, `bezahlt` and `zaehlt_auf_urlaubskonto` — payroll-relevant settings (ACC-12) that need the same accountability as the rest of the domain. `mandant_identitaet` similarly has `geaendert_von` but no `erstellt_von`.
- `antrag_art` mixes SPEC vocabulary with invented UI conveniences (`unbezahlter_urlaub`, `schichtabgabe`, `stammdaten_aenderung`, `freizeitausgleich`) inside a Postgres enum, while the structurally identical `abwesenheitsart` is a catalogue table specifically so the client can change it. Be consistent: either both are enums or both are tables.
- The seed `qualifikation` rows set `blockiert_einsatz = true`, `laeuft_ab = true` for `34a_sachkunde` and `34a_unterrichtung` but no `standard_gueltigkeit_monate`, so the expiry watchdog (SPEC §14, 60/30/7) has nothing to warn about until someone enters a `gueltig_bis` by hand. Add `// TODO(client): does the group treat the §34a Unterrichtung/Sachkunde as unbefristet, and what triggers a re-check — Zuverlässigkeitsüberprüfung interval only?`
- `mandant.module text[]`, `geschaeftsfuehrer text[]` and `bewacher_eintrag.taetigkeiten text[]` are unvalidated arrays. `bm_module_pruefen` validates `benutzer_mandant.module` against `SELECT DISTINCT modul FROM berechtigung`; the same check is absent for `mandant.module`. `taetigkeiten` has a `// TODO(client)` and should be a catalogue table for the same reason `abwesenheitsart` is.
- The `mandant → benutzer → person → mandant` foreign-key cycle (`mandant.erstellt_von`, `benutzer.person_id`, `person.erfasst_von_mandant_id NOT NULL`) is resolvable only because `mandant.erstellt_von` is nullable. State the seed ordering explicitly in §5 so the first migration is reproducible on a clean database.
- `audit_log_nachher_gin ON USING gin (nachher jsonb_path_ops)` on a monthly-partitioned, append-only table with ten-year retention adds a GIN index to every partition and materially slows the write path that every trigger in the platform goes through. Either restrict it to the recent partitions or drop it and rely on `objekt_typ/objekt_id` for the audit query the SPEC actually names (APR-02, DSH-01).
