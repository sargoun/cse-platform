# Adversarial review — crm-operations

## BLOCKING (20)

### B1. The standard SELECT policy is `USING (mandant_id = ANY (app.sichtbare_mandanten()))` on every table, unconditionally — it never narrows to `app.aktiver_mandant()` when one is set.

**Why it breaks:** A `leitung` user who legitimately holds employments/roles in reinigung and security has both mandanten in `sichtbare_mandanten()` at all times. While working inside the reinigung portal she can `SELECT` security `kunde`, `angebot`, `angebotsposition`, `auftrag_leistung.einzelpreis_cent`, `vertrag_abrechnung.stundensatz_cent`, `kalkulation.stundenverrechnungssatz_cent` and `kalkulation_position.stundensatz_cent`. That is exactly D-09 clause 6 ("a cleaning manager must not see security wage rates") and invariant 3 ("the active tenant lives in the server session") failing at the layer the draft calls the second line of defence. RLS then filters nothing for the most likely real-world leak, and the SEC-A3 suite passes only because it tests single-mandant users.

**Required fix:** Standard SELECT becomes `USING (CASE WHEN app.aktiver_mandant() IS NOT NULL THEN mandant_id = app.aktiver_mandant() ELSE mandant_id = ANY (app.sichtbare_mandanten()) END)`. The `sichtbare_mandanten()` branch is reachable only in the group view, where invariant 10 already forbids writes. Add a SEC-A3 case: a user in two mandanten, with mandant A active, gets zero rows for every table of mandant B.

### B2. None of the seven views in §6 is declared `WITH (security_invoker = true)`.

**Why it breaks:** A Postgres view executes with the privileges and the RLS exemption of its owner. On Supabase migrations run as `postgres`, which carries BYPASSRLS. `objekt_flaeche`, `angebot_steuersumme`, `referenzfaehiger_auftrag`, `lead_sla_offen`, `kunde_gruppenhistorie`, `auftrag_ohne_zeiterfassung` and `kalkulation_platzhalter` therefore return every mandant's rows to any caller who can `SELECT` the view — including a customer-portal session and a `mitarbeiter`. `kunde_gruppenhistorie` alone hands out every entity's customer list and order values. This is the cross-tenant leak SEC-A3 calls the highest-priority test in the codebase, introduced by the schema itself.

**Required fix:** `CREATE VIEW … WITH (security_invoker = true)` on all seven, and add `mandant_id` to the output of `objekt_flaeche` and `angebot_steuersumme` so callers can filter. Add a SEC-A3 case per view, not only per table.

### B3. `crm_darf_kontaktiert_werden()` is written as `SELECT <boolean expr> FROM ansprechpartner ap WHERE ap.id = p_ansprechpartner_id` with no `coalesce`, and is `LANGUAGE sql STABLE` without `SECURITY DEFINER`.

**Why it breaks:** Two ways the CRM-08/§7 UWG gate opens instead of closing. (1) If no row matches — archived-then-repointed id, a race, a bad id from an agent — the function returns NULL. `IF NOT crm_darf_kontaktiert_werden(...) THEN RAISE` does not fire on NULL, and a CHECK evaluating to NULL passes. (2) Because it runs under the caller's RLS, the same call from a job role, an agent session, or a session whose active mandant differs sees zero rows and again returns NULL. The draft names this the one field whose failure costs money directly (Abmahnung, LEG-08, D-01) and enforces it with a predicate that fails open.

**Required fix:** `RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$ SELECT coalesce((SELECT <expr> FROM ansprechpartner ap WHERE ap.id = p_ansprechpartner_id), false) $$;` plus a unit test asserting `crm_darf_kontaktiert_werden(gen_random_uuid(),'email') = false`.

### B4. `lead_aktivitaet.ansprechpartner_id` is nullable, but the §7 UWG CHECK only constrains `rechtsgrundlage_snapshot` and the re-evaluation trigger keys on `ansprechpartner_id`.

**Why it breaks:** An outgoing `kanal='email'` row with `ansprechpartner_id = NULL` and a hand-set `rechtsgrundlage_snapshot = 'bestandskunde'` satisfies the CHECK, and the trigger has no contact to re-evaluate, so it cannot reject the stale snapshot. Since the draft's design is "the send path writes the activity in the same transaction, so an unrecordable send is an unsendable send", omitting the contact id makes every outbound send recordable and therefore sendable. The gate is bypassable by leaving one nullable column empty.

**Required fix:** Add `CHECK (richtung <> 'ausgehend' OR kanal IS NULL OR kanal NOT IN ('email','telefon','sms','post','whatsapp') OR ansprechpartner_id IS NOT NULL)` and make the trigger `RAISE` when `ansprechpartner_id IS NULL` on an outgoing electronic row.

### B5. `erzwinge_widerspruch()` plus `CHECK (widerspruch_am IS NULL OR rechtsgrundlage = 'keine')` collapses an advertising objection into a total communication block, and `lead_aktivitaet`'s CHECK then refuses to record any outgoing email to that contact.

**Why it breaks:** §7 UWG / Art. 21 DSGVO objections are objections to *advertising*. Communication required to perform the contract rests on Art. 6(1)(b) and cannot be objected away. Under this design, an existing customer who unsubscribes from marketing can no longer be sent an invoice, a Leistungsnachweis, a Terminbestätigung or a Mahnung: `crm_darf_kontaktiert_werden` returns false, `policy.ts` refuses `sende_email`, and the `lead_aktivitaet` insert that the send path performs in the same transaction is rejected by the CHECK. Invoice dispatch (FIN-11 `rechnung_email`) and dunning (FIN-15) break for exactly the customers most likely to object. The equivalence "advertising objection = no legal basis for any contact" is also a legal rule the SPEC never states.

**Required fix:** Split the concepts: keep `rechtsgrundlage` for the contact relationship, add `werbewiderspruch_am timestamptz` as the advertising-specific objection, and add `zweck` (`vertraglich` / `werbung` / `intern`) to `lead_aktivitaet`. Gate only `zweck='werbung'` on `crm_darf_kontaktiert_werden`; contractual dispatch is never gated. Emit `// TODO(client): Welche Kommunikation gilt als vertraglich notwendig und ist vom Werbewiderspruch ausgenommen?`

### B6. `angebot` carries `CHECK ((status = 'entwurf') = (angebotsnummer IS NULL))` while `angebotsnummer` is stated to be assigned at first send, and `angebot_status` contains `in_pruefung`, `zurueckgezogen` and `abgelaufen`.

**Why it breaks:** An offer in internal four-eyes review (`in_pruefung`) has not been sent, so it has no number, so the CHECK rejects it — the state is unreachable. Same for withdrawing a draft (`zurueckgezogen`). Either the state machine or the number rule has to give, and today the constraint silently makes the approval step the draft relies on for invariant 7 impossible to persist. Separately, the approval CHECK lists only `('versendet','angenommen','abgelehnt')`, so `status = 'abgelaufen'` or `'zurueckgezogen'` can be reached with `freigegeben_von IS NULL AND versendet_am IS NULL` — a hole in the same invariant-7 enforcement.

**Required fix:** `CHECK (angebotsnummer IS NULL) = (versendet_am IS NULL)` — key the number on the send event, not on the status — and widen the approval CHECK to `status NOT IN ('entwurf','in_pruefung') OR (freigegeben_von IS NOT NULL AND versendet_am IS NOT NULL)`.

### B7. Invariant 8 / GoBD deletion protection rests entirely on "no table grants a DELETE policy" plus `FORCE ROW LEVEL SECURITY`. Only `dokument` and `dokument_version` get an actual `BEFORE DELETE` trigger.

**Why it breaks:** `FORCE ROW LEVEL SECURITY` binds the table owner but not roles with BYPASSRLS. Supabase's `service_role` has BYPASSRLS, and the draft itself acknowledges `service_role` exists (SEC-A5 note). So `DELETE FROM rechnung`-adjacent upstream rows — `auftrag`, `auftrag_leistung`, `vertrag_abrechnung`, `angebot`, `angebotsposition`, `kalkulation`, `kalkulation_position`, `lead`, `lead_aktivitaet`, `formular_eingang`, `raum`, `kunde` — succeeds for any script, migration or Edge Function that connects with the service key. The claim "enforced for every application role including the one an incident-response script might reach for" is false for precisely that role. LEG-01 requires deletion to be impossible, not merely unpolicied.

**Required fix:** Add `CREATE TRIGGER verhindere_loeschung BEFORE DELETE ON <t> FOR EACH ROW EXECUTE FUNCTION verhindere_loeschung()` (raising unconditionally) on every table in the domain, plus `REVOKE DELETE, TRUNCATE ON ALL TABLES IN SCHEMA public FROM authenticated, anon, service_role`. Also state `ON DELETE NO ACTION` explicitly on every FK — the draft never specifies referential actions, and a cascade from a parent would bypass the missing policy.

### B8. `vertrag_abrechnung`'s exclusion constraint is `EXCLUDE USING gist (auftrag_id WITH =, abrechnungsart WITH =, daterange(...) WITH &&)` — it includes `abrechnungsart` in the key.

**Why it breaks:** It permits `stundenbasiert` and `monatspauschale` to be simultaneously valid on the same `auftrag` on 15 March, which is the opposite of the stated purpose ("'how is this billed on 15 March' always has one answer"). The monthly billing run scans `WHERE gueltig_bis IS NULL` by `(mandant_id, abrechnungsart, abrechnungsintervall)` and would emit two invoice proposals for one contract period — a double-billing bug that reaches a `festgeschrieben`, hash-chained, immutable invoice before anyone notices.

**Required fix:** Either drop `abrechnungsart` from the exclusion key so one order has one configuration per period, or — if a multi-service contract really needs per-line billing types — add `auftrag_leistung_id uuid NOT NULL` and key the exclusion on `(auftrag_id, auftrag_leistung_id, daterange)`. The second is what FIN-01 plus OPS-05 multi-site frame contracts actually require, and the draft currently has no way to bill one contract line hourly and another as a flat.

### B9. The billing-run index `btree (mandant_id, abrechnungsart, abrechnungsintervall) WHERE gueltig_bis IS NULL` is described as the scan that "selects every active monthly-flat contract in one scan".

**Why it breaks:** A configuration that ended mid-period has `gueltig_bis IS NOT NULL` and is excluded from the partial index. If a contract is terminated on 15 March, the March billing run driven by this index never sees it and the 1–15 March service is never invoiced. The correct predicate for period P is `gueltig_ab <= P_ende AND (gueltig_bis IS NULL OR gueltig_bis >= P_start)`, which this index cannot serve. Silent lost revenue, discovered at year-end.

**Required fix:** Replace with `btree (mandant_id, abrechnungsart, abrechnungsintervall, gueltig_ab, gueltig_bis)` (no partial predicate), or a GiST index on `daterange(gueltig_ab, gueltig_bis)` per mandant, and specify the billing-run query as the range-overlap form.

### B10. `erzwinge_mandant_konsistenz()` is declared as a general pattern but is only attached to `raum`, `raumbuch_import`, `raumbuch_import_zeile`, `leistungskatalog_position`, `angebotsposition`, `auftrag_leistung`, `vertrag_abrechnung`, `auftrag_dokument` and `dokument_version`. It is absent from `angebot`, `auftrag`, `objekt`, `lead`, `lead_aktivitaet`, `kalkulation`, `kalkulation_position` and `dokument`.

**Why it breaks:** `angebot.mandant_id` and `angebot.kunde_id` can point at different mandanten. Combined with the `sichtbare_mandanten()` SELECT policy (blocking item 1), a multi-mandant user inserting under an active reinigung mandant can reference a security `kunde_id`, `objekt_id`, `lead_id` or `ansprechpartner_id` — the FK resolves because the row is readable — and produce an offer that is tenant-tagged reinigung but commercially belongs to security. The same holds for `auftrag.kunde_id`, `objekt.kunde_id`, `dokument.kunde_id`/`objekt_id`, `kalkulation.basis_objekt_id`/`angebot_id`/`auftrag_id`, `lead.kunde_id`/`ansprechpartner_id` and `lead_aktivitaet.lead_id`/`kunde_id`. The invoice built on that `auftrag` lands in the wrong GmbH — the exact failure D-10 designs the identity hue against.

**Required fix:** Attach `erzwinge_mandant_konsistenz()` to every table listed above, one check per mandant-carrying FK, and enumerate the (table, column) pairs it guards explicitly instead of describing it as a pattern.

### B11. `kalkulation.stundenverrechnungssatz_cent`, `gemeinkosten_bp` and `wagnis_gewinn_bp` are `NOT NULL` with no default and no `ist_platzhalter` column, and `kalkulation_platzhalter` only detects placeholders reached through `belagsart` / `leistungskatalog_position`.

**Why it breaks:** The three values the draft itself marks `TODO(client)` are the only ones its own placeholder machinery cannot see. `NOT NULL` with no default forces the service to supply a number on every draft calculation — i.e. to invent a Stundenverrechnungssatz and a Gemeinkostenzuschlag — and nothing then flags the row, so `kalkulation_platzhalter` returns nothing, the UI shows no warning banner, and the service rule "a kalkulation may not be festgeschrieben while any position it derives from is still a placeholder" passes. A frozen, auditable costing built on three guessed legal/financial values is precisely the outcome CLAUDE.md's "never silently pick a plausible value" forbids.

**Required fix:** Make the three columns nullable, add `ist_platzhalter boolean NOT NULL DEFAULT true` to `kalkulation`, extend `kalkulation_platzhalter` to `WHERE k.ist_platzhalter OR k.stundenverrechnungssatz_cent IS NULL OR k.gemeinkosten_bp IS NULL OR k.wagnis_gewinn_bp IS NULL OR <catalogue joins>`, and add `CHECK (status <> 'festgeschrieben' OR (ist_platzhalter = false AND stundenverrechnungssatz_cent IS NOT NULL AND gemeinkosten_bp IS NOT NULL AND wagnis_gewinn_bp IS NOT NULL))`.

### B12. Nothing links the `angebot` freeze to the `kalkulation` freeze. `angebot_nach_versand_unveraenderlich()` freezes the offer's commercial fields and its positions; `kalkulation` freezes only on its own `status = 'festgeschrieben'`.

**Why it breaks:** An offer can be approved, numbered, PDF'd and sent while its `kalkulation` is still `entwurf` and fully editable — including `stundenverrechnungssatz_cent`, `gemeinkosten_bp` and every `kalkulation_position` snapshot. The entire §7.2 argument ("a price can still be explained two years later", "the PDF in the customer's inbox no longer matches the record") is defeated by editing the costing after the send instead of before it. OPS-07's "versioned" costing and FIN-07 line-to-source traceability both rest on a freeze that never triggers.

**Required fix:** Add a `BEFORE UPDATE` trigger on `angebot` that, when `versendet_am` transitions from NULL, sets every `kalkulation` with that `angebot_id` to `festgeschrieben` (stamping `festgeschrieben_am`/`_von` from the sending user), and a CHECK/trigger refusing the send if no `kalkulation` exists for a `typ='leistung'`-bearing offer.

### B13. `UNIQUE (mandant_id, kunde_id, lower(email)) WHERE archiviert_am IS NULL AND email IS NOT NULL` on `ansprechpartner`, while `kunde_id` is nullable by design ("NULL while the contact belongs to a lead that has not converted").

**Why it breaks:** NULLs are distinct in a Postgres unique index. Every pre-conversion contact has `kunde_id IS NULL`, so the index constrains nothing for exactly the population it needs to constrain: ten form submissions from einkauf@example.de create ten `ansprechpartner` rows, each with its own `rechtsgrundlage`, `einwilligung_kanaele` and `widerspruch_am`. The stated purpose — "duplicate contacts are the main source of double-mailing" — fails, and a §7 UWG objection recorded on one row leaves nine contactable clones. The §7 UWG evidence index `btree (ansprechpartner_id, geschehen_am DESC) WHERE richtung='ausgehend'` then splits one person's history across ten ids.

**Required fix:** `CREATE UNIQUE INDEX … ON ansprechpartner (mandant_id, coalesce(kunde_id, '00000000-0000-0000-0000-000000000000'::uuid), lower(email)) WHERE archiviert_am IS NULL AND email IS NOT NULL` (or `NULLS NOT DISTINCT` on PG15+). Also add `AND archiviert_am IS NULL` to `UNIQUE (kunde_id) WHERE ist_hauptkontakt` — as written, an archived former Hauptkontakt permanently blocks naming a new one.

### B14. `raum` has `raumnummer text NOT NULL` and `UNIQUE (objekt_id, raumnummer) WHERE archiviert_am IS NULL`, called "the natural key of a Raumbuch row".

**Why it breaks:** Real Raumbücher repeat door numbers across floors ("101" in UG and in 1. OG, or per Haus A/B under one Objekt) and contain many unnumbered rows — Flur, Treppenhaus, Aufzugsvorraum, WC-Vorraum. The unique constraint wrongly collapses legitimately distinct rooms and `NOT NULL` forces the importer to fabricate numbers. OPS-04 requires an Excel/CSV import of the client's existing Raumbücher; this constraint makes that import fail or silently merge rooms, and every merged room drops m² out of `Σ m² ÷ Leistungswert × Frequenzfaktor` — a systematically under-priced cleaning offer.

**Required fix:** Make `raumnummer` nullable, key on `UNIQUE (objekt_id, etage, raumnummer) WHERE archiviert_am IS NULL AND raumnummer IS NOT NULL`, and give `raumbuch_import_zeile` an explicit `quell_schluessel text` for import idempotency instead of overloading the door number. Add the pricing-path index `btree (objekt_id, belagsart_id) INCLUDE (flaeche_qm) WHERE archiviert_am IS NULL` — the OPS-02/03 costing query groups by Belagsart for one Objekt and no current index serves it.

### B15. `firma` has a global `UNIQUE (ust_id) WHERE ust_id IS NOT NULL` but a SELECT policy that only exposes a `firma` row once the querying mandant already has a `kunde` pointing at it.

**Why it breaks:** Two consequences. (1) The CRM-06 identity flow is impossible: to attach a new reinigung customer to an existing `firma`, the service must find that `firma` — which RLS hides precisely because reinigung has no `kunde` for it yet. The only ways out are `service_role` (violating SEC-A5) or creating a duplicate `firma`, which then hits the unique constraint. (2) The unique violation is itself an oracle: a reinigung user inserting a `firma` with a given USt-IdNr learns from the 23505 error whether SSE Security already serves that company. That is the "403 confirms existence" failure AUT-06 exists to prevent, reproduced as a constraint error. `zusammengefuehrt_in_firma_id` merges have the same problem — merging requires reading both rows.

**Required fix:** Move identity resolution behind a `SECURITY DEFINER` function `firma_aufloesen(ust_id, name, land) RETURNS uuid` that matches or inserts and returns only the id (never other mandanten's attributes), grant EXECUTE to the app role, and revoke direct INSERT on `firma`. The trgm duplicate-detection search must run inside the same function and return only a similarity score plus the id, never the row. Document the residual timing/id-reuse signal in DECISIONS.md.

### B16. No policy anywhere in the domain contains a role or permission predicate; the draft defers `leitung`/`mitarbeiter` scoping to "an additional policy in Phase 3 (AUT-05)" while shipping CRM and Operations in Phase 4.

**Why it breaks:** AUT-01 gives `mitarbeiter` "own work only" and EMP-13 says employees never see customer commercials. Under the policies as written, any authenticated session with reinigung in `sichtbare_mandanten()` — including every cleaner's `mitarbeiter_zugang`-derived session — can `SELECT` the full `kunde` table with payment terms and `rechtsgrundlage`, every `angebot` and `angebotsposition` with unit prices, every `kalkulation` and `kalkulation_position` with internal hourly rates, and `vertrag_abrechnung` with contract economics. AUT-05 requires RLS to mirror application authorization, and here it mirrors nothing. Phase 3 shipping before Phase 4 does not help: this document defines the Phase 4 policies and they contain no hook for the Phase 3 predicate.

**Required fix:** Define `app.hat_recht(p_recht text) RETURNS boolean` (SECURITY DEFINER over `berechtigung`/`benutzer_mandant`) now, and add it to the SELECT policy of every commercially sensitive table in this domain: `kunde`, `ansprechpartner`, `angebot`, `angebotsposition`, `kalkulation`, `kalkulation_position`, `vertrag_abrechnung`, `auftrag_leistung`, `leistungskatalog_position`. State the required right per table in this document so Phase 4 migrations can be written against it.

### B17. `angebot.brutto_cent bigint` is a stored gross total maintained by trigger, guarded only by `CHECK (brutto_cent >= netto_cent)`, while §0 of the same document states "Totals per tax-rate group come from the view `angebot_steuersumme`, never from a stored gross."

**Why it breaks:** Invariant 1 forbids deriving VAT from a gross total, and the reason it does is that a stored gross drifts. Here there are two sources of truth for the same number and the CHECK cannot detect disagreement — it only asserts brutto ≥ netto, which holds for any wrong value. Once the offer is frozen after sending, a drifted `brutto_cent` is permanent and is what the OPS-08 PDF and the FIN-07 order conversion read. The document contradicts its own stated rule in the table immediately below it.

**Required fix:** Drop `brutto_cent` from `angebot` and read the per-group figures from `angebot_steuersumme` (with `security_invoker`), or keep it strictly as a cache with `steuer_cent` broken out per group in a `angebot_steuer` child table and a nightly reconciliation job. Keep `netto_cent` as the trigger-maintained sum of `typ='leistung'` lines only, which is correct as written.

### B18. `gueltig_bis` carries two different semantics for the same column name across sibling tables: `belagsart` and `leistungskatalog` use `CHECK (gueltig_bis > gueltig_ab)` with `daterange(gueltig_ab, gueltig_bis)` (default `[)`, upper bound exclusive), `vertrag_abrechnung` uses explicit `'[)'`, and `auftrag_leistung` uses `CHECK (gueltig_bis >= gueltig_ab)` implying an inclusive last day.

**Why it breaks:** The natural service query is `gueltig_ab <= :stichtag AND (gueltig_bis IS NULL OR gueltig_bis >= :stichtag)` — inclusive. Against a `[)` `EXCLUDE`-enforced table that returns the *superseded* Leistungswert on the changeover day as well as the new one, so "the Leistungswert on date X" has two answers on exactly the day the draft's §7.2 argument is about. Against `auftrag_leistung` the same query is right. One of the two reproduces a historic price wrong by one day, and because `belagsart` feeds `Σ m² ÷ Leistungswert`, that is a wrong price, not a wrong label.

**Required fix:** Pick inclusive `gueltig_bis` everywhere (it is the German business reading), state it once in §0, and write every range as `daterange(gueltig_ab, gueltig_bis + 1, '[)')` in the `EXCLUDE` constraints. Use `CHECK (gueltig_bis IS NULL OR gueltig_bis >= gueltig_ab)` uniformly. Add a test: a Belagsart superseded on 2026-04-01 returns exactly one row for 2026-03-31 and exactly one for 2026-04-01.

### B19. `formular_eingang.eingegangen_am`, `lead_aktivitaet.geschehen_am` and `dokument_version.hochgeladen_am` are annotated "server clock, never a client value" but are enforced only by `DEFAULT now()`.

**Why it breaks:** A DEFAULT applies only when the column is omitted. Any INSERT that supplies a value — including one an agent tool or a compromised route constructs — writes an arbitrary timestamp, and the immutability trigger then makes that fabricated instant permanent. For `lead_aktivitaet` this is the §7 UWG evidence record and the SEC-A9 audit entry; for `formular_eingang` it is the Art. 7(1) DSGVO consent timestamp; for `dokument_version` it is the GoBD upload time. Invariant 5's principle — the server clock is the source of truth, never a client timestamp — is asserted in a comment rather than enforced.

**Required fix:** `BEFORE INSERT` trigger `erzwinge_serverzeit()` setting `NEW.<col> := now()` unconditionally on all three, and `BEFORE UPDATE` rejecting any change. If a genuine client-claimed time is ever needed (TIM-09 offline capture), store it in a separate `geraet_zeit`/`gemeldet_am` column with a deviation field, exactly as invariant 5 prescribes for `zeiteintrag`.

### B20. `kunde.ist_bauleistender boolean NOT NULL DEFAULT false` is the only §13b UStG datum, and nothing anywhere in the domain stores a §48b EStG Freistellungsbescheinigung, although `vertrag_abrechnung.unterliegt_bauabzugsteuer` asserts that "validity of the Freistellungsbescheinigung at the service date is checked in finance".

**Why it breaks:** Both determinations are per service date, not per row-as-of-today. §13b(2) Nr. 4 UStG turns on whether the recipient is a Bauleistender at the time of the supply; a bare boolean with no validity range and no evidence document cannot reconstruct that for an invoice issued last year, and finalized invoices are immutable and hash-chained, so the reconstruction can never be corrected. FIN-10 requires 15% withholding unless a Freistellungsbescheinigung is valid at the service date — the finance service is told to check a certificate that has no table, no number, no issuing Finanzamt, no `gueltig_von`/`gueltig_bis` and no scan, and the boundary-reference list in §2 does not declare one either. The check as designed cannot execute.

**Required fix:** Replace `ist_bauleistender` with a time-ranged child table `kunde_bauleistender_status (kunde_id, gilt_ab date, gilt_bis date, beleg_dokument_id, erfasst_von)` under the same `EXCLUDE` discipline used for `belagsart`. Add `freistellungsbescheinigung (mandant_id, kunde_id | nachunternehmer_id, bescheinigung_nummer, finanzamt, gueltig_von date, gueltig_bis date, dokument_id, widerrufen_am)` in this domain or declare it explicitly as a finance-domain boundary reference with its columns named. Emit `// TODO(client): Wird die Freistellungsbescheinigung je Kunde, je Auftrag oder je Nachunternehmer geführt, und wer erfasst sie?`

## MISSING (15)
- OPS-11 tasks and deadlines. The draft cites OPS-11 on `auftrag` and `auftrag_dokument` but models only documents. "Tasks, deadlines, status ... on every order and project" needs an `aufgabe` table (SPEC §22 lists it) with `auftrag_id`, `faellig_am timestamptz`, owner and status, or an explicit boundary reference to it. DSH-01 ("upcoming tasks") and CAL-01 (deadlines, follow-ups, customer appointments) have no source in this schema either — `lead_aktivitaet.faellig_am` covers CRM-04 follow-ups only.
- `projekt`. SPEC §22 lists `projekt` as a distinct entity and OPS-05 says "Orders **and projects**"; DSH-01 counts "active orders, active projects" as two separate KPIs and REP-05 reports project margin and deadline adherence. The draft silently folds projects into `auftrag` (citing REP-05 there) without saying so and without declaring `projekt` in the §2 boundary list. Either state the decision and record it in DECISIONS.md, or model `projekt`.
- The relationship between `auftrag_leistung` and `lv_position` (BAU-01) is undefined. Both hold OZ-numbered, priced, unit-bearing lines; the boundary list declares `lv_position.auftrag_id` and `aufmass.auftrag_leistung_id`, which forks the FIN-07 traceability path — an Aufmaß hangs off `auftrag_leistung` while the LV position it measures hangs off `auftrag`. BAU-05 ("warning when work outside the LV is logged without a Nachtrag") cannot be evaluated without a defined join. Declare whether `lv_position` is a specialisation of `auftrag_leistung` or carries `auftrag_leistung_id`.

Also nothing forces consistency: `CHECK (typ <> 'behoerde' OR (ist_oeffentlicher_auftraggeber AND leitweg_id IS NOT NULL))` is absent, so a public buyer can be created with `xrechnung_pflicht = false` and no Leitweg-ID — and SPEC states the group then cannot invoice them at all.

Add `steuerbefreiung_grund text` on `angebotsposition` / `auftrag_leistung` with `CHECK (steuer_kennzeichen <> 'steuerfrei' OR (steuersatz_bp = 0 AND steuerbefreiung_grund IS NOT NULL))`, and emit `// TODO(client)` for the applicable §4 UStG grounds. - GoBD Stammdatenhistorie (LEG-01, SEC-A9). Only `geaendert_am` / `geaendert_von` are kept, i.e. the *last* change. Invoice-relevant customer master data — `name`, address, `ust_id`, `steuernummer`, `debitorennummer`, `zahlungsziel_tage`, `leitweg_id`, `ist_bauleistender` — must be reconstructable as at any past invoice date. No `audit_log` trigger is declared on any table in this domain, and SEC-A9 requires actor (human/agent/system), action, before, after, timestamp and IP; `akteur_typ` exists only on `lead_aktivitaet`. Declare the `audit_log` trigger attachment per table and add `akteur_typ`/`agent_aufgabe_id` to `erstellt_von`-bearing business tables.
- DSGVO Art. 17 erasure has no mechanism. `ansprechpartner`, `formular_eingang` and `lead_aktivitaet` hold personal data of natural persons; the domain grants no DELETE at all and only TODOs the *retention period*. Missing is the anonymisation path itself: which columns are overwritten, which shell is retained for the GoBD/§7 UWG audit trail, and how the conflict between invariant 8 and Art. 17 is resolved. Emit `// TODO(client): Löschkonzept — welche Personendaten werden bei einem Art.-17-Antrag anonymisiert und welcher Beleg-Rumpf bleibt aus GoBD-Gründen bestehen?` LEG-09's "data-subject request process" also needs a lookup path across all three tables (Art. 15/20), which no index supports.
- DSGVO Art. 22 / LEG-12 for `lead.punktzahl`. The score is correctly deterministic (invariant 6) and carries `punktzahl_begruendung`, but nothing records that no automated decision follows from it, and `kunde_typ = 'privat'` leads are natural persons. Add an explicit note plus, if scoring ever gates an action, a human-decision marker. This is a legal determination — emit `// TODO(client): Löst der Lead-Score irgendeine automatische Entscheidung aus (z. B. automatische Absage)? Falls ja, greift Art. 22 DSGVO.`
- Kreditoren / supplier master (ACC-07 "debtors and creditors", ACC-05 "extract supplier", FIN-14). `kunde.debitorennummer` covers the debtor side only; there is no `lieferant`/`kreditor` table and no boundary declaration for one. Also missing on `kunde`: a dunning block / `mahnstopp` flag for FIN-15.
- VOB warranty and retention on `auftrag`. `abnahme_am` is stored but there is no `gewaehrleistung_bis` (the Abnahme starts the Gewährleistungsfrist and drives the FIN-18 / REP-05 lifecycle) and no `sicherheitseinbehalt_bp` / `sicherheitseinbehalt_cent` (VOB/B §17), which the Schlussrechnung must deduct. The *period* is a legal value and must not be picked: `// TODO(client): Welche Gewährleistungsfrist wird vertraglich vereinbart (VOB/B §13 vs. BGB), und wird ein Sicherheitseinbehalt geführt?`

The `referenzfaehiger_auftrag` view is called "the only source the profile pages and the Social Media Center may read", but §3 states the `webseite` role has SELECT "on this table only" (`formular_definition`). The public profile pages therefore cannot read it, and granting the raw view would publish `auftragswert_netto_cent`, `kunde_id` and the site address. A dedicated public projection (released quote, trade, city, anonymised object description, released photo ids only) with its own `webseite` grant is missing.
- BFSG / WCAG 2.1 AA (PUB-09, LEG-07) in the `felder` contract. §1 specifies only the field `typ` discriminant. An accessible public form needs a mandatory programmatic `label`, a `hilfetext`, an `fehlermeldung` per validation rule, `pflicht`, and for `auswahl`/`mehrfachauswahl` an `optionen` list of `{wert, label}`. The field table in §4.4 shows a "Pflicht" column that has no home in the declared jsonb shape. Specify the full Zod union, since the form is consumer-facing and BFSG applies.
- The stated `raumbuch_import_zeile` purge is not implementable as written. The document says a `db_wartung` role may delete discarded staging rows, but the table has FORCE RLS and — per §0 — no DELETE policy at all. Add the explicit `CREATE POLICY del_wartung ON raumbuch_import_zeile FOR DELETE TO db_wartung USING (...)` and the corresponding `GRANT DELETE`, or the exception is documented but non-functional. Also, §0 calls this "the single exception" while `formular_eingang` separately states that spam rows "are purged by a job" — two contradictory delete stories.
- Referential actions. Every FK in the document is given as "FK -> x.id" with no `ON DELETE` / `ON UPDATE` clause. For a domain whose entire deletion protection is "no DELETE policy", the absence of an explicit `ON DELETE NO ACTION` (and specifically the absence of any `CASCADE`) needs to be normative, not implied by the Postgres default.

## INVENTED RULES — must become TODO(client) (8)
- `dokument`'s `erzwinge_loeschsperre()` trigger hard-codes *which* document categories carry a statutory deletion lock: `kategorie IN ('rechnung','beleg','buchhaltung')`. The retention *period* is correctly TODO'd, but the selection of categories is itself a legal determination and it is wrong by omission — §257 HGB / §147 AO cover Handelsbriefe, which includes `vertrag` and `angebot`; §17 MiLoG covers time records; personnel files have their own regime. Setting `loeschsperre` for three categories and leaving contracts and offers freely soft-deletable is an invented compliance boundary presented as "DOC-07 and ACC-06 true by construction". Should be a per-category configuration table with `// TODO(client): Welche Dokumentkategorien unterliegen einer gesetzlichen Aufbewahrungspflicht, und über welchen Zeitraum?`
- `kalkulation` fixes the Zuschlagskalkulation *base*: `selbstkosten_cent = lohn + material + geraet` and `gemeinkosten_bp` is documented as "basis points **on Selbstkosten**". OPS-07 states the five cost blocks but says nothing about the base the surcharge applies to. In Gebäudereinigung the Gemeinkostenzuschlag is very commonly calculated on the Lohnkosten alone; in Bau it is often split across Lohn/Material/Gerät with different rates. The percentage is TODO'd but the formula it multiplies is baked into a NOT NULL derived column. Should be `gemeinkosten_basis` (an enum: `lohn` / `selbstkosten` / `je_kostenart`) with `// TODO(client): Auf welche Bezugsgröße wird der Gemeinkostenzuschlag gerechnet — Lohnkosten oder Selbstkosten?`
- `formular_eingang.einwilligung_datenschutz boolean NOT NULL CHECK (einwilligung_datenschutz)` makes a privacy *consent* structurally mandatory for every offer request, and the column note maps `einwilligung_werbung` to `rechtsgrundlage = 'einwilligung'` vs `'anfrage'`. Processing an enquiry to prepare a quote rests on Art. 6(1)(b)/(f) DSGVO, not on consent; requiring consent for processing that is already necessary is the documented Kopplungs-/Freiwilligkeit problem, and a consent that cannot be refused is invalid. SPEC LEG-09 names a processing register, DPAs, a deletion concept and a DSAR process — no consent checkbox. The correct data shape is a `datenschutzhinweis_version` acknowledgement (which the draft already has, as `datenschutz_text_version`) plus an *optional* advertising consent. Emit `// TODO(client): Wird die Datenschutzerklärung als Hinweis bestätigt (Art. 6(1)(b)) oder als Einwilligung erhoben?`
- `raumbuch_import_zeile`: "purge rows of imports with status IN ('verworfen','fehler') **older than 90 days**". 90 days is a data-retention period, i.e. part of the DSGVO deletion concept (LEG-09) and, because the staging rows document how the live Raumbuch arose, arguably a GoBD question too. The draft correctly TODO'd retention for `formular_eingang` and `dokument` and then hard-coded a number here. Mark it `ist_platzhalter` / TODO(client) like the others.
- `referenzfaehiger_auftrag` and the PRO-05 partial index both require `status = 'abgeschlossen'`. PRO-05 says references are "pulled from real jobs where `freigegeben_vom_kunden = true`" — it does not require the job to be finished. A three-year running Rahmenvertrag is the most valuable reference a cleaning company has and this silently excludes it. Either drop the completion requirement or record the narrowing as an explicit decision.
- `lead.sla_frist_am timestamptz NOT NULL` on every lead, while `sla_stunden` exists only on `formular_definition`. REQ-05 attaches an SLA to a *submission*. Manual, referral and `vergabe_radar` leads have no form, so the intake service must invent an SLA to satisfy NOT NULL — a business rule chosen by a NOT NULL constraint. Make it nullable, or add a per-mandant default SLA with `// TODO(client): Gilt die Reaktionszeit auch für manuell erfasste Leads, Empfehlungen und Radar-Treffer?`
- `lead.punktzahl smallint CHECK (punktzahl BETWEEN 0 AND 100)` fixes the scoring scale. CRM-02 names a lead score but no range, and the criteria and weights are correctly listed as open. A 0–100 scale is a modelling convention rather than a legal rule, so this is the mildest item here, but it should be stated as an assumption in DECISIONS.md rather than as a CHECK presented without comment.
- `vertrag_abrechnung.leistungszeitraum_modus … DEFAULT 'kalendermonat'`. FIN-05 makes the Leistungszeitraum mandatory and warns that its absence voids the customer's input-tax deduction; it does not say how it is derived. Defaulting every contract to calendar-month derivation is a billing rule chosen silently for the one field the SPEC calls the most-omitted. Drop the default (make it NOT NULL, no default) so it must be chosen consciously, as the draft rightly did for `sla_stunden` and `zahlungsziel_tage`.

## MINOR (20)
- Trigger and function names are German — `set_geaendert_am()` aside, `erzwinge_mandant_konsistenz()`, `erzwinge_widerspruch()`, `pruefe_katalog_hierarchie()`, `angebot_nach_versand_unveraenderlich()`, `aktualisiere_angebot_summen()`, `crm_darf_kontaktiert_werden()`, `verhindere_dokument_loeschung()` and the `webseite` role. CLAUDE.md's language rule puts domain *identifiers* in German and *infrastructure* in English (`createInvoice`, `withTenant`, `hashChain`). Trigger functions and roles are infrastructure. Pick one convention and state it in §0.
- `lead_status` is justified as "aligned to the DESIGN §5 status-pill vocabulary so no undefined pill colour can occur", but DESIGN §5 fixes the vocabulary as In Arbeit · Aktiv · Bereit / Geplant · In Prüfung · Entwurf / Angebot · Offen · Wartet / Überfällig · Abgelehnt · Fehler / Abgeschlossen · Archiviert. Five of seven `lead_status` values (`neu`, `qualifiziert`, `gewonnen`, `verloren`, `kein_bedarf`), three of five `auftrag_status` values (`angelegt`, `pausiert`, `storniert`) and four of seven `angebot_status` values (`versendet`, `angenommen`, `zurueckgezogen`, `abgelaufen`) have no pill mapping. Per CLAUDE.md the fix is to add them to DESIGN.md first, then use them — not to claim alignment that does not exist.
- `CHECK (skonto_prozent_bp IS NULL) = (skonto_tage IS NULL)` is malformed as written; the parenthesis closes before the comparison. Should be `CHECK ((skonto_prozent_bp IS NULL) = (skonto_tage IS NULL))`.
- `dokument.exif_entfernt` is enforced only for `mime_typ LIKE 'image/%'`. TIM-10 requires "photo **and video** capture, EXIF stripped", and video containers and PDFs both carry location and device metadata. Widen to `CHECK (mime_typ NOT LIKE 'image/%' AND mime_typ NOT LIKE 'video/%' AND mime_typ <> 'application/pdf' OR exif_entfernt)`.
- `mime_verifiziert boolean NOT NULL DEFAULT false CHECK (mime_verifiziert)` and `einwilligung_datenschutz boolean NOT NULL DEFAULT false CHECK (einwilligung_datenschutz)` pair a default with a CHECK the default violates, so any INSERT omitting the column fails with a constraint error rather than being defaulted. Drop the defaults.
- The storage path `mandant/<mandant_id>/<kategorie>/<dokument_id>/<version_nr>/<dateiname>` embeds `kategorie`, which is not in `dokument`'s immutability list. Recategorising a document makes the stored object key diverge from the documented formula. Drop `kategorie` from the path; `dokument_id` already scopes it.
- `crm_darf_kontaktiert_werden` requires the channel to appear in `einwilligung_kanaele` for *every* channel under `rechtsgrundlage='einwilligung'`, but `lead_aktivitaet.kanal` also allows `vor_ort` and `portal`, which are not in the consent channel list and are not electronic advertising under §7 UWG. A site visit to a consented customer is blocked. Restrict the channel test to the electronic set and align the two lists (the CHECK gates `email·telefon·sms·post·whatsapp`; the consent array allows `email·telefon·sms·post·whatsapp`; `kanal` allows those plus `vor_ort·portal`).
- `lead.ansprechpartner_id NOT NULL` combined with `ansprechpartner.nachname NOT NULL` forces the intake service to fabricate a named natural person for every `quelle='vergabe_radar'` lead, where the notice often names only a Vergabestelle. That creates a personal-data record with `rechtsgrundlage='keine'` for every notice ingested. Make it nullable and move the requirement to the outbound gate (see blocking item 4).
- `kalkulation_position.berechnungsweg` is `text NOT NULL` with `CHECK (length(berechnungsweg) > 0)` and a free-form German-formatted example. BAU-02 requires the Rechenansatz *and* the computed result both visible and machine-checkable; a free string cannot be re-verified. Consider storing the ansatz as text plus the parsed operands, as BAU-02 will need anyway.
- `angebotsposition.einzelpreis_cent` may be negative for a Nachlass line, but no column records whether a position was authored by a human or an agent. The autonomy matrix says "Discount or concession — **never**" automatic, and nothing in the schema distinguishes the two. Add `akteur_typ` / `agent_aufgabe_id` alongside `erstellt_von`.
- `CHECK (menge IS NULL OR menge <> 0)` on `angebotsposition` blocks a legitimate zero-quantity Bedarfs-/Eventualposition, which VOB LVs do carry. Restrict the check to `typ = 'leistung'`.
- `objekt.ansprechpartner_id` has no constraint tying the contact to `objekt.kunde_id`; an on-site contact from a different customer is insertable.
- `objekt.kunde_id NOT NULL` forces a duplicate `objekt` row when the same building is contracted by two customers within one mandant (owner vs tenant), and for a security `veranstaltungsort` (REQ-03) that has no customer master record yet. Consider making it nullable with a service-layer requirement, or model the customer link on `auftrag_leistung`.
- `angebot.version` has no uniqueness or ordering constraint against `ersetzt_angebot_id`; two v2 offers can supersede the same predecessor.
- `raum.import_id` is a single FK described as "created **or last touched**", so a second import overwrites the provenance of the first. For OPS-04 under GoBD the touch history matters; consider a `raum_import_historie` link table.
- `dokument.sha256` duplicates `dokument_version.sha256` for the current version with no constraint keeping them equal — a drift risk in exactly the field GoBD integrity rests on.
- The `webseite` role's policy on `formular_definition` grants SELECT on the whole row, exposing `standard_besitzer_benutzer_id`, `eskalation_benutzer_id` and any internal content in `felder` to anonymous public traffic. Use column-level `GRANT SELECT (id, mandant_id, schluessel, version, titel, beschreibung, felder, datenschutz_text_version)` or a dedicated public view.
- `lead` has `CHECK (status <> 'verloren' OR verloren_grund IS NOT NULL)` but `kein_bedarf` is equally a loss state for REP-02 conversion analysis and requires no reason.
- The §14 UStG address fields on `kunde` (`strasse`, `plz`, `ort`) are all nullable and the document says FIN-04 handles it, but never names which columns the pre-flight validator reads. State the FIN-04 contract here so the finance phase has something to implement against.
- `angebot_steuersumme` produces no row for an offer with zero `typ='leistung'` positions; the `aktualisiere_angebot_summen()` trigger needs an explicit zero case, otherwise `netto_cent`/`brutto_cent` retain stale values when the last position is removed from a draft.
