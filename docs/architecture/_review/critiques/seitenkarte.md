# Adversarial review — seitenkarte

## BLOCKING (17)

### B1. Hard URL collision: `/reinigung`, `/security`, `/bau`, `/operations` are simultaneously public 308 redirects (§2.2) and the portal tenant dashboards `/[mandant]` (§4.1).

**Why it breaks:** Next.js route groups do not appear in the URL. `src/app/(public)/reinigung/route.ts` (or the redirect config) and `src/app/(portal)/[mandant]/page.tsx` both resolve the path `/reinigung`. Whichever is registered first wins: either every tenant dashboard is unreachable (a `leitung` user in Reinigung lands on the marketing profile after every mandant switch, because §8.3 says switching 'lands on the new area's dashboard, /[mandant]'), or the four short marketing URLs 404. There is no configuration in which both work.

**Required fix:** Drop the short public redirects entirely (the draft already argues `/unternehmen/[bereich]` is the single canonical URL, so they add nothing but this collision), or move the whole portal under a non-colliding prefix — `/portal/[mandant]/...` — and make `gruppe`, `mein`, `konto` children of it. Then the reserved-slug problem below shrinks to one namespace instead of two.

### B2. The reserved-slug check constraint on `mandant.slug` (§1.5 rule 4) lists only `gruppe`, `mein`, `konto`, `api`, `check-in`.

**Why it breaks:** The portal shares the URL root with roughly twenty-five static public and auth segments the constraint does not name: `login`, `logout`, `auth`, `einladung`, `passwort-vergessen`, `passwort-zuruecksetzen`, `mitarbeiter-login`, `kein-zugriff`, `unternehmen`, `leistungen`, `projekte`, `ueber-uns`, `news`, `kontakt`, `karriere`, `angebot`, `impressum`, `datenschutz`, `barrierefreiheit`, `sitemap.xml`, `robots.txt`, `llms.txt`, `.well-known`. TEN-08 promises a fifth area needs a DB row and no code change; under this design inserting a mandant with slug `news` or `kontakt` silently shadows a public page or an auth route, which is a code-change-required outage triggered by a data insert — the exact failure TEN-08 exists to prevent.

**Required fix:** Either prefix the portal (`/portal/[mandant]`), which reduces the reserved set to the portal's own statics, or make the constraint enumerate every static top-level segment and add a test that walks the App Router tree and fails CI when a new static root segment is added without being added to the constraint. State the mechanism in the document; a hand-maintained list with no test is not TEN-08 compliance.

### B3. Group scope (§7, 25 routes) has no defined session/RLS mechanism. `withTenant(mandantId)` sets exactly one tenant; `requireGroupScope()` is described only as marking the request read-only.

**Why it breaks:** Invariant 3 puts the active tenant in the server session and TEN-03 puts RLS on every tenant table. Under group scope there is no active mandant, so every RLS policy keyed on the session's single mandant claim matches zero rows. `/gruppe/finanzen`, `/gruppe/rechnungen`, `/gruppe/kunden`, `/gruppe/auftraege`, `/gruppe/dienstplan`, `/gruppe/zeiten` and the rest render empty — not denied, empty, which is worse because it looks like a business answer. TEN-05 and DSH-01/DSH-02 become unimplementable.

**Required fix:** Specify the group-scope session shape and the matching policy: the session carries `mandant_ids uuid[]` (the set the user holds `gruppe.lesen` over) plus a `scope = 'gruppe'` flag; every tenant table gets a second SELECT-only policy `mandant_id = ANY(current_mandant_ids())` that exists only for SELECT, so no INSERT/UPDATE policy can ever match under group scope — that makes invariant 10 enforced by Postgres, not only by `requireGroupScope()`. Name the helper (`withGroupScope(mandantIds)`), state that it sets no write policy, and add it to §1.2's legend.

### B4. The mandant switcher's live counters (§8.3, TEN-10, DESIGN §6 rule 2) are a cross-tenant aggregate rendered in the header of every single portal page, executed while exactly one mandant is active.

**Why it breaks:** `Reinigung · 24 Aufträge / Sicherheit · 8 Aufträge / Bau · 12 Projekte` requires counting `auftrag` and `projekt` rows in mandanten other than the active one. Under the stated model (`withTenant(session.mandantId)` plus RLS) that query returns the active mandant's count and zero for the other three. Every page in the product then ships a switcher showing three zeros — a visible, permanent defect on the platform's signature interaction.

**Required fix:** Define an explicit counter path: a `SECURITY DEFINER` function `switcher_counters(benutzer_id)` returning only `(mandant_id, count)` pairs for mandanten the user has a `benutzer_mandant` row in, granted to authenticated only, returning counts and nothing else. State that it is the only cross-tenant read allowed outside group scope and that it returns no business data beyond an integer.

### B5. TIM-14 / D-09 clause 1+2: the ArbZG detector 'queries by person_id, across every employment in every entity', but `einsatz` and `zeiteintrag` are tenant-scoped tables under RLS and the roster is `M1`.

**Why it breaks:** A planner in `reinigung` opening `/[mandant]/dienstplan/einsatz/[id]` runs with the reinigung mandant active. The 11h-rest and daily-maximum checks must read the person's `einsatz` rows in `security` and `bau`. RLS returns none of them, so the detector reports no conflict and the 6h cleaning + 5h security case — the explicit ROADMAP Phase 5 acceptance criterion and the confirmed reason D-09 exists — silently passes. This is the highest-value invariant in the document and it is asserted in prose with no mechanism.

**Required fix:** Specify a `SECURITY DEFINER` function, e.g. `arbzg_konflikte(person_id, von_utc, bis_utc)`, that reads `einsatz`/`zeiteintrag` across all mandanten and returns only the minimised projection the draft's own TODO proposes — `(mandant_id, beginn_utc, ende_utc, verstoss_art)`, never `objekt_id`, `kunde_id`, `auftrag_id` or any rate column. Grant EXECUTE to the scheduling service role only. Note in §4.9 that this function is the single audited hole in the RLS boundary and that a test must assert its result set contains no foreign-key columns.

### B6. D-09 clause 6 ('a cleaning manager must not see security wage rates') is asserted as an RLS consequence, but Postgres RLS is row-level. `/gruppe/personal` ('no wage data'), `/gruppe/zeiten` ('overtime aggregated per person across entities') and `/[mandant]/personen/[personId]` ('list of employments by entity name only') all read `anstellung` rows belonging to other mandanten.

**Why it breaks:** There is no row-level policy that returns an `anstellung` row while hiding its `stundensatz_intern` column. Once the row is visible to the group query, the column is visible to anything that selects it — an accidental `select *` in a service, a CSV export on `/gruppe/personal`, or a future report. `/gruppe/zeiten`'s overtime figure is derived from `stundenkonto`, which is per-employment and rate-adjacent. The document promises a guarantee its stated enforcement layer cannot deliver.

**Required fix:** Define the projection explicitly: a view `anstellung_gruppe_v (id, person_id, mandant_id, personalnummer, eintritt, austritt, aktiv)` with no cost columns, `security_invoker = false`, its own grant, and a policy allowing the group-scope mandant set. State that `/gruppe/personal`, `/gruppe/zeiten` and `/[mandant]/personen/[personId]` read only this view and never the base table, and add a test asserting the view's column list does not contain `stundensatz_intern` or any `*_cent` column.

### B7. The `PER` write model (§1.2, §1.4, §5) takes an `anstellung_id` from the request and derives the mandant from it, with no stated ownership check.

**Why it breaks:** `anstellung_id` submitted by a phone is client state. Nothing in the document says the server verifies `anstellung.person_id = session.person_id` before deriving the mandant and executing. A worker employed only by `reinigung` can post another person's `anstellung_id` to `/mein/zeiten/[id]/einwand`, `/mein/urlaub/antrag` or `/mein/schichten/[einsatzId]/wachbuch/neu` and write a row into `security`. That is a cross-tenant write via the exact parameter the model is built on, and AUT-06's 404 rule never fires because the route was never scoped in the first place.

**Required fix:** State the resolution order as a numbered rule the way §1.5 does for `[mandant]`: (1) load the `anstellung` row by id with RLS bypassed for this lookup only; (2) if `anstellung.person_id !== session.personId` → 404, not 403; (3) if `anstellung.austritt` is set and the target date is after it → 404; (4) `withTenant(anstellung.mandant_id)` for the remainder of the transaction; (5) the service re-checks the same predicate. Add it to §1.2's `PER` row so it cannot be missed by the PR that implements a single `/mein` form.

### B8. `/konto/kalender-feed` (CAL-03) is marked `USR` under the legend 'no `mandant_id` is read or written'.

**Why it breaks:** An iCal feed aggregates `einsatz`, `kalender_eintrag`, `aufgabe` and customer appointments — all tenant tables carrying `mandant_id` — across every mandant the person works in, and it is fetched by a calendar client as an unauthenticated bearer URL that is polled every few minutes, cached on the device, and syncs to whatever cloud account the client is signed into. The row is therefore both mislabelled (the legend's guarantee is false) and the single widest data-exfiltration surface in the product: object addresses, customer appointment subjects and shift patterns for three legal entities behind one guessable-if-leaked URL, outside any session and outside `withTenant`.

**Required fix:** Reclassify it as its own scope token (e.g. `FEED`), specify that the token is stored hashed, is per-user and revocable from the page, that the handler resolves person → employments → mandant set server-side and reads through the same read-only group-scope policy, and enumerate exactly which fields the feed emits (start, end, duration, object name, entity name) with an explicit exclusion of customer name, commercial terms and any money value. Same correction applies to `/konto/zugriffe`, which reads `benutzer_mandant` — a `mandant_id`-bearing table — while claiming it does not.

### B9. `kunde` users are placed inside the `(portal)` shell with the mandant switcher (§4.22, §8.3), and DESIGN §6 rule 2 makes each switcher row show a live counter.

**Why it breaks:** A customer buying from two entities gets a dropdown reading `Reinigung · 24 Aufträge / SSE Security · 8 Aufträge`. Those are the supplier's total order counts across all its customers. A customer learns the group's order volume per entity and can watch it move month to month. It is a commercial leak shipped by the default rendering of the signature component, and it contradicts the draft's own EMP-13-style promise that customers see only their own records.

**Required fix:** State that for the `kunde` role the switcher renders entity name and identity ring only, with counters either scoped to that customer's own records or suppressed, and that the counter query (see the switcher-counter finding above) takes the viewer's role as an input. Also define the `kunde` desktop navigation: §8.1's sidebar renders only groups whose module the user holds `lesen` on, and a `kunde` holds only `kundenportal.*`, so the current specification produces a 248px empty sidebar on every customer page.

### B10. `/angebot/reinigung` … `/angebot/operations` are static segments while the thank-you page is `/angebot/[bereich]/danke` (§2.3).

**Why it breaks:** The App Router matches static before dynamic at each segment and does not backtrack. Once `/angebot/reinigung` resolves against the static folder, there is no `danke` child, so `/angebot/reinigung/danke` returns 404 — for all four areas. Every offer request (REQ-01…REQ-07, the Phase 2 acceptance path) ends on a 404 after the lead has been written, so the submitter reasonably re-submits and the SLA queue fills with duplicates.

**Required fix:** Either put the confirmation at `/angebot/danke?bereich=…` (a single static route), or make the area segment dynamic throughout — `/angebot/[bereich]` and `/angebot/[bereich]/danke`, with `[bereich]` validated against `mandant.slug` — and drop the four static folders. The same static-shadows-dynamic rule applies to `/karriere/bewerbung` vs `/karriere/[stelle]`: a Stelle whose slug is `bewerbung` becomes unreachable, which needs the same slug-reservation treatment as `mandant.slug`.

### B11. §1.5 rule 3: when the user is a member of `params.mandant` but it is not the active one, the layout redirects to `/[mandant]/wechseln?ziel=…`, and §4.1 marks that route `M1`.

**Why it breaks:** `/[mandant]/wechseln` sits under `src/app/(portal)/[mandant]/layout.tsx`, which is the layout that just performed the check. Rendering it re-runs rule 1-3: the slug still differs from the session's active mandant, so it redirects to itself. Infinite redirect loop, and the only escape from a deep link into a non-active mandant is clearing the session. The `M1` marking is also wrong on its own terms: at GET time the route must read the `mandant` row of a tenant the session is not scoped to.

**Required fix:** State the exemption explicitly — `wechseln` is checked before the slug/session comparison and is the one segment the comparison skips — or move it out of the dynamic segment to `/wechseln?ziel=…&mandant=…`, which also removes the `M1` contradiction. Give it its own scope token (membership-checked, no active tenant) in §1.2.

### B12. TIM-07 states the check-in token is single use; §3.1 uses one token for two legs ('same token, second leg').

**Why it breaks:** This is a silent reinterpretation of a SPEC constraint, and it is the constraint that makes the token safe. A token that survives its first use is a bearer credential that stays valid for the whole shift window ±1h and can write a second time record from any device that has seen the URL — a worker forwarding the link to a colleague is undetectable, which is precisely the abuse a single-use token prevents in a §17 MiLoG record. It also leaves `/check-in/abgelaufen`'s `verbraucht` state undefined: consumed after which leg?

**Required fix:** Do not decide this silently. Either issue two `checkin_token` rows per `einsatz` (`zweck = 'einstempeln' | 'ausstempeln'`, the second delivered on successful check-in), which keeps single use literally true, or record the deviation as a decision in DECISIONS.md with a `// TODO(client)` and state the compensating control (device binding on first use, or a one-time re-issue that is written to `audit_log`). Also state that the token is stored hashed and that the mandant is read from the `einsatz` row, never from anything inside the token.

### B13. There is no route anywhere in the map that captures the customer-side tax facts that FIN-09, FIN-10 and FIN-11 depend on. `/[mandant]/kunden/[id]` tabs are Übersicht · Ansprechpartner · Objekte · Aufträge · Angebote · Rechnungen · Dokumente · Kommunikation · Portalzugang.

**Why it breaks:** FIN-11 requires the Leitweg-ID on every XRechnung (it is the buyer reference, BT-10, and a public buyer's invoice is rejected without it) — the page map has nowhere to enter it, so the XRechnung route can only emit invalid documents and SPEC's 'without XRechnung the group cannot invoice public buyers at all' stands. FIN-09 needs the recipient's §13b status (the USt 1 TG evidence) per customer; FIN-10 needs a §48b Freistellungsbescheinigung with a validity window so the validator can test validity 'at the service date' — the draft claims the screen 'shows which date it used' while providing no store for the certificate. The recipient's USt-IdNr, a §14 UStG field, is likewise absent.

**Required fix:** Add `/[mandant]/kunden/[id]/steuer` (permission `kunde.bearbeiten`) holding USt-IdNr, Steuernummer, Leitweg-ID, `ist_bauleistender` (§13b evidence with document reference), and `freistellungsbescheinigung` rows with `gueltig_von`/`gueltig_bis` as DATE plus the scan in the private bucket. Add a second surface on `/[mandant]/eingangsrechnungen/[id]` for the mirror case — a subcontractor's §48b certificate, validated at the service date before payment — because FIN-10 bites in both directions and the draft covers neither.

### B14. Agent cost and budget (`/[mandant]/agenten/[agent]/protokoll` per-step cost, `/[mandant]/agenten/budget`) fall under §4's blanket rule that 'every money value is rendered 1.234,56 € from integer cents'.

**Why it breaks:** A single model call costs fractions of a cent. Stored as bigint euro-cents, every step rounds to 0 and the monthly consumption stays at €0,00 no matter how much is spent. AGT-05 requires a hard stop at the cap with notification and 'never silent degradation' — the accumulator never reaches the cap, so the hard stop never fires and the first signal is the provider invoice. This is exactly the silent, expensive, late-discovered class CLAUDE.md names.

**Required fix:** State the unit explicitly and separately from invariant 1's money rule: `kosten_mikrocent bigint` (or `kosten_nanoeur`) on `agent_schritt`, summed at full precision, converted to cents only for display and only at the budget aggregate. State the currency and, because the provider bills in USD, either fix the accounting currency with a recorded FX source or record `waehrung` alongside the amount — and mark the FX rule `// TODO(client)` rather than picking one. Note that these columns are cost accounting, not invoiceable money, and never feed `rechnung`.

### B15. §1.6 gates Raumbuch and Belagsarten to the `reinigung` mandant only.

**Why it breaks:** OPS-02, OPS-03 and OPS-04 sit in SPEC §7 Operations, not in §8's cleaning trade module — Raumbuch is a platform capability, and SPEC §8's cleaning block (CLN-01…CLN-05) deliberately does not contain it. The gate also contradicts the draft's own §4.22, which promises `/[mandant]/kundenportal/objekte/[id]` with 'Raumbuch read-only' for a customer portal that is enabled for `security` and `bau`: for those two mandanten that tab renders against a module the same document disabled. Security posts and construction rooms both need room-level area data, and `/[mandant]/objekte/[id]` lists a Raumbuch tab unconditionally in §4.5.

**Required fix:** Move Raumbuch and Belagsarten to the all-mandanten row of the module table with the rest of Operations, and keep only the cleaning-specific derivations (Reviere, Turnus, Leistungsnachweise, the m²÷Leistungswert costing) in the `reinigung` module. If the client genuinely wants Raumbuch cleaning-only, that is a business decision — mark it `// TODO(client)` rather than deciding it in a module table.

### B16. `/[mandant]/personal/[anstellungId]` carries a 'Zugang' tab and a 'Nachweise' tab, while the draft's own attachment rules place `mitarbeiter_zugang` and `nachweis` on `person_id` (D-09).

**Why it breaks:** Invariant 9 in route form: a human fact is rendered — and by the tab's placement, edited — from a tenant-scoped employment route. A person employed by `reinigung` and `security` has two `/personal/[anstellungId]` pages, each with an editable Zugang tab for one login and a Nachweise tab for one certificate set. Two edit surfaces over one row is how you get the outcome D-09 exists to prevent (one valid and one expired copy of the same §34a certificate), and it lets a cleaning admin reset the SMS login of a person who is primarily a guard. It also duplicates `/[mandant]/personen/[personId]`, which the draft says is the human's page.

**Required fix:** Make the tabs on `/personal/[anstellungId]` read-only mirrors that link to `/[mandant]/personen/[personId]`, and state that every write to `mitarbeiter_zugang`, `nachweis` and `bewacher_eintrag` happens only on the person route. State which mandant may write person-level rows when several employ the person — the answer must be defined, not implicit.

### B17. The `mitarbeiter` principal has no grounded permission model. EMP-01 signs operatives in via `mitarbeiter_zugang`, which per D-09 hangs off `person_id` and therefore carries no `mandant_id`; §1.5 rule 2 resolves authorization from `benutzer_mandant` rows.

**Why it breaks:** An SMS-authenticated operative has no `benutzer` row and no `benutzer_mandant` row, so `requirePermission('mein.lesen')` has nothing to resolve against, `/[mandant]` deep links cannot 404 correctly for them, and the §4.1 rule 'mitarbeiter is redirected to /mein' cannot fire because the role is never established. The entire §5 route family (24 routes, the largest user population) rests on an identity that the auth model never connects to the permission model. §6 compounds it: `/konto/sicherheit` offers password and recovery codes to a principal that has neither, and `/konto/benachrichtigungen` is named as the home of NOT-02 while §5 puts notification channels on `/mein/profil`.

**Required fix:** State the relationship between `benutzer` and `mitarbeiter_zugang` explicitly: either every operative also gets a `benutzer` row (with `mitarbeiter_zugang` as an alternative credential on it) and roles resolve normally through `benutzer_mandant`, or the SMS principal is a distinct session type whose permissions are derived from its `anstellung` rows and which is barred from `/konto/*` and `/[mandant]/*` by the route group itself. Then fix the duplicated language and notification-preference surfaces (`/mein/profil` vs `/konto/profil` vs `/konto/benachrichtigungen`) so `person.sprache` has exactly one editor.

## MISSING (18)
- `/[mandant]/kunden/[id]/steuer` — the customer tax tab (USt-IdNr, Leitweg-ID, §13b/USt 1 TG status, §48b Freistellungsbescheinigung with DATE validity window). FIN-09, FIN-10 and FIN-11 are all unimplementable without it.
- `/[mandant]/einstellungen/mahnwesen` — FIN-15 requires escalation levels, fees and interest, and `/[mandant]/mahnungen` renders them; the settings section (nummernkreise, steuer, abrechnungsarten, arbeitszeit, agent-richtlinien, vorlagen, integrationen, datenschutz, import) has no dunning configuration at all. The level count, the day offsets, the fee per level and the interest basis (§288 BGB) are all unstated and none is marked `// TODO(client)`.
- `/[mandant]/qualifikationen` — `qualifikation` is a distinct entity in SPEC §22 and SEC-01 requires posts to declare required qualifications, but no route manages the catalogue. `/[mandant]/security/posten/[id]` can display required qualifications it has no way to define.
- `/[mandant]/nachrichten` — a staff-side message inbox. `nachricht` (SPEC §22) is reachable at `/[mandant]/kundenportal/nachrichten` and `/mein/nachrichten` but nowhere in the office portal, so a customer message lands where no `leitung` user can read it and NOT-03's 'each notification links to its record' has no target.
- A check-in token administration surface — issuing, re-issuing and revoking `checkin_token` rows, and inspecting which tokens were consumed. TIM-07 tokens must be delivered to workers and a lost link at 05:55 has no recovery path in the current map.
- A data-subject request processing inbox. `/datenschutz/anfrage` (public) and `/karriere/bewerbung` create obligations under DSGVO Art. 12(3) (one month) and Art. 15, but nothing internal receives them, no SLA watchdog escalates them, and there is no person-scoped data export for an employee or applicant DSAR.
- The Art. 30 DSGVO processing register (Verzeichnis von Verarbeitungstätigkeiten) named in LEG-09. ACC-10's GoBD Verfahrensdokumentation gets a generated route; the Art. 30 register — a different document with a different legal basis — gets nothing, and §21's DPA list (Supabase, Vercel, OpenAI) has no surface either.
- An unsubscribe / Werbewiderspruch route and the link target every outbound message must carry. CRM-08 and LEG-08 gate sending on a recorded legal basis, but nothing lets a recipient withdraw it (Art. 21 DSGVO, §7 Abs. 3 Nr. 3-4 UWG), and no route flips `rechtsgrundlage` to `keine` on request.
- A route that can grant `gruppe.lesen` and manage group-level users. `/einstellungen/rollen` and `/einstellungen/benutzer` are per-mandant (AUT-03), `/konto/zugriffe` is explicitly read-only, and `gruppe.lesen` is inherently cross-mandant — so as specified nobody can ever grant it, and the document also never says who creates the first `super_admin` or how a super_admin acquires the `benutzer_mandant` rows that §1.5 rule 2 demands before any route resolves.
- The `kunde` role's desktop navigation. §8.2 gives customers a mobile tab bar; §8.1's sidebar renders only groups whose module the user holds `lesen` on, and a customer holds only `kundenportal.*`, so every customer page has an empty 248px sidebar.
- The §14 UStG field list the `/[mandant]/rechnungen/[id]/pruefung` validator enforces. Only `Leistungszeitraum` is named. For a document that is 'the contract the implementation PRs will be built against', enumerate all of them — issuer name and address, recipient name and address, issuer Steuernummer or USt-IdNr, invoice date, number, quantity and nature of the service, Leistungsdatum/-zeitraum, Entgelt broken down per tax rate, applied rate and tax amount or the exemption reason, any agreed reduction, the §13b Steuerschuldnerschaft note, and §14 Abs. 4 Nr. 9's Hinweis auf die Aufbewahrungspflicht for Grundstücksleistungen billed to a private customer — which applies directly to Gebäudereinigung and Bau and appears nowhere.
- A surface for the month-end split. SPEC §9 and ROADMAP Phase 5 make 'a shift crossing month-end splits by actual minutes per month' an acceptance criterion, but neither `/[mandant]/stundenkonten/[anstellungId]` ('month history') nor `/[mandant]/stundenkonten/abschluss` mentions it, and a locked month whose boundary shift is not split cannot be reconciled afterwards because the lock is one-way.
- RAD-07 status transition controls. The radar routes cite RAD-07 but never enumerate its vocabulary (`neu · geprüft · verworfen (+reason) · in Bearbeitung · eingereicht`) and provide no control to set it. Because D-07 correctly removes any submit button, `eingereicht` and `verworfen` with its mandatory reason can never be recorded, and `/[mandant]/berichte/ausschreibungen` (found · screened · bid · won) has no data to report.
- The SMS provider for EMP-01. `/mitarbeiter-login` and `/mitarbeiter-login/code` ship in Phase 3 with no named gateway, no `SmsChannel` interface, no 'nicht verbunden' state and no DPA — D-04 requires every processor pinned to an EU region with a signed DPA recorded in DECISIONS.md, and phone numbers going to a non-EU gateway is a transfer. Same gap for the email sender (NOT-02, `sende_email` in AGT-02, dunning, offer delivery) and for the map tile and geocoding provider behind `/[mandant]/objekte` ('list + map'), `/gruppe/objekte` ('one map') and OPS-01's coordinates.
- The labour rate source for `/[mandant]/angebote/[id]/kalkulation`. OPS-07 costs labour; SPEC §0 names the cleaning sector minimum wage; CLAUDE.md names tariff rates as an example of a rule that must never be guessed. The route computes a labour cost with no stated rate source and no `// TODO(client)` — and pricing below the applicable sector minimum wage is a disqualification ground in a public tender the Radar module is built to win.
- Retention periods. `/[mandant]/recruiting/datenschutz` shows a 'retention clock' and `/[mandant]/einstellungen/datenschutz` shows 'retention per document category', but no period is stated for REC-07/LEG-11 applicant data or for any DOC-07 category, and neither is listed as an open question. These are legal values; they need `// TODO(client)` entries, not blank screens.
- The unit and currency of RAD-04 value bounds and of ingested notice values. `/[mandant]/radar/profile/[id]` sets 'value bounds' and `/[mandant]/radar` shows notice values — these are money and must be bigint cents per invariant 1, and TED notices arrive with decimals and occasionally in a non-EUR currency, which needs a stated rule.
- A canonical-URL decision for news and posts. A `security` news item is reachable at `/news/[slug]` and at `/unternehmen/security/news/[slug]`; the draft removes the `/reinigung` short URLs precisely to avoid duplicate content, then reintroduces it here without naming which is canonical.

## INVENTED RULES — must become TODO(client) (5)
- `/[mandant]/einstellungen/steuer` — '§13b and §48 defaults' per mandant. §13b Abs. 2 Nr. 4 UStG turns on whether the *recipient* is a Bauleistender who himself renders Bauleistungen (evidenced by the USt 1 TG certificate), determined per transaction; §48 EStG turns on a Freistellungsbescheinigung valid at the service date. Modelling either as a tenant-level default is an invented tax rule, and the screen invites a user to set a default that produces wrong VAT treatment on every invoice to a customer who does not match it.
- `/[mandant]/einstellungen/arbeitszeit` — 'ArbZG parameters, break rules'. The ArbZG limits (8h with the 10h exception, 11h rest, 30/45 minute breaks) are statutory and identical for all four mandanten; exposing them as per-mandant settings invents the rule that they are negotiable and lets a tenant weaken the LEG-03/TIM-06 checks from the UI. Only the Arbeitszeitmodell (Wochenstunden, Sollzeiten, carry-forward) and any tariff break agreement that is *stricter* than the statute are legitimately configurable, and the tariff side is itself a `// TODO(client)`.
- §1.6 decides Radar = off and Kundenportal = off for the `operations` mandant with no `// TODO(client)`, while §2.3 and §10 simultaneously raise 'Does CSE Operations sell to external customers at all?' as an open question. If that question is open, these two module defaults are answers to it, decided in a table.
- §1.6 gates Raumbuch and Belagsarten to `reinigung`, inventing the rule that the Raumbuch is a cleaning feature. OPS-02, OPS-03 and OPS-04 are Operations requirements in SPEC §7, deliberately kept out of the CLN-01…CLN-05 cleaning block.
- §2.1 and §2.3 treat `rechtsgrundlage = anfrage` as uniformly unblocking outbound messaging. An enquiry supports a transactional reply to that enquiry; it is not one of the four cumulative conditions of §7 Abs. 3 UWG for subsequent advertising, and `bestandskunde` requires an opt-out notice at collection and in every message — a mechanism the map contains nowhere. The document should distinguish transactional reply from advertising in `server/agent/policy.ts` rather than treating the CRM-08 enum as a single gate.

## MINOR (20)
- `quelle = website_kontakt` (§2.1) is outside CRM-07's stated vocabulary, which has exactly four sources: website forms · tender radar · manual entry · referral. Use the website-forms value and distinguish the form by a separate `formular_id`, or the REP-03 channel-attribution report will show two channels where the SPEC defines one.
- §1.1 and §7 invent design values. DESIGN §6 rule 4 says the 3px identity-hue bar runs across the top of the app 'at all times'; the draft renders it neutral `--border-strong` in group scope and omits it entirely in `(auth)`. CLAUDE.md requires DESIGN.md to be amended first, then used — add a documented neutral/group state to DESIGN §6 rather than choosing a token here.
- §1.3 declares `leitung` may 'never' hold `rechnung.festschreiben`, `buchhaltung.*` or `rolle.verwalten`, while the same paragraph says roles are only a default bundle because AUT-03 makes permissions configurable per role per mandant. Say which it is, and if these keys are truly ungrantable, state that `/[mandant]/einstellungen/rollen` renders them permanently disabled with a reason.
- The same paragraph grants `leitung` `freigabe.*`. §4.20 routes DATEV bookings and OCR extractions through the same approval inbox, so a `leitung` user denied `buchhaltung.*` can approve a booking into it. Scope approval permission per approval type (`freigabe.buchhaltung`, `freigabe.extern`, `freigabe.social`, …).
- `/[mandant]/nachweise` (Personal) and `/[mandant]/security/nachweise` are two route families over one person-level table, and §8.1 lists Nachweise under both sidebar groups — the same 'two routes over one table produces two truths' the draft rightly rejects for `kunde`. Likewise `/[mandant]/reinigung/leistungsnachweise/[id]/unterschrift` and `/mein/schichten/[einsatzId]/leistungsnachweis` are two signing surfaces for one immutable artifact.
- The trade prefix duplicates the mandant slug: for the security mandant the Wachbuch is at `/security/security/wachbuch`, and Nachträge at `/bau/bau/nachtraege`. Since §1.6 already gates modules per mandant, the prefix is redundant.
- `/[mandant]/benachrichtigungen` is dated Phase 3 while the justification given is that Phase 2's REQ-06 SLA escalations need somewhere to land. Move it to Phase 2. Similarly `/[mandant]/einstellungen/integrationen` is dated Phase 7 but lists DWD (Phase 5), Radar sources (Phase 8), social and job boards (Phase 9).
- `/[mandant]/bau/bautagebuch/[datum]` and `/[mandant]/stundenkonten/abschluss` depend on calendar-day and calendar-month boundaries. State that `[datum]` is a Europe/Berlin local date converted to a half-open UTC range, and that a month lock uses Berlin month boundaries — otherwise the DST nights the invariants exist for reappear at the aggregation layer.
- Several date-typed fields are named without a type where the DATE-vs-TIMESTAMPTZ call carries legal weight: `nachtrag.angemeldet_am` / `eingereicht_am` (the BAU-05 14-day watchdog), `behinderung` send date (BAU-06 evidence), `nachweis.gueltig_bis` (SEC-04 validity at the shift date), and the §48b certificate window. Fix them in this document rather than leaving each PR to choose.
- The public `/unternehmen/[bereich]/unternehmensdaten` route reads `mandant` anonymously, and `/[mandant]/einstellungen/mandant` puts bank details and `module text[]` on the same row. Specify an anon-readable projection (view) and state that anon is never granted SELECT on `mandant` itself.
- SEC-A7 requires a CSP, and PUB-11's JSON-LD is emitted inline. State the nonce strategy, and state that Inter and Caveat are self-hosted via `next/font` rather than fetched from the Google Fonts CDN — a third-party font request transmitting visitor IPs undermines PUB-13's premise and with it the draft's (correct) conclusion that no cookie banner is needed.
- `/.well-known/security.txt` is proposed for Phase 10 and correctly flagged as not in SPEC. Keep it, but note it must name a real mailbox someone monitors, or drop it.
- Accessibility is asserted only for `(public)` (PUB-09, LEG-07). DESIGN §9 applies to the whole product, and the surfaces where it matters most — `/check-in/[token]` operated one-handed and `/mein/*` in four languages including RTL Arabic — get tap-target and font-size rules but no stated WCAG conformance target.
- LEG-02 names cleaning and construction; §2a SchwarzArbG's sector list also covers the Wach- und Sicherheitsgewerbe. `/[mandant]/zeiterfassung/milog` is correctly enabled for all mandanten in §1.6 — add a line saying so explicitly, so a later PR does not module-gate it to reinigung and bau on the strength of LEG-02's wording.
- ACC-09 covers Z3 only. §147 Abs. 6 AO also provides Z1 (direct read-only access for the auditor on the live system) and Z2 — worth one line saying whether a read-only Prüfer role exists or whether the group hands over Z3 media only.
- `/[mandant]/audit` has no retention or export surface, though GoBD makes the log itself part of the 10-year record.
- FIN-01's five billing types are stated verbatim in the SPEC. The `// TODO(client)` should ask for the *rules* of each (rounding, minimum billing unit, surcharge treatment for night and Sunday hours, how a call-off interacts with a monthly flat) rather than the names, or `/[mandant]/einstellungen/abrechnungsarten` has nothing to render in Phase 6.
- `/[mandant]/rechnungen/[id]/xrechnung` promises a live KoSIT validation report, while FIN-11 places KoSIT validation in CI. KoSIT's validator is a Java tool; say whether it runs in-process, as a sidecar, or CI-only with the route showing the last CI result — an unspecified 'validation report' will become a fake one.
- APR-05's delayed release with an objection window has no queue of its own; `/freigaben/[id]/widerruf` covers APR-06 undo but nothing lists actions currently inside their objection window with a countdown.
- `/gruppe/assistent` and `/gruppe/agenten` consume agent budget (AGT-05) that §1.6 and `/[mandant]/agenten/budget` model per mandant. State which mandant's budget a group-scope agent query draws on, or give the group its own cap.
