# Adversarial review — api-karte

## BLOCKING (25)

### B1. T-07 asserts the wrong month split: `splitteNachMonat('2026-01-31T21:00Z','2026-02-01T05:00Z')` → `[{2026,1,180},{2026,2,300}]`. That is a split at UTC midnight.

**Why it breaks:** Invariant 2: stored UTC, displayed/attributed Europe/Berlin. 2026-01-31T21:00Z is 22:00 Berlin (CET, UTC+1); the Berlin month boundary falls at 2026-01-31T23:00Z. The correct answer is `[{2026,1,120},{2026,2,360}]`. The draft's expectation bakes a one-hour (two hours in CEST) misattribution into the reference test, which then propagates into §17 MiLoG day/month records (TIM-13, LEG-02), Stundenkonto month locking (EMP-04) and the invoice period split (FIN-07). It is worse than no test: it locks the bug in.

**Required fix:** Change the expected value to `[{2026,1,120},{2026,2,360}]` and state in the contract for `splitteNachMonat` and `splitteNachKalendertag` that boundaries are Berlin wall-clock boundaries converted to instants (never UTC midnight). Add a companion case in CEST (e.g. 2026-06-30T22:00Z→2026-07-01T04:00Z = `[{2026,6,0},{2026,7,360}]`) so the UTC/Berlin difference is two hours and a UTC implementation cannot pass by accident.

### B2. The unconditional immutability trigger contradicts two writes the same section specifies on finalised invoices: `POST /api/finanzen/rechnungen/[id]/versenden` "writes `versendet_am` only on real success", and `POST /.../storno` says "both linked".

**Why it breaks:** C.15 states "a trigger raising on any UPDATE/DELETE of a `festgeschrieben` row" and justifies it with "nothing legitimate remains to update". That is false by the draft's own design: `versendet_am` and the Storno back-reference are updates to a finalised row. As specified, either the send path fails at the database (FIN-02 delivery never recorded) or the trigger is quietly weakened to a column allowlist, at which point invariant 4 has no database-level guarantee at all.

**Required fix:** Move both facts off the invoice row: a `rechnung_versand(rechnung_id, kanal, empfaenger, freigabe_id, versendet_am, fehler)` child table, and store the relationship only on the Storno row (`storniert_rechnung_id` on the reversing invoice) or in a `rechnung_beziehung(von_rechnung_id, zu_rechnung_id, art)` table. Then keep the trigger unconditional and add a test that `UPDATE rechnung SET versendet_am=... WHERE status='festgeschrieben'` raises.

### B3. `KanonischeRechnung` (the payload the SHA256 chain freezes) omits every §14 UStG identity field: supplier name and address, supplier Steuernummer or USt-IdNr, recipient name and address, the §13b/§48/Kleinbetrag `pflichthinweis` text, and the Leitweg-ID.

**Why it breaks:** Invariant 4 and LEG-01/LEG-05: the chain is supposed to make a finalised invoice tamper-evident. With only `kunde_id` and `mandant_id` as references, editing the `kunde` master record or the entity's tax number later silently changes what the printed invoice, the XRechnung (FIN-11) and the PDF say, while `pruefeKette` still reports `intakt: true`. The §14 pre-flight would then have validated fields that the hash does not protect, so an auditor cannot prove the invoice as issued.

**Required fix:** Snapshot into `KanonischeRechnung`: `leistender { name, anschrift, steuernummer|ustid, hrb, gericht }`, `empfaenger { name, anschrift, ustid|null, leitweg_id|null }`, per-tax-line `hinweistext`, `abrechnungsart`, `bauabzugsteuer_cent`, and the Kleinbetrag flag. Add a test that mutating `kunde.anschrift` after finalisation leaves `pruefeKette` intact AND that the rendered PDF/XRechnung is produced from the snapshot, not from the live master record.

### B4. `POST /api/freigaben/[id]/entscheidung` and `POST /api/freigaben/stapel` take `geoeffnet_am` from the client and use it to compute the APR-08 review duration.

**Why it breaks:** Invariant 5 (server clock is the source of truth) and APR-08 itself. APR-08 exists to detect rubber-stamping; measuring it from a client-supplied timestamp means the exact actor the control targets can defeat it by posting `geoeffnet_am = jetzt − 90s`. `GET /api/freigaben/kennzahlen` then reports a fabricated distribution, and the human liability argument in SPEC §17 ("automation with a fake safety net") is reinstated with a signed audit trail claiming otherwise.

**Required fix:** Record the open event server-side: `GET /api/freigaben/[id]` writes `freigabe_ansicht(freigabe_id, benutzer_id, geoeffnet_am_server, anfrage_id)`. `entscheide()` computes `pruefdauer_sek = ctx.jetzt − max(geoeffnet_am_server for this approver)`, refuses a decision with no prior view row, and drops `geoeffnet_am` from both request bodies. Same for `stapel`, where each item needs its own view row or the batch is refused.

### B5. `arbzg_zeitraeume(person_id, von, bis)` is a `SECURITY DEFINER` function with no stated authorization predicate on the caller.

**Why it breaks:** Invariant 3 and SEC-A3/AUT-06. A SECURITY DEFINER function bypasses RLS by construction. As specified, any authenticated user in any mandant can call it with any `person_id` and enumerate that person's complete shift windows across all four entities — including people who have no employment in the caller's mandant. That is the single largest cross-tenant hole in the design, and it sits in the one function the draft explicitly exempts from isolation.

**Required fix:** Inside the function: (a) require `current_setting('app.mandant_id')` to be set, (b) assert `EXISTS (SELECT 1 FROM anstellung a WHERE a.person_id = $1 AND a.mandant_id = current_setting('app.mandant_id')::uuid AND (a.austritt IS NULL OR a.austritt >= $2::date))` and raise `no_data_found` (→404) otherwise, (c) `SET search_path = pg_catalog, public` on the function, (d) `REVOKE EXECUTE ... FROM PUBLIC` and grant only to the app role. Add a test to the SEC-A3 suite: a reinigung leitung calling it for a person employed only by security gets 404.

### B6. The `arbzg_zeitraeume` prose ("returning those four columns only … never customer, object, rate or wage data") contradicts the types it feeds. `EinsatzZeitraum` requires `einsatz_id` and `anstellung_id`, and `ArbzgVerstoss.beteiligte` is `readonly EinsatzZeitraum[]`, which the 422 `Konflikt` payload returns to the planner. `Konflikt.ueberschneidung` likewise declares `einsatz_id` while the prose says only `mandant_id`, `von`, `bis` are exposed.

**Why it breaks:** D-09 clause 6 and invariant 3. Either the function returns more than four columns (the prose is wrong and the isolation test asserts the wrong thing), or `pruefeArbzg` cannot be given its declared input. Ambiguity here is how the exception silently widens during implementation — an `einsatz_id` from another mandant on the wire is an identifier the UI will be tempted to link.

**Required fix:** Define a second, deliberately narrower type: `type FremderEinsatzZeitraum = { mandant_id, von, bis, erfasste_pausen_minuten }` with no ids, make `pruefeArbzg` accept `readonly (EinsatzZeitraum | FremderEinsatzZeitraum)[]`, and have `ArbzgVerstoss.beteiligte` and `Konflikt.ueberschneidung` carry the narrow variant for any row whose `mandant_id !== ctx.mandant_id`. Assert the column list in the isolation test against the function's actual `RETURNS TABLE` signature.

### B7. No lookback/lookahead padding is specified for the ArbZG query window. `pruefeMitZusatz(bestehend, zusatz, konfiguration)` is fed whatever range the caller passed to `arbzg_zeitraeume(person_id, von, bis)`.

**Why it breaks:** LEG-03/TIM-14/D-09 clause 2. The 11-hour rest check is a relation between a shift *outside* the window and one inside it. Staffing a 05:00 shift on Tuesday requires the Monday shift that ended at 22:00; if the planner queried Tuesday only, `pruefeArbzg` returns no `ruhezeit` breach and the assignment is allowed. This is exactly the failure D-09 was written to prevent, and it will pass T-09 (which supplies both shifts by hand) while failing in production.

**Required fix:** Specify the contract: the loader must fetch `[von − (ruhezeit_minuten + max_schichtlaenge), bis + (ruhezeit_minuten + max_schichtlaenge)]` and `pruefeArbzg` must reject a window it can prove is unpadded (pass the padding explicitly as `randbereich_minuten` and assert it ≥ `ruhezeit_minuten`). Add a test: person has a shift ending Monday 22:00; ask to staff Tuesday 05:00 querying only Tuesday; expect the `ruhezeit` breach.

### B8. `POST /api/sicherheit/schluessel/[id]/quittung` takes `{ person_id, richtung, unterschrift_png_base64 }` — a key handover receipt hung off `person_id`.

**Why it breaks:** Invariant 9 / D-09. A key receipt is not a fact about the human; it is operational evidence about one entity's object, held by one employment, with liability consequences for that GmbH. Hanging it off `person_id` makes it a person-level row that, under D-09 clause 6 (`person` is visible to every mandant the person is employed by), is readable by the cleaning company for a key issued by SSE Security. It also breaks the D-09 rule that costed/entity-scoped things hang off `anstellung_id`.

**Required fix:** `schluessel_quittung.anstellung_id` (plus `mandant_id` for RLS), not `person_id`; the endpoint takes `{ anstellung_id, richtung, ... }` and 404s if that employment is not in the active mandant. Apply the same test to `da_kenntnisnahme` (SEC-06/EMP-09 acknowledgement of an object-specific Dienstanweisung → `anstellung_id`) and to the `wachbuch_eintrag` author, neither of which the draft assigns.

### B9. There is no HTTP surface anywhere in §C for `person` or `anstellung`. `personal/person.service.ts` and `personal/anstellung.service.ts` appear in the module map with no routes, and no §C table creates, reads, updates or terminates either.

**Why it breaks:** D-09 is the confirmed model the entire scheduling, time and finance stack hangs off, and the ROADMAP puts it in the first migration. Without routes there is no way to hire, record `personalnummer`, `eintritt`, `austritt`, `arbeitszeitmodell`, `wochenstunden` or `stundensatz_intern`, so `POST /api/einsaetze/[id]/besetzen { anstellung_id }` has no way to obtain an `anstellung_id`, `GET /api/stundenkonto?anstellung_id` no subject, and EMP-15 no data. It is the largest omission in the section.

**Required fix:** Add: `GET/POST /api/personal/personen` · `GET/PATCH /api/personal/personen/[id]` (person-scoped fields only, and only for persons with an anstellung in the active mandant); `GET/POST /api/personal/anstellungen` · `GET/PATCH /[id]` · `POST /[id]/beenden` (soft, sets `austritt`), tenant `genau-einer`, with `stundensatz_intern` behind its own `berechtigung` key and stripped from every payload the `leitung` role of another area could reach. State the re-hire case: no unique on `(person_id, mandant_id)`, or a partial unique on `austritt IS NULL`.

### B10. The `kunde` role has no API surface. §B.4 defines four tenant tokens (`–`, `genau-einer`, `gruppe`, `person`) with no customer scope, `TenantScope` has no customer variant, and there is no `/api/kunde/**` counterpart to `/api/mitarbeiter/**`.

**Why it breaks:** AUT-01 lists `kunde` as one of five roles; SPEC §3 scopes it to "own projects, orders, offers, invoices, documents, messages"; DSH-03 requires a customer dashboard; ROADMAP Phase 3 requires the customer portal as an acceptance item. As drafted a customer would have to authenticate as `sitzung` inside a mandant and hit staff routes — every finance route is `sitzung+2fa`, and `GET /api/finanzen/rechnungen` is unfiltered by customer, so the first working implementation leaks other customers' invoices.

**Required fix:** Add a fifth scope `{ art: 'kunde'; kunde_id; mandant_id }`, an `assertKundenScope`, and the routes: `GET /api/kunde/uebersicht`, `/auftraege`, `/projekte`, `/angebote` (+ `POST /[id]/annehmen`), `/rechnungen` (+ `/pdf`), `/dokumente` (+ `/[id]/link`), `/nachrichten`, `/leistungsnachweise`. Every one filtered by `kunde_id` in the service AND by an RLS policy on `app.kunde_id`, with an isolation test per entity mirroring T-25.

### B11. TIM-09 offline capture cannot be submitted. The redemption statement is `... where token_hash=$1 and eingeloest_am is null and $2 between gueltig_von and gueltig_bis`, and validity is `einsatz.beginn − 1h … einsatz.ende + 1h`. Zero rows → 404.

**Why it breaks:** TIM-09 requires exactly the case this rejects: capture in a dead zone, queued locally, submitted later, "flagged as late, claimed time recorded". A worker syncing three hours after the shift ended is outside `gueltig_bis` and gets a 404 indistinguishable from a forged token, so their hours are lost — which is a §17 MiLoG (LEG-02) record failure, not just a UX problem. The `verspaetet_gemeldet` flag in the response is unreachable.

**Required fix:** Split the two windows: `gueltig_bis` governs live redemption; a separate `nachreichbar_bis` (e.g. shift end + a configured grace) governs offline submission with `offline_erfasst_am` present. The predicate becomes `($2 between gueltig_von and gueltig_bis) or ($3 is not null and $2 <= nachreichbar_bis)`, and the second branch sets `verspaetet_gemeldet = true`, stores the claimed `offline_erfasst_am` and still writes `beginn`/`ende` from the server clock at the *claimed* boundary marked as such — never from the device. Add a test: submit 3 h after `gueltig_bis` with `offline_erfasst_am`; expect 201 with `verspaetet_gemeldet`, and 404 without it.

### B12. At least five endpoint families perform tenant writes whose `mandant_id` is derived from a URL segment or an inbound address, while R-03 states the active mandant comes from the server session "never a URL segment" and invariant 10 states no create/update path executes without exactly one active mandant. No exception list is given. Affected: `POST /api/oeffentlich/angebot-anfrage/[bereich]` (creates `lead` + `ansprechpartner`), `/kontakt`, `/bewerbung`, `POST /api/webhooks/mail/[postfach]` ("tenant from the recipient address"), `POST /api/checkin/[token]` ("tenant from einsatz"), plus `POST /api/verwaltung/mandanten` and `PUT /api/verwaltung/benutzer/[id]/mandanten` which write with `Tenant: –`.

**Why it breaks:** Invariants 3 and 10. `assertSchreibbar(ctx): asserts ctx is MandantContext` as declared would reject all of them, so the implementation will either widen `withTenant` (destroying the single-source guarantee) or bypass it entirely (no RLS GUCs set, no audit tenant). Silently allowing an unenumerated set of URL-derived tenant writes is precisely how the invariant erodes.

**Required fix:** Enumerate the exceptions as first-class scope kinds rather than leaving them implicit: `{ art: 'system_eingang'; mandant_id; herkunft: 'oeffentliches_formular'|'postfach'|'checkin_token' }` and `{ art: 'plattform' }` (super_admin, 2FA, audited, may only touch `mandant`/`benutzer_mandant`). Resolution rules: `bereich`→`mandant_id` via a server-side allowlist table, `postfach`→`mandant_id` via a configured mailbox row, token→`einsatz.mandant_id` after atomic redemption. Each sets the RLS GUCs like `withTenant` does, is limited to a named set of insertable tables by RLS INSERT policy, and restate invariant 10 as "no tenant-domain write without exactly one resolved mandant, resolved only by the enumerated resolvers".

### B13. `POST /api/webhooks/supabase/auth` custom-access-token hook "stamps `benutzer_id`, role, memberships into the JWT for RLS" — while §C.2 argues the active mandant must live in a `sitzung` row "not in a JWT the client can replay after losing membership" so that "revoking a membership takes effect on the next request, not the next token refresh".

**Why it breaks:** Direct self-contradiction with an authorization consequence. If RLS policies read memberships from JWT claims, a revoked membership remains effective for the token's remaining lifetime — the exact failure the section says it is preventing — and AUT-05 ("RLS mirrors application authorization") is false during that window.

**Required fix:** RLS reads only the transaction-local GUCs set by `withTenant` (`app.mandant_id`, `app.benutzer_id`, `app.akteur_typ`, and an `app.mandant_ids` array for group reads), all derived from the `sitzung` row and `benutzer_mandant` on every request. Restrict the custom-access-token hook to `benutzer_id` only (or drop it), and add a test: revoke a membership mid-session without refreshing the token, then fetch a row of that mandant → 404.

### B14. `route()` runs "rate limit → session → AAL check → permission → tenant resolution and SET LOCAL of the RLS GUCs → Zod parse". The permission check precedes tenant resolution.

**Why it breaks:** AUT-03 makes permissions configurable **per role per mandant**, and `ServiceContext.berechtigungen` is documented as "effective, active scope only". Evaluating `berechtigung` before the active mandant is known means either the check uses a union across memberships (a user with `finanzen.rechnung.festschreiben` in bau finalises in reinigung — an invariant-3 class failure at the authorization layer) or the ordering is simply unimplementable.

**Required fix:** Reorder to: rate limit → session → tenant resolution + `SET LOCAL` → AAL check → permission (evaluated against the resolved mandant) → Zod parse → idempotency → transaction. Add a test: a user who is `leitung` in bau and `mitarbeiter` in reinigung, active in reinigung, gets 403 on a bau-only permission.

### B15. Group scope has no RLS mechanism. `withTenant` is documented as setting a single `set_config('app.mandant_id', $1, true)`, but `TenantScope.gruppe` carries `mandant_ids: readonly string[]` and every `/api/gruppe/**` route reads across several mandanten.

**Why it breaks:** Invariant 3 / AUT-05 / SEC-A2: RLS must cover every tenant-table read, including group reads. With only a scalar GUC, group queries either run with no `app.mandant_id` set (policies fail open or fail closed — both wrong) or the service layer becomes the only defence, which invariant 3 explicitly forbids ("never the only one and never absent"). TEN-05's "aggregating only the mandanten the user belongs to" then has no database-level backing.

**Required fix:** Define `withGroupRead` to `set_config('app.mandant_ids', array_to_string(ids,','), true)` and `set_config('app.modus','gruppe',true)`; write every tenant policy as `mandant_id = current_setting('app.mandant_id',true)::uuid OR (current_setting('app.modus',true)='gruppe' AND mandant_id::text = ANY(string_to_array(current_setting('app.mandant_ids',true),',')))` for SELECT, with USING-only policies (no INSERT/UPDATE/DELETE policy satisfiable in group mode). Add a test: a user who is a member of reinigung and bau enters group mode and gets zero security rows from every group endpoint.

### B16. `GET /api/auth/mandanten` returns "switcher payload with live counters per area" (TEN-06/TEN-10) while exactly one mandant is active — a cross-mandant aggregate read with no stated mechanism.

**Why it breaks:** Invariant 3. Under the RLS scheme as drafted these counts are unreachable from the active-mandant scope, so the implementation will either bypass RLS with the service-role key or leak: the switcher must show a count for each mandant the user belongs to, and nothing in the design constrains it to memberships. A count is also a real disclosure (order volume per entity).

**Required fix:** A `SECURITY DEFINER` function `switcher_zaehler(benutzer_id)` that joins through `benutzer_mandant` for that user only, returns `(mandant_id, zaehler)` and nothing else, with pinned `search_path` and EXECUTE granted only to the app role — the same treatment as `arbzg_zeitraeume`, and covered by the same isolation suite.

### B17. `POST /api/agenten/ceo/frage` is allowed with tenant `genau-einer / gruppe`, and `POST /api/agenten/wissen/reindex` builds a `pgvector` corpus over "contracts, objects, offers, correspondence" with no stated tenant predicate on retrieval.

**Why it breaks:** D-09 clause 6 ("a cleaning manager must not see security wage rates"), TEN-05 (group view is an aggregate read-only view, not a bypass) and invariant 3. Vector similarity search is trivially cross-tenant unless `mandant_id` is a hard predicate inside the query rather than a post-filter, and in group scope the retriever would legitimately hold chunks from several entities — the model then paraphrases a security contract's rates into an answer for a reinigung user. AGT-07 makes it worse by promising the assistant shows the queries it ran, which will show the leak after the fact.

**Required fix:** State that `wissens_chunk` carries `mandant_id` with RLS, and that retrieval is `WHERE mandant_id = current_setting('app.mandant_id')::uuid ORDER BY embedding <=> $1 LIMIT k` — the filter inside the ANN query, never applied afterwards. Restrict the CEO Assistant in group scope to the same aggregate projections the `/api/gruppe/**` endpoints expose (no RAG over documents at all), or forbid group scope for that endpoint. Add an isolation test: index a security contract, ask the question as a reinigung user in both scopes, assert no security chunk is retrieved.

### B18. `POST /api/bau/aufmasse` accepts `{ lv_position_id, rechenansatz, ergebnis_milli, medien_ids }` — the computed quantity arrives from the client.

**Why it breaks:** Invariant 6 ("every number goes through a tested function in server/services") and BAU-02. §D.9 only says the result is recomputed *on read* and a mismatch "raises a warning on the record". A billable Aufmaß quantity (which feeds `einheitspreis_aufmass` invoicing, FIN-01/FIN-07) must never be writable by a client, and a warning after the fact is not a control.

**Required fix:** Drop `ergebnis_milli` from the request body. The service calls `werteAus(parseRechenansatz(rechenansatz), nachkommastellen)` and persists both the formula text and the server-computed result. Keep the recompute-on-read comparison as a tamper detector for direct DB writes, and add a test that posting a mismatched `ergebnis_milli` is rejected as an unknown field by the Zod schema (`.strict()`).

### B19. Person-scoped routes take `person_id` from the request body/path under `tenant: genau-einer` with no predicate tying that person to the active mandant: `POST /api/personal/nachweise`, `POST /api/sicherheit/bewacher-eintraege`, `POST /api/personal/nachweise/pruefen`, `GET /api/verwaltung/dsgvo/auskunft/[person_id]`, `GET /api/gruppe/personen/[id]/einsatzzeiten`.

**Why it breaks:** Invariant 3 and AUT-06/SEC-A3. `person` is the one table deliberately visible across mandanten (D-09 clause 6), so RLS on `person` cannot be the guard — it is designed to permit the read. Without an explicit predicate a reinigung admin can probe arbitrary `person_id`s, confirm existence (200 vs 404), write certificate rows that gate SSE Security's §34a assignments, and export another controller's employee data as a DSGVO Auskunft.

**Required fix:** Add a single shared guard `assertPersonImMandant(ctx, person_id)` — `EXISTS (SELECT 1 FROM anstellung WHERE person_id = $1 AND mandant_id = ctx.mandant_id)` — called by every route above, throwing `NichtGefundenFehler` (404, never 403). Mirror it as an RLS policy on `person` (`USING (EXISTS (... anstellung ... app.mandant_id))`) rather than a blanket-visible policy, and add it to the SEC-A3 suite as its own case.

### B20. Nothing prevents the same `zeiteintrag` or `aufmass` being billed twice. `POST /api/finanzen/rechnungen/[id]/aus-quellen` returns `{ positionen, uebersprungen }` implying a "already billed" test, but no mechanism is defined — and it cannot be a flag written onto the finalised invoice, since finalised rows are immutable.

**Why it breaks:** FIN-07 ("every line traceable to its source") and TIM-12 ("time attaches to the order directly — no manual transfer to billing"). Two drafts generated from the same period, or a draft generated and later regenerated, produce duplicate revenue; with §17 MiLoG hours and Aufmaß quantities as the source, double-billing a public buyer is a §14 UStG and GoBD problem, not a bookkeeping annoyance.

**Required fix:** A dedicated link table `abrechnung_quelle(mandant_id, rechnungsposition_id, quelle_art, quelle_id, menge_milli)` with a partial unique on `(quelle_art, quelle_id)` restricted to positions whose invoice is `festgeschrieben` and not stornoed — so a draft may claim a source provisionally, finalisation makes the claim exclusive, and a Storno releases it. `aus-quellen` filters against it and reports each skip with a reason. Add tests: generate twice over one period → second returns zero positions; storno the invoice → the sources become billable again.

### B21. `pruefeReverseCharge({ leistungsart, empfaenger: { ist_bauleistender, ustid } })` decides §13b UStG from a bare boolean with no recorded evidence and no validity dates, and there is no endpoint or table for the USt 1 TG Bescheinigung. `POST /api/finanzen/freistellungsbescheinigungen` covers only the §48b EStG certificate (FIN-10) — a different document.

**Why it breaks:** FIN-09 / LEG-06. §13b Abs. 5 UStG turns on the recipient sustainably providing construction services, evidenced by the Finanzamt's USt 1 TG certificate, which has a validity period. A boolean with no source, no `gueltig_von`/`gueltig_bis` and no document link means the reverse-charge decision cannot be substantiated at audit — and, unlike the §48b case which the draft got right, the finalisation sequence checks nothing "as of the service date". Separately, `ist_bauleistender` structurally excludes §13b Abs. 2 Nr. 8 (Gebäudereinigung), which is directly relevant since `reinigung` is one of the four mandanten.

**Required fix:** Model it exactly like FIN-10: `GET/POST /api/finanzen/paragraf13b-nachweise` storing `{ kunde_id, art: 'ust1tg_bau' | 'ust1tg_gebaeudereinigung', nummer, gueltig_von, gueltig_bis, dokument_id }`. Change the signature to `pruefeReverseCharge({ leistungsart, leistungsdatum, nachweis: { art, gueltig_von, gueltig_bis } | null })` and check validity at the service date in finalisation step (4). Add `// TODO(client): confirm with the tax advisor which §13b Abs. 2 categories the group supplies and receives (Nr. 4 Bauleistungen, Nr. 8 Gebäudereinigung) and whether USt 1 TG certificates are on file per customer.`

### B22. The §7 UWG gate is keyed on `rechtsgrundlage` alone: `POST /api/crm/nachrichten` refuses only `rechtsgrundlage = 'keine'`. There is no message-kind distinction and no opt-out field on `ansprechpartner`.

**Why it breaks:** LEG-08/CRM-08 and D-01. §7 Abs. 3 UWG permits e-mail to an existing customer only for *similar own goods or services*, only where the address was obtained in a sale, and only with a clear opt-out notice at collection and in every message. `anfrage` permits a reply to that enquiry, not advertising — the draft says so in the newsletter note but does not encode it. And a Widerspruch (Art. 21 DSGVO / §7 Abs. 3 Nr. 3 UWG) must hard-block even a contact whose basis is `einwilligung` or `bestandskunde`; there is no field to record one, so an objection cannot be honoured.

**Required fix:** `darfKontaktiertWerden(kontakt, nachrichtenart)` where `nachrichtenart ∈ 'antwort_auf_anfrage' | 'vertragskommunikation' | 'werbung'`, with the matrix: `keine` → nothing; `anfrage` → `antwort_auf_anfrage` only; `bestandskunde` → `werbung` only if `aehnliche_leistung = true` and `widerspruch_am IS NULL` and an opt-out line is rendered; `einwilligung` → `werbung` if `widerspruch_am IS NULL`. Add `ansprechpartner.widerspruch_am`, `widerspruch_quelle` and a `POST /api/crm/ansprechpartner/[id]/widerspruch` route. Extend T-28 to cover advertising to a `bestandskunde` with `widerspruch_am` set.

### B23. R-08's enforcement is "No `DELETE` grant for the app role", but `/api/cron/bewerber-purge` must delete applicant data and `idempotenz_schluessel` rows expire after 30 days.

**Why it breaks:** REC-07 / LEG-11 require actual erasure of applicant data under DSGVO; invariant 8 forbids hard deletes only in finance, time tracking and audit. As drafted the purge job cannot execute, so either the DSGVO obligation is unmet or the DELETE grant is quietly restored globally and invariant 8 loses its database-level backing.

**Required fix:** Keep DELETE revoked from the app role and give the purge a narrowly scoped `SECURITY DEFINER` function (`purge_bewerberdaten(stichtag)`) that may delete only from `bewerbung`, `kandidat` and their documents, writes a `loeschprotokoll` row per deleted subject, and is executable only by the cron role. Same for idempotency expiry. State explicitly that no such function exists for `rechnung`, `zeiteintrag`, `audit_log` or `dokument` in a retention-locked category.

### B24. `ArbzgKonfiguration.tageszuordnung` ships with the default `'kalendertag_berlin'` and the platform runs with it until the client answers.

**Why it breaks:** LEG-03. For the security business — 24/7 posts, the SPEC's own worked example being a 22:00–06:00 shift — calendar-day attribution splits an eight-hour night shift into 2 h + 6 h, and neither part ever approaches the §3 ArbZG eight-hour limit. Of the two readings the draft correctly identifies as open, it defaults to the one that systematically suppresses breach warnings for exactly the shift pattern this group runs most. A placeholder that fails open on a working-time limit is not a neutral placeholder.

**Required fix:** Until the client answers, evaluate both readings and emit the union, with `schwere: 'warnung'` on any breach that only the stricter reading produces and the reading named in the message (`begruendung: 'nach Zuordnung zum Schichtbeginn'`). Alternatively default to `'schichtbeginn'` as the conservative reading. Keep the `// TODO(client)` verbatim and add a test: a 22:00–06:00 shift plus a 3 h day shift produces a warning under at least one reading.

### B25. `POST /api/reinigung/leistungsnachweise` takes `positionen_snapshot` as a client-supplied request field, hashed server-side afterwards.

**Why it breaks:** CLN-04 requires "a snapshot of the items as displayed at signing" as evidence of what the customer signed. Accepting the content from the browser means a tampered or stale client determines the evidence, and the sha256 the draft adds then authenticates the tampered version. The same applies to §D.9's claim about `aufmass` and to `POST /api/bau/aufmasse/[id]/gegenzeichnung`.

**Required fix:** Two steps: `POST /api/reinigung/leistungsnachweise/entwurf { auftrag_id, zeitraum }` materialises the positions server-side from `auftrag_leistung`/`zeiteintrag`, persists them with a `pruefsumme`, and returns them for display; the signing call posts `{ entwurf_id, bestaetigte_pruefsumme, unterschrift_png_base64, unterzeichner_name, geo? }` and 409s `plan_veraltet` on mismatch — the same pattern the draft already uses correctly for the Raumbuch and CAMT imports.

- Public-form bot defence is specified as rate limiting "per IP and form fingerprint".
