# Adversarial review — agenten-freigaben

## BLOCKING (20)

### B1. `berechne_preis` accepts model-authored money, quantities and formulas as raw arguments and returns them as trusted `GebundeneZahl` tokens. Specifically: `ust_split.positionen[].netto_cent: string`, `kalkulation.mengen: string[]`, `aufmass.rechenansatz: string`, `reinigung_standardzeit.raum_ids`, `kalkulation.zuschlag_profil_id`.

**Why it breaks:** Invariant 6 / AGT-07. The number-binding design is defeated at its entry point: the model writes `netto_cent: '250000'` or `rechenansatz: '3 × (4,20 × 2,75)'`, the service dutifully computes over it, and an invented figure comes back with `Quelle { art: 'berechnet' }`, konfidenz 1, a green chip in the approval UI and a hover panel citing a tested service version. `assertNoFreieZahlen` then passes it, because it is a substituted token. The whole §4.5 apparatus proves the *arithmetic* was done in code, not that the *inputs* came from the system. `zuschlag_profil_id` is worse still: choosing the surcharge profile is choosing the margin, i.e. the model sets a price — which SPEC §17 says the Back-office agent never does. BAU-02 additionally requires the Rechenansatz to be a human's measurement record, not a string the model composed.

**Required fix:** Every money/quantity input must be either (a) a `zahlenregister` token from a prior `berechne_preis`/catalogue result, or (b) a handle the service dereferences to stored rows. `ust_split` takes `{ position_token: string; steuersatz_id }[]`. `kalkulation` takes `{ auftrag: AuftragHandle | angebot: AngebotHandle }` and derives `leistung_ids`, `mengen` and the Zuschlagsprofil from the contract/catalogue. `aufmass` takes `{ aufmass: AufmassHandle }` and reads the stored `rechenansatz`. `reinigung_standardzeit` derives `raum_ids` from `revier`/`turnus`, not from the model. Add a test: no branch of `berechne_preis` accepts a numeric literal or an expression string originating in a tool argument.

### B2. `freigabe_snapshot` (§12.8) has no `mandant_id`, no `id`, no `freigabe_id` and no `erstellt_am` column.

**Why it breaks:** Invariant 3 — it is a tenant table holding customer names, amounts, extracted document content and approver identity, and it has no tenant column and therefore no RLS predicate to write. §12.8 simultaneously claims its hash chain is 'chained per mandant', which is impossible without `mandant_id`. Without `freigabe_id` an audit that starts at the snapshot table cannot reach the approval it belongs to; `freigabe.snapshot_id` alone gives one direction only, and `freigabe` is mutable while the snapshot is not.

**Required fix:** Add `id uuid pk · mandant_id uuid NOT NULL (RLS + FORCE ROW LEVEL SECURITY) · freigabe_id uuid NOT NULL REFERENCES freigabe(id) · erstellt_am timestamptz NOT NULL · kette_nr bigint`. Keep `freigabe.snapshot_id` as the reverse pointer, or drop it and query by `freigabe_id`.

### B3. The `hash` / `vorheriger_hash` chains on `freigabe` and `freigabe_snapshot` are declared 'chained per mandant' with no ordering column, no chain-head counter and no locking; and `freigabe` is a row that gets UPDATEd (status, angezeigt_am, entschieden_am, entscheidungsdauer_ms, kommentar).

**Why it breaks:** Invariant 4's construction (FIN-03/FIN-06) is `SELECT … FOR UPDATE` on a counter row precisely because a chain needs a serialised total order. Two approvers deciding two items in the same mandant concurrently both read the same `vorheriger_hash` and write a forked chain; the nightly verification job (which §12.8 says is 'the same job class as FIN-06') then reports a break on every busy day, or worse is written to tolerate forks and verifies nothing. Hashing a mutable row is separately incoherent: either the hash covers columns that change (invalid on every status transition) or it silently covers an undeclared subset.

**Required fix:** Chain only the immutable `freigabe_snapshot`. Give it `kette_nr bigint` assigned under `SELECT … FOR UPDATE` on a per-mandant `freigabe_kette` head row, exactly as FIN-03 does for `nummernkreis`. Define `hash = SHA256(canonical(nutzlast_kanonisch, artefakt_hash, diff_json, felder_json, ansicht_modell, policy_ergebnis, entschieden_von, entschieden_am, kette_nr) || vorheriger_hash)`. Remove `hash`/`vorheriger_hash` from `freigabe`.

### B4. `agent_budget` has no unique constraint on `(mandant_id, agent_key, monat)`, `agent_key` is nullable ('nullable = all agents'), and the precedence between a mandant-wide row and a per-agent row is undefined.

**Why it breaks:** AGT-05 promises a hard stop. `SELECT … FOR UPDATE` only serialises callers if they lock the *same* row. With no unique index, two concurrent runs that find no row for the month both INSERT one and each locks its own; the cap is bypassed silently — which is exactly the 'silent degradation' AGT-05 forbids, inverted. With both a wildcard and a per-agent row present and no stated precedence, it is undefined which counter is decremented and whether the other is checked at all.

**Required fix:** `CREATE UNIQUE INDEX ON agent_budget (mandant_id, agent_key, monat) NULLS NOT DISTINCT` (PG15+), upsert the row inside the same transaction as the `FOR UPDATE`, and state the rule: a run must satisfy *every* matching budget row (wildcard and per-agent), locking them in a fixed order (mandant_id, agent_key NULLS FIRST, monat) to avoid deadlock.

### B5. §5.2 mandates that every query carries an explicit `mandant_id = current_setting('app.mandant_id')::uuid` predicate and §5.3 runs `assertGleicherMandant(row.mandant_id, ctx.mandant_id)` on *every row leaving a tool* — but `person`, `nachweis`, `bewacher_eintrag` and `mitarbeiter_zugang` have no `mandant_id` at all (D-09).

**Why it breaks:** D-09 clause 6: those tables hang off `person_id` and are visible to any mandant the person is employed by. Applying the universal predicate returns zero rows; applying `assertGleicherMandant` to a row whose `mandant_id` is `undefined` throws `MandantVerletzung`, which the draft defines as an attack: it aborts the run with `abgebrochen_sicherheit`, discards artefacts, writes a `sicherheitsvorfall` and pages. So `pruefe_nachweise` mode `person` — the tool that supports SEC-02, SEC-03, SEC-04 and LEG-04 — either returns nothing or triggers a false security incident on every call. The canary that 'must never fire' fires constantly.

**Required fix:** Split the rule. Tenant tables: `mandant_id = current_setting('app.mandant_id', true)::uuid` plus `assertGleicherMandant`. Person-scoped tables: policy `EXISTS (SELECT 1 FROM anstellung a WHERE a.person_id = <t>.person_id AND a.mandant_id = current_setting('app.mandant_id', true)::uuid)`, and a separate `assertPersonImMandant(person_id, ctx)` assertion. Enumerate which tables are tenant-scoped, which are person-scoped and which are global (`modell_preis`, `belagsart` if shared), and make that list the input to a lint that fails on an unclassified table.

### B6. Catalogue query `stunden_pro_person_gesamt(person_id, von, bis)` — 'D-09 cross-entity view' — is exposed to the CEO Assistant, which runs with the initiating user's role and exactly one active mandant.

**Why it breaks:** It aggregates `zeiteintrag` rows that hang off `anstellung_id` in other mandanten. Under RLS as designed it returns only the current tenant's hours, so it silently answers the wrong question (an ArbZG-relevant total that is not a total). If it is instead given a carve-out to read across entities, a Leitung of `reinigung` learns how many hours a person worked for `security` — D-09 clause 6, 'anstellung and everything below it stay strictly tenant-scoped: a manager in cleaning must not see security wage rates'. Hours plus a known sector rate is a wage disclosure. No SECURITY DEFINER design, no return-shape restriction and no role gate is given.

**Required fix:** Remove it from the CEO catalogue. Cross-entity aggregation exists only inside the ArbZG conflict detector as a `SECURITY DEFINER` function that returns a boolean/limit verdict (`arbzg_pruefe_person(person_id, fenster)` → `{ ueberschreitung: bool, art, minuten_ueber }`) and never per-entity hours, never a mandant attribution, never a rate. Its own test asserts that a caller in mandant A cannot recover B's hours from the verdict.

### B7. ArbZG is absent from the whole section. The Back-office agent proposes replacements for absences (`einsatz_vorschlag`) using only `pruefe_nachweise` and `entwirf_text`; there is no ArbZG check, no `berechne_preis` art that aggregates hours per person, and no statement that the service layer hard-blocks an ArbZG-breaching assignment the way SEC-04 blocks an expired certificate.

**Why it breaks:** LEG-03, TIM-05, TIM-06 and TIM-14, plus D-09 consequences 1 and 2. The replacement-proposal path is precisely where a cross-entity breach is manufactured: the absent person's shift is in `reinigung`, the proposed replacement already has 6h in `security` that day, and nothing in the design looks. §12.3's risk table would classify the resulting item as a staffing proposal — not `hoch`, no forced individual review of the breach — and the approver sees a name, not '11h, §3 ArbZG'. The draft names SEC-04 as the service-layer block and stops there.

**Required fix:** Add `pruefe_arbzg` (read, deterministic) taking `{ person_ids, einsatz_fenster }` and returning `{ tagesstunden_minuten, ruhezeit_minuten, verstoss: 'keine'|'ueber_8h'|'ueber_10h'|'ruhezeit_unter_11h', quelle }`, backed by the same `SECURITY DEFINER` cross-entity aggregate as above. Make it mandatory in the `einsatz_vorschlag` plan template; any non-`keine` verdict forces `risiko: 'hoch'`, `batch_verboten`, and a visible breach banner. State that the hard block lives in `services/dienstplan/` alongside the SEC-04 block.

### B8. Hard deny D5: '`personenbezug` and requested autonomy is automatic/batched → `art22_personenbezogene_entscheidung`'.

**Why it breaks:** `personenbezug` is defined as 'touches a decision about an identified person', but the rule fires on *autonomy*, and reads run at `automatisch`. So the CEO Assistant answering DSH-05 about a named employee ('Ist Herr Y eingecheckt?') is denied, and `pruefe_nachweise` mode `person` — a read at floor `allow`, the tool SEC-02/SEC-04 depend on — is denied on every call. DSGVO Art. 22 restricts *decisions* producing legal or similarly significant effects, not reading personal data; the draft's own §6.3 correctly handles the decision case with `require_approval, einzeln, batch_verboten`. As written the two rules contradict each other and D5 disables half the agent layer.

**Required fix:** Rename the input to `personenbezogene_entscheidung: boolean`, set it only for `aktion ∈ {gated_write, external_send}` on arts that decide something about an identified person (`einsatz_vorschlag`, `bewerber_ranking`, `bewerber_antwort`, anything touching `abwesenheit` or `zeit_einwand`), and never for `read`/`draft`. Keep a separate `personenbezogene_daten` flag that drives redaction and logging, not the gate.

### B9. Three tables give three different code floors for the same action. §4.2 side-effect classes: `draft → allow`. §6.3 code floors: `aktion = 'draft' → allow`, with no exceptions. §3 autonomy matrix: 'Draft reply to an enquiry | `entwirf_text` | code floor `require_approval`'. Same conflict for 'Monthly invoice from contract', whose tool list is `berechne_preis` + `erstelle_vorgang` but whose row is also reachable through `entwirf_text`.

**Why it breaks:** §6.5 says `decide()` is called at exactly one place with a `PolicyInput` carrying both `aktion` and `aufgaben_art`; with the floors disagreeing, the implementer picks one and the gate's behaviour on the agent's single most frequent action is undefined. It also collapses SPEC §17's two distinct matrix values: SPEC lists 'Draft reply to an enquiry — proposal' and 'Any external send — approval required' as *different* rows, and the draft maps both onto `require_approval`. Requiring an approval to create a draft that a human must then separately approve to send doubles the inbox against §12.1's own ≤10-items-per-person-per-day target.

**Required fix:** Decide it once: creating an `agent_artefakt` is `draft`/`allow` for every art (nothing has left the system, nothing is a domain row, §12.7 classes it `umkehrbar_ohne_spur`); the approval attaches to the *send* or the *domain write*. Then delete the `require_approval` floor from the 'Draft reply' matrix row and mark it `automatisch` at the code floor with `freigabe_einzeln` on `sende_email`. Add a test asserting `codeFloor` is a total function of `(aktion, aufgaben_art)` with a single source table.

### B10. Policy inputs that select the code floor are model-controlled and unattributed. `PolicyInput.aufgaben_art` is 'the autonomy-matrix row this action belongs to' and `personenbezug` is a boolean, but nothing says who computes them; the discriminators they would be derived from — `erstelle_vorgang.art`, `entwirf_text.art`, `berechne_preis.art` — are fields the model fills. Separately, `erstelle_vorgang.bezug?: { tabelle: string; id: string }` takes a free-form table name and row id from the model.

**Why it breaks:** §6.3's floors are keyed on `art`: `aufgabe` and `benachrichtigung_intern` float at `allow` while `rechnung_entwurf` and `buchungsvorschlag` sit at `require_approval`. If `art` arrives in the tool call, the model chooses its own gate — the one thing §2.5 says is 'a code-level fact, not a configuration'. And `bezug` is a direct hole through §11 mechanism 3 ('Handles, not identifiers. Every id argument must be a handle minted earlier in the run by a trusted tool'): a poisoned Vergabeunterlage that names a table and a uuid gets that pair passed straight into a write.

**Required fix:** Derive `aufgaben_art` and `personenbezug` in the orchestrator from `(plan_schablone, werkzeug, target table)` before `decide()` is called, and validate that the model-supplied `art` is a member of the set the plan template permits — a mismatch is `abgebrochen_sicherheit`, not a re-classification. Replace `bezug` with a `BezugHandle` minted by `suche_bestand`/`lies_dokument`. Add the red-team case: a document instructing `art: 'aufgabe'` with an offer payload must fail Zod and abort.

### B11. `wissens_chunk` is `PARTITION BY LIST (mandant_id)` with a per-partition HNSW index (§9.5 defence 3).

**Why it breaks:** Two problems. (a) TEN-08: 'A fifth area requires a DB row, no code change.' Adding a mandant now requires `CREATE TABLE … PARTITION OF`, an index build and a migration — a code change, in the one place the SPEC singles out. (b) The isolation claim is false as stated: in Postgres, RLS policies are not inherited by partitions when a partition is addressed directly, and `FORCE ROW LEVEL SECURITY` is per-relation. A partition created without its own policy is fully readable to any role that can name it, and `wissens_chunk_<mandant>` is a guessable name. Defence 1 ('RLS with FORCE ROW LEVEL SECURITY on wissens_chunk') therefore does not cover the objects that actually hold the vectors.

**Required fix:** Either drop the partitioning and accept a single HNSW index with the `mandant_id` predicate plus a raised `hnsw.ef_search` and the canary suite (defences 2, 4, 5, 7 already carry the load), or keep partitions and (i) create them automatically from a trigger/DDL function on `mandant` insert so TEN-08 still holds, (ii) declare policy + `FORCE ROW LEVEL SECURITY` on every partition, and (iii) `REVOKE ALL` on partitions from `agent_role` so only the parent is addressable. Add a CI check that every partition of every partitioned table has `relforcerowsecurity` and at least one policy.

### B12. `sende_email.an` accepts `KontaktHandle` values only — 'handles from the CRM only' — and hard deny D2 blocks any send to a contact without a `rechtsgrundlage`. The tool's own `kategorie` enum includes `bewerber`, `lieferant` and `mahnung`.

**Why it breaks:** Applicants live in `bewerbung`/`kandidat` (SPEC §22), not in `ansprechpartner`, and carry no `rechtsgrundlage` — so the derived matrix row 'draft applicant reply' (REC-08) has no recipient path and can never be sent; same for `lieferant_rueckfrage`, since suppliers are creditor master data, not CRM contacts. Meanwhile CRM-08/LEG-08/§7 UWG govern *advertising*; applying that gate to a Mahnung (FIN-15) or a Behinderungsanzeige (BAU-06, §6 VOB/B, where the documented send date has contractual consequences) is the wrong control — a legally required notice gets blocked because a contact row was never filled in, and the draft treats missing as `keine`.

**Required fix:** Give `sende_email.an` a `EmpfaengerHandle` union minted by trusted tools over `ansprechpartner`, `kandidat`, `lieferant` and `benutzer`, each carrying its own basis: CRM contacts carry `rechtsgrundlage`; an applicant carries the application they sent; a supplier carries the `eingangsrechnung`/`bestellung` it relates to. Then scope D2 to `kategorie ∈ {kunde_information, antwort_auf_anfrage}` and add a separate deny for a recipient with no resolvable relationship of any kind. Record the reasoning in DECISIONS.md — do not widen §7 UWG by hand.

### B13. `schwelle_cent` is described as 'configurable **downwards and upwards**' (§6.4).

**Why it breaks:** It contradicts the monotone-strictness rule stated three paragraphs earlier ('A policy row can only make things stricter'). Raising the threshold to 5_000_000n moves a €25,000 offer from `stufe: 'einzeln', batch_verboten, verzoegerung_verboten` into `stufe: 'sammel'` — i.e. it can be waved through in a 14-item batch confirm dialog. That is strictly *less* strict, and it contradicts SPEC §17's matrix, which states €20,000 as the Limit of a distinct row, not as a tunable. The stated Phase 8 property test ('an offer of 2_500_000n must yield `require_approval`') passes anyway and so cannot catch it.

**Required fix:** Clamp on save and in `decide()`: `wirksame_schwelle = min(richtlinie.schwelle_cent, 2_000_000n)`, with the 2_000_000n constant carrying a comment citing SPEC §17. Strengthen the property test to assert `stufe === 'einzeln' && batch_verboten && verzoegerung_verboten` for any `geldwert_cent > 2_000_000n` under every generated richtlinie permutation.

### B14. No `berechne_preis` art produces invoice line amounts from a contract, yet 'Monthly invoice from contract' is the Back-office agent's headline task and an explicit matrix row.

**Why it breaks:** The ten kinds are `reinigung_standardzeit`, `kalkulation`, `lv_summe`, `aufmass`, `ust_split`, `abschlag_saldo`, `stunden_summe`, `mahn_betrag`, `reverse_charge_pruefung`, `bauabzugsteuer`. `stunden_summe` yields minutes, `abschlag_saldo` yields a balance, `ust_split` needs net amounts as *input*. Nothing turns a contracted monthly flat rate, an hourly rate × recorded hours, a fixed-price lot instalment or a unit price × Aufmaß into `betrag_cent`. Under §4.5 the only lawful outcome is that the run aborts with `zahl_ohne_herkunft` — so FIN-01's five billing types have no agent path at all, and the pressure will be to let the model fill in the amount, breaking invariant 6.

**Required fix:** Add `{ art: 'auftragsabrechnung'; auftrag: AuftragHandle; periode: { von, bis } }` returning `{ positionen: GebundeneZahl[]; ust_gruppen; summe_netto_cent; summe_brutto_cent }`, delegating to one `calculateAbrechnung(auftrag, periode)` per billing strategy behind the FIN-01 interface. Mark the strategy set `// TODO(client): confirm the exact five billing types (O-04)` and make the unknown swappable, as the working rules require.

### B15. Nothing binds dates or deadlines, although invariant 6 covers deadlines and `GebundeneZahl.art` already lists `'datum'`.

**Why it breaks:** `assertNoFreieZahlen` allows a numeral only if it is a substituted token, a quoted source excerpt or on the structural allow-list — and its allow-list entry is 'dates that are themselves bound tokens'. There is no producer of bound dates. So a drafted Mahnung's Zahlungsziel, a Behinderungsanzeige's date (BAU-06, where the send date is contractually load-bearing), an offer's Bindefrist and a tender's internal lead-time date (RAD-06) are all free numerals: either the run aborts on every such draft, or the allow-list gets widened until it permits any date the model writes — including a wrong payment deadline on a real dunning letter.

**Required fix:** Add a `berechne_frist` façade (or arts on the existing one) over tested services: `zahlungsziel(rechnung_id, stufe)`, `bindefrist(angebot_id)`, `einreichungsfrist_intern(ausschreibung_id)`, `leistungszeitraum(auftrag_id, periode)`. Each returns a `GebundeneZahl { art: 'datum' }` with an ISO instant plus a pre-rendered `Europe/Berlin` display string, so the displayed date is the service's date. Mark the dunning fee/interest and lead-time inputs `// TODO(client)` (O-A13, O-A12).

### B16. `ausfuehrung_key = SHA256(freigabe_id)` with a unique index, held on the `freigabe` row (§12.8).

**Why it breaks:** It is a deterministic function of that row's own primary key, so the unique index is satisfied by exactly one row and constrains nothing. It cannot prevent a duplicate send: the failure mode it claims to defend against is 'the send succeeded, the response was lost, the worker retries' — and the retry re-reads the same `freigabe`, computes the same key that is already on that same row, and has no record of whether the *effect* happened. §12.8 also promises a retry after `ausfuehrung_fehlgeschlagen`, which requires distinguishing 'not yet done' from 'done'.

**Required fix:** Move idempotency to the effect: an `ausfuehrung` outbox table `(id, mandant_id, freigabe_id, versuch, idempotenz_schluessel UNIQUE, status 'offen'|'laeuft'|'erfolg'|'fehler', externe_ref, erstellt_am, beendet_am)` with `idempotenz_schluessel = SHA256(freigabe_id || snapshot.hash)`. The worker claims a row with `UPDATE … WHERE status='offen' RETURNING`, passes the key to the transport as its provider-side idempotency key where one exists, and only a row in `fehler` may be retried — as a new attempt row, never a re-run of a successful one.

### B17. `GebundeneZahl` carries no confidence or `unsicher` flag, and no rule propagates uncertainty from `Feld<T>` inputs into a computed result.

**Why it breaks:** APR-03 requires every extracted value to carry a confidence flag with uncertain fields highlighted, and §12.5 makes that load-bearing: 'the approve button stays disabled until every `unsicher` field has been confirmed'. But `extrahiere_lv` returns `menge: Feld<string>` with an OCR confidence, and `lv_summe(artefakt)` then sums those into a `GebundeneZahl` whose `Quelle` is `{ art: 'berechnet' }` and whose implied confidence is 1. A total built from a 0.71-confidence quantity renders as a hard money chip with a service-version tooltip, is not `unsicher`, does not block the approve button, and is batch-eligible under §12.6 rule 4. That is the exact failure APR-08 exists to prevent, produced by the design rather than by fatigue.

**Required fix:** Add `konfidenz: number` and `unsicher: boolean` to `GebundeneZahl`, plus `abgeleitet_von: string[]` (the input tokens/Feld ids). `berechne_preis` sets `konfidenz = min(inputs)` and `unsicher = any(inputs.unsicher)`. Any `unsicher` bound number forces `risiko: 'hoch'`, `batch_verboten`, and renders with the warning pill and the reason. Test: an LV sum over one low-confidence quantity cannot be batch-approved.

### B18. `agent_schritt` payload blobs are deleted after a retention window (placeholder 90 days), while §8.3 claims the replay bundle 'is what goes into a GoBD/DSGVO audit folder (DOC-08, ACC-09/ACC-10)'.

**Why it breaks:** The two statements cannot both hold. LEG-01/ACC-06 require a 10-year GoBD archive in which deletion is impossible, and ACC-09's Z3 export under §147 Abs. 6 AO is demanded years after the fact. A booking proposal's extracted document text, prompt and completion are part of how a booking record arose — the Verfahrensdokumentation (ACC-10) generated from live configuration will describe an evidence trail that no longer exists for anything older than the window. The row survives with a hash, but a hash of a deleted blob proves only that something existed.

**Required fix:** Classify by domain, not uniformly. Steps belonging to finance/accounting arts (`buchungsvorschlag`, `eingangsrechnung_entwurf`, `zahlungszuordnung_vorschlag`, `rechnung_entwurf`) keep their canonical payload for the GoBD period in the immutable archive, with personal data minimised at write time by `redaktion.ts` rather than deleted later. Everything else follows the client retention answer. Restate `// TODO(client): retention for non-finance agent step payloads` and add the GoBD conflict to DECISIONS.md Open.

### B19. Catalogue results (`suche_bestand` mode `bestand`) are classified `vertrauen: 'trusted'` wholesale, while §11 lists 'customer-supplied form text' among the untrusted sources.

**Why it breaks:** `leads_neu` and `lead_sla_verletzt` return `lead` rows whose free-text message was typed by a stranger into the public offer-request form (REQ-01…REQ-04, PUB-07). Round-tripping that text through the database launders it into `trusted`, and §4.1 rule 2 says untrusted results 'can never authorise a tool call' — the converse being that trusted ones can. The Back-office agent, which reads `lead` and holds `sende_email`, is exactly the agent reached by this path. Trust is a property of provenance, not of the tool that fetched the row.

**Required fix:** Make `vertrauen` per field, not per result: the catalogue registry declares, per `abfrage_id`, which columns are user-authored (`lead.nachricht`, `ansprechpartner.notiz`, `wachbuch_eintrag.text`, any uploaded filename). Those are wrapped by `umschlag.ts` like any document text, and the same rule applies to RAG chunks derived from them. Add a red-team fixture that submits an injection through the public offer form and asserts zero out-of-allow-list tool calls.

### B20. `freigabe` RLS is specified only as a tenant row ('Approvals are tenant rows'); no role or assignment predicate is given, and §12.3 additionally offers a combined multi-mandant list.

**Why it breaks:** EMP-13: 'Employees never see group financials, other employees' data, or customer commercials.' A `mitarbeiter` of `reinigung` sits inside mandant `reinigung`, so a mandant-only policy lets them read every `freigabe` row there — titles, `geldwert_cent`, `diff_json` containing customer names, prices and margins, and `felder_json` containing extracted document content. Separately, a combined list across mandanten cannot be produced under a single `app.mandant_id` and, if produced, shows a cleaning Leitung the offer values of `security` and `bau` — the D-09 clause 6 boundary and TEN-05.

**Required fix:** Policy: `mandant_id = current_setting('app.mandant_id', true)::uuid AND (zugewiesen_benutzer_id = current_setting('app.benutzer_id')::uuid OR zugewiesen_rollen && aktuelle_rollen())`, mirroring AUT-03/AUT-05. For the combined view, show counts per mandant only (the same 'counts only' stance used for group scope), each linking to the switcher; detail requires switching, which the draft already mandates for acting.

## MINOR (19)
- Budget locking: §7 says `SELECT … FOR UPDATE` on the `agent_budget` row before every model call, and 'after the call the reservation is released and the actual cost booked in the same transaction'. If the lock is held across the model call, every agent run in a mandant serialises behind a multi-second network round trip with an open transaction; if it is not, the wording is wrong. Specify two transactions: reserve+commit, call, then book-actual+release-reservation.
- §9.3 is titled 'What is never embedded' and then describes `wachbuch_eintrag` free text being indexed with pseudonymised names. Move it to §9.2 with the pseudonymisation condition, or state plainly that it is excluded.
- Canary chunks (§9.5 defence 5) are seeded into the production corpus, so a real retrieval can surface a nonce chunk into a customer-facing draft. Exclude them from ordinary retrieval by `sichtbarkeit`, and have the canary probe deliberately bypass that filter.
- `DokumentHandle = `dok_${number}`` admits `dok_-1` and `dok_1.5` and is erased at runtime; the type reads as a guarantee it does not provide. The real control is `handles.resolve()` — say so, and validate with Zod at the boundary.
- `suche_bestand`'s return type is an undiscriminated union (`{ treffer } | { zeilen }`); callers cannot narrow. Echo `modus` in the result.
- `erstelle_vorgang` returns `{ vorgang_id?: string; freigabe_id?: string }`, so 'neither' is representable. Make it a discriminated union on an `ergebnis: 'ausgefuehrt' | 'freigabe_erstellt'` tag.
- `ToolResult.vertrauen` is a single flag, but `lies_dokument`'s comment says 'trusted metadata, UNTRUSTED content'. One flag cannot express that; per-field trust (see the blocking item on catalogue rows) fixes both.
- `suche_bestand` semantic mode takes `k?: number` with no upper bound; cap it, both for cost (AGT-05) and to bound the untrusted content entering a prompt.
- The IBAN redaction exception ('masked to last 4 where the task genuinely needs a match, e.g. CAMT reconciliation') is unnecessary: ACC-04 matching is deterministic code operating on the raw record, which never passes through `redaktion.ts`. Remove the exception rather than weaken the rule.
- The Finance agent's read set includes `nummernkreis` 'read-only, for validation'. It has no legitimate use — the agent never assigns a number — and it is the one table where a stray `FOR UPDATE` would stall finalisation. Drop it.
- `freigabe_snapshot` insert-only enforcement: revoking UPDATE/DELETE grants plus a `BEFORE UPDATE OR DELETE` trigger does not stop the table owner and does not stop `TRUNCATE`. Own the table with a separate role, revoke from the application role, and add a `BEFORE TRUNCATE` trigger. The same applies to the FIN-06 pattern this borrows from.
- ESLint `no-restricted-imports` cannot distinguish 'the write paths in `services/zeit/**`' from its read paths — import restrictions work on module paths. Split the module (`services/zeit/lesen`, `services/zeit/schreiben`) so the boundary is expressible, or the rule is unenforceable as written.
- The routes `/(portal)/[mandant]/freigaben` and `/agenten` use a `[mandant]` URL segment. That matches the prescribed folder structure, but state explicitly that the segment is display-only, is validated against the session mandant on every request, and returns 404 on mismatch (AUT-06) — invariant 3 says the active tenant is never a URL param.
- Replay `--export` produces 'a signed bundle'. No signing key, key custody or verification procedure is described; for a bundle that goes into an audit folder, that is the part an auditor asks about.
- When a run aborts with `zahl_ohne_herkunft` (§4.5) 'no approval item is created' — correct, but for the monthly billing job that means an invoice silently does not happen. NOT-01's notification list has no 'agent run failed' event; add one, or the failure surfaces only to whoever opens the Agent Center.
- `policy.decide` cannot evaluate hard deny D10 (`kanal_nicht_verbunden`) as specified: `PolicyInput` carries no channel-connection state, and the function is pure with no IO. Add `kanaele: { name: string; verbunden: boolean }[]` to the input, loaded by the caller like `richtlinien` already is.
- `PolicyInput` also lacks the acting principal's role and the `plan_schablone`, yet `PolicyDecision` names approver `rollen` and §6.3 escalates by task template. Add `rolle` and `plan_schablone` to the input.
- `decide()` takes `jetzt: Date` and the decision returns `Date` fields; 'byte-identical output' on replay (§8.3, §14) requires a canonical serialisation. Specify ISO-8601 UTC strings in the replay comparison, or the purity test is flaky across timezones and JSON round trips.
- §4.6 marks several catalogue entries 'group-readable (counts only)', but one `abfrage_id` cannot return rows in mandant scope and counts in group scope without two result shapes. Give the aggregate variants their own ids (`..._anzahl`) so the registry, not a parenthetical, enforces it.
