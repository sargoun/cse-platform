## How this table is produced, and the trap in producing it

The generator is `scripts/trace.py` in the repository once code lands; during Phase 0 it
lives beside this document's derivation in `_review/`. It extracts the IDs from
`docs/SPEC.md`, then greps each architecture document and each `### PR n` section of
`08-PR-PLAN.md` for them.

**It expands range notation before matching, and that is not cosmetic.** The documents
write `DOC-01 … DOC-08`, `APR-01 … APR-08`, `REQ-02 … REQ-06` where naming eight IDs in a
row would be noise. A grep that takes those as two literals sees the endpoints and
misses everything between them. Measured against the current set, expansion recovers
**61 per-document attributions**, and — the one that would have mattered — **7 SPEC IDs
would otherwise appear to have no PR at all** — DOC-02, DOC-03, DOC-05, REP-02, REP-05, SOC-02, SOC-03 — each of which is in fact assigned inside a range. A matrix built
without expansion reports phantom gaps and invites work to close holes that are not
there.

The generator therefore recognises `X-01 … X-08`, `X-01 ... X-08`, `X-01–X-08` and
`X-01 … 08`, and refuses a range spanning more than forty IDs so a typo cannot silently
mark half the SPEC as covered.

## What the matrix does not claim

It proves that every SPEC ID is **named** by a document and **assigned** to a PR. It
does not prove the description is adequate or the PR sufficient — that is what the
twelve adversarial critiques and the twelve verification reports in `_review/` are for.
Read it as a completeness check on the set, not as a review of it.

Nor does it cover the conventions: `K-01 … K-21` in `00-KONVENTIONEN.md`, the `D-nn`
decisions and the `O-nn` open questions of `docs/DECISIONS.md` have their own registers
and their own tests.
