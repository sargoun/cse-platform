## Gemeinsames
Alle sieben Routen stehen bereits im Manifest (/home/user/cse-platform/src/server/registry/routen.generiert.ts, Zeilen 79–85) und werden heute vom Sammelpfad /home/user/cse-platform/src/app/portal/[mandant]/[...rest]/page.tsx als NochNichtGebaut beantwortet. Keine ist ein eigener Platzhalter, keine ist unerreichbar: Wache (portalZugang + slugTor/Wechselblatt), Rechtepruefung und 404-Verhalten funktionieren schon — gebaut wird die ANTWORT, nicht die Erreichbarkeit, und deshalb ist an routen.generiert.ts nichts zu aendern. Alle sechs gebrauchten Rechte stehen im Katalog (/home/user/cse-platform/src/server/auth/katalog.generiert.ts): crm.lesen, crm.schreiben, crm.rechtsgrundlage_setzen, crm_entgelt.lesen, abrechnung.lesen, system.benutzer_verwalten.

EINE HUELLE fuer alle: PortalRahmen + portalZugang(pfad) + slugTor + kennungOder404 + DataTable/StatusPill/FilterPill, genau wie /home/user/cse-platform/src/app/portal/[mandant]/crm/kunden/page.tsx und .../kunden/[id]/page.tsx; Zusatzrechte fuer Knoepfe ueber haeltRechte aus /home/user/cse-platform/src/app/portal/rechte.ts, damit kein Knopf auf ein 404 fuehrt. Lesen geschieht in der Seite per kontext.abfrage innerhalb von withTenant (Hausmuster), Schreiben ausschliesslich ueber einen Dienst unter src/server/services/ plus einen duennen Handler nach Vorbild /home/user/cse-platform/src/app/api/crm/kunde/route.ts (Gleichursprung, Sitzung, authorize, Transaktion, 303 zurueck aufs Formular) — und JEDER neue Handler braucht eine Zeile in /home/user/cse-platform/src/server/auth/route-manifest.ts, sonst faellt die Aufzaehlungsprobe in tests/kern.

EIN DIENST traegt mehrere Seiten: die vier Kundenunterseiten (konditionen, steuer, zugang) und das Kontaktblatt haengen alle am Kundenblatt, das heute KEINE Unternavigation hat — beim Bauen kommen die Verweise dort hinzu (Uebersicht · Konditionen · Steuer · Portalzugang), sonst sind die neuen Seiten nur ueber die Adresszeile erreichbar.

ZWEI MIGRATIONEN fuer die ganze Domaene, und sie sind der Unterschied zwischen mittel und gross: (a) kunde.uebertragungsweg und kunde.rechnungsformat samt Enums fuer die Steuerseite (in 04-SEITENKARTE §5.3 und 02-datenmodell/05-FINANZEN gefuehrt, in der laufenden Datenbank nicht vorhanden); (b) eine SECURITY-DEFINER-Funktion zum Anlegen eines Kundenkontos, weil cse_app auf benutzer nur SELECT hat und eine benutzer-Zeile heute ausschliesslich im Seed entsteht. Optional dazu ansprechpartner.aehnliche_leistung, falls die §7-Abs.-3-Matrix so gebaut werden soll, wie 05-API-KARTE.md sie beschreibt (O-95).

EINE GEMEINSAME LUECKE IM SEED: 0 faellige Wiedervorlagen, 0 Debitorennummern, 0 Zahlungsziele, 0 Mahnsperren, 0 §13b-Zeitscheiben, 0 §48b-Bescheinigungen. Vier der sieben Seiten waeren in den Demodaten leer — nach Definition-of-done gehoert zu jeder dieser Routen eine Seed-Ergaenzung, sonst ist sie nicht erprobt, sondern nur uebersetzt.

EIN WIEDERKEHRENDES MUSTER, das ueberall gilt: die Seite formuliert keine Rechtsregel nach. Das UWG-Tor ist app.darf_kontaktiert_werden, der §13b-Fall kommt aus reverseChargeLage, die Kondition aus app.zahlungskondition_lesen, die Mahnsperre aus app.kunde_mahnsperre_aktiv. Und wo ein Recht fehlt oder eine Integration nicht verbunden ist (Postausgang O-501, Peppol/ZRE/OZG-RE O-22), steht der Grund an der Stelle, statt dass eine leere Liste wie eine Aussage ueber den Kunden aussieht.
